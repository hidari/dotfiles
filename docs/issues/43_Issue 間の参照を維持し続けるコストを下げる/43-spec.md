# Issue 間の参照を識別子だけにする

Issue 43 の設計。上流 agentic-coding-tools の ISSUE-24 が持つ未決タスクへの回答を兼ねる。
規約の canonical は `dev-workflow:in-repo-issue` skill なので、決定は上流へ起票して裁定する。

## 何を解くか

Issue をクローズすると `closed/` へ移動し、パスの深さが 1 段変わる。相対リンクはこの深さに
依存しているので、移動のたびに全方向を書き換えることになる。直近のクローズでは外部からの参照と
内部から出る参照の両方を補正しており、変更は例外なくリンク補正だった (`fb72a36`)。

壊れる対象がリンクだけなので、リンクを張らなければ移動を残したまま書き換えが 0 になる。

## 決定

### リンクを張らず識別子だけを書く

`## 関連` 節では他 Issue をリンクで参照せず、識別子だけを書く。

```markdown
- Issue 43: Issue 間の参照を維持し続けるコストを下げる。M1 の本体
- agentic-coding-tools の ISSUE-22: 記法混在の追跡。rename しない判断を持つ
```

失うのはクリック導線。エージェント側の導線は skill の検索手順が代替する。人間が読むときは
識別子から `docs/issues/` を引く 1 手が増える。

### 他リポジトリの Issue はリポジトリ名を前置する

上の例の 2 行目がその形。前置が無い識別子は自リポジトリを指す。

これは書き方の好みではなく、検査を成立させるために要る。番号だけでは解決先が決まらない。

- `ISSUE-<N>` 形が上流を指すとは限らない。dotfiles にも新記法の Issue が実在する
- 番号は両リポジトリで独立に採番されるので衝突する。dotfiles のローカル Issue と上流の
  同番号 Issue が別の話題を指している実例が現にある

前置が無いまま番号で解決すると、たまたま番号が一致するローカル Issue へ静かに解決される。
エラーにならないので気づけない。

### `closed/` への移動は維持する

一覧で open と closed が区別できなくなるのを避けるため。移動が壊すのはリンクであって
ディレクトリ構造ではないので、リンクを外せば移動を残せる。

これは Issue 17 と Issue 18 の前提を保つ意味もある。どちらもディレクトリ構造に依存した検査で、
構造を変えると検査対象が変わる。

### ディレクトリ名は変えない

上流 ISSUE-22 の「混在を受け入れ、既存は rename しない」に従う。加えて、番号だけの
ディレクトリ名は採番を静かに壊すことを実測した。

| ディレクトリ名 | rc | `--next` の出力 |
| --- | --- | --- |
| `43_sometitle` (対照・旧記法) | 0 | ISSUE-44 |
| `ISSUE-43_sometitle` (対照・新記法) | 0 | ISSUE-44 |
| `43` (番号のみ) | 0 | ISSUE-1 |
| `ISSUE-43_` | 0 | ISSUE-44 |

番号のみは採番スクリプトの走査パターンの末尾 `_` 要求に一致せず、既存の番号が見えないまま
rc=0 で最小値が返る。ISSUE-22 は「rename は採番を止めうる」を理由に rename を退けたが、
実際には止まるより悪い形 (沈黙する番号再利用) を踏む。

### 射程は `## 関連` 節に限る

本文中の言及は検査しない。理由は識別子の形が記法によって変わるため。

旧記法のリポジトリでは識別子が裸の数字なので、本文中の `Issue 43` を参照と判定すると
`Issue 43 件` のような文も拾う。節に限れば、そこに現れる識別子は参照だと言い切れる。

新記法のリポジトリでは識別子が一意なので本文中でも判定できるが、射程をリポジトリごとに
変えると規約が 2 つになる。狭い方へ揃える。

## 検査

### 何を検査するか

`## 関連` 節に書かれた識別子のうち、リポジトリ名の前置が無いものが、自リポジトリの
`docs/issues/` または `docs/issues/closed/` に実在するか。

実在しない識別子は、参照先が消えたか、識別子を書き間違えたかのどちらか。どちらも読む側が
参照を辿れない状態なので、同じ扱いでよい。

### 他リポジトリ参照は検査しない

リポジトリ名の前置がある行は、実在の検査対象から外す。そのリポジトリが手元にあるとは
限らないため。手元にあるかどうかで結果が変わる検査は、CI と開発機で違う答えを返す。

判定は行単位で行う。1 行に複数の識別子が並ぶとき、行頭にリポジトリ名があればその行の識別子は
すべて他リポジトリ参照として扱う。

### 記法の canonical は借りる

識別子の形を検査側で再定義しない。`issue-id.py` の `ANY_ISSUE_DIR` が接頭辞を optional に
しており、旧記法と新記法の両方を受ける。同じパターンを使う。

再定義すると、記法が変わったときに検査側だけが取り残される。取り残されても検査は動き続け、
「違反 0 件」を返す。

### 取り付け先

| リポジトリ | 取り付け先 |
| --- | --- |
| dotfiles | config-guard の新規モジュール。`markdown_links` の隣に置き、`cli.scan()` から呼ぶ |
| agentic-coding-tools | pre-commit と CI。既存の `issue-id-notation` と同じ形 |

dotfiles 側を config-guard に置くのは、既存の `markdown_links` が同じ対象 (追跡下の Markdown の
参照) を見ているため。両者の違いは、片方がリンク先のパスを見て、もう片方が識別子を見ること。

### 検査が壊れていないことをどう示すか

実装時に次を満たすこと。

- 走査した `## 関連` 節の数と、抽出した識別子の数を出力する。0 件で緑になる経路と、
  見ていないから 0 件の経路を区別できるようにする
- テストに陽性対照を置く。実在しない識別子を含む fixture が赤になることを pin する
- 他リポジトリ参照が検査対象から外れることも pin する。外れすぎて全件が素通りしても
  緑になるので、前置の無い識別子が検出されることと対で確かめる
- 検査の取り付け自体を pin する (`test_precommit_wiring.py` の形)

## 移行

### 既存のリンクをどう扱うか

既存の `## 関連` 節はリンク形式で書かれたものが残っている。件数は baseline が持つ。

一括変換はしない。リンクテキストがディレクトリ名と一致していない実例が上流 ISSUE-24 の実測に
あり、機械変換するとその不一致を識別子側へ持ち込む。

代わりに ratchet を採る。新規に書く `## 関連` 節は識別子だけ、既存のリンクは baseline に
記録して検査から除外する。baseline は単調非増加とし、Issue を触ったついでに減らす。

これは上流 ISSUE-22 が「取り付けと rename は同時にしか選べない」と書いた二択を破る形と同じ
構造で、ISSUE-46 が M2 と呼んでいるものと同じ機構を使えるなら共有する。

### 適用の順序

1. 検査を実装し、baseline を作って取り付ける (この時点で新規の混入が止まる)
2. skill の規約へ「`## 関連` 節はリンクを張らず識別子だけ」と「他リポジトリ参照は
   リポジトリ名を前置する」を書く
3. 既存の baseline を Issue を触ったついでに減らす

規約を書くのを検査の取り付けより後にするのは、規約だけ先に書くと検査の無い期間が生まれるため。
散文で規定して検査が無い状態は、まさに ISSUE-24 が「散文に書くだけでは同じ揺れが再発する」と
指摘した形。

## ISSUE-24 の未決タスクへの対応

| ISSUE-24 のタスク | この spec の回答 |
| --- | --- |
| リンクを張るかどうかを決める | 張らない |
| 半角空白を含むパスのエスケープを決める | リンクを張らないので不要になる |
| リンクテキストの書式を決める | 同上 |
| 射程を決める | `## 関連` 節に限る |
| リンク先の実在検査を先に取り付けられるか | 識別子の実在検査として実装する。書式の決定と同時に入る |
| 書式そのものを検査に落とせるか | 落とせる。「`## 関連` 節にリンクを含まない」が検査可能 |
| 検査に落とせない分を skill へ書く | 射程の理由と、他リポジトリ参照の前置規約を書く |
| 既存の該当ファイルへ適用する | ratchet で段階的に。一括変換はしない |

新規 Issue を立てず ISSUE-24 へ追記する形を既定とする。扱う対象が同じで、ISSUE-24 が既に
実測を持っているため。

## 採らなかった案

### ディレクトリ名を番号だけにする (Issue 43 の案 2)

採番が静かに壊れる (上の実測)。加えて、書き換えの原因は移動によるパスの深さの変化なので、
名前を短くしても書き換え箇所は 1 件も減らない。減るのは各書き換えの読みにくさだけ。

### `closed/` への移動をやめる

決定 (`closed/` への移動は維持する) の裏返しなので採らない。移動を残したままリンクを外すだけで
書き換えが 0 になるため、skill の Phase D と Issue 18 の検査対象まで巻き込む理由が無い。

### 移動時のリンク補正を機械化する (Issue 43 の案 3)

Issue 43 自身が「コスト自体は消えない」と書いている。補正の対象が残る限り、検算のコストも残る。
