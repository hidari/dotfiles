# refactor: Issue 間の参照を維持し続けるコストを下げる

## 背景

Issue 間の相互参照が相対リンクで書かれており、ディレクトリを動かすたびに全方向を
書き換えることになる。リンク先はディレクトリ名を丸ごと含み、タイトル部の空白は
`%20` でエンコードされているため、書き換えは目視で追いにくい。

2026-08-25 に Issue 36 を 1 件クローズしただけで 14 箇所の書き換えが要った
(外部から 36 への参照 6 件、36 から出る参照 8 件)。ディレクトリを 1 段深い
`closed/` へ移すだけでこの量になる。

書き換えを機械でやっても、検算まで含めると安くならない。`markdown_links` が
リンク先の実在を検査するので壊れたリンクは赤くなるが、**赤くなるのは壊した後**で、
コストそのものは減らない。

## この負担が効いてくる場面

- Issue のクローズ (`closed/` への移動。1 件あたり十数箇所)
- 記法の移行。dotfiles の Issue ディレクトリはすべて旧記法で、`ISSUE-<N>` 形式へ移すと
  全ディレクトリのリネームになる。上流 agentic-coding-tools の ISSUE-22 が同じ移行を
  扱っており、そちらでは rename を採らない判断をしている
- 親子や派生の相互リンク。片方向だけ張ると読んだ人に決定が届かないので、常に両方向へ書く

**この Issue が先に片付かないと、記法移行の書き換えコストを 2 回払うことになる。**

## 決めること

参照を「ファイル名だけで示せる」形にできるか。案の方向は 3 つある。

裁定は済んでいる。設計は `43-spec.md` が持つ。採るのは案 1 (リンクを張らず識別子だけ) で、
射程を `## 関連` 節に限り、識別子の実在を機械が検査する。案 2 は採らない。以下の 3 案は
判断の経緯として残す。

### 案 1: リンクを張らず識別子だけ書く

`Issue 39` のように識別子だけ書き、リンクを張らない。移動しても壊れないが、
Issue 本体へ辿る導線が消える。上流 ISSUE-24 の実測によれば、この形は既に一定数あり、
実態としては混在している。

### 案 2: 安定した短いパスを作る

ディレクトリ名にタイトルを含めるのをやめるか、`docs/issues/<ID>/` のような
番号だけのディレクトリにして、タイトルは issue.md の H1 だけが持つ。参照は
`../39/issue.md` で済み、リネームが起きない。

ただし `--next` の採番はディレクトリ名からタイトル部を読む前提を持つ可能性があり、
ディレクトリ一覧の可読性も落ちる。

### 案 3: 現状維持で書き換えを機械化する

移動時のリンク補正をスクリプト化する。skill の Phase D.3 が既に 3 方向を挙げているので
手順は確定しているが、コスト自体は消えない。

## 上流 ISSUE-24 との突き合わせ

上流の ISSUE-24 は同じ問題を「書式が 3 通り混在している」という角度で扱っている。向いている先が
「揃える」であって「維持コストを下げる」ではないため結論が同じになるとは限らなかったが、
突き合わせた結果は両立した。ISSUE-24 が持つ 8 つの未決タスクへの回答は `43-spec.md` の対応表が持つ。

ISSUE-24 の実測から、こちらの裁定を支える材料が 1 つ出た。リンクテキストにタイトルを含める形は
写した時点で既にディレクトリ名と一致していない。上流 ISSUE-22 は rename を禁じることで参照が
壊れないようにしたが、この経路は rename を禁じても防げない。リンクを外して識別子だけにすると、
写す対象が 1 個に減る。

実測値の canonical は ISSUE-24 が持つ。母数も内訳も日付付きスナップショットなので、この Issue には
再掲しない。
