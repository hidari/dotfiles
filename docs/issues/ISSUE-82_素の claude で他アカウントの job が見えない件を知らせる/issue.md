# fix(zshrc): 素の claude で他アカウントの job が見えない件を知らせる

## 背景

`home/.zshrc` は 2 系統のランチャを持つ。既定アカウント用の `claude()` は
`CLAUDE_CONFIG_DIR` を設定しない (既定パスの明示指定という賭けをせず、Keychain の
service 名の導出が変わるのを避けるため。理由は同ファイルのコメントが持つ)。追加
アカウント用のランチャは設定ファイル駆動で生成され、自分の設定ディレクトリを引数で
名指しする。

一方 daemon は設定ディレクトリ単位に 1 つ存在する (実測の詳細は ISSUE-78)。

この 2 つが噛み合うと、起動と操作でランチャが違うだけで job が見えなくなる。追加
アカウントのランチャで起動したセッションの job を、素の `claude stop` で落とそうと
すると、既定の設定ディレクトリの daemon へ問い合わせることになる。

## 実測

2026-09-06 に踏んだ。追加アカウントのランチャで起動したセッションが作った job に対して
素の `claude stop <id>` を打つと、次を返した。

```
No job matching '<id>'. Run 'claude agents' to list running sessions.
```

同じ時刻に、追加アカウント側の一覧にはその job が実在していた。`/tmp/cc-daemon-<uid>/`
の下には追加アカウント側のハッシュのディレクトリしか無く、既定側の daemon はそもそも
起動していなかった。

エラーメッセージは job が無いとしか言わない。設定ディレクトリの話は出てこないので、
原因に辿り着けない。しかも案内される `claude agents` も同じ既定側を見るため、
指示に従うほど「本当に無い」という確信が強まる。

## 何が難しいか

素直な手当ては「素の `claude` も設定ディレクトリを明示する」だが、これは既定の
`claude()` が意図的に避けている形である。Keychain の service 名の導出が
「未設定なら既定、指定時は絶対パスのハッシュ」で分岐しており、どちらの条件で分岐して
いるかが未確認のまま賭けることになる。

したがって手当ては、直すのではなく知らせる側へ寄せる可能性が高い。

## 決めること

- 知らせるだけにするか、直すか
- 知らせる場合の契機。`_claude_task_list_notice` (PR #210 で撤去済み) が起動時の通知の層を持っていたが、あれはタスクリストの整合を見るもので、job の所在は見ていない。同じ層へ足すか、job 系のサブコマンド (`stop` / `agents` など) を見て分岐するかを決める
- 判定の材料。他の設定ディレクトリに daemon があるかは `/tmp/cc-daemon-<uid>/` の
  ディレクトリ名で分かるが、ハッシュから設定ディレクトリ名は逆算できない。
  `claude-config-dirs` の各行からハッシュを計算して突き合わせる形になる

- [ ] 知らせる案を採る場合、契機と文面を決める

## 裁定 (2026-10-02)

2026-10-02の棚卸しのあと、ユーザーが次のとおり決めた。

- 知らせるか直すか: 知らせる。直す案は Keychain の分岐条件が未確認で、壊したときの影響がアカウントの認証に及ぶ
- ユーザーのコメント: 「壊したときの影響がアカウントの認証に及ぶ」のは非常に困るので、めちゃくちゃ注意して扱うこと。実装では認証と Keychain に触れる経路を変えない
- 知らせる契機: SessionStart の probe_task_list_id の層へ足す。本文が候補に挙げた `_claude_task_list_notice` は PR #210 で撤去済みである。設定ディレクトリが1つの環境では黙る
- 文面はまだ決めていない
