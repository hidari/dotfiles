# test: cppath 関数のテストを追加する

## 背景

`home/.zshrc` の「シェル関数」セクションへ `cppath` を追加した (コミット 8584e5e)。
パスを絶対化し、ホームディレクトリ配下なら先頭をチルダに置き換えて `pbcopy` へ流す。
追加時点ではテストを付けていない。

同セクションの `port-proc` / `kill-port` もテストを持たないので慣行としては一貫している。
ただし `cppath` はこの 2 つと違い、外部コマンドを呼ぶだけでなく文字列変換の分岐を 3 本
持つ。分岐の境界 (ホーム直下・ホーム自体・ホーム外) は仕様として表現する価値がある。

### テストを書く前に方式の判断が要る

このセクションは既存のテスト基盤の射程外にある。`scripts/tests/test_helper.bash` の
`load_zshrc_claude_functions` は marker slice 方式で、`# Claude Code 起動` から次の
区切り行までを切り出して source する。`cppath` はその手前の「シェル関数」セクションに
あるので読み込まれない。

ヘルパ自身のコメントが「marker 方式はブロックの外に関数を置くと読み込まれない制約を
呼び込むので、新規スクリプトではガード方式を採る」と書いている。マーカーを増やす方向は
この判断と衝突するため、方式を先に決める必要がある。

`pbcopy` へ流す副作用の観測方法も決める。関数は標準出力へ何も出さないので、`PATH` の
先頭にスタブを置いて受け取った内容をファイルへ書く形が要る。

### 副次的に見えている穴

`.zshrc` は静的検査を一切受けていない。pre-commit の shellcheck hook は `files: \.sh$`
で対象を絞っており、仮に対象へ含めても shellcheck は zsh を解析しない (0.11.0 で実測、
SC1071 でエラー終了する)。現状 zsh 構文の検査は手で `zsh -n` を回したときだけ働く。

テスト基盤を用意すると、関数の振る舞いだけでなく構文の破損も同時に捕まえられる。方式の
判断材料としてここに含める。
