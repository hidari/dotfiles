# feat: リポジトリ固有の運用指示を外部ストレージから注入する仕組みを固める

## 背景

追跡下へ置けない運用上の指示 (実プロジェクト名・実パス・体制に関する前提など) を、
エージェントのセッション開始時に読ませたい。PUBLIC リポジトリが混在するため、
指示そのものをリポジトリへ入れる選択肢は採れない。

現在は次の形で動いている。

- 外部同期ストレージ上のディレクトリを、各リポジトリの `.hidari/` 配下へ symlink する
- `.claude/settings.local.json` の `SessionStart` フックがその配下のファイルを `cat` する
- フックの標準出力はそのまま context へ入る

3 リポジトリで稼働中。ただし**手で置いた状態で、再現手順が無い**。新しいリポジトリを
作るたびに同じ配置を手作業でやり直すことになり、抜けても静かに効かないだけで気づけない。

## 現状の安全性 (実測、2026-08-25)

塞がっている。

| 層 | 実測 |
|---|---|
| symlink 側 | `~/.config/git/.gitignore_global` の `.hidari/` で ignore、3 リポジトリとも追跡 0 件 |
| 設定側 | `.gitignore` の `**/.claude/settings.local.json` で ignore |
| 万一 stage された場合 | symlink の中身は絶対パスなので gitleaks の `macos-user-path` が捕捉する |

**ただし 1 層目はマシンローカルの設定に依存している。** `core.excludesfile` を設定していない
マシンや、bootstrap 前の環境では `.hidari/` が ignore されない。テンプレート化するなら
ここを機構で埋める必要がある。

メールアドレスは `.gitleaks.toml` の `email-address` ルールで塞いだ。symlink が相対パスだった
場合に `macos-user-path` をすり抜ける経路は、これで二重に塞がれている。

## 決めること

### 1. 配置の再現手順をどこに置くか

初期化スクリプトを外部ストレージ側へ置く案が出ている。dotfiles の `bootstrap.sh` へ
入れる案もあるが、bootstrap はマシンのセットアップであってリポジトリの初期化ではないので
責務が違う。テンプレートの実体を追跡下へ置けない以上、dotfiles 側に置けるのは
「呼び出す口」だけになる。

### 2. `.cache/` の ignore をどう保証するか

`SessionStart` 以外に `PostToolUse` / `Stop` / `InstructionsLoaded` の 3 フックも同じ
テンプレートに載っている。実測した前提は次のとおり。

- `instructions-loaded-log.py` はホーム直下へ書くのでリポジトリ非依存。どこでも安全
- `handoff-sentinel.py` は `<repo>/.cache/` へ書く。git リポジトリでなければ cwd へ落ちる
- ログはマシン全体で共有されるので、複数リポジトリで同時に走らせると行が混ざる

`.cache/` の ignore も 1 と同じくマシンローカル設定に依存している。初期化時に
リポジトリ側の `.gitignore` へ入れるか、excludesfile の存在を確認するかを決める。

### 3. リポジトリの公開範囲を注入するか

`gh repo view --json visibility,nameWithOwner` が 0.73 秒で `PUBLIC` を返すことは実測済み。
`SessionStart` に載せて公開範囲を毎回 context へ入れられる。

判断材料は 2 つ。CLAUDE.md には既に「公開範囲を常に確認すること」という規範があるが、
確認は人 (エージェント) の手順であって機構ではない。一方で 0.73 秒は session_start の
コストとしては小さくなく、リポジトリがネットワーク不通のとき何を出すかも決めが要る。

### 4. 取り付けを検査するか

配置が抜けても「指示が届かない」という静かな失敗になる。config-guard で取り付けを
pin できるが、検査対象が追跡外のファイルになるため、既存の検査群と前提が違う。
