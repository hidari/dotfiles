# CLAUDE.md 族分類 草案 (2026-08-17)

Issue #24 のタスク 2 から 6 に対する草案。

ID の採番規約: `home/.claude/CLAUDE.md` を上から読み、コードフェンス内を除いて
`- ` または `N. ` で始まる行をトップレベル項目とする。直前の見出しの出現順を `H<番号>`、
その見出し配下の連番を 2 桁で付けて `H<番号>-<連番>` とする。番号はゼロ始まりで、
前文が `H0`、最初の `##` 見出しが `H1` になる。2026-08-17 時点の 314 行に対して 94 項目。

コードフェンスを除く点が要る。除かないとコミットメッセージ例の中の `- CSS Modules ...` を
項目として数えてしまう。番号付きリストを含める点も要る。含めないと作業プロトコルの
4 項目が落ちる。当初 92 と数えたのはこの 2 つの誤りが相殺した結果だった。

材料は次の 2 つの実測で、同じディレクトリに置いてある。

- `cross-reference-census.json`: 項目間の相互参照。件数は JSON 側が canonical で再掲しない
- `load-mechanism-triage.json`: 94 項目の scopable / nature 判定

## 採る構成

三層に分ける。

1. CLAUDE.md 本体には核だけを残す。文書自身の語彙定義と、他のどの族にも属さない前提。
2. 族ごとの規範を rules へ置く。原則を 1 行、その下に具体的な指示。
3. 族ごとの知識を skill へ置く。実測事例、再現条件、機構の説明。

知識を skill へ移すことは削除ではない。実測値と再現条件は境界を判断する材料として要るため、
消さずに引ける場所へ移す。常時ロードから外れるだけで、必要な場面では読める。

### verification-signal (21 項目 / 最大の族)

原則: 観測した結果がその主張の証拠になっているか確かめ、観測自体を加工や連結で壊さない。

H2-17, H2-18, H2-19, H2-20, H2-21, H2-22, H2-23, H2-24, H6-06

破られ方が 21 通りあるだけで原則は 1 つ。中で 6 つの副族に分かれる。

- 対照の作り方: H2-10, H2-11, H2-12, H2-13
- 報告と表を信じない: H2-05, H2-06, H2-07, H2-14
- 0 件と緑を信じない: H1-06, H2-08, H2-09, H2-18, H2-24
- 測定そのものの設計: H2-15, H2-17
- 狭い signal で広い主張をしない: H6-06
- 観測を自分の組み方で壊さない: H2-19, H2-20, H2-21, H2-22, H2-23

最後の副族は元は shell-execution という独立した族だった。統合したのは、破られ方の違い
でしかないと判断したためである。あちらは「自分の組み方で観測が壊れる」、こちらは
「観測は正しいが主張を支えない」で、どちらも結果を信じる前に何を見ているか確かめる話に
なる。決め手は文書自身の自己申告で、H2-24 は末尾に「シェル展開ルールの、自分のパース
コード側の類型」と書いており、その相手 H2-22 が別の族にいた。統合でこの 1 束が族の内側
へ収まる。

副族の内部構造も残る。H2-19 から H2-20 を経て H2-21 へ至る三段の一般化チェーンがあり、
この 3 項目は必ず同一ファイルに置く。H2-22 と H2-23 は H2-21 から派生する変奏になる。

H6-06 (shell-out は純粋ロジックのユニットテストが緑でも完了としない、full chain を
live smoke する) は元は test 系の族にいた。本文の主張は「ユニットテストの緑は full chain
の健全性の証拠にならない」で、この族の原則そのものである。移したことで H2-05 から H6-06
への参照は族の内側へ収まるが、H6-06 から H12-02 への参照は族またぎのまま残る。

配置: rules_always。この族は全作業に効き、paths で絞れるのは H2-09 / H2-17 / H2-18 /
H2-23 の 4 件のみで、しかも発火はコマンド実行時なのでファイル型では捉えきれない。

統合の代償として、この族は 21 項目 7038 字で全体の 22% (字数では 36%) を占める。副族を
6 つ持つので読む単位は増えないが、規範と知識の切り分けを最初に適用すべき族になる。

### test-first (4 項目)

原則: テストを書き始める前に、書く順序と作り方を決めておく。

H6-01, H6-02, H6-04, H6-08

配置: rules_always。H6-01 と H6-04 は発火すべき瞬間がプロダクトコードを書き始める前で、
テストファイルを触った時点では手遅れになる。H6-08 は E2E テストを作る方式の指定なので、
テストファイルが既にある状態で読ませても別の方式で書き始めた後になる。

当初この配置の根拠に「H6-08 の `npx` は deny がコマンド実行時に効く」を挙げたが、これは
成り立たない。deny を執行するのは settings.json の permissions であって、ルール文が
ロードされているかとは無関係である。しかも permissions.deny は一度実行を試みて失敗する
経路なので、その手前でルールとして効かせたいという要求がそもそもの意図だった。H6-08 の
本来の主張は「npm / npx はセキュリティ面で pnpm に劣るので既定で pnpm を使う」であり、
Playwright Test Agents の指定はその帰結にすぎない。本文をこの主張が読める形へ書き直す。

H6-02 (さらに必要な場合は後からテストコードを追加する) だけは発火点が違う。この項目が
効くのはプロダクトコードを書き終えてテストを足す瞬間で、テストファイルを触るまさに
その時が正しいタイミングになる。4 項目が発火タイミングを共有するという前提はここで崩れる。

族を発火タイミングで括っている点が他の族と違う。内容で括ると H6-08 (E2E の作り方) は
H6-01 (TDD の順序) と同居しないが、分割の目的が「どのファイルを触ったときに読ませるか」
である以上、この族に限ってはタイミングを軸に取る方が実装と一致する。内容軸へ戻す
余地は残る。

## 検算

核 9 + 21 + 6 + 4 + 2 + 3 + 9 + 6 + 16 + 4 + 6 + 4 + 4 = 94。

棚卸しの 94 項目と一致し、重複配置は 0 件、未配置は 0 件。検算は
`.cache/verify-family-draft.py` に本ファイルを渡して行う。

この 94 項目は移行前の CLAUDE.md に対する採番であり、移行後のファイルには対応しない。
対象は main の `7bfd9e8` が持つ版 (314 行) で、ID 集合がこの版と完全一致することを実測して
ある。移行を含む PR #117 は squash マージされたため、移行直前のコミット自体は main から
辿れず、参照できるのはこの SHA になる。ID は「見出しの出現順 + 配下の連番」で決まるので、
族ごとの構成へ移した時点で別物になる。移行直後のファイルに検算器を当てた時点では 48 件が
「存在しない ID」として出た。これは検算器が壊れたのではなく対象が入れ替わったためで、
しかも exit code は 0 のままなので出力を読まないと気づけない。この件数は CLAUDE.md へ項目が
増えるたびに動くので、当時の観測として読むこと。以降この草案の ID は `7bfd9e8` の
スナップショットを指す記号として読む。

強度は 94 項目のうち 92 が完全に保存されている。族の既定と元の強度が食い違う 9 項目は
すべて行頭ラベルで打ち消されており、取り違えは 0 件だった。変わったのは内容変更に伴う 2 件
だけになる。ログとコメントの言語は MUST GLOBAL から MUST へ下がった。「プロジェクトごとに
確定させる」という内容は「プロジェクト側より優先する」という MUST GLOBAL の語義と両立しない
ので、この降格は意味と整合する。ボーイスカウトルールは逆にプロジェクト側の MUST から
グローバルの MUST GLOBAL へ上がった。定義を user 側 canonical にする決定の帰結だが、昇格が
意図どおりかは利用者の確認が要る。

移行では分類の適用に加えて内容も動かしている。核へボーイスカウトルールの定義を新設し、
output-style から H1-15 と H1-16 を project スコープへ出して「言語をプロジェクトごとに
確定させる」を 1 項目足した。差し引きで移行後も 94 項目になるが、内訳は上の表と一致しない。

ただしこの検算器が読むのは ID 列挙行だけなので、緑が意味するのは「ID の割り当てに
漏れと重複が無い」ことに限られる。現に本ファイルの散文リストの欠落は緑のまま通過した。
検算器自身は重複と未配置の双方を名指しで報告するところまで実測してあるが、どちらの
変異でも exit code は 0 のままなので、自動ゲートには載せられず人が出力を読む前提になる。

未配置 0 件という主張の範囲にも注意が要る。94 項目は `- ` か `N. ` で始まる行だけを
数えたもので、CLAUDE.md 本体にはどちらでもない散文行が 3 行ある。うち「コミットメッセージ
には "Conventional Commits" をベースにした以下のプレフィックスを使用する。」は prefix 表の
前置きなので、表を動かすときに同時に動かさないと宙に浮く。

## 位置参照の張り替え

canonical は cross-reference-census.json で、族への振り分けは同じディレクトリの
classify-crossrefs.py が行う。以下の数字と一覧はその出力であって、手で数えた表ではない。

前の版は「分割で壊れる参照は 28 件」と書いていたが、この数はどの数え方とも一致しなかった。
census が分割で壊れると判定したのは 30 レコード、参照先の ID へ展開すると 43 本になる。
族マップを当てると族の内側 33 本、族をまたぐもの 10 本で、発信項目でまとめると 6 束。

族の内側 33 本のうち 13 本は H10-14 から prefix 表 (H10-01 から H10-13) への参照で、
git-github の内部に閉じている。残る 20 本も族名参照へ替えれば足りる。

族をまたぐ 6 束 (ファイル間参照になるので明示的な参照形式が要る):

- H12-02 (delegation) が H2-05 / H2-09 (verification-signal) と H6-05 (test-quality) を指す
- H2-09 (verification-signal) が H2-03 (single-source) を指す
- H2-16 (host-and-scratch) が H2-05 / H2-08 (verification-signal) を指す
- H2-18 (verification-signal) が H6-05 (test-quality) を指す
- H6-05 (test-quality) が H2-03 (single-source) と H2-08 (verification-signal) を指す
- H6-06 (verification-signal) が H12-02 (delegation) を指す

shell-execution を verification-signal へ統合した効果がここに出ている。統合前は H2-24 から
H2-22 への参照が族をまたいでいて 11 本 / 7 束だった。文書自身が「シェル展開ルールの類型」と

手で数えた前の版はこのうち 3 束 (H2-09 から H2-03、H2-16 から H2-05、H6-06 から H12-02) を
落とし、逆に族の内側に閉じている 2 件 (H6-07 から H2-03、H1-11 から H12-02) を族またぎ側へ
数え、族またぎである H2-24 から H2-22 を族の内側の一覧へ置いていた。

H6-06 を verification-signal へ移した効果も書き直す。前の版は「族またぎが 1 件減る」としたが減っていない。
移動で族の内側へ収まったのは H2-05 から H6-06 への 1 本 (相互参照ではなく一方向で、census
にも実文にも逆向きは無い) だが、H6-06 から H12-02 への 1 本は移動の前後どちらも族またぎの

既存の破断が 1 件ある。H2-24 の「下の 0 件を健全の根拠にしない」は実際には上 (H2-08) を

方向語を持つ参照 15 本すべてを行番号と突き合わせた結果、誤っているのはこの 1 本だけだった。

## 決定

1. 元の test 系の族を test-first と test-quality に割る。あわせて H6-06 を verification-signal へ、H6-08 を
   test-first (rules_always) へ置く。H6-08 を内容ではなく発火タイミングで括った理由は
   test-first の節に書いた。
2. H5-01 と H5-02 は核へ移す。どちらも言語とレイヤを横断するコーディングの原則で、
   frontend 族の markup / CSS glob には載らない。
3. commit prefix 表は常時ロードに残す。置き場所は git-github 族のままで核へは移さない
   (常時ロード量はどちらでも同じで、核は語彙定義と前提だけに保つ方が本体が短い)。
   表を動かすときは前置きの散文も同時に動かす。`### コミットメッセージ例` の
   `### コミットメッセージ例` は節ごと削る。
4. ボーイスカウトルールの定義を user CLAUDE.md へ新設する。現在の user CLAUDE.md は
   H1-02 と H1-17 の 2 箇所で語を使っているだけで定義を持たず、定義はプロジェクト側の
   CLAUDE.md にある。一般的なボーイスカウトルールを土台に各リポジトリの記述を参考として
   書き起こし、プロジェクト側は参照へ書き換える。文面は利用者が最終調整する。
5. 知識の移し先 skill は 1 つにまとめ、族ごとに `##` セクションを置く。族ごとに分けると
   どれを読むべきかの判断コストが常時発生し、常時ロードを減らした分がそこで戻るため。
6. H6-08 の本文を書き直す。現在の文は「`npx` が deny だから Playwright Test Agents を
   使う」という形をとっているが、本来の主張は「npm / npx はセキュリティ面で pnpm に劣る
   ので既定で pnpm を使う」で、Playwright の指定はその帰結である。

## 実測で崩れた前提

族の割り当ては機械で検算できるが、族の原則が項目を覆えているかと、配置の根拠が実態と
合っているかは検算の対象外である。CLAUDE.md 本体の実文と突き合わせた結果、次が崩れていた。
分類をやり直す材料ではなく、移行を進めながら 1 項目ずつ判断する対象として残す。

原則が項目を覆えていないもの:

- verification-signal: H2-17 (`node --test` にファイルか glob を渡す) は硬いエラーで落ちる話で、
  もっともらしい signal の話ではない
- verification-signal: H2-23 は本文自身が「あちらは展開結果、こちらはプロセス境界」と書いており、
  展開結果を名指しする原則の外にある
- single-source: H2-02 (警告ゼロの維持)
- test-quality: H6-03 (モックを使わない) は H6-05 を経由しないと原則へ繋がらない
- delegation: H12-01 (SubAgents を積極的に使用する / Agent と Workflow の恒久許可) は使用を
  促す許可であって、族名が警告している内容と極性が逆になる
- delegation: H1-11 (反復的な計画と実装) は委譲とも段数とも関係がない。H12-02 が抱える 8 つの
  規範のうち、相関キーに ID を使う / 実験は隔離コピーで行わせる / 少なくとも 1 案には
  前提を疑う出発点を与える の 3 つも原則の外にある
- frontend: H5-04 と H5-08
- session-protocol: H8-02 (git-branch-switcher を使う) はツール指定であって実測ではない
- collaboration: H1-01 (役割宣言) は行動規範ではなく核の H0 と同じ前提の性質を持ち、H1-03
  (言語設定に忠実に) は output-style 族の原則に一致し、H1-09 (変更前にコードを読む) は
  作業順序である
- host-and-scratch: H1-19 (1Password の `op`) は破壊リスクにも scratch にも掛からない。H2-16 と
  H2-25 の理由は「フックに邪魔されない」「誤コミットしない」で、host を壊さない話ではない

配置の根拠が実態と合わないもの:

- verification-signal: 「paths で絞れる 3 件は発火がコマンド実行時」と書いたが、H2-09 (テストの ID 集合を
  pin する) の書き込み先は test / CI ファイルなのでファイル編集時に発火する
- single-source: 「絞れるのは H1-13 と H2-01」と書いたが H6-07 も triage では scopable
- test-first: H6-02 の発火点。H6-08 は決定 6 に沿って「npm / npx ではなく pnpm を既定で使う」へ
  書き直したので、E2E の作り方に閉じない一般規範になった。テストの族に置き続けるかは
  読み直してから決める
- security: 「scopable 0 件」は triage の判定規約 (全ソースに掛かる glob は絞れたと見なさない)
  の帰結であって、どんな glob でも表現できないという意味ではない
- git-github: H10-14 は prefix 1 行ではなく 402 字あり、`(wip)` の付け方と「日本語の散文は Bash
  コマンド文字列に載せない」という独立した規範を 2 つ抱えている。「16 項目のうち 14 は
  30 字程度の参照知識」は 13 項目にしか当てはまらず、読む単位も 3 つではなく 5 つになる。
  prefix 表を skill へ逃がすとこの 2 規範が常時ロードから落ちる
- output-style: 12 族で唯一 rules_always か rules_scoped かを宣言していない

読む単位の主張について。「94 項目から 13 へ減る」は総数の話である。rules_scoped は test-quality と
frontend の 2 つだけなので、1 つの作業で開く単位は 11 から 12 になる。字数で見ると paths
スコープによる削減は最大でも 15.6% で、削減の主経路が規範と知識の切り分けであることは
変わらない。

## 残る作業 (Issue #24 のタスク)

族ごとの再配置は適用済みで、CLAUDE.md 本体は核 + 12 族の構成になった。見出しが族の既定の
強度を示し、既定と異なる強度の項目だけが行頭にラベルを持つ。再配置は項目の本文に触れずに
所属だけを付け替える形で行い、前後で本文の集合が一致することを検算した。

- 各族の規範と知識の境界を項目単位で引き、知識を skill へ移す。再配置は済んだが、1 項目の
  中に規範と実測事例が同居している状態は変わっていない。字数の削減はここから先で起きる
- 用語依存の族またぎ参照 8 本を族名参照へ張り替える。位置語を持つ 3 本は処理済みで、残るのは
  「変異注入」「dead pin」「二重管理」のような語が別の族の定義に依存している形。1 ファイルの
  うちは壊れないので Issue #36 の分割と同時に行う

既存の破断 1 件 (H2-24 の方向語) は移行時に直した。あわせて再配置で新たに壊れた 1 本も
外した。H2-24 から H2-22 への「上の」で、当時は shell-execution が別の族として後ろに置かれて
いたため向きが反転していた。統合後は同じ族に収まるので、この参照は族の内側になる。
どちらも位置語を「上」「下」へ直すのではなく外し、項目名で指す形にしてある。

族名で指す案は一度採って失敗した。位置語を外した箇所に統合前の族名を書いたところ、その族が
統合で消えて参照先が存在しなくなった。族名は不変ではないので、参照先として使えるのは項目名の
方である。しかも誤った名前を指す参照は、探すと「該当箇所なし」の 0 件で返るので気づきにくい。
