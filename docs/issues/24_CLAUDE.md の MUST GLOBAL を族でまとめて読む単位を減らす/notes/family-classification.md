# CLAUDE.md 族分類 草案 (2026-08-17)

Issue #24 のタスク 2 から 6 に対する草案。

ID の採番規約: `home/.claude/CLAUDE.md` を上から読み、コードフェンス内を除いて
`- ` または `N. ` で始まる行をトップレベル項目とする。直前の見出しの出現順を `H<番号>`、
その見出し配下の連番を 2 桁で付けて `H<番号>-<連番>` とする。番号はゼロ始まりで、
前文が `H0`、最初の `##` 見出しが `H1` になる。2026-08-17 時点の 314 行に対して 94 項目。

コードフェンスを除く点が要る。除かないとコミットメッセージ例の中の `- CSS Modules ...` を
項目として数えてしまう。番号付きリストを含める点も要る。含めないと作業プロトコルの
4 項目が落ちる。当初 92 と数えたのはこの 2 つの誤りが相殺した結果だった。

材料は次の 2 つの実測で、同じディレクトリに置いてある。

- `cross-reference-census.json`: 項目間の相互参照 47 件 (分割で壊れるもの 28 件)
- `load-mechanism-triage.json`: 94 項目の scopable / nature 判定

## 採る構成

三層に分ける。

1. CLAUDE.md 本体には核だけを残す。文書自身の語彙定義と、他のどの族にも属さない前提。
2. 族ごとの規範を rules へ置く。原則を 1 行、その下に具体的な指示。
3. 族ごとの知識を skill へ置く。実測事例、再現条件、機構の説明。

知識を skill へ移すことは削除ではない。実測値と再現条件は境界を判断する材料として要るため、
消さずに引ける場所へ移す。常時ロードから外れるだけで、必要な場面では読める。

### 4. test-first (4 項目)

原則: テストを書き始める前に、書く順序と作り方を決めておく。

配置: rules_always。H6-01 と H6-04 は発火すべき瞬間がプロダクトコードを書き始める前で、
テストファイルを触った時点では手遅れになる。H6-08 は E2E テストを作る方式の指定なので、

当初この配置の根拠に「H6-08 の `npx` は deny がコマンド実行時に効く」を挙げたが、これは
成り立たない。deny を執行するのは settings.json の permissions であって、ルール文が

本来の主張は「npm / npx はセキュリティ面で pnpm に劣るので既定で pnpm を使う」であり、
Playwright Test Agents の指定はその帰結にすぎない。本文をこの主張が読める形へ書き直す。

H6-02 (さらに必要な場合は後からテストコードを追加する) だけは発火点が違う。この項目が
効くのはプロダクトコードを書き終えてテストを足す瞬間で、テストファイルを触るまさに
その時が正しいタイミングになる。4 項目が発火タイミングを共有するという前提はここで崩れる。

族を発火タイミングで括っている点が他の族と違う。内容で括ると H6-08 (E2E の作り方) は
H6-01 (TDD の順序) と同居しないが、分割の目的が「どのファイルを触ったときに読ませるか」
である以上、この族に限ってはタイミングを軸に取る方が実装と一致する。内容軸へ戻す
余地は残る。

## 決定

1. 族 4 は test-first と test-quality に割る。あわせて H6-06 を族 1 へ、H6-08 を
   test-first (rules_always) へ置く。H6-08 を内容ではなく発火タイミングで括った理由は
   test-first の節に書いた。
2. H5-01 と H5-02 は核へ移す。どちらも言語とレイヤを横断するコーディングの原則で、
   frontend 族の markup / CSS glob には載らない。
3. commit prefix 表は常時ロードに残す。置き場所は git-github 族のままで核へは移さない
   (常時ロード量はどちらでも同じで、核は語彙定義と前提だけに保つ方が本体が短い)。
   表を動かすときは前置きの散文も同時に動かす。`### コミットメッセージ例` の
   コードフェンスは削る。
4. ボーイスカウトルールの定義を user CLAUDE.md へ新設する。現在の user CLAUDE.md は
   H1-02 と H1-17 の 2 箇所で語を使っているだけで定義を持たず、定義はプロジェクト側の
   CLAUDE.md にある。一般的なボーイスカウトルールを土台に各リポジトリの記述を参考として
   書き起こし、プロジェクト側は参照へ書き換える。文面は利用者が最終調整する。
5. 知識の移し先 skill は 1 つにまとめ、族ごとに `##` セクションを置く。族ごとに分けると
   どれを読むべきかの判断コストが常時発生し、常時ロードを減らした分がそこで戻るため。
6. H6-08 の本文を書き直す。現在の文は「`npx` が deny だから Playwright Test Agents を
   使う」という形をとっているが、本来の主張は「npm / npx はセキュリティ面で pnpm に劣る
   ので既定で pnpm を使う」で、Playwright の指定はその帰結である。

## 実測で崩れた前提

族の割り当ては機械で検算できるが、族の原則が項目を覆えているかと、配置の根拠が実態と
合っているかは検算の対象外である。CLAUDE.md 本体の実文と突き合わせた結果、次が崩れていた。
分類をやり直す材料ではなく、移行を進めながら 1 項目ずつ判断する対象として残す。

原則が項目を覆えていないもの:

- 族 1: H2-17 (`node --test` にファイルか glob を渡す) は硬いエラーで落ちる話で、
  もっともらしい signal の話ではない
- 族 2: H2-23 は本文自身が「あちらは展開結果、こちらはプロセス境界」と書いており、
  展開結果を名指しする原則の外にある
- 族 3: H2-02 (警告ゼロの維持)
- 族 5: H6-03 (モックを使わない) は H6-05 を経由しないと原則へ繋がらない
