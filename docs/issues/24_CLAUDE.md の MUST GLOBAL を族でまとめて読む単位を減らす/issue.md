# CLAUDE.md の MUST GLOBAL を族でまとめて読む単位を減らす

## 背景

`home/.claude/CLAUDE.md` の `[MUST GLOBAL] 必ず守ること` はフラットな箇条書きで、1 項目が長い
(最長で 1 行 400 字超)。項目間に構造が無いため、読むたびに全項目を舐めることになる。
2026-08-04 時点で 37 項目。着手時には数え直すこと (この節は追記で増え続ける)。

### 2026-08-17 の再計測 (前提が変わっている)

この Issue の前提は既に崩れている。着手前に必ずここを読むこと。

執筆時点 (commit `ce3ce3c`, 2026-08-04) の見出し構成を実際に取り出すと、
`[MUST GLOBAL] 必ず守ること` が 12〜56 行の単一セクションで、`検証` の節は存在しなかった。
現在は `[MUST] あらゆる ”検証” 時に守ること` が独立セクションとして 57〜177 行に存在する。

| 本 Issue の記述 | 2026-08-17 の実測 |
|---|---|
| `必ず守ること` はフラットな 37 項目 | 同セクションは 19 項目 |
| 族 A (最大の族) 12 項目を括り出したい | 別セクション `あらゆる ”検証” 時に守ること` が 26 項目で既に存在 |

つまり本 Issue の主目的だった「族 A の括り出し」は、Issue とは無関係に通常の作業の中で
既に達成されている。Issue はそれを知らないまま open で残っていた。
あわせて、執筆時点にあった `[MUST] 実験的な動作指定` セクションは現在削除されている。

下の「分類の下書き」も同様に古い。族 A の 12 項目は現在の検証セクション 26 項目へ育っており、
しかもそこに族 B (二重管理) / 族 C (静的検査へ委譲) / 族 F (スクラッチ配置) が混在している。
分類をそのまま使わず、現在のファイルに対して引き直すこと。

ただし行数そのものが問題ではない。各項目が持つ実測値と再現条件は、境界を判断するための材料
として要る。問題は「読む単位」が項目数と等しいことにある。

分類してみると、既に族は存在していた。最大の族は 12 項目 (全体のおよそ 3 分の 1) を占め、しかも本文中で
「上の `git push` ルールの一般形」「上の〜のメタデータ版」「〜族で some-path pass ≠
all-path healthy」と相互参照し合っている。リンクは張られているが、構造として括られていない。

## 分類の下書き

### 族 A: 観測した signal がその主張を支えているか (12 項目)

最大の族。共通する原則は「見えた結果が、主張したいことの証拠になっているか確かめる」。
破られ方が 10 通りあるだけで、原則は 1 つ。

- `git push` をパイプに繋がない (成否が隠れる)
- 長時間コマンドの結論は専用クエリで確認する (末尾コマンドの exit が隠す)
- exit code 判定はパイプにも後続にも繋がない (上 2 つの一般形)
- シェルの展開規則を確かめる (0 件 / 何も起きない / 無関係な件数が成功に見える)
- `node --test --test-name-pattern` の 0 件実行 (件数では判別できない)
- 保護ブランチの classic API 404 を「保護なし」と結論しない
- 他者由来の報告を検証済みの網羅的事実として扱わない
- 検索キーになる識別子を推測で作らない (上の自己版。疑うべき前提が自分の作った検索キーになる)
- 「0 件」「空」「緑」を健全の根拠にする前に対照を並べる (`node --test` の 0 件と tirith の対照の一般形)
- 記録されたメタデータを信じて書き込み先を決めない (上のメタデータ版)
- マイクロベンチだけで性能改善の採否を決めない (上の自分の測定版)
- `tirith explain` の文面で除外を判定しない (canonical を名乗る出力でも網羅とは限らない)

### 族 B: 二重管理は必ず drift する (3 項目、節をまたぐ)

- ドキュメントにディレクトリ構成ツリーを載せない
- 機械検証可能な制約を schema と散文の両方に literal で書かない
- テストから他スクリプトのデータ構造を検証するときは source させる (実装哲学の節にある)

### 族 C: 静的検査へ委譲する (3 項目)

- 静的検査可能なルールは linter か ast-grep で記述する
- 末尾改行や行末空白は formatter/linter が担保する (上の具体化と明記済み)
- エラーや警告は全て解決し、ノイズがない状態を維持する

### 族 D: 協働の姿勢 (7 項目)

専門家として振る舞う / 口調を変えても思考能力を落とさない / ハルシネーションを避ける /
反論は率直に / 変更前にコードを読む / 疑問は AskUserQuestion で / 反復的に進める

### 族 E: 出力と文体の規約 (4 項目)

Markdown の強調と区切り線と絵文字 / ログメッセージの書き方 / ログの言語 / コメントは日本語

### 族 F: スクラッチとファイル配置 (3 項目)

`.cache/` に置く / なぜ `.cache/` か / Tirith の除外条件 (これは族 A にも属する)

### 族 G: 環境とリソースの保護 (2 項目)

CI コストを抑える / ホストで重い処理を走らせない

### 族に属さない単独項目 (5 項目)

個人情報を含む設定ファイルをコミットしない / `pwd` で確認 / `node --test` にファイルか glob を
渡す / push の粒度 / 1Password の `op`

## 2026-08-17 の草案 (レビュー待ち)

分類を引き直した草案を [族分類の草案](notes/family-classification.md) に置いた。
材料は同じ `notes/` 配下に置いてある。相互参照センサスとロード機構の仕分けは subagent が
原文を通読して作った実測で、族またぎの振り分けはセンサスから生成する道具になる。

- [相互参照センサス](notes/cross-reference-census.json): 項目間の参照 47 件
- [ロード機構の仕分け](notes/load-mechanism-triage.json): 94 項目の scopable / nature 判定
- [族またぎの振り分け](notes/classify-crossrefs.py): センサスへ族分類を当てて族の内側と
  族またぎへ機械的に振り分ける生成器

測った数字の canonical は草案側の表なのでここには再掲しない。

読む単位は 94 項目から核 + 12 族へ減る。全 94 項目に行き先があり、重複配置と未配置は
いずれも 0 件。この検算は機械で行い、未配置と重複の双方を変異注入して検算スクリプト
自体の生存も確かめた。ただし報告されるのは出力の中だけで exit code は 0 のままなので、
自動ゲートには載せられず人が読む前提になる。

副次的に確定したこと。

- 本 Issue が数えていた項目数はセクション単位のものだった。ファイル全体では 94 項目ある。
  当初 92 と数えたのは、コードフェンス内の例示を項目として数える誤りと、番号付きリストを
  落とす誤りが相殺した結果で、過小と過大の両方に同時に外れていた
- 位置参照が既に 1 件壊れている。H2-24 の「下の 0 件を健全の根拠にしない」が指す先は
  実際には上にある。分割前から沈黙して壊れていた
- 相互参照 47 件のうち 7 件は参照語を伴わない用語依存で、grep では原理的に拾えない。
  「変異注入」「dead pin」のような語が別セクションの定義に依存している形
  (センサスの coverage_note が挙げる 7 件。別に数えている 9 件は、棚卸しの posref 列に
  フラグが立っていない項目から追加で見つかった参照の数で、こちらとは別の集合)
