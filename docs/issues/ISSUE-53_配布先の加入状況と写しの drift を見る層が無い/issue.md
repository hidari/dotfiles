# fix: 配布先の加入状況と写しの drift を見る層が無い

## 背景

agentic-coding-tools の ISSUE-32 は、in-repo Issue の検査を配布先で走る状態にする作業を
5 つの層へ分けている。そのうち層 3「横断スイープで加入状況と写しの drift を検出する」は
担当リポをこのリポジトリと宣言しているが、こちら側に担当 Issue が無い。

ISSUE-46 のマイルストーン表も M2 行に「新規起票が要る (担当 Issue が無い)」と書いたまま
残っている。この Issue がその担当である。

## 実測 (2026-08-28)

上流が v0.4.0 を release し、こちらの pin を揃えた直後 (PR #178) に配布状況を走査した。
母数は開発機の作業ディレクトリ直下にある 28 リポジトリで、外部参照リポジトリは除いている。

| 経路 | 件数 | 状態 |
| --- | --- | --- |
| apm の pin で受け取る | 1 | 最新版 |
| 追跡下の写しを持つ | 1 | 旧版のまま |
| 取り込む計画があるが未着手 | 2 | 宣言そのものが無い |

追跡下の写しを持つ 1 件は、上流が release を 1 つ跨いでも旧版のまま残った。写しのハッシュが
canonical と異なることを見る経路は、hook にも CI にもどこにも無い。

別の配布先では、記法違反の報告件数が 359 から 393 へ増えていた。増分の出所は、その間に
追加されたファイルがコメント内で GitHub の数字記法を使っていることである。検査を
取り付けないまま時間が経つと、直すべき量だけが増え続ける。

### 0 件が「健全」と「見ていない」を区別しない

写しの drift も加入の欠落も、現状はどの検査も報告しない。報告が無いことは健全の証拠では
なく、見る経路が無いというだけである。上の 2 件はどちらも一度も赤くならずにここまで来た。

## 設計の前提を組み直す

ISSUE-46 が M2 の前提として次を記録している。この Issue はそこから始める。

当初は消費側の config-guard に ratchet を載せる形を想定していたが、これはこのリポジトリ
だけの機構で、pre-commit 自体を持たないリポジトリには載せる土台が無い。「検査を配布先の
git hook や CI から呼ぶ」という土俵そのものを疑うところから設計し直す。

上流の層 1 で入った増分モードは、既存違反を直さずに検査を取り付けられる入口である。
取り付けのコストは下がったが、取り付けたかどうかを見る層は別に要る。
