# fix: 配布先の加入状況と写しの drift を見る層が無い

## 背景

agentic-coding-tools の ISSUE-32 は、in-repo Issue の検査を配布先で走る状態にする作業を
5 つの層へ分けている。そのうち層 3「横断スイープで加入状況と写しの drift を検出する」は
担当リポをこのリポジトリと宣言しているが、こちら側に担当 Issue が無い。

ISSUE-46 のマイルストーン表は M2 行に「新規起票が要る (担当 Issue が無い)」と書いたまま
残っていた。この Issue がその担当である。

## 実測 (2026-08-28)

上流が v0.4.0 を release し、こちらの pin を揃えた直後 (PR #178) に配布状況を走査した。
母数は開発機の作業ディレクトリ直下にある 28 リポジトリで、外部参照リポジトリは除いている。

| 経路 | 件数 | 状態 |
| --- | --- | --- |
| apm の pin で受け取る | 1 | 最新版 |
| 追跡下の写しを持つ | 1 | 旧版のまま |
| 取り込む計画があるが未着手 | 2 | 宣言そのものが無い |

追跡下の写しを持つ 1 件は、上流が release を 1 つ跨いでも旧版のまま残った。写しのハッシュが
canonical と異なることを見る経路は、hook にも CI にもどこにも無い。

別の配布先では、記法違反の報告件数が 359 から 393 へ増えていた。増分の出所は、その間に
追加されたファイルがコメント内で GitHub の数字記法を使っていることである。検査を
取り付けないまま時間が経つと、直すべき量だけが増え続ける。

### 0 件が「健全」と「見ていない」を区別しない

写しの drift も加入の欠落も、現状はどの検査も報告しない。報告が無いことは健全の証拠では
なく、見る経路が無いというだけである。上の 2 件はどちらも一度も赤くならずにここまで来た。

## 設計の前提を組み直す

ISSUE-46 が M2 の前提として次を記録している。この Issue はそこから始める。

当初は消費側の config-guard に ratchet を載せる形を想定していたが、これはこのリポジトリ
だけの機構で、pre-commit 自体を持たないリポジトリには載せる土台が無い。「検査を配布先の
git hook や CI から呼ぶ」という土俵そのものを疑うところから設計し直す。

上流の層 1 で入った増分モードは、既存違反を直さずに検査を取り付けられる入口である。
取り付けのコストは下がったが、取り付けたかどうかを見る層は別に要る。

## ISSUE-42 が作った前例 (2026-09-02)

運用指示の注入を固める Issue が、この Issue のタスクと同型の問題を先に解いた。対象は
「in-repo Issue 検査の配布」ではなく「運用指示の取り付け」だが、母数・検出・対照の組み方は
そのまま使える。

| この Issue のタスク | ISSUE-42 が採った形 |
| --- | --- |
| 配布先の母数の定義 | 外部ストレージ上の一覧ファイル。開発機の走査に依存しない |
| 検出方式を 2 案以上 | セッション開始時の probe (今いる 1 件) と手動の棚卸し (一覧の全件) の二層 |
| 0 件と見ていないの区別 | 問題の有無にかかわらず母数を出す (`listed=N problems=M` の形) |
| 実地 1 件で drift を検出 | 受け側で取り付けを外し、検出が鳴ることと戻ることを対照で確認 |

「配布先の hook や CI から呼ぶ以外の土俵」は probe が実例になる。session_start hook は
配布先のリポジトリに何も置かずに全リポで走るので、加入の取り付けを配布先へ要求しない。

母数の数え直しで学んだこともある。当初 8 リポを調べて出した結論が、全数で数え直すと
覆った。棚卸しの表は見つけた分だけが載るので、着手の根拠にするときは数え直すこと。

**このタスクのチェックはまだ入れない。** あちらは追跡外ファイルの symlink を見る層で、
こちらは追跡下の写しのハッシュと加入状況を見る層である。形は流用できるが対象が違う。

## タスク

- [ ] 配布先の母数の定義を決める。作業ディレクトリ直下の走査は開発機の状態に依存するので、
      何をもって配布先とするかを機構が持つ形にする
- [ ] 加入状況と写しの drift を検出する方式を 2 案以上出して比較する。
      「配布先の hook や CI から呼ぶ」以外の土俵を最低 1 案に含める
- [ ] 検出結果が「0 件」と「見ていない」を区別する形になっていることを、正常なら非空に
      なる対照で pin する
- [ ] 実地で 1 件の配布先へ取り付けを通し、drift を検出できることを確かめる
