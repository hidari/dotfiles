# fix(ci): pre-commit 設定自身の構文検査がどこにも無い

## 背景

2026-09-11 に studio へ pre-commit を取り付ける作業の live smoke で踏んだ。

`.pre-commit-config.yaml` の `name` の値に裸のコロンがあると、YAML がそこを mapping と
解釈して構文エラーになる。

```yaml
name: run tests (fast: unit only)   # ← "fast:" が mapping に見える
```

踏んだのは hook 名に補足を括弧で足した形で、補足の中にコロンがあった。

pre-commit は起動時に `InvalidConfigError` を返し、hook を 1 つも実行しない。

## 何が観測されていないか

配線を pin するテストは通る。studio では `crates/repo-guards` の 8 件がすべて緑のまま
この構文エラーを見逃した。テストが YAML をテキストとして読み、行を `- id: ` で切り出して
いるためで、パーサを通していない。

つまり検査の層がこう分かれている。

| 層 | 見るもの | 構文エラーを検出するか |
| --- | --- | --- |
| repo-guards のテスト | 行の文字列 | しない |
| pre-commit の `check-yaml` | YAML の妥当性 | **自分自身の設定は見ない** |
| CI | (pre-commit を走らせる job が無い) | しない |

`check-yaml` が自分自身を検出しないのは、設定が壊れていると pre-commit そのものが起動
しないため。順序として、設定を読む側が設定を検査することはできない。

同じ穴は relay 側にもある。両リポジトリとも CI に pre-commit を走らせる job が無く、
`pre-commit validate-config` を呼ぶ経路もどこにも無い。dotfiles 自身も同様である。

## 失敗の形

エラーになるので沈黙ではない。ただし露見するのは実行時で、しかも「取り付けたつもりの
検査が 1 つも走らない」状態を伴う。取り付け直後に live smoke を回さなければ、コミットは
通り続けるので気づけない。

配線を変えるとき、テストが緑なら完了と読む形が自然に成立してしまうのが問題にあたる。

## 決めること

### どこで検査するか

案が 3 つある。どれも一長一短で、組み合わせも採れる。

1. CI に pre-commit を走らせる job を足す。設定の妥当性と hook の実効性を同時に見られるが、
   CI コストが増える。ユーザーは CI コストを負担と見ており、main マージとリリース時に
   限る方針を持つ
2. 配線を pin するテストから `pre-commit validate-config` を呼ぶ。ローカルで即座に赤くなるが、
   テストが外部コマンドへ依存する。CI に pre-commit が無い環境では落ちるので、
   skip でかわすと Issue 45 と同じ「静かに全 skip」を作る
3. テストで YAML をパースする。外部コマンドに依存せず、CI でも同じ結果になる。ただし
   YAML パーサの依存が要る (studio の repo-guards は依存ゼロを設計として選んでいる)

### 対象をどこまで広げるか

穴があるのは 3 リポジトリすべてである。dotfiles / relay / studio のどこから塞ぐか、
形を揃えるかを決める。ISSUE-53 が配布先の加入状況を見る層を扱うので、そちらと同じ
機構に乗せられるかも見る。
