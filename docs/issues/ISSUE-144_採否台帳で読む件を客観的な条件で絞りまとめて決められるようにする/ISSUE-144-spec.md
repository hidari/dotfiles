# ISSUE-144 spec: 採否台帳で読む件を客観的な条件で絞り、まとめて決められるようにする (2026-11-11 時点のスナップショット)

## 意図

採否台帳の815件を、ユーザーが原文で確かめながらでも捌ける量にする。ユーザーの申告 (2026-11-11) では、台帳の見立てを信用しきれないので原文を読んでいることと、見立てを読んでも1件ずつ決める回数そのものが重いことの両方が効いている。印象では決めていないので、1件に時間がかかる。

そこで、読む件を「誰が数えても同じになる条件」で絞り、残りは判断しないまま保管する。読む件では、機械で確かめ済みのことと、モデルが判断したことを見分けられるようにし、原文で確かめる範囲を狭める。似た件はまとめて決められるようにする。

## 目標・非目標・反目標

目標

- 既定の一覧を「昇格の条件を満たし、まだ判断していない件」にする。条件はユーザーが決め、UI で変えられる
- カードで、機械で確かめ済みの欄とモデルが判断した欄を見た目で分ける
- 選んだ複数の件へ同じ判断を一度に付けられる
- 決め済みの件と見立ての一致を、見立ての組 (見立て × 置き場の案 × 照合の状態) ごとに数える

非目標

- 見立ての作り直し、要約の作り直し、外部 DB、Jev、候補の正本の移し替え、agentic-coding-tools への配布。どれも今の詰まりに効かないと判断した (「案」節)
- 判断の自動化。一致率が高い組が見つかっても、条件へ足すかはユーザーが決める
- 受け箱の段階での絞り込み (案P2)。P1 で決めた条件を流用する形で後に検討する

反目標 (動いても失敗とみなすもの)

- 昇格していない件が「採らない」と読める表示になる、または判断として書き込まれる
- まとめての判断が、選んでいない件や表示外の件に及ぶ
- まとめての判断が、既存の判断やメモを上書きする。2026-11-10 に直した保存の性質 (変えた欄だけ送る、送れなかった判断を控えて送り直す) が崩れる
- 「確かめ済み」と表示した欄に、実際には機械で確かめていないものが混ざる
- ユーザーのメモが追跡下へ出る

## 制約

- dotfiles は PUBLIC。ユーザーのメモは Artifact の `decisions` にだけ置く
- 台帳のページは claude.ai の Artifact の中で動き、保存先は `window.claude.use("db")` の `decisions`。ページの外 (手元の file:// など) では保存先が無く閲覧だけになる
- 既存の ID は振り直さない (判断が ID で保存されている)

## 実測で確かめた前提 (2026-11-11)

- 815件すべてが `summary` / `labels` / `covered` / `placement` / `recommendation` / `reason` / `version_dependent` / `report_count` を持つ。原文 (`text`) は中央値171字、合計約18.4万字
- 見立ては採る168、保留464、採らない183。照合 (`covered.status`) は covered 13、partial 277、none 525
- `report_count` が2以上の件は112
- 機械で確かめ済みと言えるのは2つ。`covered.quote` が参照先のファイルに逐語で在ること (quote を持つ290件は全件在った)、`labels` の各札が原文 (`text` と `basis` の和) に逐語で在ること (859個中857個)。要約・見立て・理由・置き場の案・照合の状態の判定はモデルの判断
- `report_count` もモデルの判断にあたる。新しい件の値は下ごしらえの agent の出力をそのまま入れており (`merge.py`)、機械で足すのは追記で子の箇条が増えたときだけ。子の箇条の数で数え直すと、2以上の112件のうち合うのは66件だった (例: K133-051 は子の箇条が0で値が2。本文の「2つのリポジトリから届いた」を読んだ値に見える)
- 札が原文に在ることは、報告者がそう申告したことを示すだけで、実測であったことは確かめていない
- 文字 bigram の包含率は、束ねにも照合にも使えなかった。候補どうしの包含率は最大でも0.7台で0.85以上は0組、下げると無関係な件が1つの束へ連なる。既存の照合の該当行が bigram の上位5に入ったのは275件中42件 (Fable のレビューの R3・R4 を手元で一部再計算)

## 案 (会話で出し、ユーザーが P1 を選んだ)

最初の案B (外部 DB と Jev を持つ道具を agentic-coding-tools に置く) は、上の前提を知らずに組んでいた。要約・照合はもう全件にあり、bigram では束も照合も作れないと分かったので、2本の Fable の独立したレビューを経て次の3案に組み直した。

- P1 (採用): 客観的な条件で読む件を絞り、確かめ済みとモデルの判断を分けて見せ、まとめて決められるようにする。作るものは台帳 UI の変更と一致率の集計で小さい
- P2: P1 に加えて受け箱の段階で「リポジトリ固有」の件を Issue へ載せず件数だけ数える。Issue の肥大も止まるが、仕分けの手順と cross-repo-learnings に及び、落とした件の文面が残らない。P1 の条件が決まった後に検討する
- P3: 各件の見立てを別のモデルに反証させ、一致した件だけを信用する。1件ずつの判断は速くなるが、週次のリミットを大きく使い、判断の回数は減らない

## 設計

### 昇格の条件

条件は「件の客観的な欄」に対する述語の和 (どれか1つを満たせば昇格) とする。見立てを使う条件は、一致率を見てユーザーが足すと決めたときだけ加える。

条件の形は「節の和」で、1つの節は述語の積とする (どれかの節を満たせば昇格)。述語には否定を持たせる。和だけだと、札の「実測」を1つ足した時点で約9割が昇格する (札に「実測」を含む件は742件、実測と推測の両方を含む件が28件)。

使える欄

- 出所の Issue と節、台帳に載った日、再報告が追記された日 (`added` / `appended`)。モデルの判断を含まない
- 札の完全一致を含む / 含まない。札は原文に逐語で在ることだけを確かめた値
- 届いた報告の件数 (`report_count`) の下限。モデルの判断だが、件を絞れるほぼ唯一の欄なので使う (2026-11-11 にユーザーが選んだ)

判断の後に報告が追記された件は、条件によらず既定の一覧へ戻し、「判断の後に追記」の印を付ける。見直して判断を付け直すか、「このままでよい」を押すと一覧から外れる。今の判定は判断とメモで共有の `updatedAt` の日付で比べているので、メモを直すだけで印が消える。判断を変えたときと「このままでよい」を押したときだけ進む `decidedAt` を足し、それと `appended` を比べる。`decidedAt` を持たない既存の判断は `updatedAt` で代える。

既定の一覧は「昇格した件のうち判断がまだのもの」と「判断の後に追記があった件」。条件がまだ1つも無いとき (初回、または保存先に繋がらない閲覧だけの状態) は、今と同じく判断がまだの全件を出し、条件が無いことを一覧の上に出す。今の絞り込み (状態・Issue・節・見立て・照合・載った日・検索) は残し、「保管中 (昇格していない) の件も含める」を明示的に選んだときだけ全件を見せる。保管中の件のカードには「保管中 (判断していない)」と出し、「採らない」と読める表示にしない。

条件の保存先は Artifact の保存先の別の collection にし、どの端末で開いても同じ条件になるようにする。collection を足すのに Artifact の宣言の変更が要るかは、計画の前に宣言を読んで確かめる。条件の初期値は空で、ユーザーが最初に決める。決めるときの参考として、条件ごとの該当件数を UI に出す。

### カードの見せ方

カードの欄を2つの群に分ける。

- 原文と照らして確かめ済み: 札 (原文に逐語で在ったもの)、既存の規範の該当箇所の引用 (参照先に逐語で在ったもの)、出所、載った日・追記の日。群の見出しは「原文に在る」の意味に限り、札の「実測」を実測であったことの確認と読ませない
- モデルの判断: 要約、見立てと理由、置き場の案、照合の状態 (covered / partial / none)、届いた報告の件数

確かめ済みかどうかはページを組むときに判定し、データに印を持たせる。ページの側で文字列を見て推測しない。逐語で無かった札 (今は2個) と、組むときに参照先から消えていた引用は「確かめ済み」の群に入れず、モデルの判断の群に出す。`~/.claude` 配下を指す引用 (12件) は CI に参照先が無いので、テストでは fixture で代える。

### まとめて決める

- 選び方はカードごとの選択の印と、「このページの全件を選ぶ」(最大25件) の2つ。絞り込みに合う全件を一度に選ぶ手段は持たない。目で見た件にしか及ばないようにする (2026-11-11 にユーザーが選んだ)
- 一覧の上に「選んだ N 件に 採る / 保留 / 採らない を付ける」と「選択を外す」を置く。絞り込みやページを変えても選択は残し、件数を常に表示する
- 選んだ件のうち既に判断がある件は飛ばし、「N 件は判断済みのため飛ばした」と出す。既存の判断を上書きしない (2026-11-11 にユーザーが選んだ)
- 書き込みは今の1件ずつの保存の経路をそのまま使う (変えた欄だけ送る、控え、送り直し)。メモは触らない
- 取り消しは直前のまとめての判断を1回だけ戻す。飛ばした件には触れていないので、付けた件を未判断へ戻すだけで済む

### 一致率の集計

1回きりの作業で、ページの機能にはしない。セッションが保存先の `decisions` を読み、判断の値だけを見立ての組ごとに数える。保存先は文書ごと返すのでメモも読み込まれうるが、集計にも出力にも使わない。結果は会話でユーザーへ見せ、追跡下には置かない。25件は少ないので、結論ではなく傾向の手がかりとして扱う。

### 台帳の一式の置き場

組み立ての一式 (`build.py` / `delta.py` / `merge.py` / 雛形) は、今は ignore 配下の `.cache/ledger/` にあり、書き捨てとして消される位置にある。ページの論理を足してテストを書くので、スクリプトと雛形は追跡下へ移す。台帳のデータ (`items-new.json`、815件、約1.15MB) は仕分けのたびに大きく変わり、ユーザーの判断に関わる作業の状態なので、追跡せず ignore 済みの `.hidari/` へ置く。移す前に全文を読み、漏洩検査を通す。

### テスト

- ページの論理 (昇格の判定、確かめ済みの群への振り分け、まとめての判断の対象の決め方、取り消し) を純粋な関数として切り出し、`node --test` でユニットテストを書く
- 組み立ての側 (確かめ済みの印を付ける、ID を引き継ぐ) は pytest で書く
- E2E は、保存先の偽物 (`window.claude.use("db")` の形を持つもの) を差し込んだページを Playwright で開き、決定的な経路を1本通す: 条件を決める → 一覧が絞られる → 判断済みを含めて複数を選びまとめて判断する → 保存先に未判断だった選んだ件だけが書かれ、メモが残っている → 取り消すと戻る
- Playwright はこのリポジトリで最初の JS の依存になる。台帳の一式のディレクトリに閉じた package.json を pnpm で持ち、E2E は手元だけで回す。`node --test` と pytest は CI に載せる。E2E は user CLAUDE.md の指定どおり Playwright Test Agents で作る
- claude.ai の中での確認は1回だけ手で行う。2026-11-10 の確認手順 (未判断の件で書き、確かめてから消す) を再利用する
