# PUBLIC リポジトリに露出している個人情報と private リポジトリ情報を棚卸しする

本 Issue 本文では、対象そのものを書き足して露出を増やさないため、private リポジトリ名・
marketplace 名・メールアドレスを伏字にする。ファイルパスと件数は公開情報なのでそのまま書く。

## 背景

`home/.claude/settings.json` の skip-worktree 運用を見直す過程で、この運用が守ろうとしていた
情報が既に別経路で公開済みであることが判明した。skip-worktree は 2 種類の情報
(ローカルユーザー名を含む絶対パス、private な plugin リポジトリの参照) を committed から
排除するために存在するが、同じ情報がバイナリ・git 履歴・ドキュメントの 3 経路から漏れている。

調査は 4 方向 (バイナリ / 追跡テキスト / git 履歴 / 検出網の穴) から並列に行い、
各結果を独立したエージェントが再現・反証した。以下はすべて実測で確認した内容。

## 露出の一覧

重要度順に並べる。上ほど実害が大きい。

### 1. private リポジトリの成果物が公開履歴に丸ごと残存している

security 系 plugin の 15 ファイルが、origin から到達可能な blob として公開履歴に残っている
(削除コミット全体で 1555 行)。dev-workflow 系の 5 skill も同型。

さらに削除コミット `a50a72ad` のメッセージが移設先を owner 付きのリポジトリ名で名指ししている。
つまり第三者は公開情報だけで「private リポジトリが存在すること」「その名前」「その中身の実物」
の 3 つを突き合わせられる。`CLAUDE.md` が現在も plugin 名で参照しているため対応関係も固定されている。

名前の露出より一段上の問題であり、本 Issue で最も重い。

### 2. 第 3 の private リポジトリが内部構造ごと露出している

`docs/superpowers/archive/2026-06-26-windows-vm-verification-skill.md` と同 `-design.md` に
計 50 件。リポジトリ名だけでなく、crate 構成・xtask のサブコマンド名・ssh host alias・
IP 解決スクリプトのパス・Windows 側のチェックアウトパスまで具体的に記載されている。

### 3. 勤務先ドメインのメールアドレス

`docs/issues/closed/7_Claude Code の 2 アカウント運用で設定を共有する/issue.md` に 1 件。

全 141 コミットの author メタデータを調べたところ、このアドレスは 1 件も現れない。
つまりこの Issue が唯一の露出経路であり、現ツリーの編集だけで新規露出は止まる
(履歴には残る)。勤務先ドメインを直接示すため個人特定性は今回の発見の中で最も高い。

同じファイルにある個人用のアドレスは、全 141 コミットの author として既に GitHub 上で
公開済みのため、削除しても公開状態は変わらない。

### 4. ローカルユーザー名を含む絶対パス

現在の追跡テキストには 0 件。露出は次の 2 経路のみ。

| 経路 | 件数 | 状態 |
| --- | --- | --- |
| `home/.config/herdr/resources/herdr-cheatsheet.af` と `home/.config/nvim/resources/nvim-cheatsheet.af` の平文領域 | 10 | 検出網を素通り |
| 同 2 ファイルの zstd 圧縮領域 | 72 | strings でも grep でも原理的に検出不能 |
| git 履歴 (`scripts/backup-tool/tests/test_paths.py` / `scripts/tests/backup.bats` / `.zshrc`) | 7 | CI が意図的に対象外 |

圧縮領域の 72 件にはリポジトリのチェックアウトパスまで含まれ、平文側には一切現れない。

漏れている内容自体は `~/Downloads` 配下の画像ファイル名で、認証情報や機微データは含まない。
実害はハンドルネームと実名が紐づく点にある。

この 2 ファイルは Affinity の編集元ドキュメントで、実行時に読む consumer がリポジトリ内に
存在しない (Raycast のスクリプトが参照するのは書き出し済みの PNG のみ)。にもかかわらず
追跡バイト総量 38,376,476 のうち 32,698,777 (85.2%) を占める。履歴にも旧版 blob が 4 本残る。

PNG 2 本は個人情報を含まず、実行時依存があるので追跡を続けてよい
(XMP・ICC・ピクセル内容まで確認済み)。

### 5. marketplace 名

テストフィクスチャとドキュメントに現ツリーで 12 件、履歴を含めて 24 件。
単なるラベルでそれ単独では何も開かない。フィクスチャの分はダミー名へ置換しても
仕様の表現力が落ちないので、コストの割に確実に減らせる。

## 検出網の穴

`.gitleaks.toml` と pre-commit / CI の組み合わせには構造的な穴がある。すべて対照実験で確認した。

### バイナリを素通りする

使い捨てリポジトリで pre-commit と同一のコマンドを実行した結果。

- 実物の `.af` (8.4MB、ローカルユーザー名を 6 箇所含む) を stage → 走査バイト数ほぼ 0 で exit 0
- 同じ内容をテキストファイルで stage → 1 件検出して exit 1

陽性対照が赤くなるのでルール自体は生きている。原因は「バイナリだから」ではなく
「git 差分モードだから」で、git がバイナリ差分の中身を出力しないため gitleaks が
内容を受け取っていない。pre-commit も CI も同じ理由で素通りする。

過去の遺物ではなく現在も開いている穴で、今日同じファイルを再コミットしても通る。

なお `gitleaks dir` に直接渡せば検出できるが、これを CI に足しても解決しない。
構造的に同一の 2 ファイルで検出結果が割れることを実測しており、バイナリ検出は内容依存で
信頼できない。バイナリ由来の露出は gitleaks 以外の手段で確認する必要がある。

### 検出できない表記が 3 つある

- ホーム相対表記。今回の露出の多くがこれで素通りしている
- 大文字で始まるユーザー名。macOS のファイルシステムは case-insensitive なので実在パスとして機能する
- 相対形

### コミットメッセージを走査しない

gitleaks は diff の内容のみを対象にする。commit-msg 段階のフックも別の検査しか行わない。
実際、露出を含むコミットメッセージが複数存在する。うち 1 件は
「この形式だと gitleaks に弾かれる」と検出網の存在に言及しながら、
メッセージ経由なら素通りすることに気づいていない。

### config-guard の守備範囲

`home/.claude/settings.json` の committed 版のみを検査する。これは設計どおりで、
実際 committed 版は全履歴を通じてクリーンだった (curation は機能している)。
ただしリポジトリ全体の露出を見る役割は持っていない。

## 対処の制約

すべて履歴書き換えと force push を要する。ただし GitHub 側に残るクローズ済み PR の diff・
Actions のログ・API 経由の参照は force push 後も残りうる。
「履歴を書き換えれば消える」という前提で計画を立てるべきではない。
