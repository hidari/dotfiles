# fix: Closes の識別子抽出がリンクテキストの空白で 0 件になる

## 背景

`dev-workflow:in-repo-issue` の Phase C.1 が PR 本文から close 対象の識別子を抽出するとき、
`Closes ` と数字のあいだに半角空白が入ると 0 件を返す。エラーではなく空なので、自動クローズが
静かに止まる。

astralys-art で稼働中のエージェントから委譲された報告を、dotfiles 側で再現して境界を詰めた。

### 現行パターン

```
(Closes|Fixes) \[?[^] ]*[0-9]+
```

### 実測

| 本文 | 抽出 |
| --- | --- |
| `Closes [ISSUE-27](../x/issue.md)` | `ISSUE-27` |
| `Closes [264](path)` | `264` |
| `Closes [Issue #1299](../x/issue.md)` | 0 件 |
| `Closes Issue #1299` | 0 件 |
| `Closes #1299` | `#1299` |
| `Closes A#1` / `Closes [A#1](x)` | `A#1` |
| `Closes A #1` / `Closes [A #1](x)` | 0 件 |

**リンクの有無は無関係**で、`Closes ` と数字のあいだの半角空白だけで決まる。委譲元の報告は
「リンク形式かつ空白入りの組み合わせ」を条件としていたが、リンクを外しても 0 件になる。
「リンクを外せば通る」は回避策として機能しない。

リンクテキストが裸の番号でも通る。記法が混在するリポジトリでは、旧番号の Issue も新形式の
書き方で閉じられることになる。別の配布先が実際にこの状態にあり、そこから報告された。

機序は `[^] ]*` が空白を含まないこと。`Issue` の直後で止まり `[0-9]+` が空白に当たって失敗する。
空へバックトラックしても開始位置は `I` なので数字に一致しない。

### 既知であることと、それでも直す理由

skill の「PR / コミット規約」節は旧記法の `Closes [Issue #8](...)` を 0 件になる書き方として
既に挙げている。つまりこれは規約を外れた書き方の帰結であって未知のバグではない。

それでも直す価値があるのは、抽出がリンク**テキスト**だけを見ていて、識別子が確実に居る
リンク**ターゲット** (`docs/issues/<ID>_...`) を見ていないため。ターゲット側からも拾えば、
リンクを持つ本文ではテキストが散文でも通り、しかも skill の設計方針「パターンは識別子の形
そのものを持たない」と矛盾しない (v0.8.0 の規約では本文にリンクを張らない。下の 2026-09-17 の節)。

委譲元は旧 GitHub Issues 番号からの継続採番で、識別子が GitHub の番号空間と重なっている。
規約どおりに書けば (当時はリンクテキストを識別子だけ、v0.8.0 以降はリンクの無い `Closes <ID>`)
当面は通るが、同じ形の本文を書く経路は他にも生まれうる。

### 直すときに一緒に見る箇所

抽出は grep と sed の 2 段で、grep だけを直すと sed が取り残される。sed は行頭の
`Closes ` と開き括弧だけを剥がす前提なので、grep をリンクターゲットまで拾う形へ広げると、
剥がし残しがそのまま識別子として渡る。2 段のパターンはどちらも skill の Phase C.1 にある。

検査は緩めすぎる方向へ倒すこと。抽出が広がると、本文中の無関係な数字を close 対象として
拾い、存在しない Issue を閉じようとする経路が生まれる。抽出 0 件は静かな不発として現れるが、
抽出しすぎは「存在しない Issue」のログとして現れるので、後者の方がまだ気づける。
それでも変異注入の重点は広がりすぎる側に置く。ただし C.3 が識別子をパターンとして読む間は、
抽出しすぎた値が実在する別の Issue に当たり、このログも出ない (下の 2026-09-18 の節)。

### パターンの直下に、パターンを説明する注記が 3 つある (2026-08-29)

上流で並行作業しているエージェントからの指摘を、こちらで実体を読んで確認した。Phase C.1 の
コードブロックの直後に、現行パターンの性質を述べる注記が 3 つ並んでいる。

1. パターンは識別子の形そのものを持たない、という性質の主張
2. GitHub 素形式専用へ戻さないこと、という将来の変更への制約
3. 現行パターンは数字記法からも拾う、という実測の記録

パターンを変えると、1 と 3 は真偽が変わりうる。3 は現行の正規表現に結び付いた実測なので、
正規表現を変えた時点で測り直しになる。1 は、リンクターゲットから拾う形へ広げるとパターンが
ディレクトリ構造を持つことになるため、主張の射程を見直す必要がある。2 は制約なので変更後も
そのまま残る。

上流のリポジトリでは散文の真偽をどの検査も見ない。したがってこの 3 つは、パターンを直した
瞬間に黙って古くなる位置にある。

### 上流の並行作業とは衝突しない (2026-08-29)

上流は `fix/issue-41-close-bundling-gate` で作業中で、その差分に Phase C.1 と同じファイルが
含まれる。ファイル単位で見ると衝突するように見えるが、ハンク単位では重ならないことを上流側が
実測して回答した。C.1 のコードブロックの 2 行は差分に一度も現れず、担当エージェントにも
コードブロックを編集しない制約がかけられている。

ファイル単位の一致を衝突と読むと、着手できるものを待たせることになる。粒度を上げて確かめる
こと。

### 上流 v0.8.0 で Closes 行からリンクが外れた (2026-09-17)

dotfiles は同日に agentic-coding-tools の pin を v0.8.0 へ上げた。v0.8.0 の skill は、PR 本文の
Closes 行をリンクの無い `Closes <ID>` と定めた。C.1 のパターンは、リンク付きで書かれたマージ済みの
PR を拾うために `\[?` を残した。

v0.8.0 の skill は、識別子を装飾したときの実測も記録している。バッククォートで囲むと、識別子は
先頭の装飾ごと抽出され、C.3 の「見つからない」分岐で no-op になる (ログに 1 行残るだけで、終了
コードは 0)。数字を含まない語をキーワードと識別子の間に挟むと (`Closes in-repo Issue <ID>`)、
抽出は 0 件になる。

これで下のタスクの比べ方が変わる。リンクターゲットから拾う案が効くのは、リンクを持つ本文 (主に
旧形式) だけになった。リンクを持たない本文にはターゲットが無いので、テキストが `Closes Issue 45`
のように規約から外れると、この案では救えない。どちらの形にするかは、この差を入れて比べる。

### 装飾の `*` が C.3 の検索でグロブとして働く (2026-09-18)

v0.8.0 の skill は `**` の装飾も「見つからない」で no-op になるとしているが、dotfiles で測ると
違った。C.3 は抽出した識別子を `find -path` のパターンへそのまま埋め込むので、先頭の `*` が
グロブとして働く。fixture (active な `145_z` と `ISSUE-52_x` と `ISSUE-152_w`、closed な `45_y`) での
結果は次のとおり。`ISSUE-152_w` は、新形式の番号の末尾一致に当たらないことの対照である。

| 本文 | 抽出 | C.3 が選んだ Issue |
| --- | --- | --- |
| `Closes **ISSUE-52**` | `**ISSUE-52` | `ISSUE-52_x` |
| `Closes *ISSUE-52*` | `*ISSUE-52` | `ISSUE-52_x` |
| `Closes **45**` | `**45` | `145_z` (`closed/45_y` にも一致し、この fixture では `145_z` が先に返った) |
| `` Closes `ISSUE-52` `` | `` `ISSUE-52 `` | 見つからない |

数字だけの識別子は、ディレクトリ名のどこかに `<数字>_` を含む別の Issue にも一致する。番号の
末尾が一致する旧形式の Issue も、新形式の `ISSUE-<N>` も含まれる (`**45` は `ISSUE-45_` に一致する)。
find がそちらを先に返せば、その Issue に当たる。先頭に `?` が残る値 (`?5`) も同じように働く。
`ISSUE-<N>` に当たることと `?` の件は上流が知らせてくれたもので、dotfiles でも確かめた。

新形式の識別子では、`*` の装飾は意図した Issue に当たる。skill が書く「自動クローズが効かない
まま緑で通る」とは逆に、クローズの判定まで進む。

別の Issue に当たったときの帰結は C.3 の分岐で決まる (分岐から読んだもので、プローブは find まで
しか通していない)。タスクが全部 `[x]` ならその Issue が閉じ、未完のタスクがあればその Issue の
status が in_progress へ書き換わる。上の「直すときに一緒に見る箇所」は、抽出しすぎが「存在しない
Issue」のログとして現れることを前提にしているが、この経路ではそのログが出ない。

上流はこの件を agentic-coding-tools の ISSUE-62 として起票した (2026-09-18)。

### 影響範囲

修正対象の skill 本体は agentic-coding-tools にある。dotfiles は調整点として起票し、上流へ
委譲する。dotfiles でも PR #223 の本文の Closes 行 2 本 (`Closes [Issue 45](...)` と
`Closes [Issue 4](...)`) が、どちらもこの 0 件の形だった。当時の規約 (v0.7.0 の
`Closes [<ID>](...)`) からも外れていた。同じ PR で 2 件とも `closed/` へ移していたので、実害は
無かった。v0.8.0 以降は `Closes <ID>` で書く (旧形式の識別子なら `Closes 45`)。
