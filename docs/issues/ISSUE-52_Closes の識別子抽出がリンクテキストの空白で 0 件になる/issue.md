# fix: Closes の識別子抽出がリンクテキストの空白で 0 件になる

## 背景

`dev-workflow:in-repo-issue` の Phase C.1 が PR 本文から close 対象の識別子を抽出するとき、
`Closes ` と数字のあいだに半角空白が入ると 0 件を返す。エラーではなく空なので、自動クローズが
静かに止まる。

astralys-art で稼働中のエージェントから委譲された報告を、dotfiles 側で再現して境界を詰めた。

### 現行パターン

```
(Closes|Fixes) \[?[^] ]*[0-9]+
```

### 実測

| 本文 | 抽出 |
| --- | --- |
| `Closes [ISSUE-27](../x/issue.md)` | `ISSUE-27` |
| `Closes [Issue #1299](../x/issue.md)` | 0 件 |
| `Closes Issue #1299` | 0 件 |
| `Closes #1299` | `#1299` |
| `Closes A#1` / `Closes [A#1](x)` | `A#1` |
| `Closes A #1` / `Closes [A #1](x)` | 0 件 |

**リンクの有無は無関係**で、`Closes ` と数字のあいだの半角空白だけで決まる。委譲元の報告は
「リンク形式かつ空白入りの組み合わせ」を条件としていたが、リンクを外しても 0 件になる。
「リンクを外せば通る」は回避策として機能しない。

機序は `[^] ]*` が空白を含まないこと。`Issue` の直後で止まり `[0-9]+` が空白に当たって失敗する。
空へバックトラックしても開始位置は `I` なので数字に一致しない。

### 既知であることと、それでも直す理由

skill の「PR / コミット規約」節は旧記法の `Closes [Issue #8](...)` を 0 件になる書き方として
既に挙げている。つまりこれは規約を外れた書き方の帰結であって未知のバグではない。

それでも直す価値があるのは、抽出がリンク**テキスト**だけを見ていて、識別子が確実に居る
リンク**ターゲット** (`docs/issues/<ID>_...`) を見ていないため。ターゲット側からも拾えば、
テキストが散文でも通り、しかも skill の設計方針「パターンは識別子の形そのものを持たない」と
矛盾しない。

委譲元は旧 GitHub Issues 番号からの継続採番で、識別子が GitHub の番号空間と重なっている。
リンクテキストを規約どおり識別子だけにすれば当面は通るが、同じ形の本文を書く経路は他にも
生まれうる。

### 影響範囲

修正対象の skill 本体は agentic-coding-tools にある。dotfiles は調整点として起票し、上流へ
委譲する。dotfiles 自身の PR 本文は規約どおりの形なので現状の実害は無い。

## タスク

- [ ] 抽出をリンクターゲットからも拾う形にするか、テキスト側の空白を許容する形にするかを決める
- [ ] 上流 agentic-coding-tools へ委譲する
- [ ] 委譲元へ回答する。当面の回避は `Closes [<ID>](path)` へ直すことで、リンクを外す案は効かない
- [ ] 配布後に dotfiles と委譲元の両方で追試する
