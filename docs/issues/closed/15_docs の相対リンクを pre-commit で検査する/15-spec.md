# Markdown 相対リンク検査の設計

## 背景と目的

Issue を `docs/issues/closed/` へ移すたびに、その Issue を指す相対リンクと、その Issue から出ているリンクの両方が切れる。`../10_...` と `../closed/10_...` の書き分けが両端の open / closed 状態に依存するためで、close する側とは別のファイルへ波及編集が要る。

これは仮説ではなく実績がある。`closed/9_.../issue.md` のリンクは導入コミットの時点で `../closed/7_...`（= `docs/issues/closed/closed/7_...`）と壊れており、main 上で壊れたまま残っていた。PR #77 のレビューで検出して直したが、検出したのは人間とレビューエージェントの目視である。

pre-commit には ruff / mypy / pytest / gitleaks / ast-grep / shellcheck が揃っているのに、Markdown の相対リンクを見るものが 1 つも無い。CLAUDE.md MUST GLOBAL の「静的検査可能なルールはプロンプトではなく、その環境の linter か ast-grep で記述する」に真正面から該当する。

本設計は追跡下の Markdown の相対リンクが実在するかを機械検査し、pre-commit と CI で止める。

## 確定した設計判断

- ゴールは検出のみとする。リンク形を open / closed 非依存にする構造変更（Issue のタスク 5）は行わない。`dev-workflow:in-repo-issue` スキルは別リポジトリにあり、仕様変更を同期させるコストが検出の価値に見合わない。検査が入れば close 時の作業は「切れたリンクを探す」から「指摘された箇所を直す」に変わり、見落としが構造的に消える。
- 検査範囲は追跡下の全 `.md`。`docs/` に絞らない。除外リストを持たない分だけ実装が単純で、将来 README や skills に相対リンクが増えても自動で守られる。現時点で壊れたリンクは 0 件なので導入コストもゼロ。
- 実装は既存の `scripts/config-guard` へチェックを 1 つ足す形にする。独立プロジェクトの新設は CI ジョブ 1 つと pre-commit hook 5 つを増やし、外部 linter の導入は依存を増やす。調査用に書いたプロトタイプは実リポジトリ全体を正しく判定して 60 行（コメント込み）だったので、どちらの周辺コストも検査本体の規模に見合わない。config-guard は既に `tool_refs`（stale なツール名参照の検出）を持っており、リンク検査は「stale なファイル参照の検出」として同族である。
- アンカーの実在は検査しない。見出しから anchor slug を生成する規則は処理系ごとに違い、自前実装は必ず drift する。パス部分だけを見る。
- リンク先は実在のみを判定し、「追跡下のファイルか」までは見ない。現在追跡外を指すリンクは 0 件で、必要になってから足せる。

## アーキテクチャ

`scripts/config-guard/src/config_guard/markdown_links.py` を新設し、`check_markdown_links(repo_root: str) -> list[Finding]` を公開する。`cli.py` の `scan()` から既存 5 チェックと同じ形で呼ぶ。

検査対象の列挙は既存の `run_git` ヘルパーで `git ls-files -z '*.md'` を実行して取る。`Path.rglob` を使わない理由は 2 つある。`.venv` や `apm_modules` を自前で除外する必要がなくなること、そして既存モジュール `apm_gitignore.py` が同じく git 経由で判定しており、パターンを揃えられることである。

`run_git` はロケーション系 `GIT_*` を除いた環境で git を起動する。pre-commit 経由の実行で hook 側の repo を読んでしまう事故を防ぐためのもので、本チェックもこの恩恵をそのまま受ける。

git の exit code が 0 以外なら例外を送出する（`git_run.py` の `run_git_checked` が担う）。`apm_gitignore.py` と同じ方針で、git のエラーを「リンクが無い」と取り違えて findings を量産することを防ぐ。

## 判定ロジック

列挙は git の index を見るが、読み取りは worktree を見る。追跡下だが worktree に無い `.md`（commit 前の削除途中）は読まずに skip する。消えたファイル自身のリンクは検査対象として意味を持たず、そのファイルへ向かう他ファイルのリンク切れは、リンク元側の実在判定が worktree を見るため通常どおり検出される。

リンクの抽出は正規表現 1 本（`markdown_links.py` の `LINK_PATTERN` が canonical）で行い、インラインリンクのターゲット部分を取り出す。画像記法は同じ形なので自然にカバーされる。

ただし抽出の前にコード領域を除く。設計ドキュメントはリンク記法そのものを例示することがあり、それを実リンクと読むと存在しないパスを指摘し続ける。実際この機能の spec と plan 自身の記法例（コードフェンス内とインラインコード内）が誤検出になった実績がある。一般的な Markdown リンクチェッカーもコードブロックを検査対象から外す。

除外は 2 段構えとする。

1. 行頭（インデントを許す）のバッククォート 3 つ以上をフェンスのデリミタと見なし、フェンス内の行は抽出しない。開始フェンスのバッククォート数を記憶し、終了フェンスにはその数以上の長さを要求する（CommonMark の規則）。長さを見ない単純トグルでは、外側を 4 本のフェンスで囲み内側に 3 本のフェンスを例示する入れ子（markdown について書く markdown）が内側の 3 本で早期に閉じ、例示コード中のリンクを実リンクと誤読する
2. フェンス外の行からはインラインコード（バッククォートのペア）を取り除いてから抽出する

`~~~` によるフェンスは扱わない。リポジトリに 0 件で、扱わないことによる副作用も「フェンス内が検査される」だけであり、実害が出た時点で足せる。フェンス行のインデントは許容する（パターンは `markdown_links.py` の `FENCE_PATTERN` が canonical）。`home/.claude/skills/windows-vm-verification/SKILL.md` に 3 スペースインデントのフェンスが実在するため、行頭固定では取りこぼす。

抽出した各ターゲットを次の順で判定する。

1. 外部 URL → 検査しない。ネットワークを叩かない。既知スキームの列挙ではなく RFC 3986 のスキーム文法（`markdown_links.py` の `EXTERNAL_SCHEME` が canonical）とプロトコル相対 `//` で判定するため、未知のスキーム（`vscode:` 等）も外部として扱う。代償として第 1 セグメントにコロンを含む相対パスは URL と解釈され検査されない（macOS ではコロン入りファイル名が実質使えず、スキーム形の文字列は URL である確率が高い）。
2. `#` で始まる → 検査しない。同一ファイル内アンカー。
3. それ以外 → `#` があればその前だけを取り、`urllib.parse.unquote` でデコードし、リンク元ファイルの親ディレクトリからの相対で解決して実在を確認する。

デコードの順序が重要である。アンカーを切り落としてからデコードする。逆順にすると、`%23` でエスケープされた `#` がデコードで裸の `#` になり、パスの一部が誤ってアンカーとして切り落とされる。

検出時は `Finding(source, detail, message)` を返す。`source` はリンク元の repo 相対パス、`detail` はリンク文字列そのもの、`message` は解決先を含む理由文とする。既存の `Finding` の並びに従う。

## 配線

`.pre-commit-config.yaml` の `config-guard-scan` hook は `always_run: true` で毎コミット発火する。CI は既存の config-guard ジョブが `uv run config-guard ../..` を回すので変更不要。

リンク検査は「変更されたファイルだけ見る」では機能しない。リンク先を消したとき、壊れるのはリンク元であり、そのファイルは変更されていないためである。hook は `pass_filenames: false` で常にリポジトリ全体を走査するため、この性質にそのまま合致する。

当初の設計は既存 hook の `files` 列挙に `.md` の選択肢を足す形だった。検査入力に無関係なコミットで hook を走らせないための絞り込みである。マージ前レビューで `always_run: true` へ変更した。理由は 3 つある。

1. `files` は「検査ごとの入力パスの選択肢」の開いた列挙であり、検査を足すたびに `scan()` への配線と `files` への追記が独立した手作業になる。追記漏れは silent に起きる（mise の入力パスの追記漏れが実際に最終レビューまで残っていた）。
2. `.md` を `git rm` しただけのコミットでは `files` にマッチする変更後パスが無く hook が発火しないことを実測で確認していた（CI の全体走査を backstop とする穴だった）。`always_run` はローカルでもこの穴を塞ぐ。
3. 列挙を守るための整合テストと自前 YAML 行パーサの維持コストが、発火を絞ることで節約できる実行時間に見合わない。裁定時点の warm フルスキャン実測は 0.4 秒台で、同レビューで `git check-ignore` をバッチ化した後は 0.14 秒。同じ設定で gitleaks が既に `always_run: true` で毎コミット走っている。

## テスト仕様

`scripts/config-guard/tests/test_markdown_links.py` に置く。`tmp_path` に最小のリポジトリを組んで実行する。git 呼び出しを含むため、テスト内で `git init` して `git add` する。

仕様として表現するもの。カテゴリ粒度で示す（個々のテスト名と件数は `test_markdown_links.py` が canonical）。

- 抽出と分類の純粋関数: インラインリンクと画像記法の抽出、リンクを含まない本文から何も抽出しないこと、外部 URL の除外（大文字小文字を無視、未知スキームとプロトコル相対も除外、第 2 セグメント以降のコロンは除外しない）、アンカーのみのリンクの除外、% エンコードのデコード、アンカー切り落としとデコードの順序（`%23` がパスとして生き残ること）。
- 実在判定: 生きた相対リンクを検出せず壊れた相対リンクを検出する、リンクを含まない `.md` で何も検出しない、% エンコードを含むリンクの解決（デコードしなければ生きたリンクを壊れていると誤判定する）、パス + アンカーはパス部分だけを判定する、ディレクトリを指すリンクの解決、repo 外へ解決されるリンクの解決先も repo 相対（`../` 始まり）で示す、検出時の `Finding` がリンク元ファイル・リンク文字列・解決先を含む。
- 対象の列挙: 追跡外の `.md` を検査しない、`.md` 以外の追跡ファイルを読まない、index にあるが worktree に無い `.md` は skip する（skip が検出漏れを生まないことも同時に検証する）、git エラーは「リンクが無い」と取り違えず明示的に失敗する。
- コード領域の除外: フェンス内とインラインコード内のリンク例を検査しない、インデントされたフェンスの認識、入れ子フェンス（開始フェンスの長さを記憶した閉じ判定）、フェンスが閉じた後やインラインコードの外にある実リンクは検査される（除外しすぎない negative case）。
- pre-commit 配線の不変条件: `config-guard-scan` hook が `always_run: true` を持つ（`tests/test_precommit_wiring.py`）。YAML は構造として読む。発火条件の列挙へ戻ると「入力ファイルの編集で発火しない検査」が再び構造的に作れてしまうため、値そのものを pin する。

各テストは変異注入で赤くなることを確認する。デコードを外す、外部 URL の skip を外す、アンカーの切り落としを外す、`always_run: true` を外すなど、1 箇所ずつ隔離して行う。
