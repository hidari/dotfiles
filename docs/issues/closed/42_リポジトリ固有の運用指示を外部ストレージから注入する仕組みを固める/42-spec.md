# 42-spec: 運用指示の注入を user スコープへ寄せ、対象の宣言と検出層を作る

この spec は ISSUE-42 の「決めること」4 項目に答える。背景と現状の安全性は issue.md が
canonical なので再掲しない。

## 前提を覆した実測 (2026-09-01)

設計の骨子は、当初の想定 (テンプレートを配って揃える) を実測が覆したことから決まった。

| # | 当初の想定 | 実測 | 出所 |
| --- | --- | --- | --- |
| 1 | テンプレートが canonical | `SessionStart` のコマンド文字列は 2 種あり、**テンプレートと一致するのは 1 リポだけ**。残る 12 リポは別の変種 | 13 リポの `settings.local.json` を JSON で読んで文字列を集計 |
| 2 | project 配線が要る | テンプレートの 4 フックのうち **3 つは user スコープの `home/.claude/settings.json` と同一内容**。project 固有なのは `cat` の 1 本だけ | 両ファイルの突き合わせ |
| 3 | 修復にコミットが要る | `.claude/settings.local.json` は 28 リポすべてで **TRACKED 0** (untracked 19 / absent 9) | `git ls-files --error-unmatch` を 28 リポで実行 |
| 4 | 非空の project hooks は user 側を置換するかもしれない | **置換しない**。project 側に独自 hook を持つリポで、user スコープにしかない `handoff-sentinel session` の生成物が実在する | 生成物の実在を確認 |
| 5 | 配線が欠けた 16 リポすべてが対象 | うち 5 リポは Claude のセッション履歴が 0 件、1 リポは archive 済み。**実際の対象は 10** | `~/.claude/projects/` の実ディレクトリ名と突き合わせ |

実測 1 が示すのは、写しを配る方式では canonical を名乗る写し自身が drift するということである。
実測 2 が示すのは、13 リポで維持してきた配線の 3/4 が最初から冗長だったということである。

この 2 つから骨子が決まる。**配線を揃えるのではなく、配線を要らなくする。**

実測 5 の測り直しについて。最初の測定は projects ディレクトリ名を推測で組み立てたため、
アンダースコアを含むリポが「未使用」に落ちた。実ディレクトリ名との突き合わせで訂正した。
偽陰性は「未適用」という重大な誤報になり、しかも何度引いても同じ答えが返る。

## 決めたこと

### 1. 配置の再現手順の置き場 (issue.md の論点 1 への答え)

dotfiles にセットアップスクリプトを新設する。`bootstrap.sh` には入れない。
issue.md が書いたとおり bootstrap はマシンのセットアップでありリポジトリの初期化ではなく、
責務が違う。スクリプトの本体を dotfiles が持ってよいことはユーザーが明示した。

スクリプトは冪等で、以下だけを行う。

| 実測した状態 | 動作 |
| --- | --- |
| `.hidari/` が無い | 作る |
| `.hidari/private-ops` が無い / dangling | 張り直す |
| 対象リポで `.hidari/` または `.cache/` が ignore されていない | **作らずに落ちる** (論点 2 への答え) |

**実装後の訂正 1: `--ops <path>` を必須にした。** 当初は `$HOME/.hidari/private-ops` を既定値に
する設計だったが、実測するとそのパスは存在せず、既存 21 リポの symlink はすべて外部ストレージの
絶対パスを直接指していた。一度も成立したことのない既定値だった。live smoke が `--ops` を明示して
いたため露見しなかった。dotfiles は PUBLIC なので実体のパス (ユーザー名とメールアドレスを含む) を
コードへ書けず、既定値を持つことが原理的にできない。

**実装後の訂正 5: 訂正 1 を緩めて、`--ops` を省略したときは実行時に導出する形にした。**
訂正 1 が塞いだのは「実体のパスをコードへ書くこと」であって「既定値を持つこと」ではなかった。
実行しているリポジトリ自身の `.hidari/private-ops` を `readlink` すれば、リポジトリへ何も
書かずに同じ値が得られる。導出できないときは空の `$OPS` で進まずに落ちる (空のまま進むと
取り付け済みのリポが軒並み `missing` に見える)。

これを足したのは、一覧を `$HOME` 相対へ戻す判断 (次節の訂正 6) と対になるためである。
一覧だけを相対形にしても、起動コマンドの `--ops` が絶対パスを要求する限り、ユーザー名と
メールアドレスは同じ 1 行に現れ続ける。露出面は片方だけでは閉じない。

**実装後の訂正 2: `hooks` キーの報告を実装せず、この表から削除した。** 当初は
「`.claude/settings.local.json` の `hooks` キーが残っている → 報告する。自動では消さない」と
書いていた。この行は移行期の補助として書かれたもので、下記「配線の移動」が完了した時点で役目を
終えている。テンプレートから `hooks` を消したので新しいリポでは生まれず、既存 21 リポからも
消した。残る発生条件は「手で足したとき」だけで、実害は運用指示が 2 回 context に載ることに
限られ機能は壊れない。`repo-wiring` は sh スクリプトなので JSON を読むには `python3` か `jq` への
依存が要り、下記「4. 取り付けの検査」が置いた「新しく増える機構は 2 つ」の予算にも触れる。

**外部ストレージ側のテンプレートからも `hooks` を削除した。** 残すと新しいリポを作った瞬間に
project 側の配線が復活する。テンプレートは `permissions` だけを持つ形になった。あわせて運用指示の
文書 (`PRIVATE_CLAUDE.md`) の 3 箇所を実態へ合わせた (読み込み経路が user スコープであること、
取り付けが `repo-wiring` であること、構造図の矢印)。テンプレートの `SessionStart` は 28 リポの
うち 1 リポとしか一致しない形をしており、**canonical を名乗る写しの側が実態から取り残されて
いた**。

### 2. ignore の保証 (issue.md の論点 2 への答え)

実測すると、28 リポすべてで `.hidari/` は ignore されている。ただし対照を取ると層の薄さが出る。
`core.excludesfile` を無効にして測り直すと **26 リポが ignore されなくなった**。
per-repo の `.gitignore` に記述を持つのは 2 リポだけで、残りは global が唯一の層である。
allowlist 方式 (`.claude/*` で閉じて `!` で開ける) のリポでも再包含の穴は無かった。

対照が無ければ「28 リポ全部で ignore 済み」という緑だけが見え、層が 1 つしかないことは
見えなかった。

2 層目は `.git/info/exclude` に置く。scratch repo で確かめたところ、global を無効にしても
この記述だけで ignore が効き `git status` にも現れない。

| 案 | 層 | コミット | 外部リポを汚すか | clone に travel するか |
| --- | --- | --- | --- | --- |
| global のみ (現状) | 1 | 不要 | しない | しない |
| per-repo `.gitignore` | 2 | 要 | する | する |
| **`.git/info/exclude`** | **2** | **不要** | **しない** | しない |

per-repo `.gitignore` を採らないのは、その唯一の利点である travel が実質的に効かないためである。
`.hidari/private-ops` の symlink 自体が travel しないので、clone しただけでは `.hidari/` が
存在せず、ignore だけ先回りしても守る対象が無い。どのみちスクリプトを走らせる必要がある。

スクリプトの順序は次のとおり。

1. `.git/info/exclude` に記述が無ければ書く
2. `git check-ignore` を**配下パス**で引いて ignore を確かめる
3. それでも ignore されなければ **symlink を作らずに落ちる** (再包含などの異常)
4. `.hidari/` を作り symlink を張る

3 を残すのは、スクリプト自身が ignore を用意しても穴が残る経路があるため。fail-closed に倒す。
symlink の中身は絶対パスなので、追跡候補になった時点で `macos-user-path` と `email-address` の
露出面ができる。gitleaks は 3 層目にあたる。

問い合わせを `.hidari/` ではなく `.hidari/private-ops` の形で行うのは、末尾スラッシュ付きの
ディレクトリパターンがディレクトリパスで問い合わせたときだけ実体を要求するためである。
配下パスなら実体が無くても一致することは scratch repo で確認した。

論点 2 のもう一方である `.cache/` について、この spec は当初こう書いていた。

> 実測すると、調べた 8 リポはすべて自前の `.gitignore` でも ignore しており、
> `check-ignore` が指すのは per-repo 側だった。つまりこちらはマシンローカル設定に
> 依存していない。

**実装後の訂正 3: これは誤りだった。** 一覧が確定してから 21 リポ全数で数え直すと、
per-repo が効いているのは 13 リポで、**8 リポは global だけに依存していた**。
当初調べた 8 リポは per-repo 側に偏っており、母数が足りていなかった。
しかも global 依存の 8 リポは、この spec の実装で新規に取り付けた 8 リポと同じ集合だった。

| ignore の層 | 件数 |
| --- | --- |
| per-repo の `.gitignore` が効いている | 13 |
| global だけが効いている | 8 |
| ignore されない | 0 |

棚卸しの表は見つけた分だけが載るので過小評価に外れる。着手の根拠にするときは数え直すこと。

そこでスクリプトは `.hidari/` と `.cache/` の**両方を `.git/info/exclude` へ書く**。
`.git/info/exclude` は追跡外なので「追跡外だけを機械化する」境界の内側にある。
**自動では `.gitignore` へ足さない。** 追跡下の変更はコミットを伴い、その境界を越えるためである。

`.cache/` の ignore が確かめられない場合も `.hidari/` と同じく **fail-closed で落ちる**。
当初は「報告する」に留める案だったが、`.git/info/exclude` へ書いた後もなお ignore されないのは
再包含という異常であり、`.hidari/` と扱いを分けると分岐が増える。`.cache/` には作業の引き継ぎ書
など実プロジェクト情報が入りうる。実測では 21 リポすべてが ignore されており (「ignore されない」
は 0 件)、この判断で落ちるリポは現時点で存在しない。

テストが `.git/info/exclude` の効果を単独で測れるのは、`core.excludesfile` が `~` 形式で
書かれているためである。テストは `HOME` を一時ディレクトリへ差し替えるので global が解決せず、
`.git/info/exclude` が唯一の層になる。絶対パスで設定されていると **テスト環境でも global が効き、
この guard は dead pin になる**。

### 3. 公開範囲の注入 (issue.md の論点 3 への答え)

**採らない。** 0.73 秒を全セッションに乗せる対価に見合わない。ネットワーク不通時の挙動も
決めが要る。規範としては user CLAUDE.md に既にあり、今回の主目的の外にある。
この判断を記録することでこの論点を閉じる。

### 4. 取り付けの検査 (issue.md の論点 4 への答え)

二層にする。

| 層 | 実体 | いつ | 見る範囲 | 書き込み |
| --- | --- | --- | --- | --- |
| 実行時 | `guard_probes.PROBES` へ述語 1 件 | 全リポ・毎セッション開始 | 今いるリポ 1 件 | しない |
| 棚卸し | セットアップスクリプトの `--check` | 手動 | 一覧の全件 | しない |

棚卸しを config-guard へ足さない理由は 2 つある。`config-guard scan` は pre-commit で
`always_run` なので、そこへ他リポの状態を混ぜると一時的な状態が dotfiles のコミットを止める。
そして別コマンドとして足すと、適用する側と検査する側が別の実装になり「検査は通ったが
適用が違う」が起きうる。適用と検査が同じコードなら、その食い違いは構造的に起きない。

この判断で新しく増える機構は 2 つに収まる。probe 1 件と、スクリプト 1 本である。
config-guard には触らない (配線を pin する既存検査への追記を除く)。

probe が書き込まない理由は 2 つある。セッション開始時に副作用を持つ hook は、意図しない
作業ツリー (他人のリポの clone、一時ディレクトリ) にも書き込む。そして書き込みが成功すると
次回から probe は無言になるので、間違った対象へ取り付いたことに気づけない。

## 設計

### 配線の移動

```mermaid
flowchart LR
    subgraph BEFORE["変更前"]
        U1["user scope settings.json<br/>4 フック"]
        P1["各リポ settings.local.json<br/>4 フック (3 つは user と同一)"]
    end
    subgraph AFTER["変更後"]
        U2["user scope settings.json<br/>5 フック (cat を 1 件追加)"]
        P2["各リポ settings.local.json<br/>permissions のみ"]
        P3["リポ固有の hook が要る場合<br/>そのリポだけが書く"]
    end
    BEFORE --> AFTER
```

user スコープへ足すコマンドはリポ相対で書けるため、そのまま全リポで効く。
`.hidari/private-ops` が無いリポでは `cat` が失敗し、標準エラーを捨てるので無音になる。
つまり **symlink の有無がそのまま opt-in ゲートとして働く**。

**実装後の訂正 4: user スコープ側にもフォールバックが要った。** user 側のコマンドは当初
`$(git rev-parse --show-toplevel)` だけを使っていたが、project 側は
`${CLAUDE_PROJECT_DIR:-$(git rev-parse --show-toplevel)}` というフォールバック付きだった。
**重複ではなく片方が上位互換**で、そのまま project 側を消すと hook の cwd がリポ外のときに
拾えなくなる。user 側へフォールバックを移してから消した。

config-guard の検査は `PRIVATE_CLAUDE.md` という部分文字列だけを見ており参照の形を pin
しないので、この変更で検査は落ちない。`settings_invariants.py` のコメントが
「パスの綴りごと pin すると参照の形を変えるたびにここが落ちるので、実体のファイル名だけを見る」
という設計意図を持っている。

リポ固有の hook は project 側に書けば user 側と両方走る (実測 4)。

### 一覧と検出層の関係

**probe は一覧を読まない。** 読ませようとすると鶏と卵になる。一覧は private-ops にあり、
到達経路は `.hidari/private-ops` なので、その symlink が無いリポでは一覧そのものが読めない。
読めない状態を沈黙として報告すると、対象外のリポで常に鳴ることになる。

probe が見るのは `.hidari/` の有無だけである。このディレクトリの存在は既に全リポで
opt-in マーカーとして機能しており、新しい状態を増やさずに「対象かどうか」を表せる。

| `.hidari/` | `.hidari/private-ops` | probe |
| --- | --- | --- |
| 無い | — | 無言 (対象外) |
| ある | 解決する | 無言 (健全) |
| ある | 無い / dangling | **鳴る** |

この形で最も起きやすい失敗を捕まえる。symlink の dangling と、外部ストレージが未マウントで
実体へ届かない状態である。どちらもエラーにならず、指示が静かに載らなくなる。

一覧を読むのは棚卸しコマンドの側とする。あちらは dotfiles から走るので `.hidari/private-ops`
経由で private-ops へ到達でき、鶏と卵が起きない。4 象限を見るのはこちらである。

| 一覧に載っている | `.hidari/` の状態 | 棚卸し |
| --- | --- | --- |
| はい | 揃っている | 無言 |
| はい | 欠けている | **報告** (取り付けの欠落) |
| いいえ | 無い | 無言 (意図的に対象外) |
| いいえ | 揃っている | **報告** (一覧が古い) |

「意図的に対象外」と「作り忘れ」を区別できるのは、一覧が意図を持つためである。
一覧が無ければこの 2 つは同じ形をとる。区別が要るのは棚卸しの時点であって、
セッション開始のたびに要るものではない。

**実装後の訂正 7: 4 象限のうち「いいえ × 揃っている → 報告 (一覧が古い)」は実装しなかった。**
`--check` は一覧の行を舐めるだけで、一覧に載っていないリポを見るための母集団を持たない。
この象限を実装するには「マシン上の全リポ」を得る新しい機構 (走査対象のルートを決めて
探索する) が要り、この spec 自身が置いた「新しく増える機構は 2 つに収まる」予算を超える。
走査ルートの既定値をどこに置くかで、訂正 5・6 が閉じたのと同じ露出面の論点も再び開く。

したがって実装されているのは 2 象限 (載っている × 揃っている / 欠けている) である。
落ちる側の失敗は「取り付け済みだが一覧に無いリポに沈黙する」形で、実害は棚卸しの
過小評価にとどまる (取り付けそのものは効いている)。実装は ISSUE-72 へ切り出す。

この分担により、マシン層へ private-ops の symlink を新設する必要が無くなる。
各リポの `.hidari/private-ops` という現行の運用がそのまま唯一の経路であり続ける。

### 一覧のフォーマット

置き場は private-ops。dotfiles は PUBLIC でリポ名を書けない。

載せるのは**対象リポだけ**とする。対象外の種別は書かない。
行が増えるのは対象を増やしたときだけになる。

Claude をまだ導入していないリポは、種別が対象であっても**導入時に足す**。載せた時点で
取り付けが要求されるので、先に載せると棚卸しが欠落を報告し続け、直せない赤が常時点灯する。
常時点灯する赤は、赤を無視する訓練になる。
載せ忘れたまま使い始めても実害は運用指示が載らないことだけで、指示が効かないので人が気づく。
取り付けはコマンド 1 回で済む。

種別の割り当てはユーザーの判断であり、機械的な指標からは導出できない。所属組織が自分で
ないことは「外部」を意味せず、Claude を一度も使っていないことは「対象外」を意味しない。
設計時の推定を実データへ突き合わせたところ、外部と推定した 5 件のうち 4 件が通常へ移り、
未使用ゆえ対象外と見た 5 件のうち 2 件が対象に入った。

件数の canonical は一覧そのものなので、この spec は数を持たない。推定と実際で取り付けが
要るリポの**件数は一致したが中身が 3 件違った**。件数の一致を根拠にすると取り違えたまま
通過するので、突き合わせは必ず名前の集合で行う。

| 規則 | 内容 | 理由 |
| --- | --- | --- |
| 1 行 1 リポ | `$HOME` からの相対パス | 絶対パスを書かないので、万一引用しても露出面を作らない |
| 絶対パスの行 | **却下**として報告 | 黙って受けると、出力へユーザー名が載る経路が復活する |
| 状態を書かない | 配線済みかどうかは書かない | 状態の canonical はファイルシステム。書けば必ず drift する |
| 行の文法 | 有効 / 無視 / **却下** の 3 分類 | 2 分類だと文法違反が「無視」に吸われて静かに消える |
| 未知の行 | 却下として報告 | 素通りさせない |

行の文法を 3 分類にするのは `claude_config_dir_line_kind` (bootstrap.sh) の作法に倣う。
あちらも追跡外の行指向ファイルを読み、名前をリポジトリへ書かないための外部化である。

一覧を読むコードは dotfiles 側にあるので、テストは環境変数でパスを差し替えて fixture で書く。
これも `CLAUDE_CONFIG_DIRS_FILE` の作法に倣う。private-ops 自体は git 管理にしない。

**実装後の訂正 6: 実装は一度この規則の逆へ倒れていた。** 絶対パスだけを有効とし、相対パスを
却下する形で実装されており、`--check` は `ok:` / `missing:` / `vanished:` のいずれの行でも
ユーザー名を含む絶対パスを stdout へ出していた。`--check` は手動の棚卸しなので、結果を貼って
相談するのが実際の使い方であり、貼るたびに露出面ができる。

この乖離は他の訂正と違って spec 側に記録が無いまま残っていた。**spec と実装が食い違ったとき、
どちらが正しいかは自動では決まらない。** ここでは spec の理由 (PUBLIC リポで露出面を作らない)
が実装の都合より重いと判断し、実装を spec へ寄せた。あわせて起動コマンド側の露出も訂正 5 で
閉じた。一覧を相対形へ寄せただけでは `--ops` の絶対パスが残るためである。

## 検証

手動の確認は 2 回に固定する。どちらも対照を先に取る。実施場所は実地の 1 件 (下記) とし、
このリポジトリでは行わない。受け側で確かめないと「配る側では動くが届いていない」を見逃す。

| # | 確認 | 対照 (これが無いと 0 件を健全と誤読する) |
| --- | --- | --- |
| V1 | 対象リポで新セッションを開き、指示が 1 回だけ context に入る | project 側を消す前に開き、**2 回入ることを先に見る** |
| V2 | probe が沈黙しない | symlink を一時的に外し、**鳴ることを先に見る**。鳴ってから戻す |

V1 は機構を外すと壊れることを、V2 は検査が実際に見ていることを示す。

設定の変更が実行中のセッションへ反映されるまでには数回のツール呼び出しぶんの遅れがある。
1 回確認して空でも「反映されない」と決めないこと。

### 実施結果

実地の 1 件で headless セッション (`claude -p`) を使って観測した。回数はモデルの自己申告に
なるが、symlink を外して 0 になることまで見れば、数えている対象が hook の出力だと確かめられる。
project 側の設定を退避しておき、3 状態を意図的に作って比較した。

| 状態 | 運用指示が context に載る回数 |
| --- | --- |
| project 側の hooks を戻す (対照) | 2 |
| project 側を消す | 1 |
| symlink を dangling にする | 0 |

V2 は 3 段階で確かめた。健全時は無出力、dangling で鳴る、そして hook 経由 (headless) でも
モデルの context に届く。直接実行で鳴るだけでは「hook として登録された経路で届く」証拠に
ならない。

**probe を直接実行するときは `CLAUDE_PROJECT_DIR` を明示すること。** 未設定だと
`_project_root()` が `None` を返し、probe は何も見ずに健全と答える。**壊れている状態でも黙る**
ので、直接実行の無出力を健全の根拠にできない。4 象限 (環境変数の有無 × symlink の健全性) で
対照を取ると、鳴るのは「設定あり かつ dangling」の 1 象限だけになる。

## 実地の 1 件

外部リポ 1 件を受け側の検証対象にする。このリポは配線と symlink が既に充足しており、
今回の変更では追跡下の変更が発生しない。受け側として検証に使える。

このリポには別途 pre-commit を導入する。gitleaks が CI にあるが走査モードが working tree
に限られ、コミット時に止まる層が無い。導入する hook の集合は ISSUE-64 が「汎用のものだけを
採る」として挙げた集合に従う。

**この導入は ISSUE-64 の作業であり、この spec の範囲には含まれない** (下記「関連」節のとおり
追跡下の検査層はあちらが canonical)。ここに書いてあるのは、受け側として選んだリポが
ISSUE-64 の対象と重なるという関係の記録である。実装計画の側がこれを自分のタスクとして
取り込んでいたが、範囲外として切り出した。
