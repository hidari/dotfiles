# chore: 保留にしたタスクリスト統合 3 本を適用する

## 背景

Issue #10 でタスクリストを導出名へ寄せる移行を行ったが、統合 3 本を保留にした。移行先となる 2 つのリストを別の Claude Code セッションが同時に書き換えていたためである。

統合は「移行先の採番上限を読む → その値をオフセットにファイルを書く → 上限を更新する」という read-modify-write なので、読んでから書くまでの間に移行先へタスクが増えると採番が壊れる。

移行スクリプトはリポジトリ管理外に置いてある使い捨てで、起票の時点で 1 本ずつ処理できる形に直してあった。`.highwatermark` が実在する最大 ID より小さいことがある問題への対処も入れてある。この対処が無いと移行先の既存タスクを上書きする。

## タスク

- [x] 移行先 2 本を担当するセッションが動いていないことを確認する
- [x] バックアップを取り直す (前回のものは移行前の状態なので古い)
- [x] dry-run で残りの統合対象を確認する
- [x] 1 本ずつ適用し、各回で移行先の既存ファイルがハッシュ単位で変わっていないことを確認する
- [x] 未完了タスクの subject 集合が保たれたことを確認する
- [x] Issue #10 の未チェック項目を閉じる

## 着手条件の絞り込み (2026-07-29 実測)

「他にセッションが動いていないこと」は条件として広すぎた。統合 3 本の移行先は 2 本のリストに集中しているので、停止確認はその 2 本を担当するセッションだけでよい。着手前に実行中プロセスの作業ディレクトリを実測し、移行先と重なるものが無いことを確認する。

```bash
ps -eo pid,command | grep '[c]laude'
lsof -a -p <pid> -d cwd -Fn | grep '^n'
```

## 採番の実測結果

移行先 2 本とも `.highwatermark` が実在する最大 ID より小さかった (乖離は 9 と 34)。Issue #10 で記録した「セッション中の採番が書き戻されない」現象は解消しておらず、移行スクリプトの補正はこれからも必要である。

使い捨てリストでの実測では、`.highwatermark` を据え置いたまま外部プロセスが高い ID のファイルを 1 つ置くと、同一セッションの次の採番はそのファイルより上に飛んだ。採番は `.highwatermark` だけでなくディレクトリ上のファイルも見ていると読める。ID 衝突のリスクは当初の想定より低い。

2026-07-30 に対話セッションでも同じ挙動を確認した。`.highwatermark` が据え置かれたまま新規タスクが 2 件作られ、次の採番はその 2 件より上に付いた。headless での確認に留まっていた確度はこれで上がった。あわせて、記録値が実 ID より小さくなる現象そのものも対話セッションで再現した。

## 一括削除の挙動 (2026-07-30 決着)

保留の理由だった「全タスク完了時の一括削除が、外部から追加された未完了タスクを巻き込むか」を対話セッションで実測し、巻き込まないことが分かった。

前回 headless (`-p`) では対照すら発火せず測定器が動いていなかった。対話セッションでは発火するので、この経路でなければ測れない。使い捨てにできる空のリストを実験台にして、外部からのファイル直置きを注入とした。

| 条件 | セッションが作ったタスク | 外部から直置きしたタスク | 結果 |
| --- | --- | --- | --- |
| 実験群 | 2 件とも completed | 1 件 pending | 削除は起きず全件残存 |
| 対照群 | 3 件とも completed | なし | 全件削除、`.highwatermark` を実 ID 最大へ更新 |

実験群は 2 回とも同じ結果だった。差は外部注入の未完了タスクの有無だけなので、削除判定はディスクを読み直して行われており、セッションが知らない未完了タスクも数に入る。

あわせて、削除のトリガーがタスクの完了操作に限らないことも分かった。読み取りだけの一覧取得でも判定が走り、条件を満たせばその場で削除された。読むだけのつもりの操作がファイルを消しうるので、外からタスクを置いた直後にリストを覗く手順は安全ではない。

`.highwatermark` は削除の瞬間に実 ID 最大へ書き戻される。移行先の 1 本が過去に一括削除されて空になり `.highwatermark` だけ残っていた状態は、これで説明がつく。

移行したタスクが未完了である限り、移行先のセッションが自分のタスクを完了させても巻き込まれない。

## 実施記録 (2026-07-30)

統合 3 本すべてを適用した。移行先は 2 本で、片方へ 1 本、もう片方へ 2 本を寄せた。

| 移送元 | 総数 | 未完了 | 移行先の適用前 | 採番オフセット |
| --- | --- | --- | --- | --- |
| 1 本目 | 4 | 2 | タスク 0 件 (過去に一括削除され `.highwatermark` だけ残存) | 記録値をそのまま使用 |
| 2 本目 | 4 | 4 | タスク 141 件 | 実 ID 最大を使用 (記録値との乖離 34) |
| 3 本目 | 12 | 1 | タスク 145 件 (2 本目の適用後) | 実 ID 最大を使用 |

乖離分の 34 件は連番で実在していたので、記録値をそのままオフセットにしていればこの 34 件を上書きして失っていた。Issue #10 で入れた実 ID との突き合わせがそのまま効いた形になる。1 本目の移行先で乖離が出ていないのは、そのリストが適用前に一括削除を経ており、そのとき記録値が実 ID 最大へ書き戻されていたためである。起票時点に記録した乖離 9 はこれで消えている。

適用には起票時点のスクリプトをそのまま使わず、別に書き直したものを使った。変えたのは 2 点。

- 移送元の削除をやめ、コピーだけにした。検証してから退避する順にできる
- 算出したオフセットで書き込む先が既に存在したら適用前に中止する

このガードは変異注入で確かめた。実 ID との突き合わせを殺すと中止し、中止の判定ごと殺すと既存ファイルが実際に上書きされた。隔離ディレクトリでの検証は 24 項目すべて通した。

適用後の検証は 3 つ。

- 移送先の既存ファイルがハッシュ単位で不変であること (適用のたびに確認)
- 移送されたタスクが、ID 以外の内容においてハッシュ単位で移送元と一致すること
- 未完了タスクの subject 集合が移行の前後で一致すること

3 つ目は稼働中の無関係なセッションが同時にタスクを 1 件完了させ 1 件追加したため、素の比較では差が出た。そのセッションのリストを除いた集合は 26 件で完全に一致した。この差分は逆に、並行セッションの書き込みを検出できていることの確認にもなった。

移送元 3 本は削除せず、タスクリストの外にあるバックアップ置き場へ退避した。スクラッチ用のディレクトリはまとめて消えることが前提なので、そちらには置かない。

## 適用後のレビューで出た検証の穴

適用してから多角レビューを回したところ、上に書いた検証の主張が実態より強いことが分かった。移行の結果そのものは健全で、subject の重複は無く ID も一意である。

### 中止のガードは平時は死んでいた

オフセットは必ず移行先の実 ID 最大以上に採られるので、新しい ID は常に既存より大きくなる。存在チェックが真になる経路が無く、健全なコードでは到達しない。守っているのは「オフセットの算出そのものが壊れたとき」だけである。

変異注入が赤になったのは、その変異がまさに算出を壊すものだったからで、本番の入力経路で踏まれる分岐であることの証明にはなっていない。CLAUDE.md の変異注入のルール (赤は pin の有効性を保証せず、守る分岐が本番の入力経路で到達可能かまで確認する) をそのまま踏んだ。

根本は変異注入の解釈ではなく順序にある。ガードを先に書き、後から変異でテストを作った。先に「上書きが起きる入力」を構成してから守っていれば、その入力が健全なコードでは構成できないことがその場で分かったはずである。テストを先に書く原則を、機能ではなく防御的なガードに適用しなかったのが誤りだった。

到達不能と分かったガードをどうするかは、このスクリプトが使い捨てなので今回は判断を保留した。残すなら不変条件の assert として意図を明示し、消すならオフセットが常に実 ID 最大以上であることをコードのどこかで表現し直す必要がある。

### 冪等性が無い

同じ組み合わせを二度適用すると、二度目もオフセットを取り直して既存を避けるため、同じタスクが別の ID で二重に入り、成功として終わる。移行先へファイルを移すループも 1 件ずつなので、途中で止まれば部分適用の状態が残る。「一時ディレクトリへ全件書いてから移す」が守るのは変換の失敗までで、移送そのものは原子的でない。

今回は 3 本を 1 回ずつ適用し、適用後に subject の重複が無いことと ID が一意であることを確認した。移送元も退避済みなので、誤って再実行しても移送元が無い時点で止まる。

### 今回は踏まなかったもの

移送元と移行先に同じリストを指定しても止まらない。上の到達不能と同じ構造で、最も壊れた指定に対して唯一の判定が最も無力になる。

移行先の記録値が空や数値以外のとき 0 として扱う実装にしたが、移行先が 0 件のリストではこれが実害になる。実 ID 最大も 0 なのでオフセットが 0 に落ち、採番が一括削除前の値まで巻き戻る。過去に削除された完了タスクと同じ ID が再利用され、他のリストからの参照が別のタスクへ解決される。今回の 3 本のうち 1 本がまさに 0 件のリストへの移送だった。記録値が正常に読めたので踏まずに済んだだけである。

隔離ディレクトリの検証はこの組み合わせを見ていなかった。記録値が壊れているケースと移行先が 0 件のケースを別々に置いて、両方が通ることしか確かめていない。壊れやすい配置は単独で並べるだけでなく掛け合わせる必要がある。

このほか、移送元の記録値が実 ID より大きいと dry-run の表示範囲が実際に書かれる範囲より広く出る。今回の 3 本では起きない条件だった。
