# refactor: CLAUDE.md を rules と skill へ分割し常時ロード量を減らす

## 背景

`home/.claude/CLAUDE.md` は 1 枚しかないため、どの作業をしていても全文が常時ロードされる。
2026-08-17 時点で 314 行 / 45KB。セクション別の行数は次のとおり。

| セクション | 行数 | 直下項目 |
|---|---|---|
| あらゆる ”検証” 時に守ること | 121 | 26 |
| MUST GLOBAL 必ず守ること | 45 | 19 |
| テストコード | 48 | 8 |
| コミットメッセージ | 32 | - |
| セキュリティ | 16 | - |
| SubAgents、Plugins, Skills の活用 | 16 | 2 |
| 作業プロトコル | 12 | - |
| プロダクションコード | 11 | - |

言語別の内容はほぼ無い。Rust / TypeScript / Swift / Kotlin の出現数はいずれも 0 で、実際の質量は git (17) / gh (9) / zsh・bash (5) と、言語非依存の検証・テスト方法論に寄っている。

## 実測で確定した機構 (2026-08-16、Claude Code 2.1.233)

バイナリの zod 定義と `HOOK_EVENT_REGISTRY` から直接読んだ。推測ではない。

`InstructionsLoaded` フックが実在する。ペイロードの schema は次のフィールドを持つ(値の canonical はバイナリ側であり、ここでは再掲せずフィールド名のみ記す)。

- `file_path` / `memory_type` / `load_reason` は必須
- `globs` / `trigger_file_path` / `parent_file_path` は任意
- `matcher` は `load_reason` に対して効く
- observability-only と明記されており blocking は非対応

`~/.claude/rules/*.md` は User スコープで実在し、`paths` frontmatter によるスコープが効く。
プローブを置いて次のレコードを実測した。

    file_path: ~/.claude/rules/probe-user-scoped.md
    memory_type: User
    load_reason: path_glob_match
    globs: ["**/*.rulescope"]
    trigger_file_path: <repo>/.cache/probe.rulescope

副次的に確定したこと。

- フックの登録は settings.json を書いた瞬間に効く。セッション再起動は不要(PostToolUse へ同じロガーを仮付けした対照で確認)
- gitignore 対象の `.cache/` 配下のファイルでもトリガーになる

## 踏んだ罠 (運用上の注意)

`paths` 付き rules の glob 登録はセッション開始時にキャッシュされる。セッション途中で作った `~/.claude/rules/` は自分のセッションからは見えず、同じファイルを読んでも発火しなかった。
subagent は毎回新鮮に走査するため、subagent 経由で読ませて初めて発火した。

この観測は `paths` 付きのプローブで取ったもので、射程は glob 登録に限る。paths 無しの常時層は別の挙動をする (「compact の挙動を実測した」節)。compact を挟まないセッション途中で常時層が拾われるかは未測定。

rules を 1 枚足しても再起動するまで効かない。しかも「効かない」が無言なので、書いて動かして反応が無いと `paths` の書き方の誤りと誤診する形をしている。
動作確認は subagent を 1 本投げるのが最短。

## 測定結果 (2026-08-17)

セッションを再起動し `~/.cache/claude/instructions-loaded.jsonl` を読んだ。対照は成立している。

| file_path | memory_type | load_reason |
|---|---|---|
| `~/.claude/CLAUDE.md` | User | session_start |
| リポジトリ直下の `CLAUDE.md` | Project | session_start |
| `~/.claude/rules/probe-user-always.md` (`paths` 無し) | User | session_start |

`paths` を持つ `probe-user-scoped.md` はこの 3 件に並んでいない。同一ディレクトリの同一形式で片方だけが出るため、分岐点が `paths` frontmatter の有無であることを単独レコードより強く言える。

フックの申告とは独立に、再起動後のコンテキストへ `probe-user-always.md` の本文が実際に注入されていること、`probe-user-scoped.md` の本文は入っていないことも確認した。
「フックは鳴ったが中身は入っていない」形の乖離は無い。

確定: `paths` を持たない `~/.claude/rules/*.md` は session_start で常時ロードされる。

### このログで測れないこと

auto-memory の `MEMORY.md` と SessionStart フックの `additionalContext` は、コンテキストへ実際に入っているのにレコードが 1 件も出ない。
このログは注入経路の一部しか見ていない。

したがってレコードの非存在を「ロードされていない」と読んではならない。
今回 `probe-user-scoped.md` を陰性と判定できたのは、同じ経路 (rules ディレクトリの走査) の対照が出ているからであって、経路が違うものには同じ推論を使えない。

## 二重ロードの発見と解消 (2026-08-20)

分割に着手する前に、同じ 54KB を 2 回払っている経路が見つかった。分割で減らす量とは別勘定になる。

`Read` ツールで `home/.claude/` 配下のファイルを読むと、祖先の `home/.claude/CLAUDE.md` が `nested_traversal` でコンテキストへ注入される。
このファイルは `~/.claude/CLAUDE.md` の symlink 実体なので、User memory として既にロード済みの内容と完全に同一である。

| 読み方 | 発火 |
|---|---|
| `Bash` の `head` で同ディレクトリのファイルを読む | しない |
| `Read` ツールで読む | する |

同じディレクトリの同種のファイルで片方だけが出るため、分岐点がツールの種別であることを単独レコードより強く言える。
同一セッション内では 2 回目以降は発火しないが、subagent は起動ごとに新鮮なコンテキストを持つため、起動した本数だけ二重化する。

`claudeMdExcludes` (settings.json のキー) で止まる。除外の有無で対照を取った。

| 設定 | subagent のコンテキスト | フックのログ |
|---|---|---|
| 除外なし | 注入される | `nested_traversal` を記録 |
| 除外あり (プロジェクトの local) | 注入されない | 記録なし |
| 除外あり (ユーザースコープ) | 注入されない | 記録なし |

セッション再起動なしで効いた。
ユーザースコープへ置いたのは、config-guard が `home/.claude/settings.json` を index 経由で検査しており、取り付けを不変条件として pin できるため。

### 残る穴

- config-guard が見るのは `home/.claude/settings.json` だけで、プロジェクトスコープの settings は覆っていない
- `claudeMdExcludes` というキー名が Claude Code 側で変わったら静かに壊れる。設定の存在は pin できるが、それが効いていることは pin できない (未知のキーは無警告で無視される)
- skill の重複登録 (`home:` プレフィックスで 15 個) は別経路で、この除外では止まらない。載るのは description だけなので影響は小さい

## 分割案の下書き

`paths` で絞れるかどうかで性質が分かれる。
絞れない側を rules に置いても常時ロード量は減らないため、置き場所の判断はこの軸で行う。

スコープできる (触ったときだけロード):

| 移す先 | 内容 | paths |
|---|---|---|
| testing-practices | テストコード 48 行 (変異注入・dead pin・検査機構の 3 種変異) | テストファイル群 |
| frontend-practices | プロダクションコード 11 行 (semantic HTML・a11y・aspect-ratio) | tsx / jsx / html / css |

スコープできない (常時ロードのまま):

| 移す先 | 内容 | 理由 |
|---|---|---|
| verification-practices | 検証セクションの残り | 全作業に効く方法論でファイルに紐づかない |
| shell-practices | 検証セクションの Bash ツール項・shell-out 項・`node --test` 項 | 規範が効くのは Bash ツールの使用時と任意の言語でコードを書くときで、`.sh` の編集時ではない |
| git-github-practices | push 後の確認、長時間コマンドの結論、ruleset 判定、コミット prefix | git 操作はファイル編集と無関係に起きる |
| subagent-practices | SubAgents の節 + 検証セクションの subagent 運用項 | 同上 |

測定の結果、常時ロード組も rules へ置けることが確定した。
ただし置いても session_start で払うトークンは変わらない。
減るのは CLAUDE.md 本体の行数と族ごとの独立性であって、セッション開始時のコストではない。

したがって本 Issue の目的である常時ロード量の削減を達成する経路は 2 つに限られる。

1. `paths` で絞れる族を条件付きロードへ移す
2. 常時ロード組そのものを skill へ逃がすか削る

置き場所を rules へ移すだけでは達成されない。
1で移せる量が上の3つ分しかないため、削減幅の主たる決定要因は 2 の側になる。

skill 側への切り分けの軸を 1 本立てる。rules に置くのは「こう振る舞え」という規範、skill に置くのは「こういう事実がある」という知識。
現行ファイルは 1 項目の中でこの 2 つが混ざっており、行数が膨らんでいる主因になっている。Node の `--test-name-pattern` の挙動、zsh の `pipestatus`、BSD sed の `\b`、tirith の除外集合といった一次実測は `verification-latest-techniques` skill へ寄せられる。

言語別 (rust / typescript / swift / kotlin) は現状ゼロ行のため、この Issue では作らない。
空ファイルを先に置くと、存在するのに参照価値が無い状態が続いて信用を落とす。

## 工程 1 の打ち切りと工程 2 の設計 (2026-08-21)

### 工程 1 の残余は実測で薄い

畳み込みは「読む単位」を減らす操作であって「量」を減らす操作ではない。
残り 12 カテゴリへ当てても効かないことを、着手前に次の実測で確認した。

| 根拠 | 数値 |
|---|---|
| 質量上位 3 のうち 2 つは既に畳み済み | テスト緑 top=2 項目 / 委譲 top=3 項目 |
| 残り 10 カテゴリの規模 | 各 3KB 未満、項目も 1KB 未満 |
| 語彙と前提 (14 項目 6.6KB) | 異種混在で族が立たない (どのカテゴリにも属さない前提の置き場という設計上の性質) |
| 変更の記録 (16 項目) | うち 13 個はコミット prefix の 1 行列挙で畳めない |

### 切断線を「トリガ文と判定文だけ残す」へ変えた

前セッションの切断線 (遵守時に要る / 疑うときに要る) で事例だけを移す方式を、
事例率が最大 (74%) の委譲カテゴリで試したところ 17.0% 減にとどまった。
全カテゴリへ外挿しても約 10% で、Issue の目的に対して主軸にならない。

事例と機序が同じ文に融合していて単独では切り出せないことが原因。
そこで規範の骨格 (トリガ文 + 判定文) だけを常時層に残し、
手当ての詳細・機序の説明・事例をすべて references へ移す方式へ切り替えた。

観測カテゴリで実測して 64.9% 減。

### 失われるものと引き受けたリスク

方式の性質上、常時層から手当てが消える。遵守の瞬間に効いていたと思われるもの。

- `git push` を繋がずに実行し `git ls-remote` で確認する (push は頻出操作)
- `${PIPESTATUS[0]}` が zsh で空になる (回避策を思いついた瞬間に要る)
- venv の絶対パスが変わったら再インストールする (規範だが references 行きにした)

これらは references を読まないセッションでは規範から自力で導出する必要がある。
成立するのは「トリガ文が発火したら references を読みに行く」場合に限る。

効果指標も代理変数のままである (「常時層に載っていても守られなかった 1 例」節)。

### 追加の実測

- 常時層のコストは session_start だけでなく subagent の dispatch ごとに払う。
  subagent がツールを一切使わずに CLAUDE.md の本文と由来パスを引用できることで確認した。
  この経路は `instructions-loaded.jsonl` に記録が出ない (ログ行数が 64 のまま変わらなかった)。
  「ロードされているのにログが 0 件」の実例であり、削減効果の検証にログを使うと静かに間違える
- CLAUDE.md は 2026-08-12 の 36,599B から 08-21 の 52,766B へ 9 日で +44%。
  一回きりの削減は追記で食われるため、削減量ではなく上限を検査で固定する必要がある
- `bootstrap.bats` の reverse-drift テストは `git ls-files` を使うので tracked ファイルしか見ない。
  新規ファイルを untracked のまま変異注入すると dead pin に見える。
  git add してから変異させると意図したテストだけが赤くなり、未カバーのパスを名指しする

## compact の挙動を実測した (2026-08-21)

分割方針は「compact で何が失われるか」を前提に置いていたが、そこは未検証だった。
同一セッション内で `/compact` を挟み、フックのログと `/context` の 2 系統で観測した。

### 対照の設計

一度発火させて「増えなかった」を見るだけでは compact の効果を分離できない。
compact の前に 3 つの対照を取り、基準線を 73 行に固定した。

| 対照 | 操作 | 結果 |
|---|---|---|
| A | 同じトリガファイルを再 Read | 増えない |
| B | 同じ glob に一致する別ファイルを Read | 増えない (dedup はルール単位) |
| C | session_start より後に作った rules のトリガを Read | 増えない (走査は session_start のキャッシュ) |

### 結果

`load_reason` に `compact` という値が実在する。compact 時に 3 件が記録された。

| file_path | memory_type | load_reason |
|---|---|---|
| `<repo>/CLAUDE.md` | Project | compact |
| `~/.claude/CLAUDE.md` | User | compact |
| `~/.claude/rules/probe-noscope.md` (paths 無し) | User | compact |

`paths` 付きの 2 プローブはどちらも 1 件も出ていない。`probe-compact-rescope.md` は session_start より前 (03:38 JST)、`probe-compact-fresh.md` は後 (03:44 JST) に作ってあり、session_start は 03:40 JST。両方ともファイルが実在して frontmatter も同形であることを確認したうえでの陰性。

`/context` も同じ向きを示した。

| カテゴリ | compact 前 | compact 後 |
|---|---|---|
| 合計 | 92.3k | 70k |
| Memory files | 17.3k (3 ファイル) | 17.5k (4 ファイル) |
| Messages | 42.6k | 19.7k |

Memory files が増えたのは probe-noscope.md (209 トークン) が加わったため。CLAUDE.md 本体は 1 トークンも減っていない。

### 確定したこと

- 常時ロード層 (CLAUDE.md と `paths` 無し rules) は compact で失われない。
  Messages とは別カテゴリに置かれ、compact のたびに再注入される
- 常時層は compact 時にディレクトリを走査し直す。
  session_start より後に作った probe-noscope.md が compact で拾われた
- `paths` 付き rules は Messages 側に入る。compact で再注入されず、圧縮対象になる
- ただし compact は `paths` 付き rules の dedup をリセットする。
  compact 後に一致ファイルを Read すると同じルールが再発火した
  (対照 A で「同一セッション内の再 Read では増えない」を確定させてあるので、compact の効果と言える)
- `paths` 付き rules の glob 登録は compact でも更新されない。
  session_start より後に作った probe-compact-fresh.md は compact 後も発火しなかった。
  常時層は再走査されるのに glob 登録は据え置かれるという非対称がある

事前に立てた予測との突き合わせ。

| 予測 | 結果 |
|---|---|
| 予測 1: CLAUDE.md は compact で失われない | 当たり |
| 予測 2: `paths` 付き rules は失われ dedup により再注入されない | 前半は当たり、後半は外れ |

### 分割方針への影響

`~/.claude/rules/00-core.md` へ常時層を移す案は不要になった。CLAUDE.md 本体が既に compact 耐性を持つ。

`paths` 付き rules には穴がある。compact のあと規範が戻るのは、一致ファイルへ特定の操作をしたときだけ。
どの操作が該当するかで穴の広さが決まる。実測は「発火経路を実測した」節。

`~/.claude/rules/` は symlink ではなく実ディレクトリで、`home/.claude/rules/` はリポジトリに存在しない。
bootstrap の SYMLINK_PAIRS にも無い。切り出す前にここを配線しないと、rules は他マシンへ配布されず
`instruction_budget` の `RULES_GLOB` からも外れる (今は glob が 0 件に一致するので予算検査は素通りしている)。

## 発火経路を実測した (2026-08-21)

compact 節が残した 1 点。`paths` 付き rules が Read で発火することは分かっていたが、
Edit / Write でも発火するかは測っていなかった。

### 前提

compact の実験で使った `probe-compact-rescope.md` (`paths: ["**/*.rulescope"]`) を撤去せずに
前セッションを終え、触らないまま新しいセッションを開始した。glob 登録は session_start でしか
更新されないので、プローブはセッションを跨いで置いておかないと登録されない。
判定後に撤去したので `~/.claude/rules/` は空に戻っている。

### 手順

dedup はルール単位かつセッション単位なので、一致ファイルへの最初の 1 アクションだけが情報を持つ。
順序を固定し、陰性のときだけ次へ進めた。基準線は 86 行。

| # | ツール | 操作 | ログ増分 | 注入 |
|---|---|---|---|---|
| 1 | Write | 新規ファイル `.cache/phase0w.rulescope` を作成 | 0 | なし |
| 2 | Edit | 同じファイルを書き換え | 0 | なし |
| 3 | Read | 同じファイルを読む (positive control) | +1 | あり |

3 で記録された行は `load_reason` が `path_glob_match` で、`trigger_file_path` は 1 で作ったファイル。

### 確定したこと

- 発火するのは Read のみ。Write と Edit では発火しない
- この陰性は dedup 由来ではない。dedup はルール単位なので、1 か 2 で発火していれば
  3 でも注入されないはず。3 が注入された以上 1 と 2 は発火していない。
  ログ増分 0 と合わせて 2 経路で確認している
- トリガファイル側の glob 判定は動的。session_start の時点で存在しなかったファイルが
  発火させている。session_start のキャッシュに固定されるのは rules 側の登録だけで、
  一致するファイルの一覧ではない

### 切り出しへの影響

Edit ツールは原則として同一会話内の事前 Read を要求するので、実運用の Edit は
直前の Read が発火させている。今回それを回避できたのは Write 直後で file state が
current だったため。穴が開くのはこの経路、つまり対象を読まずに書く場面に限られる。

分割案の 3 つでは testing-practices がこれを踏む。TDD で最初にテストを書く場面は
テストファイルの新規作成そのもので、既存を読まずに Write することになる。

## 切り出しを 1 つ実施した (2026-08-21)

配線と最初の 1 つを同じ変更で入れた。git は空ディレクトリを追跡しないので、
`home/.claude/rules/` を作るには最初の rules ファイルが要る。

対象は frontend-practices にした。当初の予定は shell-practices だったが、
下記のとおりスコープできないと分かったので差し替えた。

### shell-practices はスコープできない

分割案は paths を `sh / zsh / bats` としていたが、該当する 3 項目の適用場面は
どれもシェルスクリプトファイルの編集ではない。

| 項目 | 効く場面 |
|---|---|
| Bash ツールでコマンドを組むとき | Bash ツールの使用時。Bash は rules を発火させない |
| shell-out / 外部 CLI オーケストレーション | 任意の言語で subprocess を起動するコードを書くとき |
| `node --test` にはテストファイルか glob を渡す | Bash ツールの使用時 |

判定したセッション自身が反例になっている。`.sh` を Read ツールで 1 度も開かずに
作業したが、Bash ツールでコマンドを組む規範は繰り返し必要だった。
`sh` にスコープしていれば全て沈黙している。

testing-practices にも同じ穴が部分的にある。「検査機構 (ゲート・ガード・lint ルール・
CI チェック) を足したときの変異は 3 種いる」はテストファイル以外を触る場面の規範。

### 発火の確認と、確認できなかったこと

`paths: ["**/*.tsx", "**/*.jsx", "**/*.html", "**/*.css"]` で切り出し、
subagent に `.tsx` を Read させて注入を確認した。見出しと 6 項目がそのまま入っている。

同時に確認できなかったことが 1 つある。その subagent は起動時の User memory にも
同じ 6 項目を持っていた。CLAUDE.md からの削除は済んでいて live ファイルにも残って
いないので、実行中のセッションが session_start でキャッシュした削除前の版を保持し、
subagent がそれを継承したことになる。常時層が compact で再走査される挙動と同じで、
編集の反映も新セッションか compact を待つ。

つまり今回観測したのは「scoped rules が発火する」ことだけで、「常時層から消えた」
ことは観測できていない。後者の確認には新セッションが要る。

### 副次的に直ったもの

bootstrap を走らせたところ、追加の設定ディレクトリ側の `references` が張られて

## 常時層に載っていても守られなかった 1 例 (2026-08-21)

分割の前提は「量を減らせば読まれる」だった。compact の実測と同じセッションで、その前提に対する反例が 1 件出たので記録する。

### 何が起きたか

ブランチを push したあと、次の形でコマンドを組んだ。

    git push -u origin <branch> 2>&1 | tail -5; echo "exit=${PIPESTATUS[0]}"

出力は `exit=` で、判定が空のまま返った。push 自体は成功していたので実害は無く、`git rev-parse` で local と remote の HEAD を突き合わせ直して確認した。

### 2 層の両側で同時に失敗している

この 1 件は「references へ移したから届かなかった」だけでは説明できない。

| 層 | 内容 | 結果 |
|---|---|---|
| 常時層 `CLAUDE.md` | exit code で判定するコマンドはパイプにも後続コマンドにも繋がない | コンテキストに載っていたが破った |
| `references/observation.md` | 回避策の `${PIPESTATUS[0]}` は zsh では常に空になる。`pipestatus` が 1 始まり | 読まずに回避策を自作し、まさにその誤りを踏んだ |

判定文を破ったうえで、手当てを再発明し損ねた。工程 2 の切断線 (判定文は常時層、手当ては references) は設計どおりに機能しており、失敗したのは判定文の遵守と references の参照のどちらもである。

### 誤りが二重で、しかも同じ形で返る

zsh 5.9 で実測した。

| 式 | 結果 |
|---|---|
| `${PIPESTATUS[0]}` | 空 |
| `${pipestatus[0]}` | 空 |
| `${pipestatus[1]}` | 正しい終了ステータス |

`PIPESTATUS` は zsh に存在せず、加えて zsh の配列は 1 始まりなので `[0]` も空を返す。独立した 2 つの誤りがどちらも空文字列という同じ形で返るため、片方を直しても症状が変わらない。エラーにもならないので、出力を読まなければ判定が行われたように見える。

### この 1 件から言えること / 言えないこと

言えるのは 1 つだけ。規範が常時ロード層に載っていることは遵守の保証にならない。

言えないのは以下。n=1 で対照が無い。

- 分割によって遵守率が上がるか下がるか
- 常時層が 33KB だから守れなかったのか、量とは無関係なのか
- references へ移した項目の遵守率が実際に落ちているか

より一般には、本 Issue が測っているのはバイト数だけで、遵守そのものは測っていない。削減量は目的ではなく代理変数であり、代理変数の改善が目的の改善を意味することはこの 1 件では支持されていない。

## dedup の粒度と subagent のコストを実測した (2026-08-21)

frontend の切り出し後、別リポジトリのフロントエンド作業をしていたセッションが
同一 `session_id` で `frontend-practices.md` を 5 回発火させていた。うち同じトリガファイルが
3 回ある。「dedup はルール単位かつセッション単位」では説明がつかないので測り直した。

### dedup のキーは (agent 文脈, rule)

一致する `.tsx` に 4 回触れて、注入は 1 回だけだった。

| # | 操作 | ログ増分 | 注入 |
|---|---|---|---|
| 1 | Read `.cache/probe-dedup.tsx` | +1 | あり |
| 2 | Read 同一ファイル | 0 | なし |
| 3 | Bash で内容を書き換え | 0 | なし |
| 4 | Read 同一ファイル (内容変更後) | 0 | なし |
| 5 | Read 別ファイル `.cache/probe-dedup-other.tsx` | 0 | なし |

トリガファイル名でも内容ハッシュでもキーにしていない。一度注入されたら、その文脈では
何を読んでも復活しない。

**3 は「Bash 経由の書き込みは発火しない」の証拠にならない。** 1 で注入済みなので dedup が
効いており、増分 0 は何も区別しない。この節自身が下で「増分 0 から言えるのは注入されなかった
までで、一致しなかったではない」と書いているとおりで、レビューで気づいた。

Bash 経由の書き込みが発火しないことは別の観測が示している。`testing-practices.md` の
発火回数が 0 の状態 (dedup が新鮮な状態) で、一致する `.cache/probe-a.test.ts` を Bash の
リダイレクトで新規作成したが増分は 0 で、そのあとの Read で初めて +1 になった。

### subagent は親の dedup を継承しない

main loop が注入済みの状態で subagent 1 本に同じファイルを読ませたところ、ログが +1 された。
記録された `session_id` は親のもの、`load_reason` は `path_glob_match`、
`trigger_file_path` は同じファイル。

つまりログの発火回数はセッションの数ではなく agent 文脈の数を数えている。5 連発の正体はこれで、
ログだけでは main loop と subagent を区別できない。

親子だけでなく兄弟どうしも独立している。glob の形を測るために起動した subagent 2 本は
同じ rule を別々に発火させた (08:41:03 と 08:41:07)。共有していれば後発は dedup で
抑制されるはずなので、独立を裏づける 3 つ目の文脈になる。

常時層のコストが subagent の dispatch ごとに掛かることは既知だったが、`paths` 付き rules も
同じく agent 文脈ごとに払う。切り出しで減るのは「全 agent 文脈 × バイト数」から
「一致ファイルを読んだ agent 文脈 × バイト数」への差分であって、subagent を多用するほど効く。

### ログの読み方を 2 つ訂正する

- ログはマシン全体で共有される。測定中に別リポジトリのセッションが 3 行書き込んだ。
  総行数の増分を基準線にすると他セッションの活動で汚染される。前の 2 つの節はこの形で
  測っており、幸い結論は絞り込んだ集計とも一致したが、方法としては壊れている。
  `file_path` と `trigger_file_path` で絞ってから数えること
- ログは注入ログであって一致ログではない。dedup で抑制された一致は記録されない。
  増分 0 から言えるのは「注入されなかった」までで、「一致しなかった」ではない

### session 途中に作った rules も登録される

「発火経路を実測した」節の前提は「glob 登録は session_start でしか更新されないので、
プローブはセッションを跨いで置いておかないと登録されない」だった。今回それを直接測ったところ、
成り立たなかった。

`testing-practices.md` を session_start の 18 分後に作り、同じセッションの main loop で
一致ファイルを読んだところ発火した。subagent 2 本でも発火した。

前の実験がプローブをセッション跨ぎで置く必要があったのは、`~/.claude/rules/` 自体が
その時点で空だったためと考えられるが、ディレクトリの有無が効くのかどうかは切り分けていない。
言えるのは「ディレクトリが既にあれば、途中で足したファイルは同じセッションで発火する」まで。

## testing-practices を切り出した (2026-08-21)

テスト系は 2 カテゴリある。判定基準は shell-practices と同じで、規範が効く瞬間に
glob 一致ファイルの Read が起きるかを見る。

### 2 カテゴリのうち移せるのは 1 つ

行番号ではなく項目の書き出しで指す。この Issue の分割そのものが行番号をずらすため、
位置参照は書いた側から壊れる (Issue #24 の前提条件)。

| 項目 | 効く瞬間 | Read が起きるか |
|---|---|---|
| 先にテストを書く (TDD 的アプローチ) | プロダクトコードを書く直前 | 起きない |
| pnpm / npx、Playwright Test Agents | Bash ツール使用時 | 起きない |
| モック不使用、弱い assertion、gaming の確認 | 既存テストを読むとき | 起きる |
| 変異注入、dead pin、多段検査の pin | pin テストを書いたあと | 既存テストを読んでいれば起きる |
| 検査機構の 3 種変異、範囲を数える、緩める変更 | ゲート / lint / CI を足すとき | 起きうる |

「テストを書き始める前に順序と方式を決める」は丸ごと残した。TDD 順序が回避したい失敗は
「テストを書かないこと」で、その失敗の側ではテストファイルの Read が起きない。
**トリガが失敗側に無い規範はスコープできない。** shell-practices の判定を一般化するとこうなる。
pnpm / npx の項は Bash ツール使用時の規範なので、shell-practices とまったく同じ理由で残る。

「検査機構の 3 種変異」以下は移す側へ入れた。効く瞬間に触るのは workflow yml や lint config
だが、検査機構を足すときは必ずテストも書く運用なので兄弟テストの Read が起きる、という賭けを
引き受けている。届かない回が観測されたら CLAUDE.md 側へ戻す。

**表の 3 行目と 4 行目は「読むとき」に限る。** 発火経路は Read だけなので、既存テストを
1 つも読まずに新しいテストファイルを Write する経路では届かない。実運用では兄弟テストを
読むことが多いが、保証はない。TDD カテゴリを常時層に残した判断はこの穴も埋めている。

### paths は測ってから決めた

管理下の git リポジトリ 26 個を走査し、テストファイルを持っていた 20 個から
追跡ファイル 1,216 件を集めて命名規約を数えた。

| パターン | 一致 | 限界カバレッジ |
|---|---|---|
| `**/*.test.*` | 650 | +650 |
| `**/tests/**` | 372 | +370 |
| `**/*.spec.*` | 148 | +89 |
| `**/*_test.*` | 67 | +9 |
| `**/test/**` | 37 | +13 |
| `**/__tests__/**` | 37 | +3 |
| `**/test_*.*` | 約 100 | 残りをほぼ吸収 |
| `**/*.bats` | 9 | +0 (すべて `tests/` 配下) |

`**/*.bats` は限界カバレッジ 0 だったので入れていない。dotfiles の bats は全部
`scripts/tests/` にあり `**/tests/**` が拾う。

**`spec/` `specs/` は入れなかった。テストディレクトリではなかった。** 最初の集計で使った
正規表現 `(^|/)specs?/` が 2 つを融合させて 58 件という数字を作っていたが、実体を見ると
55 件が `docs/superpowers/specs/` の設計ドキュメント、3 件が名刺デザインの仕様だった。
入れていれば設計ドキュメントを読むたびにテスト規範が注入され、しかも「発火している」ので
緑に見えて気づけない。自分で作った検索キーが偽陽性を生んだ形で、実体を見るまで分からなかった。

一方 `*.spec.ts` / `*.spec.tsx` (148 件) は Playwright の E2E で本物なので残した。
同じ `spec` でもディレクトリ名と拡張子で意味が逆になる。

確定したパターンを dotfiles の追跡ファイル 280 件へ当てると 60 件が一致し、
すべて `tests/` 配下だった。追跡下に限れば偽陽性は 0 件。

**ただしこの測定は射程が足りない。** レビューで指摘されて測り直した。発火は追跡状態を
問わないので、`git ls-files` を母集団にした時点で `.venv` や `node_modules` を見ていない。
同じ Issue の別の節が「gitignore 対象の `.cache/` 配下でもトリガーになる」と実測済みで、
自分で確かめた事実と測定方法が食い違っていた。

追跡外も含めて数え直すとこうなる。

| パターン | own | vendored |
|---|---|---|
| `**/test_*.*` | 88 | 187 |
| `**/tests/**` | 31 | 0 |
| `**/*.test.*` | 5 | 2 |
| `**/test/**` | 0 | 245 |
| 残り 4 パターン | 0 | 0 |

`**/test/**` は dotfiles では vendored しか拾わない (`mypy/test/helpers.py` など、
`test` という名のディレクトリに居るだけの補助モジュール)。

それでも落とさない。落とすと `test/rls/assert.sql` や `test/hosted-db/run.sh` のような
本物 13 件が漏れる。RLS テストを書いている最中に規範が沈黙するのは、この Issue が避けたい

偽陰性は沈黙する。`instruction_budget` の docstring が既に採っている
「誤るなら厳しい側へ倒す」と同じ判断を当てた。

`.Tests.ps1` はレビューの指摘を受けてパターンを 1 つ足し、8 個にした。Pester は
`<Script>.Tests.ps1` を対象スクリプトの隣へ置く規約で、`tests/` ディレクトリを要求しない。
リポジトリの唯一の Pester ファイルが覆われていたのは `tests/` 配下に居る偶然によるもので、
規約どおりコロケーションした瞬間に沈黙するところだった。`**/*.test.*` は `Tests` を
拾えない (単複とケースが違う)。

### glob の形をすべて発火させた

frontend が実証したのは `**/*.tsx` という形だけで、今回は未実証の形を使っている。
dedup は agent 文脈ごとに 1 回なので、1 文脈で 1 形しか測れない。文脈を分けて形ごとに測った。
件数は下の表が持つ (本文に literal で書くとパターンを足すたびに複数箇所の同時更新が要る)。

| 形 | パターン | プローブ | 文脈 | 結果 |
|---|---|---|---|---|
| ファイル名の途中にワイルドカード | `**/*.test.*` | `.cache/probe-a.test.ts` | main loop | 発火 |
| ディレクトリ | `**/tests/**` | `.cache/tests/probe-b.md` | subagent | 発火 |
| ファイル名の接頭辞 | `**/test_*.*` | `.cache/probe/test_c.py` | subagent | 発火 |
| 末尾まで literal | `**/*.Tests.ps1` | `.cache/psprobe/Probe.Tests.ps1` | subagent | 発火 |

`**/*.spec.*` と `**/*_test.*` は 1 番目と同型、`**/test/**` と `**/__tests__/**` は
2 番目と同型なので、この 4 つで全形を覆う。4 番目はレビューで足したパターンで、
frontmatter を 8 個へ編集したあとも壊れていないことの確認を兼ねている。
各プローブは狙ったパターン以外のどれにも一致しないよう単離した。

subagent には注入テキストの見出し行を verbatim で返させ、ログと 2 系統で突き合わせた。
2 本とも `# [MUST] テストが緑であることを、仕様を守れている証拠にしない` を返し、
ログにも同じ時刻に `path_glob_match` が記録された。

frontmatter は frontend と同じ flow style (1 行) にした。block style が Claude Code 側の
パーサで通るかは未実測で、通らなければ「予算は下がったのにルールは死んでいる」という
沈黙した失敗になる。`is_always_loaded_rule` は yaml.safe_load なのでどちらも通してしまい、
検査では捕まらない。

### references の逆参照を張り替えた

`home/.claude/references/*.md` は 8 ファイルすべてが冒頭で
「`~/.claude/CLAUDE.md` の「<カテゴリ名>」カテゴリが持つ規範の」と居場所を名指ししている。
カテゴリを rules へ移すと、この逆参照が黙って嘘になる。

frontend には references が無かったので PR #137 はこれを踏んでいない。今回が初のケース。
`references/testing.md` の 3 行目を `~/.claude/rules/testing-practices.md` へ張り替えた。
残る 7 カテゴリを切り出すときも同じ手当てが要る。

### 移した先にしか定義が無い語が常時層に残る

レビューで見つかった。委譲カテゴリの「implementer には実装と変異注入までを任せる」が
`変異注入` を使っているが、その操作的定義 (メカニズムを一時的に壊して FAIL することを
確かめる) は今回 rules へ移った行が持っていた。テストファイルを Read しないセッションでは、
語だけが常時層に残って定義が届かない。

効くのは brief を書くコントローラ側である。implementer はテストファイルを読むので rules が
届くが、委譲を設計する側には届かない。

最初はポインタ (`定義は ~/.claude/rules/...`) を足したが、レビューで「参照を 1 本増やして
常時層に恒久コストを載せる bandaid」と指摘されて自己完結な言い換えへ変えた。
括弧で操作的定義を書けばポインタも往復も dangling リスクも要らない。

レビューは「バイト数はほぼ同じ」と述べていたが、測ると自己完結版のほうが 16B 多い
(ポインタ版 28,996B に対し 29,012B)。採用の根拠はバイトではなく、参照が rot しないこと。
レビューの主張も検証していない前提として扱う。

**移設の規約として「語の操作的定義は常時層に残し、手順と事例だけを移す」を採る。**

CLAUDE.md 側に残った他の語 (`dead pin` / 免除 / narrowing / gaming / negative case) は
移した先に閉じている。

**ただしこの検算は母集団が狭かった。** CLAUDE.md しか見ておらず、`references/*.md` を
見ていない。references は常時層から名指しされる読み先で、その読者がテストファイルを
Read しているとは限らない。実際 `references/observation.md` が `変異注入` と `dead pin` を
定義なしで使っている。検算の母集団は「常時層」ではなく
「テストファイルを Read せずに到達しうる集合」= CLAUDE.md + `references/*.md` である。
observation.md は今回の変更で触っていないので本 PR では直さない。

### 結果

CLAUDE.md は 32,287B から 29,012B へ (3,275B 減、11 カテゴリ)。
`ALWAYS_LOADED_BUDGET_BYTES` も同じ値へ下げた。

途中で語の定義を足したとき予算が超過し、`test_real_repo_is_within_budget` が実際に赤くなった。
意図した変異ではないが、検査が本番の増加を捕まえることの実証になっている。

**ただしこの検査はラチェットではない。** 定数は実測値の写しで、切り出しのたびに手で書き換える。
今回も 28,942 → 28,996 → 29,012 と 2 度「上げて」いる。検査は増減の向きを区別しないので、
増加は定数を書き換えるだけで無音で通る。起票理由 (9 日で +44%) を防ぐ力は無い。
別タスクへ切り出した。

検証は以下。

- 予算の変異を両方向。1 下げると `test_real_repo_is_within_budget` が、

## 予算をラチェットにした (2026-08-22)

`ALWAYS_LOADED_BUDGET_BYTES` は上限を名乗るが、超えたときに上限のほうを書き換えれば
全緑で通っていた。実際に 1 セッションで 28,942 → 28,996 → 29,012 と 2 度上げている。
起票理由 (9 日で +44%) を防ぐ力がここで抜けていた。

### 禁じるのは引き上げではなく無音の引き上げ

最初の案は厳格な単調非増加だった。**余裕が 0B ちょうど**なので (実測 29,012 = 定数 29,012)、
入れた瞬間から CLAUDE.md へ 1 バイト足すたびに同じ PR で移設が必要になる。
しかもこの PR で余裕を作ることもできない。定数を上げればラチェット自身が止めるため。

目的に立ち返ると、防ぎたいのは「上げること」ではなく「無音で上げること」だった。
`BUDGET_RAISES` へ `(日付, 引き上げ後の値, 理由)` を 1 行足すことを引き上げの条件にした。
据え置きと引き下げには記録を要求しない。

記録の 3 要素は互いに従属させず独立に報告する。1 つを他の内側へ入れると、
外側を緩めた瞬間に内側が無言で vacuous になる。

### baseline は ast で読む

`git show origin/main:<予算モジュール>` の中身から定数を取る。regex だと
コメントや docstring 中の同名を拾い (定数名は Finding のメッセージにも出る)、
`exec` だと baseline 側の任意コードを実行する。`ast.parse` は Python のパーサ自身なので
どちらも起きない。

読めないときは `[]` ではなく Finding にする。skip すると緑が「健全」と
「そもそも見ていない」を区別しなくなる。

### CI は origin/main を持っていなかった

PR #139 の実 CI ログを読んで確定した。`actions/checkout` は既定 (`fetch-depth: 1`) で
以下しか fetch しない。

```
git fetch --depth=1 origin +<sha>:refs/remotes/pull/139/merge
git checkout --force refs/remotes/pull/139/merge
```

`refs/remotes/origin/main` は作られない。config-guard の job へ明示的な fetch step を足した。
**この step を消すと「baseline を取得できない」で赤くなる**ので、外れたことに気づける。
取れないときに skip する設計だったら、step を消した瞬間にラチェットが黙って無効になっていた。

### 超過時に「どこを削るか」を出す

超過量だけの報告は行動につながらず、定数を上げる方が早いという判断を誘う。
CLAUDE.md を H2 で区切った内訳の重い順 3 件を Finding のメッセージへ載せた。
粒度を H2 に留めるのは、H3 まで割ると件数が読める量を超えるため。

あわせて config-guard の出力へ常時サマリを 1 行足した。

```
config-guard: 常時 29012B / 予算 29012B、scoped 2 枚 4506B
```

scoped 層を併記しないと、移設した分が数字の上で「消えた」ように見え、
「移せば必ず勝ち」というメトリクスのままになる。移設は無料ではなく、
一致ファイルを読んだ agent 文脈ごとに払っている。

### 変異注入

| 変異 | 種別 | 結果 |
|---|---|---|
| 定数を記録なしで +1 | (1) 検査対象 | 赤。**予算検査は緑のまま**ラチェットだけが赤くなる |
| +1 に正しい記録を添える | 緩める方向の正常系 | 緑。詰まないことの確認 |
| `evaluate_ratchet` を早期 return | (2) 検査機構 | 検出が消える |
| `parse_budget` を regex へ退化 | (2) 検査機構 | コメント・文字列・関数内を拾い 3 件が赤 |
| `scan()` から呼び出しを外す | (3) 取り付け | 検出が消え、配線テストも赤 |
| サマリの print を消す | (3) 取り付け | テストが赤 |

CI の fetch step を消す変異は CI 上でしか確認できないため実施していない。
step が必要である根拠は上の実 CI ログで、step が効くことはこの PR の CI が示す。

### 上の 6 種が覆えていなかった dead pin

レビューが穴を 1 つ見つけた。**`BASELINE_REF` の値そのものが pin されていない。**

git 越しの比較を突くテストは全て `ref=` を明示していたので、既定値を通る経路を
一度も実行していなかった。`BASELINE_REF = "HEAD"` へ変えても 259 件すべて緑のまま、
config-guard も緑になることを実測で再現した。clean checkout では working tree == HEAD
なので常に `current == baseline` となり、ラチェットが無条件に通る。
**この機構が防ごうとしている「無音で無効になる」形そのもの**だった。

origin repo を clone して HEAD と `origin/main` が別の値を持つ状態を作り、
既定の ref で呼んで Finding が出ることを見るテストで塞いだ。変異を入れたまま
新テストを走らせて赤くなることを確認済み。

一般化すると **本番だけが通る経路をテストが一度も通っていない** という形で、
「守る分岐が本番の入力経路で到達可能か」の裏返しに当たる。変異を機構と取り付けに
かけるだけでは見えず、既定引数のように「テストが毎回上書きする値」が盲点になる。

### 観点どうしが衝突した 1 件

boy-scout が「この節のサマリ出力例に実測値を literal で書くのは、同じ diff で
件数記述を削った方針と整合しない」と指摘し、code-reviewer は「設計ドキュメントは
スナップショットという規約に照らして問題ない」と判断した。

**数値のまま残した。** 削った「9 件」は誤った値 (実際は 14 件) で canonical が
テストファイル自身だったのに対し、サマリ出力例は日付付きの節に置いたその時点の
実行結果で canonical は実行そのものだから。プレースホルダにすると
「この機構が何を出すか」が読めなくなり、情報が減る。

同じ形で、同じ節が既に答えを持っていた。** それを書いた当人が、自分の新しい観測に
当てはめないまま矛盾だと結論した。最も単純な説明を排除する手順を踏んでいなかった。

引用も不正確だった。「発火経路は Read のみ」は「発火経路を実測した」節の結論で、
「dedup の粒度と…」節が確立したのは (a) 同一文脈では別ファイルでも復活しない
(b) Bash 経由の書き込みでは発火しない、の 2 点だけである。2 つの節の結論を 1 つの節名の
下に合成していた。節名で参照する規約の下では、これは引用の捏造に近い。

**1 行目の `trigger_file_path` が実在しない** (`ls` で確認済み)。リポジトリルート相対の
`tests/test_instruction_refs.py` は存在せず、実体は `scripts/config-guard/tests/` 配下にある。
`cd scripts/config-guard` してから相対パスで走らせた Bash コマンドが、セッションのルートで

このログを証拠に使うときの前提が 1 つ崩れている。

**3 行目を帰属できない**。17:33:08 は squash マージ (コミット時刻 17:33:00 UTC) の 8 秒後で、

### 確かめられなかったこと

- 各エントリがどの agent 文脈のものか。subagent のトランスクリプトは削除済みで復元できない
- main loop の文脈へ `testing-practices.md` が最初に注入された時刻。したがって
  **「テストを書いている最中に規範が届いていたか」も決まらない**。届いていなかった可能性も、
  届いていて守らなかった可能性も残る (部分一致の弱い assertion を書き、レビューで指摘される
  まで気づかなかったこと自体は起きた)

### 対照の設計

dedup が効いている文脈では何を測っても増分 0 になる。**最上位の制約は agent 文脈を 1 つに
固定すること。** subagent を一切起動しないセッションで、1 操作ずつ間隔を空けて測る。

- Bash 読み (`cat <一致ファイル>`) / Bash 書き / Write / Edit / Read の 5 経路を個別に
  (「Bash 経由の書き込み」は測定済みだが Bash の読みは未測定)
- 相対パスと絶対パスを分ける (cwd 解決の仮説)
- ブロックされるコマンド (Tirith が止める形) と通るコマンドを分ける
- 一致ファイル名が **出力にだけ** 現れるコマンド (`git log --stat` 等) を 1 本
- 同一文脈で trigger を変えて 2 回 (dedup の粒度が trigger 単位かの判定)

### なぜ測るか

移設の判断は「scoped 層は一致ファイルを読んだ agent 文脈ぶんだけ払う」というコストモデルに
乗っている。今回このモデルが崩れた証拠は無かったが、**ログだけでは検証できないことが
はっきりした。** 文脈を識別できない観測系のままでは、コストモデルも発火経路も測り直せない。
測るなら観測系の側を先に直す。

## 発火の条件を単一文脈で測り直した (2026-08-22)

前節の対照設計に従って測った。測定のあいだ subagent は 1 本も起動していないので、以下で数える
`path_glob_match` は全て main loop のものになる (記録の検証を 1 本へ委譲したのは、測定を終えて
ログをスナップショットした後)。基準線はセッション開始時点で 0 件、数えるときは `file_path` で
絞った。Claude Code は 2.1.238 (`CLAUDE_CODE_EXECPATH` で確認。`claude --version` は zshrc の
関数が非対話シェルに無いため失敗するので使えない)。

プローブは 1 セル 1 rule にした。dedup のキーが (agent 文脈, rule) なので、rule を分けさえ
すれば単一文脈でも独立したセルをいくつでも置ける。計 34 枚を使い、全て撤去した。

### 測る前に、前提のほうが壊れた

最初に置いた 10 枚は 1 枚も発火せず、陽性対照の Read まで沈黙した。プローブの内容ではなく、
rules の登録がツールとパスの組み合わせで決まっていた。

| rule ファイルへの操作 | 登録 |
|---|---|
| session_start のスキャン | 既存ファイルを登録する |
| Bash での書き込み (パス形式を問わない) | 登録される |
| Write ツールで `~/.claude/rules/<name>.md` を新規作成 | 登録される |
| Read ツールで `~/.claude/rules/<name>.md` を開く | 影響しない (n=1) |
| Read / Write ツールで `home/.claude/rules/<name>.md` を触る | 登録されない。登録済みなら落ちる |

`~/.claude/rules` は `home/.claude/rules` への symlink なので、どちらのパスでも実体は同じ
ディレクトリの同じファイルになる。それでも結果が分かれる。ファイルシステム上の出来事では
説明がつかず、ハーネスがツール呼び出しに現れたパス文字列で判定していると推測できるが、
内部は見ていないので推測のままにする。

Edit ツールだけは単独で測れない。同一会話での事前 Read を要求するので、リポジトリ側パスの
Edit は必ず同じパスの Read を連れてくる。表の最終行が先に効くため、実運用では区別が要らない。

落ちた登録はそのセッション中は戻らない。Bash での書き直しでも、`rm` してからの再作成でも
戻らなかった。一方で一度も登録されていないパスは `~` 側からの作成でまだ登録できるので、
「落ちた」と「まだ登録されていない」は別の状態として振る舞う。

### 実運用では、rules を開いた時点でそのセッションでは死ぬ

このリポジトリは rules を `home/.claude/rules/` 側で読み書きする。上の表の最終行に当たるので、
レビューのために開くだけでも、編集しても、そのセッションでは発火しなくなる。

session_start で登録済みの本物の rules でも同じだった。対照を付けて測った。

| 手順 | 結果 |
|---|---|
| 触っていない `testing-practices.md` の一致ファイルを Read (対照) | 発火 |
| `home/.claude/rules/frontend-practices.md` を Read ツールで開く | - |
| 直後に `.tsx` を Read | 発火しない |

この 3 行は rule 違いの群間比較であって、frontend が発火する状態を先に観測してから落ちたのを
見たわけではない。dedup があるので同じ rule での前後比較は原理的に取れない (一度発火したら
二度目が出ない)。取れる最強の形が群間比較になる。プローブ側では作り方を揃えて比べてある。
Bash で作って発火した 2 枚 (ag / aj) と、同じ作り方のあとリポジトリ側パスで Read した 2 枚
(ah / ai) が沈黙した。

含意が 1 つある。切り出し作業をしているセッションは、まさにその rule ファイルを開く
セッションなので、同じセッションで発火を確認すると偽陰性が出る。確認するなら rule 本体は
Bash で開くか、新しいセッションで行う。

### 発火の条件

登録済みの rule に対して、1 セル 1 rule で測った。基準線はいずれも 0 件。

| セル | 操作 | 発火 |
|---|---|---|
| P | Bash `cat` (リポジトリ相対パス) | しない |
| Q | Bash `cat` (絶対パス) | しない |
| R | Bash `>>` で追記 | しない |
| S | Write ツールで新規作成 | しない |
| T | Edit ツールで書き換え | しない |
| U | 一致パスを `echo` するだけ (ファイルに触らない) | しない |
| V | `ls -l` で stat するだけ | しない |
| W | 権限で拒否されるコマンドへ一致パスを渡す | しない |
| X | 存在しない一致パスを `cat` | しない |
| Y | 存在しない一致パスを Read ツールへ渡す | 発火 |

9 セルの陰性が「rule が死んでいた」ではないことは、各セルの rule に対して同じ文脈で Read を
掛けて確かめた。9 枚とも発火し、ログにも同一秒で 9 行記録された。

測ったツールは Bash / Read / Write / Edit の 4 つ。Grep と Glob はこのセッションでは提供されて
いないので測っていない。どちらもパス引数を取るので、全ツールに対する全称にはできない。

Y から言えることが 1 つある。照合されるのは Read ツールの `file_path` 引数であって、
コンテキストに入った内容ではない。前節の「`trigger_file_path` が実在しない」はこれで
説明がつく。読めなかった Read でも発火する。

### 注入される本文と dedup

| 観測 | 結果 |
|---|---|
| 初回発火の前に rule を書き換えた | 新しい版が注入される |
| 発火後に rule を書き換えた | 再注入されない |
| 同じ rule に一致する別のファイルを Read | 再発火しない |

1 行目から、本文は登録時にキャッシュされるのではなく注入の瞬間に読まれると言える。
3 行目は「dedup のキーは (agent 文脈, rule)」の再確認だが、今回は subagent が 1 本もいないので
帰属に曖昧さがない。

### ディレクトリ名の glob はツリー全体を覆う

`**/pxdir` の形の rule を置いて `.cache/pxdir/note.txt` を Read したところ発火した。
ディレクトリ名だけを書いた形が、その配下のファイルを Read したときに発火することを意味する。
glob の corpus 問題で「広い 1〜2 個へ寄せる」を採るときの材料になる。

ログの `globs` フィールドを rule の記法の canonical として読まないこと。
`testing-practices.md` の実体は `**/tests/**` のように末尾へ `/**` を付けた形だが、
ログは `**/tests` へ正規化して記録する。

## skills の二重登録を実装から特定して live probe で確かめた (2026-08-23、Claude Code 2.1.238)

前回まで `home/` にスコープされた skill の登録は挙動の A/B で追っていた。引き金の候補は
「`home/.claude/rules/` への一括書き込み」と「subagent の起動」の 2 つで、どちらも決め手が
なかった。今回は振る側をやめ、走っている実行ファイルを読んで機構を特定し、そこから立てた予測を
live probe で確かめた。

結論から書くと、引き金は前者だった。「一括書き込みの直後に出た」という前回の観測は偶然の隣接
ではなく因果で、書き込みそのものではなく「cwd 配下のファイルをツールで触ったこと」が条件を
満たしていた。

### 読み方

実行ファイルは Bun の single-file executable (306MB) で、JS ソースが平文で埋まっている。
ホスト実機で大きいバイナリを一括ロードしない規範があるので、チャンクの逐次読みに
チャンク境界をまたぐ overlap を持たせた検索スクリプトで当たりを付け、オフセット 250MB 以降の
68MB だけを切り出してから読んだ。

識別子は minify されているのでバージョンが変われば変わる。以下の名前は 2.1.238 のもの。

### 機構

1. Read / Write / Edit の各ツールが、触ったファイルの絶対パスを添えて
   `HWr(session.host, <path>, dynamicSkillDirTriggers)` を呼ぶ (Edit は `bhv`、Write は `Chv`)
2. `HWr` は `XcT(host, [path], cwd)` を呼ぶ。`XcT` は `dirname(path)` から cwd に向かって
   `while (u.startsWith(cwd + sep))` で遡り、各祖先 `u` について `join(u, ".claude", "skills")` を
   stat する。条件が strictly-under-cwd なので、リポジトリ直下の `.claude/skills` はこの経路に
   入らない
3. 見つかったディレクトリは `B_l` 経由で `dynamicSkills` へ入る。skillRoot は walk が組み立てた
   `<u>/.claude/skills/<name>` で、`XcT` は `i.push(p)` と未解決のまま積む。`realpath` も取るが
   sync-owned prefix の判定にしか使わない
4. `XcT` は候補パスを `dynamicSkillDirs` へ stat の前に無条件で add する。よって同じディレクトリは
   1 セッションに 1 回しか評価されない
5. gitignore ガードは `BUo(u, o)`、つまり祖先ディレクトリ `u` に対して効く。skills ディレクトリ
   自身は見ていない
6. scoped 化の判定は `ujT(skill, cwd)`。skillRoot の中で最後に現れる `/.claude/` の位置より前を
   取り、cwd からの相対パスを prefix にする。空・`..` 始まり・絶対パスなら null
7. prefix が得られたとき、同名衝突があれば `djT` が `<prefix>:<name>` へ改名して description に
   `scoped to <prefix>/ — use this instead of the unscoped ...` を足す。衝突が無ければ `y4m` が
   名前を変えず `from <prefix>/.claude/skills — applies when ...` を足す。`y4m` の枝は定義上
   同名の既存エントリが無いので重複を生まない。重複するのは `djT` の枝だけ

`.claude/skills/<name>/` を plugin として adopt する経路 (`Tyi`、内部名 `skills-as-plugins` /
`@skills-dir`) は上とは別で、配下に `.claude-plugin/` があるものだけが対象になる。候補は user
scope の `<userConfigDir>/skills` と project scope の `<cwd>/.claude/skills` の 2 つだけ
(`aFp`)。plugin のロード (`F$`) はメモ化されるが、`clearPluginCache` (`y1`) が
`pluginLoad` を `undefined` に戻すので「1 回きり」ではなく「無効化されるまで」が正しい。

### live probe

機構から「`home/` 配下のファイルをツールで 1 つ触れば登録される」という予測が立つので、
その状態を作って確かめた。

- 事前状態: このセッションは調査をすべて Bash 経由で行っており、`home/` 配下を Read / Write /
  Edit のいずれでも触っていない。skill 一覧に `home:` prefix も `from home/.claude/skills` の
  注記も無い
- 操作: `home/.gitignore` を Read ツールで 1 回読んだ。このパスは `paths` 付き rules のどの
  パターンにも一致しないので、rules の発火と混ざらない
- 結果: 直後に `New skills discovered in home/.claude/skills` として 16 個が `home:` prefix で
  登録された

登録された 16 個はすべて `scoped to home/ — use this instead of the unscoped "<name>" skill ...`
の文言だった。これは `djT` の衝突あり側の枝で、16 個すべてに unscoped の双子が存在することを
意味する。

`home/.gitignore` は `.claude/skills/` を ignore しているが登録は起きた。ガードが見るのは祖先
`<repo>/home` で、そちらは追跡下にあるため素通りする。deploy 先が gitignore されていることは
この経路の防御にならない。

### 最初に書いた結論の誤りと、その直し方

この節の最初の版は引き金について逆の結論を書いていた。検証で 6 点の食い違いが出て、いずれも
バイナリを読み直して確認したうえで訂正した。誤りの型を残しておく。

- `ujT` と `djT` (scoped 化の判定) だけを読み、その母集団 `TJn()` = `dynamicSkills` がどう
  埋まるかを追っていなかった。空いた穴を「skillRoot が realpath 化されるとしたら」という仮定で
  埋め、その仮定を必要条件として書いた。実際には realpath 化する経路は存在せず、パスは ancestor
  walk が最初からその形で組み立てている
- 「セッションに一度しか起きず再発しない」「30 回書き込んでも再発しない」を、書き込み説を
  弱める材料として読んだ。実際は `dynamicSkillDirs` のメモ化の予測どおりの挙動で、書き込み説を
  支持する材料だった。同じ観測が反対の結論を支えうる
- description のバイト数を frontmatter から数えるとき、YAML の引用符を剥がさずに数えて 10B
  過大になっていた。8 行の内訳と合計は互いに整合していたので、内部整合の検算では見つからない

### 説明できていないこと

- prefix 無しの `security-redteam` などがどの経路で載るのかは確かめていない。`.claude-plugin/` を
  外せば消えるかどうかも未確認
- `HWr` は末尾で `ZcT([path], cwd)` を呼び、これが `paths` 付きの照合を行っている。Write と Edit
  も同じ `HWr` を通るのに、前回の実測では Write / Edit で rules が発火しなかった。`ZcT` の内部に
  さらに条件があるはずだが追っていない
- `blockedMarketplaces` に `{"source":"skills-dir"}` を入れると `usr()` が false を返して
  skills-as-plugins が止まる。ただし `Upi` も `kme` も `pn("policySettings")` しか読まないので
  ソース上は managed settings 層限定に見える。他の層が合流しないかまでは追っていない

### 再現手順

バージョンが上がるとオフセットも識別子も変わるので、当たりの付け方だけ残す。

1. `$CLAUDE_CODE_EXECPATH` で走っている実行ファイルを特定する (`claude --version` は zshrc の
   関数が非対話シェルに無いので使えない)
2. チャンク読み + overlap の検索で `skills-as-plugins` を探し、その周辺のオフセットを見る
3. そのオフセット以降を切り出してから `dynamicSkillDirTriggers` を探すと、ツール側の呼び出しから
   `HWr` → `XcT` → `B_l` の連鎖にたどり着く。scoped 化側は `scopedSkillName` を export している
   オブジェクトから辿る
4. バイナリ由来のバイトが混ざった検索結果を `grep` にパイプすると、マッチしても行が出ずに 0 件に
   見える。`grep -a` を使うか、対照を並べて検査自体が生きていることを先に確かめる

## command と agent の二重登録の出所を確定し方針を決めた (2026-08-23、apm 0.28.0 / Claude Code 2.1.240)

前節で見つけた別系統を決着させた。出所は Claude Code ではなく apm の deploy 規則で、抑止ノブは
存在しない。最初に採ろうとした案は plugin の契約を壊すことが分かり、別の案へ切り替えた。実施は
[Issue #40](../../40_skill%20バンドルの%20command%20と%20agent%20の二重登録を止める/issue.md)。

### 出所は apm が 2 経路で配っていること

prefix 無しで載っていた 8 件は `~/.claude/commands/` の 5 ファイルと `~/.claude/agents/` の
3 ファイルに過不足なく一致する。どちらも apm の deploy 先で `home/.gitignore` が ignore しており、
`home/apm.lock.yaml` の `deployed_files` が両経路への配布を記録している。配られるファイルは完全に
同一ではない。agent 3 件は両側でハッシュが一致するが、command 5 件は apm が frontmatter を
再直列化するぶんだけ差がある。system prompt に載る description のほうは両側で同一。

引き金は構造で、合成パッケージの対照で切り分けた。

| root SKILL.md | `.claude-plugin/` | verbatim `.claude/skills/<pkg>/` | flat `.claude/{agents,commands}/` |
|---|---|---|---|
| あり | あり | 配る | 配る |
| なし | あり | 配らない | 配る |
| あり | なし | 配る | 配らない |

root SKILL.md が verbatim コピーの引き金、`.claude-plugin/` が flat 分解の引き金で、両方あると
両方走る。Claude Code はこの 2 つを別経路として登録するので、同じ description が prefix 有無で
2 回載る。`home/.gitignore` のコメントは以前からこの規則を書いていたが、再現して確かめたのは今回が
最初になる。

### 抑止ノブは無い

plugin.json の明示宣言で止まるかを 4 ケースの対照で測った。`"skills": ["./skills"]` は nested
skills の flat 分解を止める。実物の 2 bundle は既にこれを使っており、だから sub-skill の flat コピーが
存在しない。一方 `"commands"` と `"agents"` を同じ形で宣言しても flat 分解は止まらなかった。

消費側にもノブは無い。`home/apm.yml` の末尾には `includes: auto` という行があるが、`includes` は
apm の manifest schema にも 0.28.0 の雛形にも現れないキーで、認識される設定ではない。`apm targets`
はどちらの deploy も同じ `claude` ターゲットとして扱う。

### 同名衝突は 1 件に潰れ、勝つ側が名前空間で逆になる

command と sub-skill が同名だと system prompt には 1 件しか載らない。勝つ側は名前空間で逆になる。

- prefix 名前空間では command が勝つ。`security-blue-red-team:security-vulnerability-assessment` と
  `web-monkey-qa:monkey-qa` は、どちらも command 側の短い英語 description で載っており、
  sub-skill 側の長い日本語 description は載っていない。一次証拠は自分の system prompt
- bare 名前空間では skill が勝つ。既存の bare command と同名の skill ディレクトリを合成して置き、
  headless セッションに該当行を出力させたところ、skill 側の marker が載り command 側は消えた

この結果、`skills/security-vulnerability-assessment/SKILL.md` (1,575B) と
`skills/monkey-qa/SKILL.md` (1,227B) は一度も system prompt に載っていない。計 2,802B の
authored content が dead になっている。

### prefix 無しの agent 名は解決しない

plugin の中にしか存在しない agent を prefix 無しで dispatch できるかを、合成 plugin で測った。
結果は不可で、Claude Code 自身が registry を列挙したエラーを返す。

```
Agent type 'zz-probe-agent' not found. Available agents: blue-team-agent, claude, ...,
security-blue-red-team:blue-team-agent, ..., zz-probe-plugin:zz-probe-agent
```

security bundle は SKILL.md と command のどちらでも agent を `subagent_type: red-team-agent` と
bare 名で呼んでいる (計 6 箇所)。一方 web-monkey-qa は `web-monkey-qa:monkey-explorer-agent` と
prefix 名で呼んでいる。同じリポジトリの 2 bundle で流儀が割れており、どちらの経路を残すかを決めると
片方は必ず張り替えが要る。

### シナリオごとの常時ロード bytes

description のみを数えた値。衝突の勝敗規則は上記の実測に従う。

| シナリオ | 常時ロード | 削減 |
|---|---|---|
| S0 現状 | 9,997B | — |
| S1 flat 側の deploy 先 (`~/.claude/{commands,agents}`) を消す | 6,929B | 3,068B (30.7%) |
| S2 verbatim コピー側の `commands/` `agents/` を消す | 9,731B | 266B (2.7%) |
| S3 root SKILL.md と `skills` 宣言を外して全部 bare へ | 8,830B | 1,167B (11.7%) |
| S4 root SKILL.md を外し sub-skills を配らない | 3,068B | 6,929B (69.3%) |
| S5 flat 側を消し sub-skills も撤去 | 3,584B | 6,413B (64.1%) |
| S6 sub-skills だけ撤去 | 6,652B | 3,345B (33.5%) |

内訳は bare 名前空間が flat commands 1,093B (5 件) と flat agents 1,975B (3 件) と bundle root
516B (2 件) で 3,584B、prefix 名前空間が同内容の commands と agents 3,068B と、載っている
sub-skills 3,345B (2 件) で 6,413B。sub-skill の残り 2 件 2,802B は同名の command に隠れて
載っていない。S2 と S3 が中途半端な数字になるのは、重複を消すと隠れていた sub-skill の長い
description が出てきて相殺するため。

### 削減が最大の S4 は plugin の契約を壊す

いったんは S4 を採ると決めたが、レビューで 3 点が出て取り下げた。いずれも実測で確認した。

- **`schemas/` の deploy 経路が消える**。root SKILL.md を外した形で apm を走らせると `.claude/` に
  届くのは agent と command だけで、`schemas/` は 1 件も届かない。実物の agent と command は
  `${CLAUDE_PLUGIN_ROOT}/schemas/<name>` を 6 箇所で参照しており、参照先ごと消える
- **`/monkey-qa` が壊れる**。この command は `Skill(skill="web-monkey-qa:monkey-qa")` を起動する
  薄い entry point で、実体は S4 が削除する sub-skill にある
- **web-monkey-qa の dispatch が prefix 名に依存している**。S4 では prefix 名前空間そのものが
  消えるので、`web-monkey-qa:monkey-explorer-agent` への 3 箇所の dispatch が解決しなくなる

つまり flat 側 (bare 名) は「軽いほう」ではなく「契約を満たしていないほう」だった。`${CLAUDE_PLUGIN_ROOT}`
が解決し `schemas/` が届くのは verbatim コピー経由の prefix 側だけで、残すべきはこちらになる。

### 決定

S5 を採る。上流の 2 bundle から sub-skills を撤去して bundle を command と agent だけにし、
dotfiles 側は apm install 後に flat 側の deploy 先を削除する。登録は prefix 名の 1 経路になり、
常時ロードは 9,997B から 3,584B へ 6,413B (64.1%) 減る。

採った理由は、契約を壊さない案の中で削減が最大であること、残る経路が `schemas/` と
`${CLAUDE_PLUGIN_ROOT}` を満たしている側であることの 2 つ。上流では security bundle の bare
dispatch 6 箇所を prefix 名へ揃え、`/monkey-qa` には削除する sub-skill の本体を取り込む必要がある。
dotfiles 側の後始末は apm install のたびに再生成されるぶんを消す形になるので、bootstrap か apm の
lifecycle script のどちらに置くかは Issue #40 で決める。

`dev-workflow` と `justfile` は `commands/` も `agents/` も持たないので影響を受けない。

### 落とし穴

- **削減量だけを見て S4 を薦め、plugin の契約を確かめていなかった**。root SKILL.md を外すと
  verbatim コピーが消えるところまでは測っていたのに、そのコピーが `schemas/` の唯一の deploy 経路で
  あることと、`${CLAUDE_PLUGIN_ROOT}` が解決する場所であることを結び付けていなかった。バイト数の
  比較表は正しく、正しい表の上で誤った結論に至った
- **衝突の勝敗規則を片方の名前空間から一般化しかけた**。prefix 名前空間の観測だけで「command が
  勝つ」を全体の規則にして S3 を 3,584B 削減と見積もったが、bare 名前空間は逆で実際は 1,167B
  だった。名前空間ごとに測り直して初めて表が正しくなった
- **プローブの位置が違うと疑ったが、それ自体が外れだった**。合成パッケージと実物で結果が食い違った
  ので `package_type` の違いを疑ったが、どちらも `marketplace_plugin` で同じ経路だった。実際の
  差分は plugin.json の `"skills"` 宣言の有無で、疑う先を間違えると 1 手無駄になる
- **`uv run --project` を pytest に渡すとリポジトリ全体を収集して 17 件の collection error になる**。
  テストが壊れているように見えるが呼び出し側の誤りで、pytest には `--directory` を渡す

## corpus 問題を数字で決着させた (2026-08-24)

`paths` の 8 パターンは 26 リポジトリのうちテストファイルを持つ 20 個から導出したので、その
corpus に無い規約は沈黙する。この形をどうするかを決めた。三択は「実際に使うと分かってから足す」
「偽陽性許容を徹底して広い 1〜2 個へ寄せる」「リポジトリ固有の規約は project scope へ置く」
だった。

### 三択の前提が 2 つとも外れていた

先に測ったところ、議論の土台に置いていた前提が両方とも実態と違った。

**取りこぼす規約の例として挙げていた RSpec と Cucumber は、管理下に実体が無い。** 追跡下の
`.rb` はごく少数でどれも spec ではなく、`.feature` と `.java` と `.kt` は 1 件も無い。
足しても限界カバレッジは 0 で、corpus 問題の実例にはなっていなかった。

**実在する最大のギャップは Rust のインラインテストで、これはどの命名規約 glob でも当てられない。**
追跡下の `.rs` のうち `#[cfg(test)]` を持つものは 445 件あり、現行 8 パターンが拾えるのは
14 件だけだった。限界カバレッジは 431 件になる。拾えている 14 件はすべて `**/test_*.*` 経由で、
`test_support.rs` `test_api.rs` `test_macros.rs` のようにテスト基盤として切り出された側にあたる。
本番ファイルへ同居する側は、ファイル名にもディレクトリ名にもテストであることの痕跡が出ないので
残らず漏れる。三択はどれも「ファイルパスで当てる」前提に立っていたが、その前提が最大のギャップに
対して成立していない。

**この 14 件は最初「0 件」と数えていた。** Rust の集計だけ判定を手書きし、8 パターンのうち
`**/test_*.*` を落とした対照で数えていたためで、レビューの指摘で気づいた。壊れた対照は
エラーではなく、もっともらしい数字を返す。ここでは「0 件」という、主張をより強く見せる方向へ
外れていた。

### 偽陽性のコストは当初の見積もりより安い

`**/specs/**` を除外したときの理由は「入れると設計ドキュメントを読むたびにテスト規範が注入される」
だった。この機構の理解は誤っている。同じ Issue の「注入される本文と dedup」節が
「同じ rule に一致する別のファイルを Read → 再発火しない」を実測しており、dedup のキーは
(agent 文脈, rule) なので、コストは一致件数ではなく agent 文脈あたり 1 回で頭打ちする。

除外の判断そのものは正しい (`specs/` の実体はほぼ全件が設計ドキュメントで、一致が偽陽性しか
生まない)。誤っていたのはコストの大きさの見積もりで、広い側へ寄せる案を実際より高く見せていた。
理由の文面を機構に合わせて直した。

### 候補集合を数えた

管理下のリポジトリを `find -maxdepth 3` で 28 個列挙した (`-maxdepth 2` だと 27 個で、1 段深くに
置かれた 1 件が漏れる)。vendored ディレクトリを除いた追跡ファイル 7,774 件へ候補集合を当てた。

`**` を含む glob の意味を決めるのは Claude Code のマッチャなので、ここでは近似して数えている。
近似の規則は 2 つで、末尾が `/**` の形はパスの構成要素にそのディレクトリ名が現れるかを見て、
それ以外は basename に対して当てる。全行を同じ規則で数えた。

| 集合 | 一致 | 非コード | うち `.md` |
|---|---|---|---|
| A 現行 8 パターン | 1,168 | 28 | 0 |
| B A + `**/*-test.*` + `**/test-utils/**` | 1,205 | 28 | 0 |
| C 広い 2 個 (`**/*test*` `**/*spec*`) | 1,140 | 43 | 41 |
| D B + `**/*.rs` | 2,103 | 28 | 0 |

C は basename の意味論では A より一致が少ないうえに `.md` の誤爆だけが増える。`**/tests/**` が
拾っていたディレクトリ単位のテストが、basename に test を含まないぶん落ちるため。

ワイルドカードがディレクトリ名にも当たって配下を覆う意味論だとすると C は一致 1,493 / 非コード 211
(うち `.md` 174) になる。この意味論は未実測で、実測済みなのは `**/pxdir` のようにディレクトリ名を
literal で書いた形が配下を覆うことまで。どちらの読みでも C は採らない。前者なら A の下位互換、
後者なら測って除外した `**/specs/**` と同じ失敗をより広い範囲で作り直す形になる。

**この C 行は最初 1,493 / 203 と書いていた。** 他の行を basename の規則で数えたのに、C だけ
フルパスへの一致を混ぜていたためで、レビューで再現しなかったことから分かった。対照は検証対象と
同じ規約で作る、という規範を表の中で破っていた。

substring 形はさらに `Dockerfile.testing` や `docker-compose.testing.yml` のような
「単語の一部に test を含むだけ」のファイルも拾う。

B が足す 2 パターンは実測で見つけた本物のギャップにあたる。ハイフン形の
`markdown-renderer.contract-test.tsx` は `*.test.*` の `.test.` にも `*_test.*` の `_test` にも
一致せず、テストファイルなのに沈黙していた。`test-utils/` はテスト基盤の置き場で、
`tests` `test` `__tests__` のいずれにも一致しない。

### 採ったのは D

`**/*.rs` を入れて、現行では漏れている Rust のインラインテスト 431 件を回収する。`.rs` 全体に対する当たりは 42% で、
Rust リポジトリでは実質的に常時ロードに近くなるが、dedup が agent 文脈あたり 1 回で頭打ちする
ぶんコストは限定される。取りこぼしは静かで、規範を外れたテストを書いても誰も気づかない。
この非対称が広い側を選ぶ理由になる。

corpus 問題そのものは、パターンを選び直しても解けない。解けるのは「何を覆っていないかを記録に
残す」ことだけなので、`DELIBERATELY_EXCLUDED` へ次の 4 つを理由ごと足した。

- `**/*test*` と `**/*spec*` は substring 形として却下したことと、その根拠
- `**/*_spec.rb` と `**/*.feature` は実体が無く限界カバレッジが 0 であること

件数は書いていない。リポジトリごとに違う数字を pin へ literal で持つと、手元で裏取りした人には
偽に見えるため。

### 実マッチャで発火を確かめた

`rules_paths.py` の pin は「意図した変更なら実プローブで確かめること」を要求している。
`.cache/probe-glob/` へ 5 ファイルを置き、新パターンごとに別の subagent へ Read させた。

| プローブ | 対象 | 結果 |
|---|---|---|
| `existing.test.ts` | 陽性対照 (`**/*.test.*`) | 発火 |
| `hyphen-test.ts` | `**/*-test.*` | 発火 |
| `test-utils/helper.ts` | `**/test-utils/**` | 発火 |
| `plain.rs` | `**/*.rs` | 発火 |
| `plain.txt` | 陰性対照 | 発火せず |

ログの `globs` は 11 個で新しいリストと一致した。subagent は毎回新鮮に走査するので、
セッション開始時の登録が古いままでも新パターンを観測できる。

**最初のプローブ設計は dedup で壊れていた。** 1 つの subagent に 5 ファイルを順に読ませたところ、
先頭の陽性対照が唯一の発火を消費し、残り 4 件は記録に出なかった。この結果は「新パターンが
発火しない」と読める形をしているが、実際には「dedup に抑制された」であり、正しく動いている設定を
壊れていると誤診しうる。dedup のキーが (agent 文脈, rule) である以上、パターンごとに別の agent
文脈が要る。陰性対照を各 agent の先頭に置いたのは、その agent が発火を観測できる状態にあること
自体を示すため。

プローブは測定後に撤去した。


## triage の 18 件を現行と突き合わせた (2026-08-24)

タスク D の入力である `notes/load-mechanism-triage.json` (2026-08-17、commit 7bfd9e8 の採番) を
現行の CLAUDE.md へ当て直した。

### 母集団を triage ではなく実体にした

## 本体に残す核を確定した (2026-08-24)

### 核の定義

CLAUDE.md 本体に残すのは、次のいずれかに当てはまる規範とする。

1. **トリガが失敗側に無いもの。** 規範を破る瞬間に特定のファイルを開いていない。
   git 操作・Bash の組み立て・subagent の設計・対話の姿勢・出力テキストの装飾が該当する
2. **語の操作的定義。** 移設先にしか定義が無いと、語だけが常時層に残って定義が届かない
   (「移した先にしか定義が無い語が常時層に残る」節)。テストの分類・ボーイスカウトルールが該当する
3. **新規作成が主要な失敗経路のもの。** 発火するのは Read だけなので、
   ファイルを新しく書き起こす場面ではトリガが立たない。既存文書の更新が失敗側なら
   Edit の前に Read が要るので届くが、新規作成が主戦場の規範は移せない
   (「MUST GLOBAL の降格は理由付けが逆で、レビューで差し戻した」節)
4. **強度の判定が不定なもの。** ラベル無しの項をカテゴリ既定として読むかどうかで
   強度が変わる項がある。判定が割れるものを移設で動かすと、降格が誰にも見えない形で通る
   (「カバレッジの項も静かに降格していた」節)
5. **前提と方針。** 開発スタイル・公開範囲の確認・個人情報・CI コスト・作業プロトコル。

## 語の検算を機構へ落とした (2026-08-24)

`config_guard.term_definitions` として実装した。

### 宣言は定義を持つ側に置く

rules の frontmatter へ `defines` を足し、その rules が定義する語を宣言させる。
用語リストを別ファイルへ持つ案は、定義の所在と宣言の所在が離れて二重管理になるので採らない。

`defines` は Claude Code が知らないキーだが、未知のキーは無警告で無視されるので発火には
影響しない。`rule_paths` は `paths` しか読まないため、予算判定にも paths の pin にも影響しない。

先行節が挙げた語のうち `免除` は宣言しない。testing-practices が「検査を緩める変更
(免除・除外・narrowing)」と列挙している中の 1 語だが、他の 4 語と違って操作的定義を
持たない普通の日本語で、意味が一般語から復元できる。同じ列挙の `narrowing` を宣言して
`免除` を落としたのはこの違いによる。宣言する語の条件は「意味が一般語から復元できないこと」。

母集団は `instruction_refs` が参照検査に使う `SOURCE_GLOBS` をそのまま使う。
再宣言すると参照検査と語の検査が別の規約で別の集合を見たまま両方緑になる。

外すのは語を宣言した rules 自身だけにした。当初は rules を glob 単位で丸ごと外していたが、
それだと paths の違う別の rules での使用が見えない。paths が違えば同時には注入されないので、
そこでの使用は CLAUDE.md での使用と同じく定義が届かない。

### 出現と欠落は機械では区別できない

括弧で操作的定義を併記した箇所も、定義の所在を名指しした箇所も、語としては同じに見える。
そこで出現のうち手当て済みのものを `ACKNOWLEDGED` へ理由ごと記録し、
新しい出現だけが報告される形にした。

免除は検査を緩める方向の変更なので、実態から乖離した免除も報告する。
語を宣言から外す・出現を消すのどちらでも免除だけが残るので、両方をテストで pin した。

### 3 種の変異のうち 1 つが素通りしていた

検査機構を足したときの変異は 3 種いる。実際に回したところ、3 つ目で穴が見つかった。

| 変異 | 結果 |
|---|---|
| 検査対象を壊す (母集団へ定義済みの語を素で置く) | 報告された |
| 検査機構を壊す (常に空を返す) | 6 件が赤 |
| 取り付けを外す (`cli.scan()` から 1 行消す) | **全緑のまま素通り** |

3 つ目は実リポジトリで語を置いても検出されない状態を作るのに、テストは 314 件すべて緑だった。
`test_cli.py` へ配線の pin を足して、外すと赤くなることを確認した。

### frontmatter のパースを 1 箇所へ寄せた

`rule_paths` の中にあった YAML パースを `rule_frontmatter` として切り出し、
`rule_defines` からも使う形にした。キーごとに読み方を書くと、壊れた frontmatter の
扱いを片方だけ変えたときに気づけない。

### レビューが見つけた 3 つの「静かに緩む」経路

マージ前のレビューで、いずれも検査が黙って見なくなる形の穴が 3 件見つかった。
3 件とも実装に対して再現してから直した。

| 穴 | 再現した形 | 手当て |
|---|---|---|
| paths の違う別 rules での使用 | 0 件 (報告なし) | 宣言元だけを外す形へ変えた |
| 常時ロードされる rules が宣言した語 | 全出現が偽陽性になる | `is_always_loaded_rule` で対象から外した |
| `defines` の型違い (ブラケット忘れ) | 0 件 (宣言ごと沈黙) | `malformed_defines` で報告する |

もう 1 件、免除の乖離の報告文が「宣言から語が落ちた」場合に偽を言っていた。
語は現に出現しているのに「出現しないので免除を消せ」と指示する形で、
そのとおり直すとその語が完全に無検査になる。原因ごとに文言を分けた。

いちばん厄介だったのは 1 件目で、`test_occurrence_inside_rules_is_not_reported` が
「別の rules での使用は報告しない」を仕様として pin していた。実装のバグより、
誤った仕様が pin されている方が後から直しにくい。

### simplify が見つけた「宣言側の沈黙」

品質レビュー 4 観点のうち 3 つが同じ 1 行を指した。母集団のリーダー `population_files` が
`instruction_refs.source_files` とバイト単位で同一だった。glob だけを共有して読み方は
コピーしており、後者が持つ `git ls-files` との突き合わせ pin はコピー側へ届かない。
このモジュールの docstring が禁じている再宣言を、関数のレベルでやっていた。

宣言側にも沈黙が 2 つ残っていた。どちらも「捨てた事実がどこにも出ない」形で、
型違いの `defines` を直したときと同じ穴が別の場所にあった。

| 沈黙 | 起きること |
|---|---|
| 宣言した語が本文に無い | 綴り違いで、その語はどこで使われても報告されない |
| 常時ロード rules への `defines` | 宣言が黙って捨てられる (定義は届くので検査は不要だが、捨てたことが見えない) |

前者は本文だけを見る必要がある。全文を見ると `defines` の宣言自身に当たり、
「宣言した語が本文にある」が常に成立して検査が vacuous になる。frontmatter を落とす
`rule_body` を `instruction_budget` へ置き、区切りの解釈を `rule_frontmatter` と共有した。

免除の理由文にも誤りが 1 件あった。`references/testing.md` の 2 件を
「testing-practices が名指しする読み先なので rules と同じ文脈でしか読まれない」と
していたが、`CLAUDE.md` → `references/observation.md` → `references/testing.md` という
テストファイルを一度も Read しない到達経路が実在する。testing.md 自身が冒頭で定義元を
名指ししているので免除自体は妥当で、理由の方を実態に合わせた。結果 4 件が同じ理由になり、
同じ事実には同じ文字列を使う形へ揃った。

テストにも同型の重複があった。宣言元の除外を 2 本へ割ったとき、片方が
`test_term_absent_from_population_is_clean` とバイト単位で同一になっていた。
`_rule()` の本文が必ず対象語を含むので、前者は名前が言う状態を作れていない。
pin は 2 本に見えて 1 本ぶんだった。

### 覆っていない範囲

母集団はこのリポジトリ内に閉じている。skill が配布先の CLAUDE.md を参照する形の
越境参照はこの検査からも見えない (上流の ISSUE-25 と同じ位置にある穴)。

照合は本文全体への部分文字列一致で、コードフェンスやインラインコードを区別しない。
語境界は CJK に無いので regex を挟んでも近似の精度は上がらない。誤って報告する側へ
倒れるので免除で吸収できるが、免除表が伸びること自体がこの機構の弱点になる。

免除はファイル単位なので、既に免除したファイルの中で同じ語が新しく使われても無音になる。
出現数を免除へ持たせる案は、正当な編集のたびに数字の更新を要求するので採らなかった。

これら 2 つと、参照グラフから「定義が届く文脈」を機械で出す案は Issue #41 へ切り出した。
