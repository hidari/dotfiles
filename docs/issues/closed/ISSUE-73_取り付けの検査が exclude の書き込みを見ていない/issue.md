# fix: 取り付けの検査が exclude の書き込みを見ていない

## 背景

ISSUE-42 は運用指示の取り付けを 2 つの書き込みで定義した。`.git/info/exclude` への
`.hidari/` と `.cache/` の追記と、`.hidari/private-ops` の symlink である。

`repo-wiring --check` が見ているのは symlink だけである。`is_wired` は symlink である
ことと解決先の一致を見るが、exclude の中身は一度も読まない。したがって
`listed=21 problems=0` は「symlink が 21 本ある」としか言っていない。

## 実測 (2026-09-02、PR #194 のマージ直後)

一覧の 21 リポを全数走査した。

| 検査 | 件数 |
| --- | --- |
| `.git/info/exclude` に `.hidari/` がある | 8 / 21 |
| `.git/info/exclude` に `.cache/` がある | 0 / 21 |
| 両方ある | 0 / 21 |
| exclude が手つかずの既定値 (240 バイト) | 13 / 21 |

240 バイトは新規 `git init` が置く既定の exclude と同一である (対照として新規 init を
作って確認した)。つまり 13 リポでは書き込み経路が一度も走っていない。

同じ時点で `--check` は `listed=21 problems=0` を返す。**検査は 2 つの書き込みのうち
1 つしか見ないのに、緑は「両方できている」に見える。**

実害は現時点では無い。global の `excludesfile` が効いており、21 リポすべてで
`.hidari/` と `.cache/` は実際に ignore され、追跡下への漏れも 0 件である。ただし
二層目を置いた理由は「global は bootstrap が配るので、bootstrap を通していない
マシンでは効かない」ことなので、spec が書いた保証は実際には入っていない。

## この形の危うさ

検査が対象の一部しか見ないとき、失敗は「エラー」ではなく「緑」として返る。しかも
`--check` は母数 (`listed=21`) を出すので、見ていないのではなく見て問題が無かったように
読める。ISSUE-42 の最終レビューでも、この緑を根拠に「21 リポへ適用済み」と報告した。

## 決めること

- 検査を広げる範囲。exclude の 2 パターンだけを見るのか、`check-ignore` で実効を見るのか
  - パターンの存在と ignore の実効は別物である。`.gitignore` の再包含があるとパターンが
    あっても ignore されない。逆に global だけでも ignore は成立する
  - 二層目の存在を確かめたいので、`check-ignore` の実効ではなくパターンの存在を見るのが
    目的に合う。実効だけを見ると global で成立してしまい、二層目の欠落を検出できない
- パターンの一覧を取り付け側と検査側で共有する形
  - 現在は取り付け側にリテラルで 2 つ並んでいる。検査側にも並べると二重管理になる
- 報告の強度。symlink の欠落と同じ `problems` に数えるか

## タスク

- [x] パターンの一覧を取り付け側と検査側で共有する形にする
- [x] `--check` を広げ、変異注入で「exclude を書かない変異」が赤くなることを確かめる
- [x] 21 リポへ `repo-wiring` を流し、`--check` が緑になることで適用を確認する
- [x] ISSUE-42 の spec へ、二層目の適用が検査されるようになったことを追記する

## 決めた結果 (2026-09-02)

**パターンの存在**を見る形にした。実効 (`check-ignore`) は採らない。実効だけを見ると
global の `excludesfile` で成立してしまい、二層目の欠落を検出できないためである。
この差はテストで pin してある。パターン存在の判定を実効判定へ置き換える変異を入れると、
global を用意した 1 件だけが落ちる。global の無い環境では実効判定でも通ってしまうので、
その 1 件が無いと差を測れない。

一覧は `WIRED_DIRS` へ 1 本化した。書く側・実効を確かめる側・二層目の存在を見る側の
3 箇所が同じ集合を使う。probe のパス名を統一できるのは、末尾スラッシュのパターンが
配下のどのパスにも一致するためで、隔離環境で確かめた。

報告は `partial:` として `problems` に数える。symlink があっても二層目が無ければ
spec が書いた保証は入っていないので、`ok` とは区別する。

### 適用の実測

| 時点 | `--check` | `.hidari/` | `.cache/` | 両方 |
| --- | --- | --- | --- | --- |
| 検査を広げる前 | `problems=0` | 8/21 | 0/21 | 0/21 |
| 検査を広げた直後 | `problems=21` | 8/21 | 0/21 | 0/21 |
| 21 リポへ適用後 | `problems=0` | 21/21 | 21/21 | 21/21 |

適用前に 21 リポの exclude を退避してハッシュ台帳を作り、適用後に全数で差分を突き合わせた。
追加されたのは `.hidari/` と `.cache/` だけで、削除された行は 0 件 (21/21 で期待どおり)。
サイズは既定値の 240 バイトから 257 バイトへ 17 バイト増で、追加した 2 行と一致する。

## 関連

ISSUE-42 から派生。二層目 (`.git/info/exclude`) を導入した側で、その適用を検査する層が
欠けていた。

ISSUE-72 とは `--check` の射程を広げる点で隣接するが、方向が違う。あちらは母集団を
一覧の外へ広げる話で、こちらは 1 リポあたりに見る項目を増やす話である。同じ
`--check` を触るので、着手が重なるなら順序を決めること。
