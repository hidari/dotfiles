# fix: 取り付けの検査が exclude の書き込みを見ていない

## 背景

ISSUE-42 は運用指示の取り付けを 2 つの書き込みで定義した。`.git/info/exclude` への
`.hidari/` と `.cache/` の追記と、`.hidari/private-ops` の symlink である。

`repo-wiring --check` が見ているのは symlink だけである。`is_wired` は symlink である
ことと解決先の一致を見るが、exclude の中身は一度も読まない。したがって
`listed=21 problems=0` は「symlink が 21 本ある」としか言っていない。

## 実測 (2026-09-02、PR #194 のマージ直後)

一覧の 21 リポを全数走査した。

| 検査 | 件数 |
| --- | --- |
| `.git/info/exclude` に `.hidari/` がある | 8 / 21 |
| `.git/info/exclude` に `.cache/` がある | 0 / 21 |
| 両方ある | 0 / 21 |
| exclude が手つかずの既定値 (240 バイト) | 13 / 21 |

240 バイトは新規 `git init` が置く既定の exclude と同一である (対照として新規 init を
作って確認した)。つまり 13 リポでは書き込み経路が一度も走っていない。

同じ時点で `--check` は `listed=21 problems=0` を返す。**検査は 2 つの書き込みのうち
1 つしか見ないのに、緑は「両方できている」に見える。**

実害は現時点では無い。global の `excludesfile` が効いており、21 リポすべてで
`.hidari/` と `.cache/` は実際に ignore され、追跡下への漏れも 0 件である。ただし
二層目を置いた理由は「global は bootstrap が配るので、bootstrap を通していない
マシンでは効かない」ことなので、spec が書いた保証は実際には入っていない。

## この形の危うさ

検査が対象の一部しか見ないとき、失敗は「エラー」ではなく「緑」として返る。しかも
`--check` は母数 (`listed=21`) を出すので、見ていないのではなく見て問題が無かったように
読める。ISSUE-42 の最終レビューでも、この緑を根拠に「21 リポへ適用済み」と報告した。

## 決めること

- 検査を広げる範囲。exclude の 2 パターンだけを見るのか、`check-ignore` で実効を見るのか
  - パターンの存在と ignore の実効は別物である。`.gitignore` の再包含があるとパターンが
    あっても ignore されない。逆に global だけでも ignore は成立する
  - 二層目の存在を確かめたいので、`check-ignore` の実効ではなくパターンの存在を見るのが
    目的に合う。実効だけを見ると global で成立してしまい、二層目の欠落を検出できない
- パターンの一覧を取り付け側と検査側で共有する形
  - 現在は取り付け側にリテラルで 2 つ並んでいる。検査側にも並べると二重管理になる
- 報告の強度。symlink の欠落と同じ `problems` に数えるか

## 決めた結果 (2026-09-02)

**`check-ignore -v` が返す出所**を見る形にした。`<file>:<line>:<pattern>\t<path>` の
`<file>` が `.git/info/exclude` か追跡下の `.gitignore` なら合格、global の
`excludesfile` なら不合格とする。

### 3 案を順に試して、2 案が実測で覆った

最初は **パターンの存在**を見る形で実装した。実効 (`check-ignore`) だけを見ると global で
成立してしまい欠落を見逃す、という理由からである。これは反証で 2 方向とも破れた。

偽陽性 (効いているのに `partial`) が 7 形。git は末尾空白と `\r` を落としてから
パターン化し、ルート固定 (`/.hidari/`)、スラッシュ無し (`.hidari`)、グロブ
(`.hidari/*`) も効かせる。`check-ignore -v` の出所はいずれも `.git/info/exclude` である。
バイト単位の照合は git が受ける表記の幅を取りこぼす。

偽陰性 (効いていないのに `ok`) が 2 形。exclude 内の後続の否定 (`!.hidari/`) と、
取り付けた後に置かれた `.gitignore` の再包含である。どちらも `git status` に
`?? .hidari/` が出る、つまり symlink が追跡の射程へ出ている状態で `ok` を返していた。

次に **出所が `.git/info/exclude` か**を見る形へ変えたところ、実地で 21 リポ中 14 リポが
`partial` になった。原因は per-repo の `.gitignore` が先に一致していたことである。
**守りたいのはマシンローカルの設定に依存しないことであって、`exclude` というファイルの
存在ではない。** 追跡下の `.gitignore` は clone したどのマシンでも効くので合格でよい。
判定を「出所が global ではないか」へ直した。

### 一覧の共有

`WIRED_PATTERNS` へ 1 本化した。書く側・取り付け時に実効を確かめる側・`--check` で出所を
見る側が同じ集合を使う。ディレクトリ名ではなく exclude へ書く表記そのものを持つ。名前で
持つと使う側が末尾スラッシュを付け直すことになり、その導出が利用箇所の数だけ増える。

probe のパス名を統一できるのは、末尾スラッシュのパターンが配下のどのパスにも一致する
ためで、隔離環境で確かめた。

### 報告

`partial:` として `problems` に数える。symlink があっても ignore が global 依存なら、
spec が書いた保証は入っていない。

### 変異注入

| 変異 | 落ちるテスト |
| --- | --- |
| 出所の照合を外す | 5 件 (機構そのもの) |
| `.gitignore` を受理しない | **1 件** (14 リポが該当する分岐) |
| `exclude` を受理しない | 7 件 |
| ループを先頭要素だけに | **1 件** |

`.gitignore` を受理する分岐は、追加する前は誰も pin しておらず、消しても全テストが緑で
通った。実地で 14 リポを確認したことはテストの代わりにならない。

### 適用の実測

| 時点 | `--check` の判定 | `problems` | exclude に両方 |
| --- | --- | --- | --- |
| 検査を広げる前 | symlink のみ | 0 | 0/21 |
| パターン存在で判定 | 綴りを照合 | 21 | 0/21 |
| 21 リポへ適用後 (同判定) | 綴りを照合 | 0 | 21/21 |
| 出所が exclude かで判定 | 厳しすぎ | 14 | 21/21 |
| 出所が global でないかで判定 (採用) | — | **0** | 21/21 |

適用前に 21 リポの exclude を退避してハッシュ台帳を作り、適用後に全数で差分を突き合わせた。
追加されたのは `.hidari/` と `.cache/` だけで、削除された行は 0 件 (21/21 で期待どおり)。
サイズは既定値の 240 バイトから 257 バイトへ 17 バイト増で、追加した 2 行と一致する。

独立の検算として、21 リポすべてで `git status --porcelain` に `.hidari` が出ないことを
確認した (0/21)。判定を 3 案のあいだで動かしても、この値は一度も変わっていない。
`--check` の値が案ごとに 0 / 21 / 14 / 0 と動いたのに対し、実際の露出はずっと 0 だった。
**検査の値が動いたのは実態が動いたからではなく、何を測っているかが動いたからである。**
