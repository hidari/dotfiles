# chore(hooks): コマンド単位の暫定告知を畳むか判断する

## 背景

ISSUE-59 で、検査層の沈黙をセッション頭に 1 回告げる層 (`guard-health.py`) ができた。
それ以前から `tirith-check.py` の fail-open 経路が同じ事実をコマンド単位で告げており、
tirith 不在のときは Bash 呼び出しのたびに同じ文が積む。文面自身が「以降のコマンドも同じ
状態です」と書いており、繰り返しであることは認識されている。

ISSUE-59 はこれを畳まずに残す判断をした。理由は本文にある。セッション頭の 1 回で実運用に
足りるかは、実際にセッションをまたいで運用してからでないと判断できない。畳んでから足りないと
分かった場合、コマンド単位の文脈を戻すのは「セッション頭で見落とした」を後から復元する形に
なり、先に畳むより高くつく。

ISSUE-59 の他のタスクは全て完了したので、この 1 件を切り出してあちらを閉じた。

## 判断の材料

### ISSUE-67: 別のフックで 1 セッション 1 回が足りなかった

ISSUE-67 が、**別のフックで「1 セッション 1 回」が実際に足りなかった実例**を持っている。
`handoff-sentinel.py` のコンテキスト閾値通知は 1 セッション 1 回のラッチで、超過を告げた
あとも作業が続いて使用率が伸びたが、二度目は鳴らなかった。

フックは違うが設計上の問いは同じである。「セッション頭の 1 回で足りるか」。少なくとも
handoff-sentinel の側では足りていない。ただし性質が違う点もある。コンテキスト使用率は
時間とともに単調に悪化するのに対し、tirith の不在はセッション中に変化しない事実である。
**悪化しない状態なら 1 回で足りる**という反論が成り立つので、そのまま持ってくることはできない。

### 2026-08-31: 告知で気づけたが、何を止めるかは分からなかった

apm ガードの沈黙を `guard-health.py` がセッション頭で告げ、その告知から原因を追って PATH
snapshot の問題まで辿り着けた。気づく目的では 1 回で足りている。

ただし「沈黙している」ことは伝わったが「それが作業を止める」ことは分からなかった。`apm install`
を実際に打って deny されるまで、告知は状況の説明であって制約の宣言ではないと読んでいた。

この材料も ISSUE-67 と同じ理由でそのまま持ち込めない。apm ガードのコマンド単位の反応は
fail-closed の deny で、tirith のそれは fail-open の通知である。deny は打った時点で目的を
達するが、通知は読み飛ばされうる。**止まるものと素通りするものでは繰り返しの価値が違う。**

また対象そのものが違う。この観察は apm ガードのものであって tirith 不在のものではないので、
タスク 1 が求める証拠には数えていない。

## 判断 (2026-09-01): 畳まず残す

理由は 3 つで、いずれも判断の場で実測して確かめた。tirith 不在の実事象は待っていない。

### 1. 「不在はセッション中に変化しない」が反証された

上の「判断の材料」が ISSUE-67 の類推を退ける唯一の根拠として置いていた前提は誤りである。
ISSUE-56 の実測表は、tirith 自身が実体の `rm -f` / `rm -rf` / `mv` / 実行権限の剥奪をすべて
allow と判定することを記録し、「2 回の許可されるコマンドで検査を沈黙させられる」と結論して
いる。事故 (brew の upgrade やリポジトリの移動) でも同じ遷移が起きる。

悪化しない状態なら 1 回で足りるという反論は、この前提の上にしか立たない。前提が落ちたので
反論も落ちる。

### 2. 2 つの層は測っている時点が違う

`tirith-check.py` は毎回 `guard_resolve.resolve_tirith_bin()` を呼び、その実体は `shutil.which`
である。コマンド単位の告知は Bash 呼び出しごとの連続監視であり、`guard_probes.probe_tirith` は
セッション頭の 1 点測定にあたる。t=0 で健全なら `guard-health.py` は無出力で終わり、次の
SessionStart まで誰も測り直さない。

つまり畳んで減るのは繰り返しではなく被覆する時点で、「セッション中に検査が死ぬ」経路の検出が
丸ごと消える。

### 3. 畳む側が頼る安全網が未実測

`guard-health.py` の docstring と ISSUE-59 の spec は「compact でも発火するので長時間セッション
では再告知が起きる」と書く。matcher は config-guard が静的に pin しているが、実際に compact で
再発火することを見るテストは無く、`test_guard_health.py` は `source="startup"` しか流していない。

ISSUE-67 はまさに「鳴るはずの 2 度目が鳴らなかった」事例である。同型の未実測前提に依存して
先に畳むのは順序が逆になる。

### 証拠待ちをやめる理由

上の 3 点はどれも tirith 不在の発生を待たずに確かめられ、しかも結論を左右する。一方で実事象を
待つ構えには終わりが無い。tirith の不在は事故か意図的な無効化でしか起きないので、待ち続ける
限りこの Issue は永久に open のまま残る。判断できる材料が揃った時点で判断する。

### 判断の根拠に数えなかった観測

セッション頭の告知が subagent の文脈へ届いていない可能性がある。判断の場で走らせた subagent が
「自分の文脈に検査層の健全性の行が無い」と報告し、同時にその subagent の Bash 呼び出しには
PreToolUse 由来の tirith 通知が届いていた。

確かめたのは subagent の自己申告と配線の読みだけである。`handoff-sentinel.py` の `agent_id`
ゲートとの非対称を根拠に挙げる読みもあったが、あの行は `main()` に置かれた全 action 共通の
ガードで SessionStart 固有ではないため根拠にならない。

この軸が確かなら「コマンドを打つ側の agent だけが tirith の沈黙を知らない」ことになり残す判断を
さらに強めるが、未確定なので数えていない。測るなら別 Issue が要る。
