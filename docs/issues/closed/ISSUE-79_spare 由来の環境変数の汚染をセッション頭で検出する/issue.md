# feat(hooks): spare 由来の環境変数の汚染をセッション頭で検出する

## 背景

2026-09-06 に、このリポジトリで起動したセッションの `CLAUDE_CODE_TASK_LIST_ID` が
別プロジェクトの名前になっていた。実測で機序が確定した。

daemon は対話セッションの起動を速くするため `claude bg-spare` プロセスを事前に
ウォームしておき、起動要求が来たときに claim して割り当てる。この spare は
daemon を起こした client の環境変数をそのまま継承する。claim のときに差し替えられる
のは一部だけで、残りは spare を spawn した時点の値のまま残る。

| claim で差し替わる | spare 起動時のまま残る |
| --- | --- |
| 作業ディレクトリ | `CLAUDE_CODE_TASK_LIST_ID` |
| `CLAUDE_JOB_DIR` | `HERDR_WORKSPACE_ID` |
| `CLAUDE_CODE_SESSION_ID` | `HERDR_PANE_ID` |
| `CLAUDE_PID` | `HERDR_TAB_ID` |
| `CLAUDE_CODE_MESSAGING_SOCKET` | `HERDR_STARTUP_CWD` |

事故のセッションの worker は 18:33:08 に spare として spawn され、20:32:40 に claim
された。約 2 時間、別プロジェクトの環境変数を着たまま待機していたことになる。
daemon を起こした client の作業ディレクトリは `daemon.lock` の `spawnedBy.cwd` が
記録しており、実際に別プロジェクトだった。

## このリポジトリ側の導出は正しい

`home/.zshrc` の `_claude_task_list_id` は作業ディレクトリから正しい値を導出し、
ランチャがそれを `command claude` へ渡している。壊れているのは「client が渡した値が
spare の worker へ届かない」という本体側の経路で、導出そのものではない。

したがってこのリポジトリで書けるのは修正ではなく検出である。

## なぜ検出する価値があるか

汚染された値は空でも不正でもなく、実在する別プロジェクトの名前である。タスク管理の
ツールを使うとそのプロジェクトの生きたバックログへ書き込む。事故のセッションでは
70 件を超える他プロジェクトのタスクが提示された。

失敗が例外ではなく、もっともらしい成功として返る形なので、使うまで気づけない。

`HERDR_PANE_ID` の側も、既に閉じられたペインを指すことがある。この場合はエージェントの
状態通知が黙って捨てられ、ユーザーからは動いていないように見える。

## 検出の案

`home/.claude/hooks/guard-health.py` が SessionStart で検査層の沈黙を告げる層を既に
持っている。同じ層へプローブを足すのが素直に見えるが、あの層の責務は「検査層が生きて
いるか」なので、環境変数の整合がそこへ収まるかは判断が要る。

判定そのものは単純で、`_claude_task_list_id` と同じ導出を作業ディレクトリに対して行い、
`CLAUDE_CODE_TASK_LIST_ID` と突き合わせるだけである。ただし導出のロジックがシェル関数側
にあるので、二重実装にしない置き方を決める必要がある。

`HERDR_PANE_ID` は `herdr pane list` に含まれるかで判定できるが、herdr が動いていない
環境でも壊れない形にすること。

## 決めたこと

**`guard-health.py` の層へ足す。**あの層の責務は名前のうえでは「検査層が生きているか」だが、
実体は既にそれより広い。`probe_private_ops` が見ているのは検査層ではなく運用指示の到達で、
「このセッションが正しい前提の上に乗っているか」にあたる。環境変数の整合も同じ側にある。
別フックにすると告知が 2 通に割れ、systemMessage と additionalContext の両方へ載せる同じ
出力ロジックを 2 実装持つことになる。

**導出は Python 側で書き、シェルとの同値性を対照テストで pin する。**ただしリポジトリルートの
解決そのものは `hook_git.py` へ出し、`handoff-sentinel.py` と共有した。

ルート導出は着手時に 4 実装あった。`home/.zshrc` と `home/.claude/statusline-command.sh` と
`handoff-sentinel.py` と `apm-install-guard.py` である (最初に数えたときは 4 つ目を見落として
3 と書いていた。レビューの指摘で数え直した)。素直に書くと 5 つ目になる。

寄せたのは `handoff-sentinel.py` の 1 つだけである。`apm-install-guard.py` は `GIT_` 接頭辞ごと
落として fail-closed に倒す方針を理由つきで選んでおり、失敗の返し方が違うので寄せる対象では
ない。シェル側の 2 つは Issue 12 の領分なので触っていない。

シェルと Python のあいだは寄せられないので、同じディレクトリに対して両者が同じ値を返すことを
`scripts/tests/zshrc-claude.bats` の対照が pin する。片方だけ変えると、正しいセッションを汚染と
報告するか汚染を見逃すかのどちらかになり、どちらも実行はされているのに間違った答えを返す形なので
この対照でしか境目が作れない。

**`HERDR_PANE_ID` の実在検査は含める。**未設定と herdr 不在は対象外として通す。herdr を使わない
環境で常に鳴らすと、この層の出力そのものが読まれなくなる。あるのに応答しないのは対象外ではない
ので沈黙として扱う (tirith プローブと同じ扱い)。

## 検証 (2026-09-06)

変異注入は 14 種すべて赤で生存 0。1 件だけ最初に生き残ったのは、herdr の終了コードを見る分岐を
壊す変異である。検体が読めない応答を返していたため、終了コードを無視しても後段のパースが同じ
`healthy=False` を返して変異が下流に吸収されていた。検体を「一覧として読めて pane も載っている
が終了コードだけ非 0」へ変えて、その分岐だけが判定を決める形にした。

変異が赤いことは分岐が本番で到達可能であることを示さないので、実 herdr と実環境変数に対する
live smoke も通した。汚染していないセッションでは全プローブが沈黙し、`CLAUDE_CODE_TASK_LIST_ID`
を別プロジェクトの名前へ差し替えると宣言値と導出値の両方を添えて告げ、`HERDR_PANE_ID` を実在
しないペインへ差し替えると告げる。`CLAUDE_PROJECT_DIR` を落とした経路も沈黙する。
