# feat(hooks): レートリミットの逼迫で handoff を促す

## 背景

セッションがレートリミットで強制終了すると、引き継ぎもメモリも書けないまま文脈が失われる。
実際に 2026-09-05、週次リミットに当たった前セッションが handoff を書けずに落ち、次の
セッションが `.cache/` の残骸と git の状態から状況を復元している。

`home/.claude/hooks/handoff-sentinel.py` は既に 2 つの契機で引き継ぎを促す。推定コンテキスト
使用率と、ツール呼び出しの破損回数である。どちらもリミットを見ていない。

## 実測 (2026-09-05、Claude Code 2.1.261)

### hook はレートリミットを独立に取得できない

hook の入力にレートリミットは無い。共通スキーマが持つのは `session_id` / `transcript_path` /
`cwd` / `prompt_id` / `permission_mode` / `agent_id` / `agent_type` / `effort` だけである。
transcript にも永続化されておらず、`usage` は token 数しか持たない。Notification イベントの
型に quota 系はあるが、いずれもリミット到達後の自動再開用で接近の通知ではない。

ネットワークを介さないローカルの取得元は statusLine の stdin だけだった。したがって
「statusline が書き、hook が読む」以外の配線は取れない。これは案の比較ではなく構造的な制約。

### statusLine の stdin が渡してくる形

```json
"rate_limits": {
  "five_hour": { "used_percentage": 0,  "resets_at": 1788649800 },
  "seven_day": { "used_percentage": 20, "resets_at": 1788908400 }
}
```

型定義と実際の出力が食い違う。バイナリ内の schema は `utilization` (0-100) と `resets_at`
(ISO 8601 文字列) を宣言するが、実際に届くのは `used_percentage` と epoch 秒である。schema を
読んで実装すると動かない。

`rate_limits_available` は stdin に存在しない。`jq` で問い合わせると `null` が返るが、これは
値ではなくキーの不在である。欠落の判定には `rate_limits` と対象窓キーの有無を使う。

### 現行の statusline は本体の値を使わず、失効した窓を表示する

`home/.claude/statusline-command.sh` は stdin の `rate_limits` を読まない。Keychain から
OAuth トークンを取り出し Haiku へ `max_tokens=1` を投げ、応答ヘッダ
`anthropic-ratelimit-unified-5h-utilization` を読んで 360 秒キャッシュしている。

同一時刻・同一アカウントで両者を並べると値が食い違う。

| | 本体の値 | プローブの値 |
| --- | --- | --- |
| 5h 使用率 | 0% | 49% |
| 5h リセット | 23:10 UTC | 18:10 UTC |

観測時刻は 18:12 UTC。プローブは 18:07 に旧窓の値を書き、TTL は 18:13 まで有効だった。
つまり 18:10 のリセットから 3 分間、失効した窓の 49% を出し続けていた。

本体側は `resets_at <= now` の窓を落とすため、窓跨ぎでは古い高い値ではなく欠落を返す。
閾値判定にとってこの差は決定的で、プローブを使うとリセットで圧が下がった瞬間に発火する。

### 2 経路でスケールが 100 倍違う

真の使用率 20% が経路ごとにこう表現される。

| 経路 | 表現 | スケール | 型 |
| --- | --- | --- | --- |
| statusLine stdin | `20` | 0-100 | number |
| プローブキャッシュ | `"0.2"` | 0.0-1.0 | string |

取り違えると「常時発火」か「絶対に発火しない」のどちらかになる。どちらも例外を出さずに
成立するので、CI では捕まらない。

### 値が欠ける条件

- 窓が失効したとき (本体が落とす)
- セッション開始直後の初回 API 応答前
- headless (`claude -p`) では statusLine 自体が実行されない
- API key / Bedrock / Vertex / サブスクリプション無しでは `rate_limits` 全体が欠落

後ろの 3 つはバイナリ由来で live 未再現。断定ではなく設計前提として扱う。

### 鮮度

アイドル中は statusline が起動しない。`statusLine.refreshInterval` が未設定のため定期タイマは
張られず、会話メッセージの更新イベント (300ms デバウンス) と reset 時刻の 1 回起床だけになる。
5 分間のポーリングで spawn 0 回を実測した。

ただしリミットは消費すれば増えるものなので、アイドル中は値も動かない。並列セッションが消費
する場合はずれるが、その間このセッションは引き継ぎを要さない。稼働中は毎ターン更新される。

## 決めたこと

取得元は本体の `rate_limits` にする。Haiku プローブは撤去する。根拠は上の実測 3 点。

- 本体は失効した窓を落とすので、窓跨ぎで古い高い値を返さない
- スケールが 0-100 でそのまま閾値と比較でき、変換を挟まない
- プローブは推論リクエストなので、リミットを測るためにリミットを消費している

## 決めたこと (実装で確定)

### 監視する窓

`five_hour` と `seven_day` で足りるか。schema は `seven_day_opus` / `seven_day_sonnet` /
`model_scoped[]` も宣言しており、表示名はそれぞれ Opus limit / Sonnet limit / Fable limit で
ある。実測した stdin には `five_hour` と `seven_day` しか来ていないが、これが「この環境に該当
枠が無い」のか「その時点で出ていないだけ」なのかは未確定。Opus を常用しているなら、先に枯れる
のが `seven_day` とは限らない。

決めた: 監視対象を名指しで持たず、届いた窓を全部走査する。未確定を解く必要がそもそも無くなる。
名指しにすると、サーバが新しい窓を出したときに静かに見落とす。`model_scoped[]` は配列で形が
違うため初版では見ない。

### 再武装の契機

ISSUE-67 が指摘するとおり `_notify_once` は 1 セッション 1 回のラッチで、一度鳴ると二度と
鳴らない。同じ機構で 2 段の閾値を足すと同型の欠陥が増える。

決めた: state を 1 セッション 1 ファイルの JSON にし、`窓名:段` をキー、発火時の `resets_at` を
値として持つ。次に読んだ `resets_at` が違えば別の窓なので鳴り直す。窓ごとにファイルを増やす形は
採らなかった。ISSUE-67 が挙げる「消えない state」を悪化させるため。

### 欠落時の扱い

決めた: 欠落を 0% と読まず、判定不能として飛ばす。窓が失効している場合も落とす。本体は
`resets_at` を過ぎた窓を落として渡すが、キャッシュから読み直す経路では過ぎた窓が残るため、
読む側でも落とす。

### アカウントタグの導出をどこに置くか

キャッシュはアカウントごとに分ける必要がある。分けないと 2 アカウントが同じファイルを潰し合う。
導出規則 (既定の設定ディレクトリは `default`、それ以外は絶対パスの sha256 先頭 8 桁) は現在
statusline だけが持つが、案の採用で hook 側にも同じ導出が要る。shell と Python で言語が違う
ため、素直に書くと二重実装になる。

決めた: 二重実装を許容し、代わりに一致を end-to-end で pin する。statusline が書いたキャッシュを
フックが読んで発火するところまでを 1 つの bats で通し、どちらかの導出がずれたら赤くなるように
した。片側だけのテストではこのずれを検出できず、ずれた結果は「エラーではなく無言」で返る。
言語をまたぐ導出の共有そのものは Issue 26 の集約対象。
