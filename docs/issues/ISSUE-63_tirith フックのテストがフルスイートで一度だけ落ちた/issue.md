# fix(test): tirith フックのテストがフルスイートで一度だけ落ちた

## 背景

`scripts/claude-hooks/tests/test_tirith_hook.py::test_tirith_prefixed_variables_are_not_forwarded`
が、フルスイート実行 1 回で失敗した。PR #183 の作業中 (2026-08-28)。

**再現していない。** この Issue は原因の特定ではなく、観測を失わないために立てる。次に同じ
失敗を見たときに、ゼロから調べ直さないで済むようにする。

## 観測できたこと

| 項目 | 値 |
| --- | --- |
| 失敗したのは | フルスイート実行 1 回 |
| そのときの所要時間 | 43.59 秒 |
| 通常の所要時間 | 15〜20 秒 |
| 失敗の形 | assert (エラーや例外ではない) |
| 単独実行 | 緑 |
| その後のフルスイート | 5 回連続で緑 |

失敗した回の直前は、同じコマンド内で pytest を 3 回連続で起動し、そのあいだにファイルの
コピーを挟んでいた。マシンの負荷が高かった可能性がある。所要時間が通常の 2.4 倍だったのは
それと整合する。

**負荷が原因だと確かめてはいない。** 所要時間と失敗が同じ回に起きたという相関だけである。

## 手掛かり

テスト自身が race を既知として記述している。

```
# hook-event の fire-and-forget が同じファイルを上書きする race を避けるため check に絞る
```

fake tirith は `[ "$1" = check ]` のときだけ `$ENV_LOG` へ書く。`_hook_event` は Popen による
fire-and-forget で、`hook-event` を第 1 引数に渡すので書き込まない。この防御は成立している
ように読める (`&&` の右辺にリダイレクトが付くので、条件が偽なら何も書かない)。

したがって同じファイルへの上書きとは別の経路を疑う必要がある。負荷が効くとしたら、フックが
`check` サブプロセスに掛けている timeout (既定 10 秒) を超えて `TimeoutExpired` になり、
fake が書き込む前に kill される経路が考えられる。その場合フックは fail-closed へ倒れ、
`$ENV_LOG` は空か不在になり、`forwarded == ["TIRITH_INTEGRATION=claude-code"]` が外れる。
**これは仮説であって、確かめていない。**
