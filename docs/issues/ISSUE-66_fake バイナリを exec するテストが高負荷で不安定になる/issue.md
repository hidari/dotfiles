# test(hooks): fake バイナリを exec するテストが高負荷で不安定になる

## 背景

ISSUE-59 の作業中、claude-hooks のテストが同一コミットに対して緑と赤を行き来した。
2026-08-31 に 3 回観測している。いずれも並列 subagent を 6 本走らせている最中で、負荷が落ち着くと同じコミットが安定して緑になる。

赤くなったのは次の 2 件で、どちらも fake の tirith スクリプトを一時ディレクトリへ書いて実行するテストである。

- `test_tirith_が_clean_へ応答すれば健全` (`scripts/claude-hooks/tests/test_guard_probes.py`、ISSUE-59 で追加)
- `test_clean_command_allows_silently` (`scripts/claude-hooks/tests/test_tirith_hook.py`、既存で main から変更なし)

失敗時の文面は `tirith: check timed out — blocked for safety` で、壁時計のタイムアウトに当たっている。`probe_tirith` の上限は 5 秒、tirith-check.py 側は既定 10 秒である。
即座に終了する fake スクリプトがこの上限を超えるのは、実行そのものではなく起動が遅れていることを意味する。

## 機序の見立て (未確定)

失敗した時間帯に `ps` を取ったところ `syspolicyd` が CPU 83.8% を占めていた。macOS が実行ファイルの署名・ポリシーを評価するデーモンで、新規に作成された実行ファイルを exec するたびに評価が走る。これらのテストはテストごとに新しいスクリプトを書いて実行するため、評価の対象が毎回「初見のファイル」になる。

この見立てはまだ相関でしかない。同時刻に無関係な cargo のビルドも走っており、`syspolicyd` の負荷をテストへ帰属させる対照実験はしていない。着手時には機序の確定から始めること。見立てが外れていると、手当ての方向 (fake の作り方を変える) ごと外れる。

### 2026-09-26 の観測

ISSUE-106 の着手前ゲートで同じ形を踏んだ。別のリポジトリのセッションがテストを回している最中で、`syspolicyd` が CPU 48〜63%、`XprotectService` が67%を占めていた。この repo の側では subagent を走らせていない。

- 落ちたテストは回すたびに入れ替わった。1回目は `test_guard_probes.py` の9件 (偽 tirith 1件と偽 herdr 8件)、単独で回し直すと8件、pre-commit 経由の2回は `test_guard_probes.py` の5件と `test_tirith_hook.py` の10件で、どれも偽バイナリの起動が上限の5秒を超えた形だった
- 起動の遅れを直接測った (`#!/bin/sh` と `exit 0` だけのスクリプトを新しく書いて exec する)。新しいファイルの初回は0.12〜1.4秒で、1回だけ41.8秒かかった。同じファイルの2回目は6〜33ms、`/bin/sh -c` の直接起動も6〜30msだった
- 混雑が引いたあとは `test_guard_probes.py` の43件が4.33秒で全部緑になった (混雑中は68秒)

「実行ではなく、新しい実行ファイルの初回の起動が遅れる」ところまでは、同じファイルの2回目を対照に置いて確かめられた。一方で、遅れの原因が `syspolicyd` か `XprotectService` か、負荷を制御した対照はまだ取っていない。

### 2026-09-29 の観測

混雑していない時間帯でも、新しい実行ファイルの初回の起動には毎回約0.3秒かかる。中身の違う `#!/bin/sh` のスクリプトを5本書いて測ると、初回は中央値333ms (330〜381ms)、同じファイルの2回目は中央値14ms、`/bin/sh -c` の対照は中央値10msだった。測った直後の `ps` では、`XprotectService` が CPU 56.6%を占め、`syspolicyd` は上位に出ていなかった。これも相関で、機序の確定にはならない。

同じ形のテストは claude-hooks の外にもある。backup-tool の `tests/conftest.py` の `fake_command` (2026-09-29 に足した) と、node-security-notifier の `test_notify.py` の偽 osascript で、どちらもテストごとに新しい実行ファイルを書く (2026-10-22 追記: 後者は ISSUE-131 で通知の経路ごと外したので、今は backup-tool だけ)。backup-tool では、111件のスイートが4.35秒かかり、時間の上位8本 (1本0.16〜0.61秒) はすべて偽コマンドを使うテストだった。backup-tool の src は subprocess に timeout を持たないので、遅れで赤くはならず、時間だけがかかる。

手当ての候補のうち「fake をテストごとに作り直さない形」について、マージ前のレビューの委譲先が次の形を測っている (自分では再現していない)。session スコープで固定のラッパーを1本だけ作り (`#!/bin/sh` と `. "$FAKE_BODY_DIR/${0##*/}"`)、テストごとにはラッパーへの symlink と、実行権限を持たない本文のファイルを置く。初回だけ約300msかかり、その後は1回あたり8〜12msだった。プロダクトの subprocess 呼び出しが `env=` を渡していないことが、この形の前提になる。

### 受け箱から届いた別の原因の候補 (2026-10-22)

他のリポジトリのセッションから、新しい実行ファイルの初回の起動が遅れる原因として、syspolicyd と XprotectService の負荷のほかに次の2つが届いた。どちらも報告者の実測で、dotfiles では再現していない。

- Homebrew の ad-hoc 署名のターミナルのホスト (端末多重化のアプリなど) を brew で上げると、システム設定の「デベロッパツール」の一覧ではオンのまま見えるのに、今の版には許可が効かなくなる。その配下で起動する新しい実行ファイルは毎回検査を受け、回線が不安定なときは1回の起動が数十秒止まる (`sample` で `_dyld_start` のまま)。新しい実行ファイル10個の初回起動は、そのホストの配下で48.5秒、`open -a Terminal <.command>` の配下で0.28秒だった。今の版のバイナリ (Cellar のパス) を一覧に足し直すと、再起動なしで3.7秒まで下がった。ローカルネットワークの許可も同じ仕組みで外れる
- VPN クライアントの脅威保護 (Endpoint Security 拡張) が初回の実行を検査し、作りたての実行ファイルを起動するテストが30秒のタイムアウトで落ちた。エラー文言は「実行できない」で原因を指さなかった。mktemp のディレクトリに小さいスクリプトを置き、初回と2回目の実行時間を比べると切り分けられる。保護を OFF にすると緑に戻った

あわせて、変更と無関係なテストがまとめてタイムアウトしたら、まず `uptime` の load average を見るという報告もあった (別のプロセスで load 74 のとき。単独で回し直すと全件緑)。

dotfiles で確かめたこと (2026-10-22): PR #275 の着手後ゲートで `scripts/tests/bootstrap.bats` の1件が status 非0で落ちた。直後の `uptime` の1分平均は80.33で、単体3回・ファイル全体2回・スイート全体1回の再実行はすべて緑だった。これが偽バイナリの初回起動の遅れによるものかは確かめていない。

報告者の提案 (未検証): brew で ad-hoc 署名のホストを上げたら、デベロッパツールとローカルネットワークの許可を今の版で足し直す手順を、上げる操作の側 (brew の post-install の案内か、dotfiles の更新スクリプトの警告) に組み込む。署名付きの配布物があればそちらへ寄せると、版ごとに外れる問題自体が消える。

### 2026-10-30 の変化

ISSUE-139 で `guard_probes.py` の `herdr-ids` プローブとそのテストを撤去した。最後のタスクで読み替え先にしていた `test_guard_probes.py` の偽 herdr は、もう無い。代わりに同じ ISSUE-139 で、config-guard の `test_herdr_app_keys.py` と `test_cli.py` に偽 `herdr-app` を起動するテストが入った。成功を測るテストは上限を120秒へ緩め、時間切れを測るテストは上限を0.001秒にしているので、起動の遅れで赤くなる形は持たない。遅れは時間としてだけ出る。

## 実害の範囲

- CI で観測されたことは無い。CI は subagent を並列で走らせないので、同じ負荷はかからない
- ローカルでは、この repo の品質ゲートが並列レビューを既定にしているため、今後も同じ状況が繰り返し起きる。マージ直前の検証で赤が出ると、原因がコードか環境かをログまで読まないと判別できない
- 別のリポジトリで並行して走るセッションの負荷でも起きる (2026-09-26)。コミット時の pre-commit も同じテストを回すので、混雑しているあいだはコミットも落ちる
