# chore: pre-commit と gitleaks を残りのリポジトリへ展開する

## 背景

ISSUE-64 が 2 リポジトリ (relay / studio) へ pre-commit と gitleaks を入れ、取り付けの形を
確立した。着手時に「まず 2 リポジトリで形を作る」という裁定があり、残りへの展開はそこから
切り出してある。

秘密の混入を止める層が入っていないリポジトリが残っている状態そのものが、この Issue の
対象にあたる。非公開であることは 1 層目で、gitleaks は 2 層目である。

## 母集団

取り付け対象の一覧は `scripts/repo-wiring/repo-wiring` が `--check` で突き合わせる
運用ファイルが持つ。件数はそこを数え直すこと。この Issue の起票時点では 38 だったが、
一覧は運用の中で増減するので、着手時の値を根拠にしないこと。

一覧に載っているかと、実際に取り付いているかは別の問いである。後者を見る層は ISSUE-53 が、
一覧と実態の突き合わせは ISSUE-72 が扱う。この Issue は取り付ける作業そのものを持つ。

**母集団は 2 つある。**上の一覧と、開発機の作業ディレクトリ直下にある実リポジトリで、
両者は一致しない。ISSUE-53 と ISSUE-72 の実測は後者を母数に取っており、その値は 28 だった。
起票時点でこの Issue が挙げた 38 は前者の値である。どちらを数えたかを書かずに件数を比べると、
差分が「取り付け漏れ」にも「一覧漏れ」にも見えるので、判定が両方向へ壊れる。

## 形は 2 つある (どちらも正しい)

ISSUE-64 の裁定で、provisioning はリポジトリの既定に従わせることになった。

| 形 | 供給 | 起動 | 採る条件 |
| --- | --- | --- | --- |
| mise 形 | mise.toml の pin | `mise exec -- gitleaks` | repo 内の既定が mise で、他のツールも同じ経路を通っている |
| brew 形 | Homebrew | PATH 直起動 | mise を使っていない |

揃えるのは `.gitleaks.toml` の検出集合であって起動経路ではない。dotfiles の
`.gitleaks.toml` が canonical で、各リポジトリにはバイト単位で同一の写しを置く。

## 展開で毎回踏むもの

ISSUE-64 の 2 リポジトリで両方とも踏んだので、手順に含めること。

1. `core.hooksPath` が設定されていると `pre-commit install` は取り付けに失敗するのに、
   コミット自体は成功する。検査が一度も走らないまま緑が続くので、`--all-files` の緑を
   取り付けの根拠にしない
2. 旧手順がドキュメントに残っていると、clone した側がそれを踏んで同じ状態を再現する。
   設定ファイルだけでなく README や CLAUDE.md も対象に入れる
3. 既存の git hook が持っていた検査は全経路を移す。1 つ落ちても静かに走らなくなるだけで、
   何も報告されない
4. `stages` を書かない hook は `default_stages` に載り、その既定は全 stage である。
   宣言しないと commit-msg と pre-push でも同じ hook が起動し、分オーダーの検査が
   コミット 1 回につき 2 度走る。エラーではなく待ち時間として返るので気づきにくい。
   `default_stages: [pre-commit]` を置けば塞がり、`stages` を明示した hook と upstream の
   manifest 宣言は影響を受けないので検査の網は減らない (pre-commit 4.6.1 で実測)

## 決めること

### 一括で回すか、リポジトリごとに判断するか

一覧にあるリポジトリを 1 つずつ手で見るのは重い (件数は「母集団」節が指す運用ファイルを
着手時に数え直すこと)。一方で mise 形と brew 形の判別、既存 hook の
有無と中身、取り付け経路の所在はリポジトリごとに違う。

自動化するなら、判別と適用を分けて、適用の前に人が形を確認する形が要る。ISSUE-53 が
作る層が判別の材料を出せるなら、そこへ乗せられる。

### 既存履歴の走査をどこまでやるか

ISSUE-64 では取り付け前に両リポジトリの全 ref を gitleaks で走査した。検出があれば扱いを
決めてから取り付ける方針で、実際には偽陽性 2 件だけだった。

`--staged` は差分しか見ないので、既存違反は取り付けの障害にならない。走査は「取り付けた
瞬間に赤くなるか」ではなく「過去に漏れているか」を見るために要る。件数が多いリポジトリで
どこまでやるかを決める。
