# docs: リポジトリと作業ディレクトリの改名の手順をまとめる

## 背景

2026-10-31に受け箱から仕分けた報告で起票した。別のリポジトリのセッションが、GitHub のリポジトリと手元の作業ディレクトリを改名した記録である。dotfiles では確かめていない。改名の手順はどこにもまとまっておらず、リポジトリごとに移行の手順を組み直している。下は報告を手順の観点で分けたもの。

### GitHub 側

- `gh repo rename` は auto mode の classifier に共有リソースの変更として止められた。ユーザーに `!` で打ってもらう必要がある (実測)
- 改名の直後でも、remote を新しい名前へ向け直せば、push、PR の作成、PR の CI、squash merge が新しい名前でそのまま通った (実測)
- Direct Upload でデプロイする構成は、配信側がリポジトリ名を知らないので改名の影響を受けない。workflow が `GITHUB_REPOSITORY` や `github.repository` を使っていないことは grep で確かめた (実測)

### 作業ディレクトリ

- 作業ディレクトリはセッションの中では動かせない。理由は ISSUE-130 の「作業ディレクトリを動かすと届け先が消える」節にある。移動先で引き継ぎ書が注入されなくなる件は ISSUE-84 の「4つ目の経路: 作業ディレクトリの移動」節にある
- 報告者の提案: repo-wiring に、作業ディレクトリの改名 (一覧の行の差し替え、共有の projects 配下のメモリの移動、`--check`) をまとめて行うサブコマンドを足せば、リポジトリごとに移行のスクリプトを書かずに済む。セッションの外で実行する前提を明記する (推測)

### 取り付け対象の一覧

- repo-wiring の一覧の書き換えは、該当する行がちょうど1行あることと移動先の行が無いことを先に確かめ、名前順の位置へ差し替えたものを diff で dry run してから適用した (実測)

### メモリとセッション記録

- 2つのアカウントの設定ディレクトリの `projects` が同じ共有先への symlink なので、作業ディレクトリの改名に伴うメモリとセッション記録の移動は `mv` 1回で済んだ (実測)。共有の仕組みは ISSUE-49 で入れた

### 旧名の洗い出し

- 旧名の残りを `<owner>/<旧名>` の形だけで grep したら、見出しや skill の説明文にある単独の旧名を見落とし、並列のコードレビューが拾った。洗い出しでは旧名を単語として探す grep も並べる (実測)
- 手順書の GitHub の URL を新しい名前へ書き直すより、名前を書かない手順の文にする方がよい。旧 URL はリダイレクトで届くので、リンクの検査では古い記述に気づけない (実測。レビューの指摘を採用した)

### Claude Code の設定

- `~/.claude.json` の `projects` は作業ディレクトリの絶対パスをキーに持つので、改名すると信頼の確認がやり直しになる。並行するセッションが同じファイルを書くので、機械的な書き換えは避ける (推測)

## タスク

- [ ] 改名の手順の置き場を決める (README、references、skill のどれか)。上の観点ごとに、手順と確かめ方を書く
- [ ] repo-wiring に改名のサブコマンドを足すかを決める。足すなら、セッションの外で実行することをどう守らせるかも決める
- [ ] 手順に、移動先での handoff-sentinel の record の打ち直しを含めるかを ISSUE-84 と合わせて決める

## 関連

- ISSUE-72: 取り付け済みだが一覧に無いリポを棚卸しで検出する。改名で一覧と実体がずれたときに拾う側
- ISSUE-49 (closed): 複数 Anthropic アカウント間でメモリを共有する。メモリの移動が1回で済む前提を作った
- ISSUE-130: セッション中に作業ディレクトリを動かすと outbox の届け先が消える件を持つ
- ISSUE-84: 作業ディレクトリの移動で引き継ぎ書が注入されなくなる件を持つ
