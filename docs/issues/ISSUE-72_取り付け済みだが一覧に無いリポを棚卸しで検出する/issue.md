# feat: 取り付け済みだが一覧に無いリポを棚卸しで検出する

## 背景

ISSUE-42 の spec は運用指示の棚卸しを 4 象限で定義した。

| 一覧に載っている | `.hidari/` の状態 | 棚卸し |
| --- | --- | --- |
| はい | 揃っている | 無言 |
| はい | 欠けている | 報告 (取り付けの欠落) |
| いいえ | 無い | 無言 (意図的に対象外) |
| いいえ | 揃っている | 報告 (一覧が古い) |

実装されたのは上 2 つだけである。`repo-wiring --check` は一覧の行を舐めるだけで、
一覧に載っていないリポを見るための母集団を持たない。取り付け済みなのに一覧から漏れた
リポには完全に沈黙する。

沈黙する側の失敗は静かで、しかも自己修復しない。一覧は「対象かどうか」の意図を持つ
唯一の場所なので、そこから漏れたリポは棚卸しの視界に永久に入らない。取り付け自体は
効いているため運用指示は載り続け、人が気づく契機も無い。

ISSUE-42 ではこの象限を実装せず、spec へ訂正 7 として記録した。理由は、実装に
「マシン上の全リポ」という新しい母集団が要り、ISSUE-42 自身が置いた「新しく増える
機構は 2 つに収まる」予算を超えるためである。

## 決めること

- 母集団をどう得るか。走査ルートの既定値をどこに置くか
  - ISSUE-42 は一覧を `$HOME` 相対へ寄せ、`--ops` を実行時導出にして、出力と起動
    コマンドの両方から絶対パスを消した (訂正 5・6)。走査ルートを絶対パスで受ける
    形にすると、その露出面が再び開く
  - 走査の深さをどこで止めるか。作業ディレクトリ直下だけを見るのか、入れ子も追うのか
- 「意図的に対象外」との区別をどう保つか
  - 4 象限の 3 つ目 (いいえ × 無い) は無言でなければならない。休眠や archive のリポで
    鳴ると、直せない赤が常時点灯し、赤を無視する訓練になる
- 報告の強度。`problems` に数えて exit 1 にするのか、警告として数えないのか
  - 一覧が古いことは取り付けの欠落と違って実害が無い。同じ強度で報告すると、
    直さなくてよい赤で `--check` の緑が失われる

- [ ] 「意図的に対象外」を無言に保つ機構を決める
- [ ] 報告の強度を決め、`--check` の終了コードとの関係を定める
- [ ] 実装とテスト (4 象限すべてに対照を置く)

## 関連

ISSUE-42 の spec 訂正 7 から切り出した派生。

ISSUE-53 とは扱う対象が違う (あちらは配布物の写しの drift) が、「開発機にある全リポの
母集団を得る」という前提を共有している。あちらの実測も作業ディレクトリ直下の 28 リポを
母数に取っており、母集団の得かたを片方だけで決めると二重実装になる。先に着手した側が
決めた形を、もう一方が使えるようにすること。

ISSUE-73 とは同じ `--check` を触るが方向が違う。こちらは母集団を一覧の外へ広げる話で、
あちらは 1 リポあたりに見る項目を増やす話である。着手が重なるなら順序を決めること。
