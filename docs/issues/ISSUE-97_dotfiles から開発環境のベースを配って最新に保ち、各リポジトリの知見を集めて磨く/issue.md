# feat: dotfiles から開発環境のベースを配って最新に保ち、各リポジトリの知見を集めて磨く

## 背景

ユーザーの構想。dotfiles がローカル開発環境のベース (skill / plugin / rules / CLAUDE.md / hooks / 検査の設定) を各リポジトリへ配り、最新に保つ。逆向きに、各リポジトリで得たプラクティスを集めて一般化し、ベースを磨く。

### 今の配布の経路

| 経路 | 配るもの | 届き方 |
| --- | --- | --- |
| apm (agentic-coding-tools から) | skill / plugin | deploy 先はホーム直下の 1 箇所で、全リポジトリへ同時に届く (上流 ISSUE-22) |
| symlink (dotfiles から) | hooks / settings / CLAUDE.md / rules | 同じく全リポジトリ共通 |
| リポジトリごとの写し | PUBLIC へ置く `.gitleaks.toml` と pre-commit の設定 (ISSUE-86。PRIVATE には既定ルールだけの設定を置く)、in-repo Issue の template と採番スクリプト、issue-scoped-artifacts の hook block | 写した時点で止まる |
| GitHub の設定 (計画中) | ruleset (ISSUE-50) | dotfiles の汎用定義を API で各リポジトリへ適用する |

### 鮮度が落ちても誰も告げない

apm の pin が上流から遅れた実例 (2026-09-17) は ISSUE-101 へ切り出した。写しの側の drift は ISSUE-53 の実測がある (旧版のまま残る写しと、宣言そのものが無い配布先)。

dotfiles 自身の in-repo Issue の template も、`## 関連` の案内文が上流の template と食い違ったまま残っていた。このファイルが最後に変わったのは PR 23 のときで、2026-10-20に別の作業でテンプレートを開いたときに気づいて揃えた。検査が無いので、写した側を読み比べるまで誰も気づかない。

## 試験: 仕分けの一次選別に Jev を使えるか (2026-09-30時点のスナップショット)

仕分けの工程のうち、主張と証拠の照合と、候補と既存規範の重複判定を、TypeSafe の Jev (確率を返す分類器、API を直に呼んだ) に一次選別させられるかを測った。期待値と合否の基準は API を呼ぶ前に固定した。

### 条件

- 送ったのは追跡下の公開済みファイル (home/.claude/rules/ の rust-practices.md と testing-practices.md、home/.claude/CLAUDE.md) と、ISSUE-89 に書かれた主張と候補の文面と、対照の主張だけ。非公開リポジトリの材料は使っていない
- 質問はどちらも choice。主張と証拠の照合は supports / contradicts / says_nothing の3択、重複判定は既存の項目の本文と none の中から選ばせた
- state と主張は日本語のまま、質問文と選択肢の説明だけを英語と日本語の2通りにした。各3回、平均の確率で判定し、平均の confidence が0.8以上なら自動採用、未満なら人へ回すとした
- 採点した項目は25件 (照合17件、重複判定8件)。うち実物の項目は9件 (ISSUE-89 の主張と候補が8件、PR 243 で直した古い参照が1件) で、残りの16件は真・偽・無関係の対照として作るか、既存の文から採った
- 24回の呼び出しで入力は約16万トークン、費用は1セント未満。モデルは jev-1.13.0

### 結果

- 事前に決めた基準では、日本語の質問文が合格、英語の質問文が不合格になった。ただし差は1件で、同じ誤答の confidence が0.82と0.79に分かれて閾値をまたいだだけなので、言語の差とは読めない
- 対照の16件はすべて自動採用で正解し、confidence は0.97以上だった。自動採用で正解した割合 (84〜88%。選んだ答えだけなら92〜96%) はこれに支えられている
- 実物の9件では、英語の質問文で自動採用の正解が6件、人へ回ったのが2件、誤答のまま自動採用が1件だった。日本語の質問文では自動採用の正解が5件、人へ回ったのが4件で、そのうち1件は誤った選択が閾値すれすれで人へ回ったもの
- 選択を誤ったのは2件で、どちらも隣り合う量を入れ替えた主張 (再コンパイルと再リンクの量を実行時間と言う、テストケース数を実行されたテストの ID 集合と言う) を supports と読んだ。前者は英語の質問文で3回とも supports だったが confidence が0.18まで落ち、日本語の質問文では3回中1回が supports で、どちらの質問文でも人へ回った。後者は両方の質問文で3回とも supports で、confidence が0.8前後のまま残り、英語の質問文では閾値をすり抜けた。ISSUE-89 の BP-17 が問題にしたのは後者の種類の違いにあたる
- 重複判定は8件すべて選択が正しかった (新しい規範を none と、既存の言い換えを該当の項目と選んだ)。無関係な主張とはっきりした否定も取りこぼしが無かった
- 人へ回った件数は英語の質問文で2件、日本語で4件だった。差の2件は上の後者の誤答 (英語では誤答のまま自動採用) と重複判定の1件なので、質問文の言語を選ぶ根拠にはならない

### ここから言えること

- 委譲された主張の反証の代わりにはならない。量の入れ替えを閾値の上で見逃すことがあり、コマンドを実行して確かめる種類の反証は原理的に扱えない
- 結果からは、判定の向きで扱いを分ける形 (contradicts と says_nothing と none は閾値を超えれば採用し、supports は必ず人かエージェントの確認へ回す) が一次選別に使えそうに見える。ただしこれは事前に決めた規則ではなく、実物の項目で contradicts が閾値を超えて出たことも無いので、新しい項目で事前に固定して試し直すまでは使わない
- 正しい supports はすべて0.97以上で、誤った2件より高かった。supports だけ閾値を0.95前後に上げれば分けられそうに見えるが、この値も結果に合わせて作ったものである。しかも正しい supports はすべて対照の項目で、実物には期待値が supports の項目が無かったので、この差が対照と実物の難しさの差なのかを区別できない
- 実物の項目は9件で、量の入れ替えを含むものは2件しかないので、傾向の手がかりにとどまる
- TypeSafe 公式の agent skill (typesafe-ai/skills) は、この試験では要らなかった。標準ライブラリだけの小さなスクリプトと API リファレンスで足りた。入れるかは保留にする

### 再試験で事前に固定すること (2026-10-19)

TypeSafe の公式ドキュメント (model-jaggedness) が jev-1.13 の弱点として挙げる2つが、前回の誤答2件と重なる。

- 選択肢の順序: 先頭の選択肢へ寄る。前回は supports を先頭に置き、誤答はどちらも supports だった。各項目を2通りの順序で送り、順序で選択が変わったものは人へ回す
- 数: 数を数えるのが苦手とされる。件数・量・ID 集合を含む主張は、送る前にコードで分類して Jev に判定させない
- state は判定に関係する節だけにする。無関係な内容が増えると精度が落ちるとされ、前回はファイル全体を送っていた
- モデルは版の ID で送る。2026-10時点で `jev-latest` は jev-1.13.0、`jev-preview` は jev-1.14.0 を指し、alias は新版の公開で動く。1.13.0 と 1.14.0 の両方で回せば版の差も見られる
- キーはエージェントが読まない。キーを使う呼び出しはユーザーが `!` で走らせる (agentic-coding-tools の ISSUE-65 の裁定と同じ境界)

仕分けの工程で受け箱の項目の重複判定に使う案もあるが、受け箱は非公開のリポジトリからの知見も受けるので、項目をそのまま API へ送らない。送るなら一般化した文面だけにし、ユーザーの同意と `!` の実行を経て、結果は提案としてだけ扱う。

stale な記述の検出には使わない。ISSUE-115 の試験で、過去形の記述やツール名の言及を stale に寄せる傾向が出ている。
