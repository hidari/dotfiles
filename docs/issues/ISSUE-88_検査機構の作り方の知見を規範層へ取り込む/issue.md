# docs(rules): 検査機構の作り方の知見を規範層へ取り込む

## 背景

委譲元から届いた「検査機構を作るときの落とし穴」の知見を、dotfiles の規範層 (常時層の
CLAUDE.md / paths 付き rules / references) へ取り込む。

材料は検証ワークフローで実測と突き合わせてある。**委譲元の主張のうち 3 件は反証または
解釈依存なので、そのまま規範として書かないこと。**

### 反証された前提

- 「分母と分子を両方数えて突き合わせる手当てが既存に無い」は偽。`rules/testing-practices.md`
  が既に「数える」ことを規定し、`references/testing.md` の「範囲の穴は 3 種の変異では
  見えない」節が Pester の実例を分母と分子の形で持つ。**新規なのは 2 点だけ** — (a) 突き合わせを
  常設の別検査として置くこと (b) 落ちた側が列数最大という偏りの向き
- 委譲元の推測「INS-1 と INS-6 は失敗側にトリガがあるので paths 付き rules へ寄せられる」の
  うち INS-1 は誤り。検査機構を足すときに編集するのは `scripts/**/*.py` / `rules/*.yml` /
  `sgconfig.yml` / `.pre-commit-config.yaml` / `.github/workflows/*.yml` で、どの rules の
  `paths` にも一致しない。同型は ISSUE-48 の軸F が既に記録している
- INS-3 の新規性は解釈に依存する。`references/observation.md` の既存 3 実例はいずれも
  その場で書いた使い捨てコマンドなので、射程は実質すでに届いている。確実に新規なのは
  「ツールの出力どうしを突き合わせている限り決着しない、一次の実体へ降りて初めて付く」という
  決め手の方

### 受け箱から追加の候補 (2026-10-22)

他のリポジトリのセッションから受け箱経由で届いた。上の INS-1〜6 と違って検証ワークフローを通しておらず、反証も置き場の検討もしていない。根拠の欄は報告者の申告で、dotfiles で確かめたのは最後の段落だけである。

| ID | 内容 | 根拠 |
| --- | --- | --- |
| INS-7 | 警告をエラーにするビルドで、変異が引数や変数を未使用にすると、テストより先にコンパイラの未使用警告で赤くなる。変数を使い続ける形 (固定値ではなく `n % 2`、述語を評価して結果を捨てる) で入れ直し、赤の原因がテストの失敗であることをログで確かめる | 実測 |
| INS-8 | 変異が緑のとき、pin の弱さより先に (a) 変異が等価でないか (b) fixture の値がそろっていて区別できないかを疑う。(a) は空の表から insert して0行だった例、(b) は持ち越す列の値が全行同じで「最古」と「最新」の取り違えを区別できなかった例。INS-5 と同じ「見逃し ≠ pin が弱い」の別の形 | 実測 |
| INS-9 | 変異の判定は rc だけでなく、狙った FAIL の行が出たかで行う。bash で `$var` の直後に全角の読点を書くと、そのバイトが変数名の続きとして読まれ、`set -u` で unbound variable になってハーネスごと落ちた。rc は非0だが FAIL の行は出ない。`${var}` で閉じる | 実測 |
| INS-10 | 変異が実際に入ったかを diff で確かめてから結果を読む。perl の置換パターンが対象の行と合わず、変異が入らないまま緑で残った | 実測 |
| INS-11 | 変異の実行器が「変異前のファイルが写しと一致すること」を確かめる作りだと、コードを整理したあとの再実行は全件 ABORT する。写しと変異の旧文字列を今のコードから組み直す | 実測 |
| INS-12 | 成果物に残った綴りを数える検査 (Release に Debug 専用の型が残らないか) の変異は、条件コンパイルを外すだけでは dead strip で消えて効きを測れない。実際に使うところまで変異に含める。数える綴りには型名に加えて文字列の literal (環境変数名・ヘッダ名) も持たせる | 推測 (後段は実測) |
| INS-13 | 包みの層を挟んだ契約は2段の変異で両側から示せる。利用側の述語を偽にすると利用側が赤、そこへ包みが失敗を握り潰す変異を重ねると利用側は緑へ戻り契約テストだけが赤 | 実測 |
| INS-14 | 生成の直後に同じ生成物の整合を確かめる検査 (lock を書き換えた直後の `--locked`) は構造上落ちない。検査に見えるだけで「確かめ済み」と読ませる。生成物と独立の入力 (ビルドやテスト) で見る | 実測 |
| INS-15 | E2E で「ある要素が0件」を自動再試行の assertion で確かめると、描画前の最初の判定で通るので何も確かめていない。先に陽性の要素が見えるまで待ってから0件を確かめる | ドキュメントのみ |
| INS-16 | 時間切れを確かめるテストの代役 CLI を `sleep` だけのシェルスクリプトにすると、子を殺しても孫の sleep が出力のパイプを持ち続けて打ち切りが遅れる (`exec sleep` にする)。本体の側は子をプロセスグループの頭にし、上限でグループごと kill してから読み手を join する。テストは孫がパイプを握る形 (`sh -c 'sleep 600 & sleep 600'`) にして外側の期限を付けないと「子だけ kill」の実装でも緑になる。グループごと止まるかは、実際に走らせて `ps -o pid,pgid,ppid` で孫の pgid が子と同じか (孫が setsid していないか) を確かめてから設計に乗せる | 前半は推測、後半は実測 (変異で赤を確認) |
| INS-17 | `assertIs(x, os.environ)` や `assertEqual(env, os.environ)` が落ちると失敗の文言に環境変数の中身 (トークンを含む) が丸ごと出る。変異注入でわざと落とす運用では委譲先の出力に残った。`assertTrue(x is os.environ, "<名前>")` の形で見る | 実測 |
| INS-18 | 発生率が数%の現象は30回程度では有無を言えない。再現ループで0/59、本番の手順の下で2/約25と食い違い、観測の形を変えると消えたように見えた | 実測 |

dotfiles で確かめたこと: `references/testing.md` / `references/observation.md` / `rules/testing-practices.md` には、INS-7〜18 の語 (等価・未使用・孫・dead strip など) がどれも出てこない。同じ検索で「変異」は testing.md に17件当たる (対照)。INS-9 の形は、追跡下のシェルスクリプト35本と `.zshrc` に `\$[A-Za-z_][A-Za-z0-9_]*[^\x00-\x7f]` を当てて、`.zshrc` のコメント1行だけが当たり実害は0件だった。INS-17 の形 (`os.environ` を assert の比較相手にするもの) は、追跡下の `*.py` で0件だった。対照に置いた `os.environ` の参照は29件ある。INS-7 と INS-9 はそれぞれ、dotfiles のメモリにある変異の横取りと結果行の取り違えの記録と同じ型で、メモリには入っているのに規範層には無い。

### 受け箱から追加の候補 (2026-10-22、2回目の仕分け)

上の INS-7〜18 と同じく、他のリポジトリのセッションから届いたもので、検証ワークフローも反証も通していない。根拠の欄は報告者の申告である。

| ID | 内容 | 根拠 |
| --- | --- | --- |
| INS-19 | ライブラリの assertion が実装の切り替えの前後で同じ意味を持つと、既存のテストは切り替えを pin しない。Playwright 1.62 の toBeDisabled / toBeEnabled と click の actionability は `aria-disabled="true"` も無効として数えるので、disabled から aria-disabled への切り替えで既存の assertion はすべて緑のまま通った。切り替えを pin できたのは toBeFocused だけで、変異を1つずつ入れて狙ったテストだけが赤になることで確かめた | 実測 |
| INS-20 | 経路を通ったことの確認には、計測の仕組みを外す変異を少なくとも2形当てる。E2E で「古い応答が届いた」をテストランナー側の時刻で近似した確認は、変異「遅延0」では赤だったが「待つ相手を外す」変異では緑のままで、dead pin だった。判定を時刻ではなく応答の本文 (作った行の識別子が無いこと) へ置き換えると、計測を外す変異で赤になった | 実測 |
| INS-21 | node:test の `test(name, { timeout }, fn)` の timeout は、テスト関数が同期の処理でイベントループを塞いでいるあいだは発火せず、処理が終わると緑で通る (89秒かかって緑だった)。処理時間の上限は、テスト本体の中で `performance.now()` の差を測って上限と比べる形で pin する。2乗に後戻りする正規表現へ戻す変異で赤になった。かかった時間は2乗の形で2.1秒、線形の形で1.3msと分かれた | 実測 |
| INS-22 | 綴りで行を数える検査は、同じ綴りを含むコメント行を拾う。workflow の YAML で「`node-version` を含む行」を数えたらコメント行で数が割れ、しかも変異の赤は手前のファイルのコメントで出ていて、狙った側の変異は一度も見られていなかった。「その綴りで始まる行」へ直し、変異ごとに失敗の文言まで読んで気づいた。INS-9 と同じ「赤の原因を読む」の別の形 | 実測 |
| INS-23 | 「この型を作るのは1ファイルだけ」を型名の出現で書いた ast-grep のルールは、名前を式に持たない生成 (Swift の implicit member の `.shared` や `.init(...)`、`extension T { Self(...) }`) を0件で通す。危ない文脈だけを型の位置で当てると狭められたが、引数の位置へ推論させて渡す形は構文では見えないまま残った。守りたい性質を決めるのが作る口だけでなく上書きできる別の口にもあり、口を閉じても性質は閉じていなかった。並列レビューに射程の穴を探させて見つかった | 実測 (ast-grep 0.45) |

INS-7 と INS-10 には2件目の報告が届いた。どちらも新しい番号は振らない。

- INS-7 の2件目 (実測): 関数の唯一の呼び出しを消す変異は、未使用の検査がビルドを止めてテストまで届かなかった。呼び出しを残したまま効果だけを外す変異に変えた
- INS-10 の2件目 (実測): 置き換え式の変異を、フォーマッタが配列を複数行に組み直したあとのファイルへ文字列一致で当てて空振りした。置き換えのスクリプトは assert で止まったのに、続くテストは変異していないソースで緑になった。報告者の提案は「変異を当てるスクリプトの終了コードを見てからテストを回す」
