# feat(hooks): 検査層が沈黙している状態をセッション頭で検出する

## 背景

PreToolUse の 2 つのガードは、どちらも「自分が機能していない状態」を検出できない。検出できて
いるつもりの箇所はあるが、射程が実態より狭い。ISSUE-55 と ISSUE-56 の両方がこの層を必要と
していると本文に書いており、担当する Issue が無かった。

失敗の形が共通している。守れていないことが「エラー」ではなく「何も起きない」として返るので、
出力を見ても気づけない。

### apm ガード側 (ISSUE-55 由来)

フックは shim が PATH 上に解決されるかを見て、解決されなければ deny する。しかしこの判定へ
到達するのは `guarded_command` がパースできた形だけである。shim を配置した動機はパースできない
形を捕まえることなので、検出は「shim が要らない場所でだけ働く」構造になっている。

shim 不在でフックへ 6 形を投入した実測 (2026-08-28)。

| 形 | フックの応答 |
| --- | --- |
| `apm install` | deny |
| `/opt/homebrew/bin/apm install` | deny |
| `PATH=/usr/bin apm install` | deny |
| `bash -c "apm install"` | 無音の素通り |
| `X=apm; $X install` | 無音の素通り |
| `echo install \| xargs apm` | 無音の素通り |

deny になる 3 形は、フックが自力で捕まえる 3 形と一致する。

### tirith 側 (ISSUE-56 由来)

tirith バイナリが見つからないとき、フックは判定を出さずに警告文だけを文脈へ載せる。これは
fail-open の可視化として正しい向きだが、告げているのはコマンド単位である。「tirith が入って
いない」はセッション単位の事実なので、同じ文が Bash 呼び出しのたびに積む。文面自身が
「以降のコマンドも同じ状態です」と書いており、繰り返しであることは認識されている。

この経路にはテレメトリを使えない。記録の呼び出しが tirith 自身を起動するので、tirith 不在と
いう当の状態では必ず失敗して握り潰される。

## なぜ config-guard に置けないか

ISSUE-56 の検討で確定している。CI に tirith が無く、skip 条件が検出対象と一致して自己敗北する。
「tirith が無いから検査しない」と「tirith が無いことを検査する」が同じ条件で分岐するため、
検査が必要な状況でだけ検査が動かない。

apm 側も同型で、リポジトリ側の配線 (bats / config-guard) が見るのは宣言であって実配置ではない。
CI にホーム環境が無いので実配置は原理的に見られない。

## 決めること

- 置き場。SessionStart フックが第一候補だが、ホームのフック層は Issue 26 が集約を進めている
  最中なので、どちらの層に属するかを先に決める
- 検出の形。存在検査 (ファイルがあるか) では足りない。apm 側は「PATH 上の apm が shim へ
  解決されるか」で、置いてあっても PATH に載っていなければ守っていないため。tirith 側は
  「起動して応答するか」まで見るかどうか
- 告げ方。セッション頭に 1 回で足りるのか、劣化したまま長時間走るセッションでは再告知が
  要るのか
- 検出したときに止めるのか通すのか。ホームのフックは user スコープで全プロジェクトに効くので、
  倒し方を誤ると全リポジトリのシェルが死ぬ

- [ ] コマンド単位の暫定告知 (tirith-check.py の fail-open 経路) を、この層ができたら畳む

畳まない理由: 畳むと tirith 不在時にコマンド単位の文脈が Bash 呼び出しのたびに積む挙動が
消える。この Issue が作った SessionStart 層はセッション頭の 1 回で告げるだけであり、実運用で
その 1 回の告知だけで十分に機能するかは、実際にセッションをまたいで運用してからでないと
判断できない。畳んでから足りないと分かった場合、コマンド単位の文脈を戻すのは「セッション頭で
見落とした」を後から復元する形になり、先に畳むより高くつく。このため実運用で確かめるまでは
tirith-check.py 側の fail-open 経路をそのまま残す。
