# ISSUE-59 spec: 検査層が沈黙している状態をセッション頭で検出する

問題の記述と背景は同ディレクトリの `issue.md` が持つ。この spec は Issue の「決めること」4 件に
対する決定と、その根拠になった実測を持つ。

## 決定

| 決めること | 決定 | 根拠 |
| --- | --- | --- |
| 置き場 | 独立した SessionStart フックと、述語を持つ共有モジュール | 下記「置き場」 |
| 検出の形 | apm は PATH 解決、tirith は解決検査と応答検査の 2 段 | 下記「検出の形」 |
| 告げ方 | `systemMessage` で全開始理由に対して。健全なときは黙る | 下記「告げ方」 |
| 止めるか通すか | 通す。プラットフォームが止めることを許さない | 下記「止めるか通すか」 |

射程は「名前付きプローブの登録簿」とする。プローブ 1 個が述語 1 個と文面 1 個を持ち、まず apm と
tirith の 2 件を登録する。この Issue で扱う範囲を 2 件に閉じつつ、同じ形の穴が出たときに機構ごと
作り直さずに済む形にするため。

## 実測 (2026-08-29)

この日の測定はすべてこのリポジトリの作業機で行った。件数は日付付きのスナップショットとして扱う。

### SessionStart はセッションを止められない

`exit 2` でも session は続行し、stderr がユーザーへ出るだけである。PreToolUse の `exit 2` に相当
する経路は無い。したがって「検出したときに止めるか通すか」は、この層に置く限り選択肢が無い。

告げ先は 3 経路に分かれる。`stderr` はユーザーの端末だけに出てモデルには入らない。
`additionalContext` はモデルの文脈に入る。`systemMessage` は両方へ届く。

`additionalContext` が SessionStart で機能することは公式ドキュメントに明記が無いが、
`handoff-sentinel.py` が実際に使っており、この spec を書いたセッションでも発火している。

複数の SessionStart フックは並列に実行され、順序は保証されず、一つの失敗は他を巻き込まない。

### セッション開始理由は matcher で分かれる

matcher は開始理由 (startup / resume / clear / compact / fork) でフィルタする。全理由を覆えば
compact のたびに再告知されるため、再告知の機構を別に書かずに済む。

これは PreToolUse の matcher がツール名を見るのとは意味が違う。同じ述語を使い回すと、
ツール名を書いた SessionStart 登録を正しい配線として数えてしまう。

### apm 側の述語は既に存在する

`apm-install-guard.py` の `shim_resolves` が、PATH 上の apm が配布した shim へ解決されるかを
`os.path.samefile` で見ている。文字列比較ではないので symlink でも正しい。足りないのは述語では
なく呼ぶ場所で、現在は deny 経路の中にあり、パースできたコマンド形からしか到達しない。

この spec を書いたセッションの開始時点で、shim は実配置されていなかった。親ディレクトリだけが
存在して中身が空だった。誰にも告げられないまま素通りしていた状態で、この層があれば捕まえられた
形そのものである。

このとき PATH の状態は 2 つに分かれていた。新しく起こした対話シェルの PATH には shim の
ディレクトリが載っていたが、Claude Code の PATH には載っていなかった。フックは Claude Code の
プロセスから起動されるので、フックが見る PATH は後者である。したがってこの述語は、ガードが
実際に見る PATH を測っている。

配置したあとも、Claude Code を再起動するまでは後者が変わらない。つまり配置直後のセッションでは
このプローブは沈黙を報告し続けるが、それは誤報ではない。そのセッションの Bash 呼び出しに対して
shim は実際に横取りしていないためである。

### tirith 側で沈黙する経路は 1 つだけ

フックの倒れ方を経路ごとに分けると、静かなのは 1 つに絞られる。

| 経路 | フックの倒れ方 | 静かか |
| --- | --- | --- |
| `TIRITH_BIN` 未設定でバイナリが解決しない | fail-open | 静か |
| `TIRITH_BIN` 設定済みでパスが存在しない | fail-closed | うるさい |
| 想定外の exit code / timeout | fail-closed | うるさい |

ポリシーファイルはリポジトリにもホームにも存在せず、組み込みの既定で動いている。したがって
「ポリシー破損で全部素通り」は現状の構成では起こらない。

### tirith の自己診断は述語として使えない

`tirith status` は protection を off と表示しながら rc 0 を返した。ヘルプ自身が「外部からは
per-shell の live mode が見えない」と書いており、exit code は「保護されている」と「見えなかった」
を区別しない。`tirith doctor` も rc 0 を返し、報告する hook status は shell の preexec フックを
指していて Claude Code のフックの生存は見ていない。

したがって曖昧さのない述語は、実際にコマンドを流して応答を見る形しか無い。

### 陰性対照は監査統計を壊す

block される文字列を流すと、監査カウンタの blocked が呼び出し 1 回につき 1 増える。
`TIRITH_INTEGRATION` の有無でも `--no-daemon` でも変わらなかった。5 回ずつの前後比較を 3 通り
行い、いずれも +5 だった。

blocked は 7 日で 466 件しかない。セッション開始と compact のたびに合成 block を積むと、
やがて統計の大半が合成物になる。tirith が働いているかを判断する材料そのものを、健全性の検査が
壊す形になる。

clean なコマンドを流す場合は scanned だけが増える。scanned は同じ 7 日で 51000 件を超えており、
blocked と warned は動かなかった。

なお「危なそうに見えるコマンド」は対照にならない。`git push --force`、`chmod 777 /etc/passwd`、
`docker run` でホストルートを bind する形は、いずれも rc 0 だった。対照は実測で選ぶ必要がある。

### tirith の起動コスト

20 回連続で 0.706 秒。1 回あたり約 35 ミリ秒で、セッション頭に 1 本流すコストは既存フックの
timeout に対して無視できる。

### 実行ビットがフック本体と共有モジュールを分けている

`home/.claude/hooks/` の追跡下の mode は、フック本体が 100755、共有モジュールが 100644 で
分かれている。settings.json に現れるのは 100755 のものだけで、現状の孤児は 0 件である。

この分け方は既存の実態であり、孤児検出のために新しい規約を作る必要が無い。

## 置き場

独立した SessionStart フックを 1 本置き、述語は共有モジュールへ集める。

| ファイル | 役割 |
| --- | --- |
| `home/.claude/hooks/guard_probes.py` | プローブの登録簿と述語。print も `sys.exit` も持たない |
| `home/.claude/hooks/guard-health.py` | SessionStart フック。登録簿を回して結果を組み立てる |

`shim_resolves` と tirith のバイナリ解決を、それぞれ現在の持ち主から `guard_probes.py` へ移し、
PreToolUse の 2 フックは移した先を import して使う。同じ判定を 2 箇所へ書くと、片方だけ直した
ときに沈黙して食い違う。この Issue が扱っている欠陥を実装で作り直すことになるため、canonical を
1 つにする。

`pretooluse.py` が「純関数だけを共有し、倒し方は各フックが持つ」という前例を作っている。
`guard_probes.py` は subprocess を持つので純関数ではないが、print と `sys.exit` を持たない線は
同じく守る。共有層だけを直接テストできる状態を保つため。

既存の SessionStart フックへ相乗りする案は採らない。SessionStart は並列実行なので本数を減らして
も速くならず、一方の失敗がもう一方を巻き込む形になる。加えて ISSUE-58 が `handoff-sentinel.py`
に手を入れる予定であり、無関係な関心を混ぜると両方の変更が絡まる。

PreToolUse 側でセッション単位にメモ化する案も採らない。セッション単位の状態をファイルへ持つ必要
があり、その状態ファイル自身が腐る対象になる。またセッション頭ではなく最初の Bash まで告げられ
ない。

## プローブの契約

プローブは引数を取らず、名前と健全性と文面を持つ結果を返す関数とする。登録簿はその関数の並びで
ある。プローブを表す型は作らない。名前を結果に載せれば足りるため。

文面は沈黙しているときだけ意味を持ち、次の 2 つを含める。

- 何が検査されなくなるか。状態の名前だけでは深刻さが伝わらないため
- 直し方。ユーザーだけが実行できる操作を含む場合はそれを明示する

## 検出の形

### apm

PATH 上の apm が配布した shim へ解決されるかを見る。移設した述語をそのまま使う。

文面には、shim を迂回できる形が無音で素通りすることを含める。`issue.md` が実測表として持って
いる 3 形がそれにあたる。直し方は bootstrap の実行と Claude Code の再起動で、後者は PATH が
起動時に snapshot されるため、シェルの再読み込みでは足りない。

### tirith

解決検査と応答検査の 2 段とし、結果を 3 つに分ける。

| 状態 | 報告 |
| --- | --- |
| 解決し、clean なコマンドに応答する | healthy |
| `TIRITH_BIN` 未設定で解決しない | unhealthy。検査が沈黙している |
| `TIRITH_BIN` 設定済みでパス不在、または応答しない | unhealthy。すべての Bash が止まる |

3 行目は静かな失敗ではないが、セッション頭で原因を名指しできる価値があるため報告する。

応答検査はフックと同一のフラグと環境変数で呼ぶ。呼び方が違うと、デーモンを経由するかどうかが
変わり、フックが通る経路とは別のものを測ることになる。

流すコマンドは、副作用が無く rc 0 が返ることを実測で確かめたものにする。値は実装が持つ。
検出されるコマンドを選ぶと監査統計を汚すので、選定の際は clean 側であることを測ってから決める。

「起動するが何も止めない」状態はこの層では覆わない。覆うには陰性対照が要るが、それは監査統計を
壊す。この判断は上の実測に基づく。

## 告げ方

沈黙しているプローブが 1 件でもあれば、`systemMessage` として 1 通にまとめて出す。matcher は
全開始理由を覆う。

健全なときは何も出さず exit 0 とする。毎セッションの出力はノイズになるため。この選択によって
「健全」と「検査自体が走らなかった」が実行時には区別できなくなるが、その区別は配線を静的に
pin する層が持つ。実行時は黙り、配線は叫ぶ。

## 止めるか通すか

通す。SessionStart はセッションを止められないため、選択の余地が無い。

強制が要る形は PreToolUse 側の責務のままである。この層が変えるのは、素通りしうる状態にあることが
セッション頭で分かるようになる点だけで、素通りする形そのものは減らない。

## 倒し方

- プローブが例外を投げても他のプローブは走る。1 件の失敗が全体を沈黙させないため
- プローブ自身の失敗は unhealthy として報告する。検査できなかったことを健全へ潰さない
- フック全体の例外は捕まえて `systemMessage` で報告し exit 0 とする。stderr へ倒すとモデルの
  文脈に入らないため
- timeout は既存の SessionStart フックに揃える

## 配線の検査

必須フックの宣言と、配線漏れの検出を別の層に分ける。

必須であることの宣言は名前で書く。存在するファイルの集合から必須集合を導くと、フック本体を消せば
要求も消えて緑になる。これは ISSUE-59 が扱っている自己敗北を検査側に作り込むことになる。

現在の必須フック検査は PreToolUse に固定されているため、イベント軸へ一般化する。この一般化は
Issue 26 のタスク 1 件にあたる。matcher の述語はイベントごとに分ける。PreToolUse の matcher は
ツール名を見るが、SessionStart の matcher は開始理由を見るため、同じ述語では正しくない配線を
配線として数える。

配線漏れの検出は導出でよい。フック本体が settings.json のどこにも現れないものを孤児として報告
する。ファイルが消えても要求は消えない。要求は名前で宣言する層が別に持っているため。孤児検出は
ファイルシステムの視野を必要とするので、settings.json の dict だけを見る既存の検査とは別の
モジュールへ置く。

## 覆わない範囲

この層が覆わないものを明示する。ISSUE-59 の発端が「機構は動くが射程が狭い」であったため、
射程の穴を数えることをタスクに含める。

- tirith が起動して応答するが、何も検出しない状態。陰性対照が監査統計を壊すため覆わない
- shim を迂回する形そのもの。この層は状態を告げるだけで、素通りする形は減らない
- `home/.claude/hooks/` 以外の場所にある検査層。今回の登録簿は 2 件で始める

## テスト

- 共有モジュールの各プローブを、健全と沈黙の両方で検査する
- フックが、1 件のプローブが例外を投げても他を走らせることを検査する
- フックが、健全なときに何も出さないことを検査する
- 配線の検査を、必須フックの欠落と孤児の両方で検査する

変異注入は 3 種 (検査対象、検査機構、取り付け) に加えて、射程の穴を数える。取り付けを外す変異は、
新しいフックを settings.json から外すと孤児が 1 件になる形で成立する。

変異が下流で吸収されないよう、検体は結果が分岐する位置に置く。過去に、変異が狙った分岐へ届いて
いたのに検体が後段で同じ出力へ収束して観測できなかった例がある。
