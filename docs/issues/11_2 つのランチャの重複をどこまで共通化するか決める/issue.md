# refactor: 2 つのランチャの重複をどこまで共通化するか決める

## 背景

`home/.zshrc` の既定アカウントの `claude()` と、追加アカウント用のランチャは本体の大半が同一である。ID の導出、通知、空ガード、else 分岐の形がそのまま重なっていて、違うのは config dir の引数と `CLAUDE_CONFIG_DIR` の前置だけ。

Issue #25 の Phase 3b (Task 8) で追加アカウント側は設定ファイル駆動の生成へ移した。生成器が持つテンプレートと既定の静的定義とのあいだで重複が残っているため、本 Issue の論点自体は解消していない。

Phase 3b のマージ前ゲートで、この重複に具体的なコストが 2 つ加わったことが分かった。生成器のテンプレートは全エスケープ済みの関数本体をそのまま eval 文字列へ埋めているため、本体が「エスケープ空間」でしか編集できず、shellcheck も構文ハイライトも中を見られない。起動規約を変えると素の `claude()` とエスケープ付きコピーの 2 箇所編集になり、後者の退行だけが静的検査を素通りする。

テンプレート本体を静的なワーカー関数へ出して eval をラッパー 2 行まで縮めれば、共通化の範囲という本題に答えないままでもこの 2 点は解ける。設定ファイル由来の文字列から生成されるコードが最小になるので、eval の攻撃面も同時に縮むという副次効果がある。

Issue #10 のレビューで複数の観点から指摘された。ただし完全な共通化は `CLAUDE_CONFIG_DIR` の unset-vs-empty 制約でブロックされる。個人アカウントはこの変数を一切設定してはいけない (既定パスの明示指定という賭けをしないため) ので、共通の起動パスへ寄せると空文字を渡すか、環境変数の配列を組み立てるような間接を増やすかのどちらかになる。

一方、ID を解決して通知する 2 行はこの制約に触れないため抽出できる、という指摘もあった。この 2 行だけを `_claude_resolve_task_list()` のような形へ寄せると、config dir 側が `_claude_config_dir()` で resolve と検証を 1 つにまとめているのと同じ抽象度に揃う。

この重複には実害の前例がある。Issue #10 の実装中、仕事アカウント側の空ガードだけテストが無く、変異させても全件 green のまま通ってしまった。重複そのものより、重複した分岐が片方しか pin されないことが危険だった。

## タスク

- [ ] eval テンプレートの本体を静的なワーカー関数へ出し、生成される文字列をラッパーだけに縮める
- [ ] 共通化の範囲を決める (ID 解決と通知の 2 行だけ / 起動まで含めた全体 / 現状維持)
- [ ] 決めた範囲で抽出し、両方のランチャから使う
- [ ] 変異注入で、共通化後も両ランチャの空ガードが独立に pin されていることを確認する
