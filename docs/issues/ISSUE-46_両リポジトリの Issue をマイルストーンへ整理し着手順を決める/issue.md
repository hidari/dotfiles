# docs: 両リポジトリの Issue をマイルストーンへ整理し着手順を決める

## 背景

dotfiles と agentic-coding-tools に open Issue が積み上がっている (2026-08-25 時点で
両リポ合わせて 46 件)。それぞれの本文には順序制約が書かれているが、散文の中にしかないため
全体を俯瞰する手段が無い。着手のたびに全件を読み直すことになり、読み直さないまま着手すると
先行条件を踏み外す。

この Issue はその俯瞰を 1 箇所に置き、着手順の根拠を記録する。個々の作業は各マイルストーンが
指す Issue が持つ。

### 整理が必要だと分かった経緯

in-repo Issue の検査が配布先で走っていない、という問題を調べる過程で、同じ問題に触れる Issue が
両リポに散在していることが分かった。触れている Issue は上流だけで 9 件あるが、それを担当する
Issue は 1 件も無い。

同時に、判断材料そのものが腐っていることも分かった。参照先が closed になったことを参照元が
知らない stale な参照が両リポにある。訂正はタスクが持つ。

## 実測 (2026-08-25)

着手順の根拠になるものだけを挙げる。件数は日付付きのスナップショットとして扱うこと。

### 記法移行の母数

上流 ISSUE-22 の方法 (`issue.md` を持つディレクトリを `closed/` 込みで数え、`.cache` 配下の
probe を除く) で数え直した結果、旧記法 930 件 / 新記法 32 件 / 旧記法を持つリポジトリ 12。

同じセッションで最初に出した値は 833 件 / 11 リポジトリだった。ずれた要因は 2 つある。

1. 1 段深い場所にあるリポジトリ 1 件を漏らした。`find -maxdepth 3` では届かない
2. 母集団が違った。ディレクトリ数を数えており、`issue.md` を持つものに絞っていなかった

ISSUE-22 は 2026-08-24 時点で旧記法 911 件と記録しており、この 930 件との差は 1 日ぶんの
起票と読める。ISSUE-22 自身も計上を 3 回訂正しており、外れる方向は過小と過大の両方だった。

要因 1 は並行して調べていた別セッションも踏んでいる。ISSUE-22 の訂正記録にも同型の漏れが
あるが、そちらが挙げる件数と今回漏らしたリポジトリの件数は一致しないため、同一のリポジトリを
指しているかは確かめていない。

### ディレクトリ名を番号だけにする案は採れない

Issue 43 の案 2 を対照付きで測った。

| ディレクトリ名 | rc | `--next` の出力 |
| --- | --- | --- |
| `43_sometitle` (対照・旧記法) | 0 | ISSUE-44 |
| `ISSUE-43_sometitle` (対照・新記法) | 0 | ISSUE-44 |
| `43` (番号のみ) | 0 | ISSUE-1 |
| `ISSUE-43_` | 0 | ISSUE-44 |

番号のみは採番スクリプトの走査パターンに一致せず、既存の 43 が見えないまま rc=0 で
ISSUE-1 が返る。ISSUE-22 は「rename は採番を止めうる」を理由に rename を退けたが、実際には
止まるより悪い形 (沈黙する番号再利用) を踏む。この案は採らない。

### Issue クローズの書き換えコストの原因は移動

Issue 43 が挙げる書き換えコストの原因を、直近のクローズ (`fb72a36`) で確かめた。原因は
`closed/` への移動でパスの深さが 1 段変わることで、`--name-status` と `-U0` で見たところ
外部ファイル側の変更は例外なく相対リンクの補正だった。件数は Issue 43 が持つ。

壊れる対象がリンクだけなので、リンクを張らなければ移動を残したまま書き換えが 0 になる。
一覧性も失わない。

### 検査を取り付ける土台が大半のリポジトリに無い

`.pre-commit-config.yaml` を持つのは 3 リポジトリだけで、残りは pre-commit 自体が未導入。
検査の取り付けを論じる前に、取り付け先が存在しない。母集団は上の記法移行と同じ走査。

加えて apm がデプロイしたものは追跡下に無いため、git hook からも CI runner からも存在が
保証されない。配布側から `apm install` 時の自動セットアップを仕掛けることもできない
(`apm lifecycle trust` の対象は消費側の宣言で、これは配布側スクリプトの自動実行を防ぐ
意図的な設計)。

## マイルストーン

各マイルストーンの詳細と順序制約は、それが指す Issue が持つ。この表は所属だけを示す。

| # | マイルストーン | 指す Issue | 先行 |
| --- | --- | --- | --- |
| M1 | Issue 維持コストの原因を消す | Issue 43、ISSUE-52 | なし |
| M2 | 検査を配布先で走る状態にする | 新規起票が要る (担当 Issue が無い) | M1 |
| M3 | skill バンドルの二重登録を止める | ISSUE-27、Issue 40 | なし |
| M4 | PUBLIC 露出の scrub | ISSUE-15、ISSUE-23、Issue 21、Issue 29 | なし |
| M5 | config-guard の検査基盤を 1 実装へ寄せる | Issue 39、Issue 30、Issue 41 | なし |
| M6 | winvm の実装品質 | 上流の winvm 系 Issue | なし |
| M7 | 環境とテスト網の個別 | dotfiles の zsh / bats / PowerShell / Raycast クラスタ、ISSUE-51 | なし |
| M8 | CI の必須チェックを実効化する | ISSUE-50 | なし |

M1 の「指す Issue」に ISSUE-52 を足したのは、扱う対象が同じだから。M1 は Issue 本文から
リンクを外す方向なので、PR 本文の Closes 行がリンクの残る最後の場所になる。上流 ISSUE-24 と
同じテーブルで裁定するなら ISSUE-52 もそこへ持ち込む。

### 着手順の裁定 (2026-08-27)

**M1 を優先する。M8 (ISSUE-50) は後回し。**

M1 を先に置くのは、M2 の baseline がパスに依存するという既存の理由に加えて、ISSUE-52 で
同じ対象の欠陥が実際に稼働中のプロジェクトへ出たため。上流 ISSUE-24 が未決のまま残っている
ぶんだけ、判断待ちが下流に溜まる。

M8 を後回しにするのは、CI が緑であることの確認が手作業 (SHA を突き合わせてジョブ件数を数える)
で今のところ回っているため。取りこぼしのリスクは残るが、判断待ちを増やしてはいない。

### 件数の再計測 (2026-08-27)

| リポジトリ | open | in_progress | closed |
| --- | --- | --- | --- |
| dotfiles | 29 | 2 | 21 |
| agentic-coding-tools | 22 | 1 | 8 |

active 合計 54 件 (open 51 + in_progress 3)。背景節の「46 件」は 2026-08-25 のスナップショット。

同じセッションで一覧を目で数えて 29 と報告し、実際は 28 だった。**件数は着手の根拠にする前に
数え直すこと。**この Issue が既に書いている注意を、この Issue を読みながら踏んだ。

### M1 が M2 に先行する理由

M2 の baseline は違反をファイルパスと語の組で記録する。`closed/` への移動がパスを変えるので、
移動の扱いが決まる前に baseline を作ると作り直しになる。

### M1 の裁定内容

Issue 43 が挙げる 3 案のいずれでもない形を採る。

- `closed/` への移動は維持する。一覧で open と closed が区別できなくなるのを避けるため
- Issue 間の参照はリンクを張らず識別子だけにする
- 識別子の実在を機械が検査し、参照の腐りを検出する

失うのは Issue 本文からのクリック導線。エージェント側の導線は skill の Phase C.3 が持つ
識別子からの検索が代替する。

規約の canonical は skill 側なので、上流へ起票して裁定する。上流 ISSUE-24 が同じ対象
(Issue 間の相対リンクの書式) を扱っており、そちらはリンクを張るかどうかを未決のまま
持っているので、同じテーブルで決めること。

### M2 は担当 Issue が無く、前提の組み直しが要る

「配布先で検査が取り付けられているかを見る層が無い」という問題に触れている Issue は上流に
9 件あるが、担当している Issue は 1 件も無い。M2 の着手は新規起票から始まる。

当初は消費側 (config-guard) に ratchet を載せる形を想定していたが、これは dotfiles だけの
機構で、pre-commit 自体を持たないリポジトリには載せる土台が無い。「検査を配布先の
git hook / CI から呼ぶ」という土俵そのものを疑うところから設計し直す。
