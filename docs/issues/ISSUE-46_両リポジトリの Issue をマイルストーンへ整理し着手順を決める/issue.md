# docs: 両リポジトリの Issue をマイルストーンへ整理し着手順を決める

## 背景

dotfiles に 25 件、agentic-coding-tools に 21 件の open Issue がある。それぞれの本文には
順序制約が書かれているが、散文の中にしかないため全体を俯瞰する手段が無い。着手のたびに
46 件を読み直すことになり、実際に読み直さないまま着手すると先行条件を踏み外す。

この Issue はその俯瞰を 1 箇所に置き、着手順の根拠を実測付きで記録する。個々の作業は
各マイルストーンが指す Issue が持つ。

### 整理が必要だと分かった経緯

in-repo Issue の検査 (`issue-id.py --check`) が配布先で走っていない、という問題を調べる
過程で、同じ問題に触れる Issue が両リポに散在していることが分かった。触れている Issue は
上流だけで 9 件あるが、それを担当する Issue は 1 件も無い。

同時に、判断材料そのものが腐っていることも分かった。参照先が closed になったことを参照元が
知らない stale な参照が dotfiles に 2 件、上流に 1 件ある。上流の 1 件は「配る前に完了させる」
というゲート宣言で、配布は既に済んでいるためゲートとして機能していない。

## 実測で確定した事実

着手順の根拠になるものだけを挙げる。実測日は 2026-08-25。

### 記法移行の母数は 911 件 / 12 リポジトリ

上流 ISSUE-22 の実測値 (計上を 3 回訂正した後の確定値)。このセッションでも独立に数えたが、
`~/Develop/canbright/miterude` (98 件) を漏らして 833 件 / 11 リポジトリと出した。1 段深い
場所にあるリポジトリで、`find -maxdepth 3` では届かない。

同じ漏れを 3 者が独立に踏んでいる。ISSUE-22 の訂正記録、並行セッションの棚卸し、そして
このセッション。11 という数字はそれ自体では欠けていることが分からない形で返る。

### 記法の rename は採らない (上流 ISSUE-22 が判断済み)

理由は 2 つ。rename が採番を止めうること、911 件が現実的でないこと。既存は履歴として残し、
新規起票だけが新記法になる。

この判断に対し、ディレクトリ名を番号だけにする案 (Issue 43 の案 2) を対照付きで測った。

| ディレクトリ名 | rc | `--next` の出力 |
| --- | --- | --- |
| `43_sometitle` (対照・旧記法) | 0 | ISSUE-44 |
| `ISSUE-43_sometitle` (対照・新記法) | 0 | ISSUE-44 |
| `43` (番号のみ) | 0 | ISSUE-1 |
| `ISSUE-43_` | 0 | ISSUE-44 |

番号のみは採番スクリプトの走査パターンに一致せず、既存の 43 が見えないまま rc=0 で
ISSUE-1 が返る。ISSUE-22 は「rename は採番を止めうる」を理由に rename を退けたが、実際には
止まるより悪い形 (沈黙する番号再利用) を踏む。この案は採らない。

### Issue クローズの書き換えコストの原因は移動

Issue 43 が挙げる「クローズ 1 件で 14 箇所」の原因を `fb72a36` で確かめた。コミット
メッセージが原因を明言している。

> 移動でパスの深さが 1 段変わるので相対リンクを両方向補正した。外部から 36 への参照が
> 6 件、36 から出る参照が 8 件。

`--name-status` と `-U0` で確認したところ、外部 6 ファイルの変更は例外なく相対リンクの
補正だった。壊れる対象がリンクだけなので、リンクを張らなければ `closed/` への移動を
残したまま 14 箇所が 0 になる。一覧性も失わない。

### 検査を取り付ける土台が 10 リポジトリに無い

`.pre-commit-config.yaml` を持つのは agentic-coding-tools / dotfiles / photon-lab の
3 リポジトリだけで、残り 10 リポジトリは pre-commit 自体が未導入。検査の取り付けを
論じる前に、取り付け先が存在しない。

加えて apm がデプロイしたものは追跡下に無く (`home/apm_modules/` も
`home/.claude/skills/` も gitignore)、git hook からも CI runner からも存在が保証されない。
配布側から `apm install` 時の自動セットアップを仕掛けることもできない (`apm lifecycle trust`
の対象は消費側の宣言で、これは配布側スクリプトの自動実行を防ぐ意図的な設計)。

### M1 が M2 に先行する理由

M2 の baseline は違反をファイルパスと語の組で記録する。`closed/` への移動がパスを変えるので、
移動の扱いが決まる前に baseline を作ると作り直しになる。

### M1 の裁定内容

Issue 43 が挙げる 3 案のいずれでもない形を採る。

- `closed/` への移動は維持する。一覧で open と closed が区別できなくなるのを避けるため
- Issue 間の参照はリンクを張らず識別子だけにする
- 識別子の実在を機械が検査し、参照の腐りを検出する

失うのは Issue 本文からのクリック導線。エージェント側の導線は skill の Phase C.3 が持つ
`find -path "*/${ID}_*"` が代替する。

上流 ISSUE-24 はリンク維持に傾いているが、そちらが重視しているのは PR から Issue 本体への
導線であって Issue 間の参照ではない。衝突しない見込みだが、上流へ起票するときに突き合わせる。

### M2 の前提は組み直しが要る

当初は消費側 (config-guard) に ratchet を載せる形を想定していたが、これは dotfiles だけの
機構で、他 10 リポジトリには載せる土台が無い。「検査を配布先の git hook / CI から呼ぶ」という
土俵そのものを疑うところから設計し直す。
