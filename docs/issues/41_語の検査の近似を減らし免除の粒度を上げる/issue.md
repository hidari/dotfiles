# refactor: 語の検査の近似を減らし免除の粒度を上げる

## 背景

`config_guard.term_definitions` (Issue #36 の PR で新設) は、rules が `defines` で
宣言した語が定義の届かない層に出現していないかを検査する。マージ時点で 3 つの近似を
承知のうえで残した。どれも「検査が緩い」方向ではなく「免除表が伸びる」方向のコストで、
免除は人が書いた散文なので、伸びるほど機構の弱点になる。

### 1. 照合が本文全体への部分文字列一致

コードフェンス・インラインコード・frontmatter を区別しない。「こう書くと駄目」という
例示や、英語の一般語 (`gaming` / `narrowing` / `negative case`) の初出が誤検出になる。

姉妹モジュールの `instruction_refs` は `prose_lines()` でフェンスを落としており、
限界も docstring に明記している。同じ扱いへ揃えられる。語境界は CJK に無いので
regex を挟んでも近似の精度は上がらない。

### 2. 免除がファイル単位

`ACKNOWLEDGED` の鍵は (語, ファイル) なので、既に免除したファイルの中で同じ語が
新しく使われても無音になる。この機構が防ぎたい事象そのものが、免除済みの 3 ファイルの
中では起きても報告されない。

免除の値に登録時の出現数を持たせる案は、正当な編集のたびに数字の更新を要求するので
採らなかった。行単位の鍵は行番号が drift するので採れない。

### 3. 「定義が届く文脈」を人が判断している

免除の理由は全て「定義を持つ場所を名指ししている」か「括弧で操作的定義を併記している」で、
どちらも人が読んで確かめた事実。実際にマージ前のレビューで、理由文が実態と食い違って
いるものが 1 件見つかった (`references/testing.md` の 2 件)。

`instruction_refs.extract_home_refs` が参照グラフの辺を既に抽出しているので、
ファイルごとのロード文脈を機械で出せる可能性がある。常時層 (CLAUDE.md と paths 無し
rules) を起点に、references は名指しした側の文脈を継ぐ、という推移閉包。これで
「出現側の文脈が定義側の文脈を含まない」ときだけ報告する形にできれば、免除 5 件のうち
4 件が機械判定へ落ちる。

ただし「名指ししているから定義に辿り着ける」は参照グラフでは表現できない。
辺があることと、読み手が実際にその先を読むことは別なので、この案がどこまで
人の判断を置き換えられるかは設計してみないと分からない。
