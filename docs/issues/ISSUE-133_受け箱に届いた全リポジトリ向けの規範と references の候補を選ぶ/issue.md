### セキュリティ

- 独自ヘッダで秘密を送る配線 (認証プロキシの service token など) を fetch の包みで全要求へ足すと、fetch の仕様は別オリジンへの redirect で Authorization 以外のヘッダを落とさないので、302 を辿った先へ秘密が運ばれる。包みは接続先と同じオリジンにだけ足し、redirect は manual にする。テストは別ポートのもう1台のサーバへ 302 を返し、届いた件数0を接続先の受信を対照にして pin する。オリジン判定の「scheme が同じか」の腕は、テストのサーバが全部平文だと消しても緑で通るので、接続先を https として名乗り同じ host とポートへ平文で要求を出して腕を外す変異で赤にする (実測、変異で赤を確認)
  - 2026-10-31の仕分けで、別のリポジトリから Python 版の報告が届いた。urllib の既定の opener は redirect を追い、Request に付けた Authorization ヘッダも redirect 先へ送りうるので、Basic 認証を付ける採取の道具は redirect を追わない opener にする (ドキュメントのみ)
  - 2026-10-31の仕分けで、別のリポジトリからブラウザ自動化の経路の報告が届いた。保護下のフロントを開くとき、bypass のヘッダを context 全体の extraHTTPHeaders ではなく route で配信先のホストへの要求にだけ付けた。全体に付けると別ドメインの API へ秘密のヘッダが送られる (実測と申告。ただし仕組みからの判断で、漏れは観測していない)
- 秘密の値を会話・ログ・subagent に出さないため、書き捨てのシェルスクリプトの中で 1Password の `op read` の結果を直接ヘッダや子プロセスの環境変数へ流し、値の代わりに形 (接頭辞・長さ・文字種) だけを数えて確かめた (実測)
  - 2026-10-31の仕分けで、別のリポジトリから同じ目的の別の形が2つ届いた。鍵を env で渡して SQL の中では getenv で読み、SQL は標準入力で DuckDB に渡すと、鍵がプロセスの引数にも SQL のファイルにも出なかった。API トークンは `curl --config -` へ標準入力から `header = "Authorization: Bearer ..."` で渡すと、引数にも画面にも出さずに使えた (どちらも実測)。同じ書き捨てのスクリプトの形が auto mode の分類器に止められた報告は、新しく立てた「Claude Code の auto mode と権限」の節に置いた
  - 2026-11-10の仕分けで、別の3つのリポジトリから同じ目的の形が届いた。実物の API 応答を確かめるとき、値ではなく「キーと型」だけを出す書き捨てのスクリプトを `.cache/` に置き、トークンを画面に載せずに形を調べた (実測)。`op read` の値を表示せずに用途を判別するには、長さと形 (32桁の hex か) と、提供元の verify API の HTTP ステータスだけを出せば足りた (実測)。トークンを標準入力から `curl --config -` へ header として渡すと引数にも画面にも値が出ない、という上の子と同じ報告もまた届いた (実測)
  - 2026-11-10の仕分けで、上の3つのうち1つと同じリポジトリの別のまとめから、同じ目的の別の形が届いた。GitHub の Environment の secret は、`op read -n "<op の参照>" | gh secret set <NAME> --env <環境>` で値を画面にもログにも出さずに入れられる。`-n` は末尾の改行を付けない。成否は zsh の `${pipestatus[1]}` と `${pipestatus[2]}` で両側を見る (実測)。`op read` の末尾の改行の件は ISSUE-134 の「1Password CLI の `op read 'op://<vault>/<item>/<日付の欄>'`」の箇条の子にもある
- 値の形に関する自分の知識も、仕様を引くまでは未確認の前提として扱う。秘密の形式が発行時期で変わっていて、古い知識で形を検査すると「別の値が入っている」と誤判定した (ドキュメントのみ。手元の値の形がドキュメントと一致することは実測)

  - 2026-10-31の仕分けで、別のリポジトリから同じ型の報告が届いた。シークレットを含むログをホストへ回収し、値をファイルから読む小さなスクリプトで件数だけを出し、値ごとに合成の1行を対照に置くと、値を表示せずに「0件」と「見ていない」を区別できた (実測)
- 利用者に DevTools のスクリーンショットを頼むと、リクエストヘッダの `Authorization: Basic` の値まで写り込むことがある。頼むときは General の欄だけを指定する (実測)

- 長さの検査より前に全文へ走る正規化を足すと、それまで有界だった入力に無界の処理が入る。セキュリティの観点のレビューがこの回帰を拾った (実測)。報告者の提案は、正規化 (置換) を入力の検査より前に置く変更では、正規表現の後戻りの計算量を確かめることをレビューの観点に足すこと。正規表現の側の具体は ISSUE-134
- 反証役が「今の設定では到達しない」と判定したセキュリティの指摘でも、多層防御として安く入るもの (外部の検証 API の応答のホスト名の照合など) は採る価値がある。本番で実際に一致することも確かめた (実測)
- URL からホストを `split("://")` と `split("/")` で取り出して禁止の集合と照合するゲートは、`https://host:443` のようなポート付きと大文字のホストですり抜けた。`urlsplit(url).hostname` (ポートを落とし小文字にする) で照合し、ポート付きと大文字の例をテストで固定する (実測)
- Make の `$(filter prefix_%,$(VAR))` で名前空間を検査すると、filter は空白で語を切るので、空白を含む値 (`prefix_a other`) が通る。文字種の検査を別に置く必要がある (実測)。報告者の提案は、グローバル CLAUDE.md のセキュリティのカテゴリの「charset 検証を名前空間の検証と兼用しない」に実例として足すこと
- 多層防御のつもりで、下の層の判定 (テナントの一致) に渡す2つのラベルを同じ値から組むと、その判定は恒真になり層として効かない。レビューで「層がある」ことを確かめても見逃し、ラベルの出所を問うて初めて見つかった (実測)
- 認可の経路を、構築子を private にした証人型で表し、照合を通った値でしか効果へ進めないことをコンパイラに確かめさせた。証人は可視性の1語で黙って消える (フィールドに pub を付けてもエラーも警告も出ない) ので、ast-grep で型の守りの取り付けを数える2層の構成にすると、変異 (フィールドを広げる、mod の外で作る、ルールを外す) を全部捕まえた (実測)。報告者の提案は、証人型を入れるときのチェックリストとして、構築の場所、定義の形が tuple の struct のままであること、Clone / Copy の有無、証人を作る関数の入力になる trait の実装の集合、の4つを ast-grep で数えることを Reference (置き場のファイルは指定なし) に足すこと
  - 同じ報告の中で、証人から Clone / Copy を外し、受理する関数に証人を消費させると「1回の照合で受理できるのは1本」がコンパイラで保証される。足し戻しは derive の属性と手書きの impl の両方を ast-grep で数えられた (実測)
  - 同じ報告の中で、証人が保証するのは「証人を作る関数に渡した trait の実装 (照合の hasher、読み出しの effects) が答えた値」までで、緩い実装を書いて渡すと型にもテストにもルールにも捕まらなかった。証人型を入れるときは、入力になる trait の実装の集合を閉じる (実装を足す変更を数える) ルールまでを1組にする (実測)
  - trait の実装の集合を閉じるルールを置く件はこの項に寄せる。閉じ方の穴 (impl の trait パスの末尾で閉じると別名の use 経由の impl を通す) と、証人型のルールを denylist ではなく allowlist で書く件、綴りの列挙の穴は、ISSUE-88 の INS-55 / INS-56 にある
- 端末に出す外から来た値は、制御文字だけでなく Unicode の書式文字 (bidi の上書き、ゼロ幅、BOM) も見える形に置き換えないと、行の並びを入れ替えられたり別の値が同じ見た目になったりする。Unicode プロパティの Cc と Cf を1本の正規表現で当てると両方を覆えた。テストで改行を剥いでから検査すると改行の漏れを見逃す (実測)
  - 2026-11-10の仕分けで、別のリポジトリから補強の報告が届いた。文字の拒否集合を Unicode の1つの性質 (Default_Ignorable_Code_Point) に寄せたあと、その外の書式制御を1件だけ名指しで足したら、同じ理由が当てはまる Cf の文字が29個残っていた。並列レビューの「根本原因の深さ」の観点がこれを拾い、基準を一般カテゴリと性質の和 (Cc・Zl・Zp・Cf・DI) から通すものだけを引く形にした。名指しの例外を1件でも足したら、その理由が当てはまる一般カテゴリ全体を数える (実測)
- 本番で確かめるための一時的なエンドポイントは、本物の状態とは別の鍵だけを扱い、本物の状態を外から置けない形にすると安全に置ける。確かめたら撤去する (実測)
- 削除した API トークンの失効を、値を画面に出さずに HTTP のステータスだけで確かめた。同じエンドポイントを新しい (権限を絞った) トークンで叩くと403、削除した古いトークンだと401になり、並べると「トークン自体が拒否された」と「権限の外で拒否された」を区別できた。消す前に古い参照で同じ probe を一度回し、「生きていて広い権限を持つ」ことを対照として記録しておくと、削除後の401を削除の証拠として読めた (実測)
- 401という数字だけでは「失効したトークンを拒んだ」と「トークンが届いていない」を区別できず、本文の message の文言で見分けた。パイプの左の `op read` が失敗しても右の curl はトークン無しで走り、後者の401が返る。失効の確認は `op read | sed | curl --config -` の形で argv に値を載せずに行った (実測)
- 1Password CLI の `op read` の失敗の理由は stderr の1行 (「vault にそのアイテムが無い」など) にそのまま出るので、`2>/dev/null` で捨てずに流す。`2>&1` で値と一緒に取らないのは、op が stderr に出す告知が値に混ざりうるため。同じプロセスの中で手前の `op read` が通っていることが、承認の待ちではないことの対照になった (実測)。報告者の提案は、「`op read` / `op item get` の stderr を捨てない」を ast-grep か grep の lint にすること。捨てている箇所は「無いなら作る」の分岐で重複したアイテムを作らせうる (推測)
- シークレットマネージャの CLI で値を変数に読み、ログに秘匿値が含まれないことを `grep -cF "$VAR"` で数えるとき、参照の解決に失敗して値が空だと全行に一致し、件数がログの総行数になる。`grep -v` 系や「0件なら健全」の判定では偽の緑になりうるので、数える前に変数の長さを検査する。長さのガードで止められた (実測)。報告者の提案は、手順書や skill に値が空でないことの確認を必ず前に置くこと
  - 2026-11-10の仕分けで、別のリポジトリから同じ手当ての報告が届いた。値を `op read` でシェル変数に入れて `grep -c -F "$VAR"` で出現回数だけを数えるとき、変数の長さ (非空であること) を併記した (実測)
- 巨大な書き出しの SVG を追跡下へ入れる前の全文の確認は、座標データ (d・transform) を省いた本文を読み、省いた値の文字種が描画コマンドと数だけであることを別に数える形で行い、これで実質的に全体を読んだことになる (実測)。見立て (推測。仕分けたセッションの解釈): グローバル CLAUDE.md の「未読のファイルを追跡下へ入れるときは先に全文を読む」の射程を、この読み方まで広げてよいかは反証にかける
- トークンの回し方の手順には、計画して回す場合 (新しいトークンで確かめてから古いものを失効) と、漏れた疑いがある場合 (範囲を読み取ってから古いものを先に失効) の分岐を、最初から持たせる。前者の順序は安全装置だが、漏洩の場面では逆向きに働く (実測。反証レビューで見つかった)。見つけた反証レビューの観点は hook と委譲の節に置いた
- 非公開のリポジトリの一部を、履歴を持たない別のリポジトリへ byte 一致で一方向に写す仕組みを作った。写す前に漏洩の針 (実行時に導いた値と固定の形) を当て、写した後は写しの HEAD と origin の先端を正本と照合する (実測)。同じ報告で、品質ゲートの並列レビュー (reuse / simplification / efficiency / altitude の4観点とコードレビュー・ボーイスカウト・漏洩スイープ) を、写す範囲が将来公開されることを前提に、リポジトリ自体は非公開でも漏洩スイープまで回した (実測)。漏洩の検査を今の公開範囲ではなく将来の公開範囲で決めた形にあたる
- 設定の画面のスクリーンショットで、画面に文字で並んでいた Webhook の URL (知っていれば投稿できる秘密) の一部が transcript に入った。秘密の値を表示する画面では撮らず、名前で要素を探して押し、読むのは URL とメールアドレスを置換した文字だけにする。漏れた Webhook は末尾を削るなどの編集では無効にならないので、削除して作り直す (実測)。上の DevTools のスクリーンショットの項は利用者に頼む場面で、こちらはエージェント自身が撮った場面
- advisory の URL の owner が見慣れない形 (本家の org の移転後の名前) のときは、旧名でも同じ advisory が返るか、リポジトリの作成日と star 数を引いて出所を確かめてから中身を読んだ (実測)
- 2026-11-13の仕分けで、別のリポジトリから届いた。Makefile のレシピで外部の値を扱うときは、値を make の展開でシェルの文字列に埋め込まず、環境変数として渡してクォート付きで参照すると、シェルへの注入に強くなる (実測、レビューで確認)。仕分けたセッションの解釈: この節の Make の `$(filter prefix_%,$(VAR))` の項と同じく、Make が値をシェルへ渡す境界の話

### ホスト環境

- ローカルのサービスのポートを固定するとき、既定のポートや OS の一時ポートの範囲を避ける。E2E の vite preview を既定の4173で起動すると、同じ機械で並行して動く別のプロジェクトのサーバーとぶつかり、strictPort で起動の時点で止まった (実測)。別のリポジトリは、OS の一時ポートの範囲 (macOS は49152〜65535で sysctl で実測、Linux の既定は32768〜60999) や Supabase の自動割り当ての帯の外 (20000未満) に固定すると、外向きの接続が同じ番号を選んで待ち受けに失敗する偶発的な起動の失敗を構造的に避けられる、と報告した (macOS の範囲は実測、Linux と Supabase の帯はドキュメントのみ、効果は推測で実装と検証はこれから)。固定のポートで E2E を並列に回せない報告は、hook と委譲の節に置いた
- `docker volume prune -f` は現行の Docker では匿名ボリュームだけを消す。実行前に名前付きボリュームの一覧をファイルへ書き、実行後の一覧と diff して不変を確かめると安全に使える (実測)
- dangling な匿名ボリュームの出所は、使い捨てのコンテナを `debian:*-slim` で読み取り専用マウントして `PG_VERSION` とファイルの所有者 UID を見ると絞れる (実測)
- `docker image prune -a` は、registry から pull し直せるイメージだけでなく、ローカルでビルドしたイメージ (ほかのリポジトリのテスト用ハーネスなど) も消す (ドキュメントのみ)
- 報告者の提案は、ホスト全体に効く掃除 (Docker の匿名ボリュームと未使用イメージ、pnpm の store prune、パッケージマネージャから外したツールの設定ディレクトリ) を、各作業リポジトリの Makefile ではなく、マシン共通の設定を持つリポジトリのスクリプトとして1本にまとめること (推測)。見立て (推測。仕分けたセッションの解釈): マシン共通の設定を持つリポジトリは dotfiles にあたり、採るなら独立した Issue に切り出す候補
- 短いコンテナの peak は、until ループで `docker stats --no-stream` を0.5秒おきにファイルへ追記し、処理の終了後に `sort -h` で最大を取ると取れる。26秒の処理で23サンプル取れた (実測)。報告者の提案は、長時間のプロセスのメモリを見る規範 (無音なら RSS を見る) に、「短いコンテナの peak は単発の stats では映らないので、短い間隔で見張りながら回す」を添えること (実測)
