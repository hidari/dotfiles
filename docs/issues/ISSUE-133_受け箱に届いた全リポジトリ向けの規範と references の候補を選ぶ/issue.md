# docs(rules): 受け箱に届いた全リポジトリ向けの規範と references の候補を選ぶ

## 背景

2026-10-21 に受け箱へ届いたまとめのうち、特定の技術領域に閉じず、どのリポジトリの作業にも効きうる知見をここへ集める。2026-10-22に届いた7件から足した分は、各節の末尾に置いた。2026-10-23に仕分けた5件 (届いたのは2026-10-22) から足した分も各節の末尾に置き、/goal の運用は新しい節に置いた。2026-10-31に仕分けた72件 (届いたのは2026-10-22〜2026-10-30) から足した分は、各節の末尾と、新しく立てた節に置いた。検査と変異注入の知見は ISSUE-88、初回の exec の遅れは ISSUE-66、起動元シェルの PATH の鮮度は ISSUE-69 へ分けた。特定の技術領域の知見は ISSUE-134 へ分けた。

どれも他のリポジトリのセッションの報告で、根拠は報告者の申告 (実測 / 推測 / ドキュメントのみ) をそのまま書く。dotfiles で確かめたものは項目の中で分けて書く。採るかどうかと置き場は未決。

### セキュリティ

- 独自ヘッダで秘密を送る配線 (認証プロキシの service token など) を fetch の包みで全要求へ足すと、fetch の仕様は別オリジンへの redirect で Authorization 以外のヘッダを落とさないので、302 を辿った先へ秘密が運ばれる。包みは接続先と同じオリジンにだけ足し、redirect は manual にする。テストは別ポートのもう1台のサーバへ 302 を返し、届いた件数0を接続先の受信を対照にして pin する。オリジン判定の「scheme が同じか」の腕は、テストのサーバが全部平文だと消しても緑で通るので、接続先を https として名乗り同じ host とポートへ平文で要求を出して腕を外す変異で赤にする (実測、変異で赤を確認)
  - 2026-10-31の仕分けで、別のリポジトリから Python 版の報告が届いた。urllib の既定の opener は redirect を追い、Request に付けた Authorization ヘッダも redirect 先へ送りうるので、Basic 認証を付ける採取の道具は redirect を追わない opener にする (ドキュメントのみ)
  - 2026-10-31の仕分けで、別のリポジトリからブラウザ自動化の経路の報告が届いた。保護下のフロントを開くとき、bypass のヘッダを context 全体の extraHTTPHeaders ではなく route で配信先のホストへの要求にだけ付けた。全体に付けると別ドメインの API へ秘密のヘッダが送られる (推測。仕組みからの判断で、漏れは観測していない)
- 秘密の値を会話・ログ・subagent に出さないため、書き捨てのシェルスクリプトの中で 1Password の `op read` の結果を直接ヘッダや子プロセスの環境変数へ流し、値の代わりに形 (接頭辞・長さ・文字種) だけを数えて確かめた (実測)
  - 2026-10-31の仕分けで、別のリポジトリから同じ目的の別の形が2つ届いた。鍵を env で渡して SQL の中では getenv で読み、SQL は標準入力で DuckDB に渡すと、鍵がプロセスの引数にも SQL のファイルにも出なかった。API トークンは `curl --config -` へ標準入力から `header = "Authorization: Bearer ..."` で渡すと、引数にも画面にも出さずに使えた (どちらも実測)。同じ書き捨てのスクリプトの形が auto mode の分類器に止められた報告は、新しく立てた「Claude Code の auto mode と権限」の節に置いた
- 値の形に関する自分の知識も、仕様を引くまでは未確認の前提として扱う。秘密の形式が発行時期で変わっていて、古い知識で形を検査すると「別の値が入っている」と誤判定した (ドキュメントのみ。手元の値の形がドキュメントと一致することは実測)
- 秘密が漏れた範囲を確かめるとき、元の transcript から値をメモリの上でだけ取り出し、ディレクトリ配下の全ファイルを bytes で照合して件数とパスだけを出すと、値を会話へ持ち込まずに済む。環境変数の広がりも、値を表示せず「その値を含むファイルの数」で数えた (実測)
  - 2026-10-31の仕分けで、別のリポジトリから同じ型の報告が届いた。シークレットを含むログをホストへ回収し、値をファイルから読む小さなスクリプトで件数だけを出し、値ごとに合成の1行を対照に置くと、値を表示せずに「0件」と「見ていない」を区別できた (実測)
- 利用者に DevTools のスクリーンショットを頼むと、リクエストヘッダの `Authorization: Basic` の値まで写り込むことがある。頼むときは General の欄だけを指定する (実測)
- ブラウザ自動化の拡張機能が開いた新しいタブには、利用者が別のタブで通した HTTP Basic 認証が引き継がれず、ページが503になった。Basic 認証の後ろにある環境の実ブラウザでの確認は利用者のタブで行ってもらい、資格情報をエージェントが入力することはしない (実測)
- 長さの検査より前に全文へ走る正規化を足すと、それまで有界だった入力に無界の処理が入る。セキュリティの観点のレビューがこの回帰を拾った (実測)。報告者の提案は、正規化 (置換) を入力の検査より前に置く変更では、正規表現の後戻りの計算量を確かめることをレビューの観点に足すこと。正規表現の側の具体は ISSUE-134
- 反証役が「今の設定では到達しない」と判定したセキュリティの指摘でも、多層防御として安く入るもの (外部の検証 API の応答のホスト名の照合など) は採る価値がある。本番で実際に一致することも確かめた (実測)
- URL からホストを `split("://")` と `split("/")` で取り出して禁止の集合と照合するゲートは、`https://host:443` のようなポート付きと大文字のホストですり抜けた。`urlsplit(url).hostname` (ポートを落とし小文字にする) で照合し、ポート付きと大文字の例をテストで固定する (実測)
- Make の `$(filter prefix_%,$(VAR))` で名前空間を検査すると、filter は空白で語を切るので、空白を含む値 (`prefix_a other`) が通る。文字種の検査を別に置く必要がある (実測)。報告者の提案は、グローバル CLAUDE.md のセキュリティのカテゴリの「charset 検証を名前空間の検証と兼用しない」に実例として足すこと
- 多層防御のつもりで、下の層の判定 (テナントの一致) に渡す2つのラベルを同じ値から組むと、その判定は恒真になり層として効かない。レビューで「層がある」ことを確かめても見逃し、ラベルの出所を問うて初めて見つかった (実測)
- 認可の経路を、構築子を private にした証人型で表し、照合を通った値でしか効果へ進めないことをコンパイラに確かめさせた。証人は可視性の1語で黙って消える (フィールドに pub を付けてもエラーも警告も出ない) ので、ast-grep で型の守りの取り付けを数える2層の構成にすると、変異 (フィールドを広げる、mod の外で作る、ルールを外す) を全部捕まえた (実測)。報告者の提案は、証人型を入れるときのチェックリストとして、構築の場所、定義の形が tuple の struct のままであること、Clone / Copy の有無、証人を作る関数の入力になる trait の実装の集合、の4つを ast-grep で数えることを `references/security.md` に足すこと
  - 2026-10-31の仕分けで、同じ報告元から続きが届いた。証人から Clone / Copy を外し、受理する関数に証人を消費させると「1回の照合で受理できるのは1本」がコンパイラで保証される。足し戻しは derive の属性と手書きの impl の両方を ast-grep で数えられた (実測)
  - 2026-10-31の仕分けで、同じ報告元から続きが届いた。証人が保証するのは「証人を作る関数に渡した trait の実装 (照合の hasher、読み出しの effects) が答えた値」までで、緩い実装を書いて渡すと型にもテストにもルールにも捕まらなかった。証人型を入れるときは、入力になる trait の実装の集合を閉じる (実装を足す変更を数える) ルールまでを1組にする (実測)
- 端末に出す外から来た値は、制御文字だけでなく Unicode の書式文字 (bidi の上書き、ゼロ幅、BOM) も見える形に置き換えないと、行の並びを入れ替えられたり別の値が同じ見た目になったりする。Unicode プロパティの Cc と Cf を1本の正規表現で当てると両方を覆えた。テストで改行を剥いでから検査すると改行の漏れを見逃す (実測)
- 本番で確かめるための一時的なエンドポイントは、本物の状態とは別の鍵だけを扱い、本物の状態を外から置けない形にすると安全に置ける。確かめたら撤去する (実測)
- 削除した API トークンの失効を、値を画面に出さずに HTTP のステータスだけで確かめた。同じエンドポイントを新しい (権限を絞った) トークンで叩くと403、削除した古いトークンだと401になり、並べると「トークン自体が拒否された」と「権限の外で拒否された」を区別できた。消す前に古い参照で同じ probe を一度回し、「生きていて広い権限を持つ」ことを対照として記録しておくと、削除後の401を削除の証拠として読めた (実測)
- 401という数字だけでは「失効したトークンを拒んだ」と「トークンが届いていない」を区別できず、本文の message の文言で見分けた。パイプの左の `op read` が失敗しても右の curl はトークン無しで走り、後者の401が返る。失効の確認は `op read | sed | curl --config -` の形で argv に値を載せずに行った (実測)
- 1Password CLI の `op read` の失敗の理由は stderr の1行 (「vault にそのアイテムが無い」など) にそのまま出るので、`2>/dev/null` で捨てずに流す。`2>&1` で値と一緒に取らないのは、op が stderr に出す告知が値に混ざりうるため。同じプロセスの中で手前の `op read` が通っていることが、承認の待ちではないことの対照になった (実測)。報告者の提案は、「`op read` / `op item get` の stderr を捨てない」を ast-grep か grep の lint にすること。捨てている箇所は「無いなら作る」の分岐で重複したアイテムを作らせうる (推測)
- シークレットマネージャの CLI で値を変数に読み、ログに秘匿値が含まれないことを `grep -cF "$VAR"` で数えるとき、参照の解決に失敗して値が空だと全行に一致し、件数がログの総行数になる。`grep -v` 系や「0件なら健全」の判定では偽の緑になりうるので、数える前に変数の長さを検査する。長さのガードで止められた (実測)。報告者の提案は、手順書や skill に値が空でないことの確認を必ず前に置くこと
- 巨大な書き出しの SVG を追跡下へ入れる前の全文の確認は、座標データ (d・transform) を省いた本文を読み、省いた値の文字種が描画コマンドと数だけであることを別に数える形で行った (実測。これで実質的に全体を読んだことになるという評価は推測)。グローバル CLAUDE.md の「未読のファイルを追跡下へ入れるときは先に全文を読む」の射程を、この読み方まで広げてよいかは反証にかける

### 観測

- 経路に依存する測定 (WebSocket のアイドル切断など) は、測定の前後で `route -n get` の interface を記録する。VPN を外したという報告のあとも経路が utun のままで、外した経路の測定になっていなかった (実測)
- 空のダッシュボードを読む前に、その構成で何が記録される設定かを確かめる。記録を設定で切っている場合は0件が正常だった (実測)
- fail-open の作りの機構で「拒否が出ない」は、機構の不在とも窓の境界とも読める。理由つきの拒否は機構が判定したときにしか作られないので、上限の2倍超を短時間に送って1件でも出れば、本番で機構が効いている直接の証拠になる (実測)
- ビルドのログの警告を語 (warning) で数えると、コンパイラのコマンドラインにある `-warnings-as-errors` の旗の行に大量に当たる。当たった行を読んで仕分けるまで判定できない (実測)
- E2E の失敗が症状ばらばらでも、テストが作るデータに埋まった時刻と backend のログの行数を分単位で並べると、数分の窓に集中してその窓だけ backend のログがほぼ空だった。ホスト側の停止と切り分けられた (実測)
- E2E の list reporter のログからテストごとの最後の結果を (状態, ID, タイトル) の TSV に起こし、前後2回の実行の ID 集合を突き合わせる書き捨てのスクリプトを作った。旧ログに当てて既存の基準の TSV と diff が空になることを対照にしてから使った (実測)。グローバル CLAUDE.md の「件数ではなく実行されたテストの ID 集合を pin する」の実例で、書き捨てのツール自身を対照で確かめてから使った点が加わる
- GitHub の jobs API が、needs で後続を持つ集約ジョブを in_progress / conclusion null と返したまま、その後続のジョブは completed / success になっていた。しばらく後に引き直すと completed / success に変わった。直後の1回の読みを「終わっていない」の根拠にしない (実測)
  - 2026-10-31の仕分けで、別のリポジトリから同じ型の報告が届いた。全 step が success でも job が queued や in_progress のまま返り、ランナーが拾っていないと読み違えて切り替えを一度外した。job を id で読み、steps の結果と runner_name を見る (実測)
  - 2026-10-31の仕分けで、別のリポジトリから同じ型の報告が届いた。`gh run watch --exit-status` が途中のネットワークエラーで終了コード1を返し、直後に読んだ run は途中経過 (conclusion が空なのに集約の job だけ success) で、読み直すと success だった。終了コードが0以外のときはログの末尾のエラーを見てから、completed になった後の状態を読み直す (実測)
- 接続の寿命の合否を、接続の生存時間ではなく upgrade の成立 (HTTP 101) の回数と切断の件数で判定した。アプリは切断の約3秒後には張り直して101を得るので、生存時間だけを見ると切断が見えない (実測)
- 接続が想定外の時刻に切れたとき、同じ経路と同じ時刻に「同じ keepalive を持つ別実装のクライアント」を対照として並べた。別実装も切られたので、アプリの keepalive が止まったという仮説を外せた。無音の対照だけでは「経路が無音を切る」ことしか示せない。同じプロセスの中の HTTP/2 の keep-alive 接続も、最後に使ってから無音の切断の秒数ちょうどで閉じていて、わざわざ用意しなくても手に入る対照になった (実測)。報告者の提案は、接続の寿命を測る手順の雛形に「張り直しの回数を数える」と「同じ keepalive を持つ別実装の対照を同時に並べる」を入れること
- 1回だけの測定で「keepalive で接続が保たれる」と書きかけ、2回目の測定で keepalive のある接続も不規則な時刻に切られることが出た。過去の生存の記録も、観測の窓の中でたまたま起きなかっただけと読める。長時間の接続についての主張は、窓の長さと回数を添えて書く (実測)
- 測定の結果を文書へ書くとき、ログに無い時刻を推定で書いたり、区間を取り違えたりした。結論ではなく生のログだけを渡した独立のレビュアーが、14件の数字のうち6件を「導けない、言い過ぎ」と返した。記録から上限しか言えないものは上限で書く (実測)。別のリポジトリの報告でも、文書に書いた数値を subagent にログから導き直させると、自分で書いた表の誤り (中央値の取り方、外れ値の原因の取り違え、最大値の1秒のずれ) が3件見つかった。書いた本人の見直しでは見えなかった (実測)
  - 2026-10-31の仕分けで、別のリポジトリから同じ型の報告が届いた。Issue に配信と smoke の記録を書く前に、主張ごとに ID を振り、証拠の置き場ごとの検証役と取りこぼしを探す critic を立てて一次ログと突き合わせると、引き継ぎ書とメモリから写した値の食い違いが6件 (別の run の件数、同じ言葉が別の検査を指す、読み取り専用と書いた SQL に書き込みが混ざる) 出た (実測)。報告者の提案は、記録を書いた後で証拠のログを消す前に、この突き合わせを必須の段にすること
- PR の本文に数値を写すとき、測り方 (どの版か、単独か通しか) を落とすと、数値は正しいまま主張の範囲が広がる。本文を書いたあとで一次の記録と照らして見つけた (実測)
- macOS で処理の wall clock の時間が普段の10倍に跳ねたら、原因を推測する前に `pmset -g log` で Sleep から Wake までの区間と重なるかを見る。外れ値の2件はどちらもスリープで、「ツールの遅れ」という最初の解釈は誤りだった。中身のフェーズだけを見て結論し、マシンの状態 (スリープや負荷) を後回しにしていた (実測)。報告者の提案は、時間を測る検証の手順書や skill にこの1行を足すこと
- 長時間の E2E が1件だけ時間切れで落ちたとき、trace の通信記録から「今回の変更が通るパスのリクエストが、落ちた経路に何本あったか」を数えて (0本) 無関係を確かめ、そのうえで全件を回し直して rc 0 を得た。単独で回して通ることだけでは flaky と決めなかった (実測)
- 要素の数で書いた a11y の検査 (`getByRole("status")` の件数) を、id の集合で書き直した。別の仕様の変更で数が動いたとき、どちらの仕様が動いたかを読み分けられる (実測)。上の、E2E の結果を ID の集合で突き合わせる項と同じ形
- LLM の評価は1回ごとに揺れるので、不合格の顔ぶれを2回分並べて「同じケースが2回とも落ちるか」で傾向を読むと、1回の差を直しの効果と誤読しない (実測)
- E2E の line reporter のログからテストの ID の集合を作るとき、リトライの行は題名の末尾に `(retry #N)` が付くので、落とさないと同じテストが別の ID になる。「生の行数と union の件数が一致した」は正しさの証拠にならず、リトライがあるなら union は行数より少なくなるのが正しい (実測)。上の、ID の集合で突き合わせる項の落とし穴にあたる
- CI のログを grep した件数は、テスト名や、Actions がログに出すスクリプトの本文にも当たる。どのジョブの出力かを確かめずに件数を記録へ書きかけた。ジョブ名の列で絞ってから数える (実測)
- Monitor の grep に `failed` のような一般の語を入れると、テスト名に含まれる語を拾って通知が溢れた。テストランナーの集計行の形 (`N passed` など) に絞る (実測)
- 2つの run の実行テストの ID 集合を抜いて diff したが、抽出が1件もマッチせず、空同士の diff が「一致」になった。件数を先に出していたので気づけた (実測)。報告者の提案は、diff の前に両方の件数を出して非0を確かめる手順を、観測の規範の対照の項へ例として足すこと。上の、ID の集合で突き合わせる項の落とし穴にあたる

### シェルとコマンド

- bash の `set -e` は、`cd "$(git rev-parse --git-common-dir)"` のように引数の中のコマンド置換の失敗を見ない。`cd ""` が成功して処理が続き、パスがリポジトリの外を指した。コマンド置換は単独の代入の行で受ける (委譲先の reviewer がリポジトリの外で再現)
- `make -n` は再帰の `$(MAKE)` を含む行とその中で呼ばれるコマンドを実際に走らせる。待機ループを持つターゲットに当てるとループが実走する。`make -n` を当てるのは再帰の無い葉のターゲットだけにする (実測)
- macOS の zsh には `timeout` コマンドが無い (実測)。dotfiles で確かめたこと: この開発機でも `timeout` と `gtimeout` はどちらも PATH に無い
- zsh で `=` から始まる語を引数に置くと、`=cmd` のコマンドパス展開として解釈される。`echo ======` は `===== not found` でコマンドごと失敗する。区切り線は `-----` にするか引用符で囲む (実測)。dotfiles で確かめたこと: この開発機の Bash ツールでも `echo ====x` が `===x not found` で失敗した
  - 2026-10-23に仕分けた分で、2つのリポジトリから同じ報告が届いた (どちらも実測)。区切りの echo が複合コマンドごと exit 1 になり、後続のコマンドが走らなかった。報告者の提案は、グローバルの観測ルールの「Bash ツールでコマンドを組むとき、成否と状態が沈黙して失われる経路」にこの型を足すこと
  - dotfiles で確かめたこと (2026-10-23、zsh 5.9): `zsh -c 'echo ====x; echo after'` は `;` の後ろの `echo after` も走らず rc 1 になった。`&&` で繋いでいなくても落ちる。bash では両方が出て、zsh でも `"====x"` と引用すれば通った。グローバルの CLAUDE.md と `references/` と `rules/` には、`EQUALS` / `=cmd` / `====` のどれも出てこない (対照として `zsh` は `references/observation.md` に4件当たる)
- `git rev-parse --short A B` のように `--short` へ2つ渡すと落ちる (実測)。dotfiles で確かめたこと: `git rev-parse --short HEAD HEAD~1` は `fatal: Needed a single revision` で rc 128 になり、`--short` を外すと2行を返した
- `until ! pgrep -f "<コマンド>"; do sleep N; done` の形の待ちのループを background に置くと、終わらないまま残った。`pgrep -f` はコマンド行の全文を照合するので、その文字列を含むループ自身の zsh に当たり、条件が永遠に偽になる。待つ対象はプロセス名ではなく、pid (`kill -0 <pid>`) か、終わったときに書かれるファイルで見る (実測)
  - 2026-10-31の仕分けで、別のリポジトリから同じ型の報告が届いた。バックグラウンドの待ちのシェルを「HEAD の subject が一致するまで」で書くと、ブランチを切り替えた後に満たされず孤児として残り、10本ほど溜まった。条件はレポートの出現や子プロセスの終了にし、ブランチを切り替える前に自分の待ちを止める (実測)

- 同じ生成物ディレクトリを作り直す2つのタスクランナーの recipe (全体のゲートと E2E) を並べて走らせたら、片方が途中のディレクトリを読んで ENOENT で赤くなった。コードの不具合に見えるので取り違えやすい (実測)。報告者の提案は、ホスト環境やタスクランナーの規範に「同じ生成物ディレクトリを書く recipe を並べて走らせない」を足すこと
- Edit ツールは new_string の中の `\uXXXX` を JSON のエスケープとして解き、生の文字をファイルに書く。U+3040 のような未割り当ての文字は見えないので、差分を目で見ても気づけない。報告元は `od -c` と、エスケープの文字列での grep が0件になることで気づいた。回避は `\u` を書かない形 (正規表現なら Unicode プロパティ) にするか、Python の read と replace で書くこと (実測)。報告者の提案は、Edit / Write ツールで JS や JSON のソースに `\u` を書く場面がある規約やテンプレートに、書いた後にエスケープの文字列で grep して残っていることを確かめるか、Unicode プロパティで書くかを添えること。Unicode プロパティの書き方は ISSUE-134

- 既存のコミットへタグだけを push すると、pre-commit の pre-push hook は走らなかった。使い捨ての bare リモートで、新しいコミットを含む push を対照に確かめた (実測)。pre-push に CI 相当の検査を載せていても、タグを起点にするリリースは検査を通らない。報告者の提案は、リリースのタスクの側で検査を前段に置く規約を共有の手順へ入れること。事実は dotfiles のメモリの「pre-commit の stage 挙動」にある
- 「index の件数が0なら全件の同期、そうでなければ差分の同期」という判定は、同期より先に外部の書き込みが1件入ると裏返り、欠けたまま固まった。空の判定を件数0で行うと、境界 (0と1) を他の書き込みが踏む (実測)
- 消す前の worktree の確認で、ahead/behind がどちらも0で porcelain が空なことに加えて、その branch に open の PR があるか (作成の時刻とラベル) を見ると、数分前に作られた別作業の worktree を消すのを避けられた (実測)
- 常時ロードの索引を縮めるとき、行を言い換えずに子の索引へ逐語で移し、移動先に1回・元に0回あること、触らないファイルがバイトで不変であることを assert すると、条件節が落ちなかった (実測)。dotfiles のメモリの「索引の圧縮は条件を緩める」への手当てにあたる
- 重複を消すために2つの実測を1つの文へ畳んだら、どの日にどの値を読んだか、どの変更より前かが落ち、範囲も広がった。散文を参照へ畳む修正は、それ自体が次のレビューの所見を生む (実測)。報告者の提案は、グローバル CLAUDE.md の「散文を参照へ書き換えたら検算する」の4点に、「畳んだ実測の日付・値・前後関係が残っているか」を足すこと
- 複数のファイルへの書き捨ての置換や差分の適用は、置換ごとに元の文字列 (原文の抜粋) が本文にちょうど1件あることを確かめ、全部が当たってから書き込み、当たらなかったものを報告させると、半端な書き換えが残らなかった (実測。2つの報告が届いた)
  - 2026-10-31の仕分けで、同じ報告元から続きが届いた。調査役に、追記を指定した抜粋の行の後ろへ挿入させると、空行なしで直前の段落にくっつき、Markdown の上では同じ段落になった。挿入の後に空行で分ける後処理が要った (実測)
- 既存の関数の doc コメントと関数の間に新しい関数を挿すと、既存の doc が新しい関数に付き替わり、コンパイル・clippy・テストは緑のままだった。差分を読むレビューが見つけた (実測)
- 「セッションの終了時に起動したコンテナを落とすか確かめる」規則をあるリポジトリの CLAUDE.md に足したところ、レビューで「リポジトリ固有の要素が無い一般則なので、グローバルのホスト環境の節か handoff の skill か、コンテナが動いているときだけ告知する Stop hook に置くほうが、常時ロードの費用も効き目もよい」と指摘された (推測。置き場の判断はユーザーに委ねている)。常時層の予算と ISSUE-48 の到達の観点で決める
