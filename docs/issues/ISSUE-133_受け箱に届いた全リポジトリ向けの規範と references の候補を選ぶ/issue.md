# docs(rules): 受け箱に届いた全リポジトリ向けの規範と references の候補を選ぶ

## 背景

2026-10-21 に受け箱へ届いたまとめのうち、特定の技術領域に閉じず、どのリポジトリの作業にも効きうる知見をここへ集める。2026-10-22に届いた7件から足した分は、各節の末尾に置いた。2026-10-23に仕分けた5件 (届いたのは2026-10-22) から足した分も各節の末尾に置き、/goal の運用は新しい節に置いた。検査と変異注入の知見は ISSUE-88、初回の exec の遅れは ISSUE-66、起動元シェルの PATH の鮮度は ISSUE-69 へ分けた。特定の技術領域の知見は ISSUE-134 へ分けた。

どれも他のリポジトリのセッションの報告で、根拠は報告者の申告 (実測 / 推測 / ドキュメントのみ) をそのまま書く。dotfiles で確かめたものは項目の中で分けて書く。採るかどうかと置き場は未決。

### セキュリティ

- 独自ヘッダで秘密を送る配線 (認証プロキシの service token など) を fetch の包みで全要求へ足すと、fetch の仕様は別オリジンへの redirect で Authorization 以外のヘッダを落とさないので、302 を辿った先へ秘密が運ばれる。包みは接続先と同じオリジンにだけ足し、redirect は manual にする。テストは別ポートのもう1台のサーバへ 302 を返し、届いた件数0を接続先の受信を対照にして pin する。オリジン判定の「scheme が同じか」の腕は、テストのサーバが全部平文だと消しても緑で通るので、接続先を https として名乗り同じ host とポートへ平文で要求を出して腕を外す変異で赤にする (実測、変異で赤を確認)
- 秘密の値を会話・ログ・subagent に出さないため、書き捨てのシェルスクリプトの中で 1Password の `op read` の結果を直接ヘッダや子プロセスの環境変数へ流し、値の代わりに形 (接頭辞・長さ・文字種) だけを数えて確かめた (実測)
- 値の形に関する自分の知識も、仕様を引くまでは未確認の前提として扱う。秘密の形式が発行時期で変わっていて、古い知識で形を検査すると「別の値が入っている」と誤判定した (ドキュメントのみ。手元の値の形がドキュメントと一致することは実測)
- 秘密が漏れた範囲を確かめるとき、元の transcript から値をメモリの上でだけ取り出し、ディレクトリ配下の全ファイルを bytes で照合して件数とパスだけを出すと、値を会話へ持ち込まずに済む。環境変数の広がりも、値を表示せず「その値を含むファイルの数」で数えた (実測)
- 利用者に DevTools のスクリーンショットを頼むと、リクエストヘッダの `Authorization: Basic` の値まで写り込むことがある。頼むときは General の欄だけを指定する (実測)
- ブラウザ自動化の拡張機能が開いた新しいタブには、利用者が別のタブで通した HTTP Basic 認証が引き継がれず、ページが503になった。Basic 認証の後ろにある環境の実ブラウザでの確認は利用者のタブで行ってもらい、資格情報をエージェントが入力することはしない (実測)
- 長さの検査より前に全文へ走る正規化を足すと、それまで有界だった入力に無界の処理が入る。セキュリティの観点のレビューがこの回帰を拾った (実測)。報告者の提案は、正規化 (置換) を入力の検査より前に置く変更では、正規表現の後戻りの計算量を確かめることをレビューの観点に足すこと。正規表現の側の具体は ISSUE-134
- 反証役が「今の設定では到達しない」と判定したセキュリティの指摘でも、多層防御として安く入るもの (外部の検証 API の応答のホスト名の照合など) は採る価値がある。本番で実際に一致することも確かめた (実測)

### 観測

- 経路に依存する測定 (WebSocket のアイドル切断など) は、測定の前後で `route -n get` の interface を記録する。VPN を外したという報告のあとも経路が utun のままで、外した経路の測定になっていなかった (実測)
- 空のダッシュボードを読む前に、その構成で何が記録される設定かを確かめる。記録を設定で切っている場合は0件が正常だった (実測)
- fail-open の作りの機構で「拒否が出ない」は、機構の不在とも窓の境界とも読める。理由つきの拒否は機構が判定したときにしか作られないので、上限の2倍超を短時間に送って1件でも出れば、本番で機構が効いている直接の証拠になる (実測)
- ビルドのログの警告を語 (warning) で数えると、コンパイラのコマンドラインにある `-warnings-as-errors` の旗の行に大量に当たる。当たった行を読んで仕分けるまで判定できない (実測)
- E2E の失敗が症状ばらばらでも、テストが作るデータに埋まった時刻と backend のログの行数を分単位で並べると、数分の窓に集中してその窓だけ backend のログがほぼ空だった。ホスト側の停止と切り分けられた (実測)
- E2E の list reporter のログからテストごとの最後の結果を (状態, ID, タイトル) の TSV に起こし、前後2回の実行の ID 集合を突き合わせる書き捨てのスクリプトを作った。旧ログに当てて既存の基準の TSV と diff が空になることを対照にしてから使った (実測)。グローバル CLAUDE.md の「件数ではなく実行されたテストの ID 集合を pin する」の実例で、書き捨てのツール自身を対照で確かめてから使った点が加わる
- GitHub の jobs API が、needs で後続を持つ集約ジョブを in_progress / conclusion null と返したまま、その後続のジョブは completed / success になっていた。しばらく後に引き直すと completed / success に変わった。直後の1回の読みを「終わっていない」の根拠にしない (実測)
- 接続の寿命の合否を、接続の生存時間ではなく upgrade の成立 (HTTP 101) の回数と切断の件数で判定した。アプリは切断の約3秒後には張り直して101を得るので、生存時間だけを見ると切断が見えない (実測)
- 接続が想定外の時刻に切れたとき、同じ経路と同じ時刻に「同じ keepalive を持つ別実装のクライアント」を対照として並べた。別実装も切られたので、アプリの keepalive が止まったという仮説を外せた。無音の対照だけでは「経路が無音を切る」ことしか示せない。同じプロセスの中の HTTP/2 の keep-alive 接続も、最後に使ってから無音の切断の秒数ちょうどで閉じていて、わざわざ用意しなくても手に入る対照になった (実測)。報告者の提案は、接続の寿命を測る手順の雛形に「張り直しの回数を数える」と「同じ keepalive を持つ別実装の対照を同時に並べる」を入れること
- 1回だけの測定で「keepalive で接続が保たれる」と書きかけ、2回目の測定で keepalive のある接続も不規則な時刻に切られることが出た。過去の生存の記録も、観測の窓の中でたまたま起きなかっただけと読める。長時間の接続についての主張は、窓の長さと回数を添えて書く (実測)
- 測定の結果を文書へ書くとき、ログに無い時刻を推定で書いたり、区間を取り違えたりした。結論ではなく生のログだけを渡した独立のレビュアーが、14件の数字のうち6件を「導けない、言い過ぎ」と返した。記録から上限しか言えないものは上限で書く (実測)。別のリポジトリの報告でも、文書に書いた数値を subagent にログから導き直させると、自分で書いた表の誤り (中央値の取り方、外れ値の原因の取り違え、最大値の1秒のずれ) が3件見つかった。書いた本人の見直しでは見えなかった (実測)
- PR の本文に数値を写すとき、測り方 (どの版か、単独か通しか) を落とすと、数値は正しいまま主張の範囲が広がる。本文を書いたあとで一次の記録と照らして見つけた (実測)
- macOS で処理の wall clock の時間が普段の10倍に跳ねたら、原因を推測する前に `pmset -g log` で Sleep から Wake までの区間と重なるかを見る。外れ値の2件はどちらもスリープで、「ツールの遅れ」という最初の解釈は誤りだった。中身のフェーズだけを見て結論し、マシンの状態 (スリープや負荷) を後回しにしていた (実測)。報告者の提案は、時間を測る検証の手順書や skill にこの1行を足すこと
- 長時間の E2E が1件だけ時間切れで落ちたとき、trace の通信記録から「今回の変更が通るパスのリクエストが、落ちた経路に何本あったか」を数えて (0本) 無関係を確かめ、そのうえで全件を回し直して rc 0 を得た。単独で回して通ることだけでは flaky と決めなかった (実測)
- 要素の数で書いた a11y の検査 (`getByRole("status")` の件数) を、id の集合で書き直した。別の仕様の変更で数が動いたとき、どちらの仕様が動いたかを読み分けられる (実測)。上の、E2E の結果を ID の集合で突き合わせる項と同じ形
- LLM の評価は1回ごとに揺れるので、不合格の顔ぶれを2回分並べて「同じケースが2回とも落ちるか」で傾向を読むと、1回の差を直しの効果と誤読しない (実測)
- E2E の line reporter のログからテストの ID の集合を作るとき、リトライの行は題名の末尾に `(retry #N)` が付くので、落とさないと同じテストが別の ID になる。「生の行数と union の件数が一致した」は正しさの証拠にならず、リトライがあるなら union は行数より少なくなるのが正しい (実測)。上の、ID の集合で突き合わせる項の落とし穴にあたる
- CI のログを grep した件数は、テスト名や、Actions がログに出すスクリプトの本文にも当たる。どのジョブの出力かを確かめずに件数を記録へ書きかけた。ジョブ名の列で絞ってから数える (実測)
- Monitor の grep に `failed` のような一般の語を入れると、テスト名に含まれる語を拾って通知が溢れた。テストランナーの集計行の形 (`N passed` など) に絞る (実測)

### シェルとコマンド

- bash の `set -e` は、`cd "$(git rev-parse --git-common-dir)"` のように引数の中のコマンド置換の失敗を見ない。`cd ""` が成功して処理が続き、パスがリポジトリの外を指した。コマンド置換は単独の代入の行で受ける (委譲先の reviewer がリポジトリの外で再現)
- `make -n` は再帰の `$(MAKE)` を含む行とその中で呼ばれるコマンドを実際に走らせる。待機ループを持つターゲットに当てるとループが実走する。`make -n` を当てるのは再帰の無い葉のターゲットだけにする (実測)
- macOS の zsh には `timeout` コマンドが無い (実測)。dotfiles で確かめたこと: この開発機でも `timeout` と `gtimeout` はどちらも PATH に無い
- zsh で `=` から始まる語を引数に置くと、`=cmd` のコマンドパス展開として解釈される。`echo ======` は `===== not found` でコマンドごと失敗する。区切り線は `-----` にするか引用符で囲む (実測)。dotfiles で確かめたこと: この開発機の Bash ツールでも `echo ====x` が `===x not found` で失敗した
  - 2026-10-23に仕分けた分で、2つのリポジトリから同じ報告が届いた (どちらも実測)。区切りの echo が複合コマンドごと exit 1 になり、後続のコマンドが走らなかった。報告者の提案は、グローバルの観測ルールの「Bash ツールでコマンドを組むとき、成否と状態が沈黙して失われる経路」にこの型を足すこと
  - dotfiles で確かめたこと (2026-10-23、zsh 5.9): `zsh -c 'echo ====x; echo after'` は `;` の後ろの `echo after` も走らず rc 1 になった。`&&` で繋いでいなくても落ちる。bash では両方が出て、zsh でも `"====x"` と引用すれば通った。グローバルの CLAUDE.md と `references/` と `rules/` には、`EQUALS` / `=cmd` / `====` のどれも出てこない (対照として `zsh` は `references/observation.md` に4件当たる)
- `git rev-parse --short A B` のように `--short` へ2つ渡すと落ちる (実測)。dotfiles で確かめたこと: `git rev-parse --short HEAD HEAD~1` は `fatal: Needed a single revision` で rc 128 になり、`--short` を外すと2行を返した
- `until ! pgrep -f "<コマンド>"; do sleep N; done` の形の待ちのループを background に置くと、終わらないまま残った。`pgrep -f` はコマンド行の全文を照合するので、その文字列を含むループ自身の zsh に当たり、条件が永遠に偽になる。待つ対象はプロセス名ではなく、pid (`kill -0 <pid>`) か、終わったときに書かれるファイルで見る (実測)
- 同じ生成物ディレクトリを作り直す2つのタスクランナーの recipe (全体のゲートと E2E) を並べて走らせたら、片方が途中のディレクトリを読んで ENOENT で赤くなった。コードの不具合に見えるので取り違えやすい (実測)。報告者の提案は、ホスト環境やタスクランナーの規範に「同じ生成物ディレクトリを書く recipe を並べて走らせない」を足すこと
- Edit ツールは new_string の中の `\uXXXX` を JSON のエスケープとして解き、生の文字をファイルに書く。U+3040 のような未割り当ての文字は見えないので、差分を目で見ても気づけない。報告元は `od -c` と、エスケープの文字列での grep が0件になることで気づいた。回避は `\u` を書かない形 (正規表現なら Unicode プロパティ) にするか、Python の read と replace で書くこと (実測)。報告者の提案は、Edit / Write ツールで JS や JSON のソースに `\u` を書く場面がある規約やテンプレートに、書いた後にエスケープの文字列で grep して残っていることを確かめるか、Unicode プロパティで書くかを添えること。Unicode プロパティの書き方は ISSUE-134
  - dotfiles で確かめたこと (2026-10-23): `.cache/` の書き捨てのファイルへ Edit ツールで `/[\u3040-\u30ff]/` を書くと、`od -c` では `343 201 200` (U+3040 の生のバイト) と `ヿ` が入っていて、`u3040` での grep は0件だった
  - dotfiles で確かめたこと (2026-10-23): この行を書いたときも同じ化け方をして、仕分けのセッションが自分で踏んだ。さらに、Bash ツールのコマンド文字列も同じくエスケープを解いてからシェルへ渡す。バックスラッシュと u で始まるエスケープをパターンに書いた grep は生の文字を探すことになり、正しくエスケープが残っているファイルに0件を返した。生の文字が入ったファイルには1件を返したので、報告者の提案する確かめ方は Bash ツールから打つと正反対の答えになる。バックスラッシュを含まない `u3040` のようなパターンと、Python で code point を数える形では正しく数えられた

### Claude Code の hook と委譲

- SessionStart hook の command を `{ cd "$CLAUDE_PROJECT_DIR" && <recipe>; } 2>/dev/null || echo '<未確認の1行>'` の形にすると、task runner が PATH に無いときもシェルの `command not found` が文脈へ漏れず、決まった1行だけが届く。`2>&1` だと印の無い行が混ざった (実測)
- hook の設定を読んでその command 文字列をテストから `sh -c` で起こすと、「hook を外す」「fallback を壊す」変異がテストで赤になり、人が新しいセッションを開く確認を1回に減らせた。PATH は `/usr/bin:/bin` ではなく空の一時ディレクトリにする (CI の `/usr/bin` に task runner があると実物を起こす) (実測)
- 同じ作業木で2つの implementer を並列に動かすとき、brief にファイルの持ち物の一覧を書き、テストは自分の持ち物のファイルを1つずつ回させ (全体のゲートは禁止)、変異は origin を外した clone に自分のファイルを写して当てさせると、衝突せずに終わった。並列の修正役へ渡す前に、許すキーの集合や正規表現などの値をコントローラが決めて brief に書くと、解釈が割れなかった (実測)
  - 2026-10-23に仕分けた分で、別のリポジトリから5組で同じ形の報告が届いた。worktree が lint を壊すリポジトリなので隔離を使わず、規律で分けた。上の規律に加えて、変異は cp と cmp で戻させて git checkout を禁じ、index を触る変異は「変異の前と同じ git status に戻る」で判定させた。全体のゲートはコントローラが1回だけ回した。5組とも狙ったテストだけが赤くなり、最後の全体のゲートは緑だった (実測)
- 設計書を書いたあと、別の subagent に「計画を立てるのに足りない点」だけを挙げさせると、設計書の中の2つの値の組み合わせが外部 API に課金したあとで捨てる経路を作ることを見つけた。報告の数字は自分で数え直して再現してから採った (実測)
- コードレビューの委譲先が confidence 88 で指摘した退行は、検査対象のハーネスがその変更を射程に入れていない誤検出だった。指摘を当てる前に、ハーネスがその変更を射程に入れているかを定義元で確かめる (実測)
- 調査に前提を疑う役を1体入れて初めて、「Node 製の CLI」と思っていたものの実行環境の層 (別のランタイム) が出てきた (実測)。グローバル CLAUDE.md の「少なくとも1つには前提そのものを疑えという出発点を与える」と同じ形の実例
- 実装の前に、呼び出し箇所、実行系、backend の側、前提を疑う、の4観点の読み取り専用の調査を並列で回し、spec の記述を実コードと突き合わせた。spec の「env の値を空にして相対 URL にする」手順が `A || B` のフォールバックで no-op になること、空文字を真偽で判定するガードが機能を黙って止めること、spec に書いた呼び出し箇所の件数が過小だったことが、実装に入る前に見つかった (実測)
- サブエージェントの Web 調査が「確認済み」とした記述 (出典のページに無い言い回し) を、別のレビューのエージェントが出典を開き直して否定した。調査の verified の札は、出典を開き直すまで信じない (実測)。dotfiles のメモリにある「委譲先の出典は捏造されうる」と同じ型
  - 2026-10-23に仕分けた分で、別のリポジトリから同じ型の報告が届いた。subagent がベンダーの changelog や制限の表を検索の要約から持ち込み、ページを開いて文言を確かめると主張の一部はページに無かった (実測)。報告者の提案は、外部の文書の事実を設計文書に入れる前にページを開いて文言を確かめる手順を、subagent への指示の定型に入れること。定型の置き場は ISSUE-100 のテンプレートと重なる
- サブエージェントが `.test.ts` を除外した grep で検索し、共有モジュールへ寄せたあとの古い import がテストの側に残った。型検査が拾った。寄せる変更のあとは型検査を先に回す (実測)
- docs だけの PR でも simplify の4観点とボーイスカウトを回したところ、別の Issue の決定を逆向きに引用していた記述と、同じ上流の状態 (外部の Issue が open であること) を2つの Issue に書いていた二重記述が見つかった (実測)
- 最終レビューを「観点ごとの reviewer 4体と、観点ごとに1体の反証役」の Workflow にし、反証役が指摘をまとめて判定する形で体数を8に抑えた (実測)

### Claude Code の /goal

2026-10-23に仕分けた分で、2つのリポジトリから届いた。dotfiles の追跡下には /goal の運用を書いたものが無く、閉じた Issue に条件の置き場の例が1件あるだけだった。

- /goal の Stop hook は DoD の各項目を transcript の証拠で判定するので、取りこぼしに強い。そのかわり、後から取り返せない手順の条件を入れて外すと、閉じるまで同じ判定が繰り返される。マージ前のゲートを「増分を自分で読み直す」で済ませ、「CI が success なら Merge OK」という条件付きの結論のままマージしたところ、後から満たせない条件を Stop hook が評価し続け、利用者が /goal clear するまで止まらなかった (実測)。報告者の提案は、後から取り返せない手順の条件には確かめ方を具体的に書くこと (例: マージのコマンドの直前に、CI の結果を見た後の無条件の Merge OK を出す)
- マージが利用者の `!` の操作のリポジトリでは、goal の実行中にマージを待てない。handoff からの再開を、マージ準備 (マージの dry-run) を終点にした1本目と、マージ後の2本目に分けた (実測)
- 条件に CI のステップの分布を書く前に、`gh run view --json jobs --jq '.jobs[].steps[].conclusion' | sort | uniq -c` で実測した。skipped が混ざると「success 以外が0件」は満たせないので、「failure と cancelled が0件」の形にした (実測。そのときは28件すべて success)
- /goal に貼った条件文の中ほどが欠落した。2450文字で上限 (4000) の内側だったが、条項の途中から後半が消えて次の条項の末尾の句につながり、欠落した版で goal が設定されて判定役から見える条件が緩くなった。原因 (貼り付けの経路か入力欄の処理か) は未特定 (欠落は実測、原因は推測)。報告者の提案は、設定直後に表示される「Goal set:」の本文を元の条件文と突き合わせる手順を、/goal の運用の記録に足すこと
  - dotfiles で確かめたこと (2026-10-23): この仕分けのセッションは、628文字の条件文を `.cache/` に置いてから /goal に貼り、「Goal set:」の本文と突き合わせて欠落が無いことを確かめた。欠落しなかった1回なので、原因の切り分けにはならない
- 見立て (推測。仕分けたセッションの解釈): 上の4件は「Stop hook が閉じられる条件だけを書く」ことにまとまる。利用者の操作を待つ手順と後から取り返せない手順を条件から外すか、確かめる形を具体的に書くかの2択になる

### 依存とツールの導入

- 単体バイナリで配られる CLI を pin するとき、中身のランタイム (`deno compile` / `bun compile` / Node SEA など) を `strings <binary>` で確かめる。同梱ランタイムの単体バイナリから npm パッケージへ移すと、ランタイムの版の照合が新しく要る (実測に基づく推測)。dotfiles では mise の `github:` backend や Homebrew で単体バイナリを入れることがあり、導入の手順に関わる
- lockfile で依存を固めた日に、推移的な依存に公開から日の浅い版が混ざる。lockfile の全パッケージの公開日を registry の `time` で数え、実際にコードが走る依存だけを overrides で古い版へ寄せる。override は `親>子` の形で親ごとに絞れる (実測)
- 長時間の外部プロセスを回すタスクランナーには、既定でプロセスグループ単位の時間の上限と、グループ kill のあとに join する順序を共通部品として持たせる (実測。テストの側の形は ISSUE-88 の INS-16)
- Homebrew の自動更新で手元の just がリポジトリの canonical の版 (CI は sha256 の照合つき) より新しくなり、版を照合する検査で preflight が入口で止まった。ホストを変えずに揃えるには、`cargo install just --version <版> --locked --root <repo>/.cache/<dir>` でソースから組んで PATH の先頭に置く。レシピの中から just を呼び直す検査があるので、PATH で差す (実測)。dotfiles で確かめたこと: dotfiles も just を Homebrew (`home/.Brewfile`) で入れていて、版は pin していない

### 作業の規範

- グローバル CLAUDE.md の「完了前に `.cache/` の書き捨てを消す」が、後のセッションが読むキャッシュ (期限の記憶など) を巻き込むという報告があった。報告者の案は、残すものをリポジトリの CLAUDE.md で名指しすると規則の側に書くこと (推測)。dotfiles で確かめたこと: 今の規則は「残すのは次のセッションが読むもの (未消費の `.cache/handoff.md` など) だけで、既定は削除」と書いていて、例外の枠は既にある。足りないのは、何がそれに当たるかをどこで名指しするかである
- repository ruleset はブランチとタグで target が別系統なので、`gh api repos/<owner>/<repo>/rulesets/<id>` で target と conditions を読むと、既定のブランチを守る ruleset がタグの push を止めないことを確かめられる。bypass_actors が空でも target が branch ならタグは対象外 (実測)。報告者の提案は、タグを push する workflow を作る手順に「target: tag の ruleset があるか確かめる。後からタグの ruleset を足すと、bypass に GitHub Actions を入れない限りその push が落ちる」を加えること (ドキュメントのみ)
  - 2026-10-22に別のリポジトリから実測の報告が届いた。target: tag の ruleset で削除と付け替えだけを止めて作成は止めない形にすると、bypass_actors を空のまま GitHub Actions のタグの push を通せた。`update` の rule は REST の文書では parameters が required だが、parameters 無しで POST して保存された。ref_name の pattern は `refs/tags/` を前置きし、`[0-9]` の範囲の文字集合が効いた。pattern に当たる既存のタグの削除は `Cannot delete this tag`、force push は `Cannot update this protected ref` の GH013 で拒否され、admin も止まった。対照として、pattern に当たらないタグでは作成、付け替え、削除が通った。pattern に当たる探針のタグを作ると、bypass が空なので二度と消せない (実測)。タグの ruleset には `rules/branches/{branch}` に当たる「効いている規則」を返すエンドポイントが無く、適用後に読み直せるのは保存された ruleset 自体までで、効き目は実地の push で確かめるしかない (ドキュメントのみ)。見立て (推測。仕分けたセッションの解釈): 上の提案の「bypass に GitHub Actions を入れない限り落ちる」は作成も止める ruleset の話で、作成を止めない形なら当たらない
- 文書や設定のコメントに「既定でこう上書きされる」のような未検証の断定を書くと、レビューで確信度の低い指摘として毎回戻ってくる。確かめた範囲の主張に弱めて書くほうが安い (実測)
- release note を tag の push 前に書き手自身が読み直すと、「テストは配布元の検査で引き続き走る」という文が一部のファイルには成り立たない (実行の経路が無い) と気づけた。push した tag の本文は打ち直すしかないので、push の前が唯一の可逆点だった (実測)
- 他のリポジトリのセッションへの依頼の本文に、受け手の現在値 (受け手の apm.yml の pin がすべて旧 SHA を指していること) を自分で読んで書いた。handoff の値の受け売りにしないことで、受け手が同じ確認を繰り返さずに済んだ (実測)
