### in-repo-issue: 親子のキーを拡張したプロジェクトで Phase E が無音で終わる

報告 (実測): Phase E は frontmatter の `^parent:` と `^children:` を grep する。プロジェクトが frontmatter のキーを別名 (例: `parent_issue:` / `child_issues:`) で持っていると grep は0件を返し、Phase E は「親なし」として無音で終わる。親子のリンクが実在しても伝播の提案が出ない。報告元では同梱の側で親のクローズが済んでいたので実害は無かった。

報告者の提案 (推測): 親子のキー名をハードコードせず、プロジェクトのテンプレートから読む。または `parent` も `children` も見つからないのに frontmatter に `parent` / `child` を含むキーがあれば警告を出す。対象は Phase E と A.6、検索手順の親一覧。

同じ報告で、クローズを feature PR に同梱したあとの Phase C は C.3 の「既に closed」分岐で no-op になり、破綻しなかったことも確かめられている (実測)。skill が同梱節で述べている挙動どおりである。

dotfiles で確かめたこと: skill の frontmatter スキーマは `parent` / `children` を名指しし、「これ以外は持たない」と書いている。報告元のキーはこの規約の外にある。直す向きは2つあり、規約外のキーを検出して知らせる (0件を健全と読ませない) か、キー名を可変にするかで、前者は規約を変えずに済む。

### session-handoff: 注入した引き継ぎ書のキー情報を実物と突き合わせる

- dotfiles で確かめたこと (2026-11-24): 配布されている session-handoff の template.md (agentic-coding-tools の e1720e6) の「キー情報」節は、書く内容をコメントで「ブランチ、PR 番号、重要ファイルパス、実行中プロセス、一時ファイルの場所」と挙げるだけで、HEAD の SHA や作業ツリーの件数の欄は無い。注入するのは dotfiles の `home/.claude/hooks/handoff-sentinel.py` で、注入の文面は作成日時と保存先を添えて本文を渡すだけで、実物と突き合わせる指示は無い。提案は skill (上流) と hook (dotfiles) の両方にまたがる
- 仕分けたセッションの解釈: 同じまとめの観察 (引き継ぎ書のキー情報が実物と食い違った) は、ISSUE-133 の「作業の規範」節の、handoff の値の受け売りにしない項の子にも同じ型の再報告として置いた。提案のうち hook の側の半分 (注入の文面に突き合わせの指示を入れる、記録の時点で HEAD の SHA と作業ツリーの件数を控えて注入の時点で比べる) は dotfiles の handoff-sentinel の変更なので、上流へ渡すのは template.md のキー情報の欄と skill の手順に絞る。hook の側を dotfiles の新しい Issue にするかはタスクで決める

### commit-and-pr-message: --target-private で人名の層まで外れる

- 2026-11-23の仕分けで、別のリポジトリから届いた。コミット本文の漏洩検査を、送り先が PRIVATE のときの `--target-private` 付きで通した (実測)。反証役が「同じ観点の見落とし」として、まだ push していない前のコミットのメッセージに顧客の実名が入っているのを拾った。レーンは追跡ファイルの差分しか見ておらず、コミットメッセージは誰の担当でもなかった (実測)。送り先が PRIVATE だと漏洩検査の禁止語の層が外れるので、顧客の実名を含むコミット本文と追跡ファイルの追記が rc=0で通った。グローバルの規範は公開範囲を問わず実名を禁じているのに、機械の層は PRIVATE で実名を見ない。この食い違いは、PRIVATE のリポジトリで顧客名をメモ代わりに書く習慣があると毎回すり抜ける (実測)。報告者の提案: pre-merge-quality-gate の観点に「ブランチのコミットメッセージ (`git log <base>..HEAD --format=%B`) を読む」を足すか、commit-and-pr-message の `--target-private` でも人名に当たる層 (顧客名の禁止語など) は外さない。実名の禁止は公開範囲を問わないので、層2を一律に外すと規範より緩くなる (実測)

### superpowers の subagent-driven-development (外部の plugin)

dotfiles も agentic-coding-tools も canonical を持たない。直せるのは、こちらが brief を書く側の手順 (ISSUE-100 のテンプレート) までである。

- 報告 (実測): 同梱の `scripts/review-package` と `scripts/task-brief` は、cwd が対象のリポジトリの中でないと `fatal: not a git repository` と `bad BASE` で止まる。skill のディレクトリへ cd して相対で呼ぶのではなく、リポジトリの中から絶対パスで呼ぶ
- 報告 (実測): 型を剥がして走るテストランナーは型を見ないので、型エラーがあってもテストは緑になる。implementer の brief に型検査の recipe を書かないと implementer も reviewer も型を見ず、コントローラの gate で初めて赤になった。提案は、implementer と reviewer の brief の雛形に「型検査の recipe を回す」を入れること
- 報告 (実測): 同梱の `task-brief` スクリプトはタスクの節だけを切り出すので、計画の冒頭の「前提と決定」が brief に入らず、dispatch に行番号つきで足す必要があった

### macos-vm-verification: ストレージの回収と原状の作り直し

2026-11-26の仕分けで、別のリポジトリから届いた (届いたのは2026-11-24)。

- 報告 (実測): Parallels の Apple 仮想化の macOS 検証 VM で、ホストのストレージを回収するために `prl_disk_tool compact` (-i で見積もり) を当てた。`prl_disk_tool compact` は plain のディスクに使えない。`compact -i` が「The specified disk image is plain. Compacting plain disks is not supported.」を出し、rc は0のまま
- 報告 (実測): ディスクが plain の sparse ファイル (`online-compact=on`) の VM は、ゲストの OS を「システム終了」で止めると TRIM で空きが返る。1回の終了で VM のバンドルが35GBから28GBに縮み、ゲストの APFS コンテナの使用量 (`diskutil apfs list` の Capacity In Use) とほぼ同じになった
- 報告 (実測): ゲストの「システム終了」は ssh から `osascript -e 'tell application "System Events" to shut down'` で打て、そのあと `prlctl list -a` が stopped になるまで待てばよい。強制停止 (`prlctl stop --kill`) を使わずに済む
- 報告 (実測): 検証 VM の原状を、OS の更新とアクセシビリティの許可を入れた状態に作り直し、ssh から AppleScript (System Events) で窓の大きさを変えられることで確かめた。アクセシビリティの一覧に sshd-keygen-wrapper を「足した」だけではスイッチがオフのままで、ssh からの AppleScript の窓の操作は -1719 (補助アクセスが許可されない) になる。System Events のプロセス数を数えるだけの AppleScript は許可なしでも通るので、許可の確かめには窓の大きさを変える操作を使う必要がある
- 報告 (実測): 撮影に向いた原状として、自動アップデート (ダウンロードとインストール) をオフ、おやすみモードをオンにした。自動アップデートの状態は ssh から `defaults read /Library/Preferences/com.apple.SoftwareUpdate` の AutomaticDownload・ConfigDataInstall・CriticalUpdateInstall が0であることで確かめられる。おやすみモードのオン・オフは、システム設定の「集中モード」の画面からは切り替えられない (そこは設定だけ)。コントロールセンターから切り替える
- 報告 (ドキュメントのみ): macOS のソフトウェアアップデートは ssh から入れられない (Apple silicon では所有者の認証が要る)。ゲストの画面でユーザーに操作してもらう
- 使用感 (実測): doctor の「GUI セッション」の行で、ログインの画面かどうかを先に見られるのが役に立った。スナップショットを使わずに原状そのものを作り直す手順 (OS の更新、許可、止め方) は skill に無い
- 報告者の提案 (実測。根拠は上の1つ目と2つ目): skill に、ストレージの回収の節を足す。plain の sparse ディスクでは `compact` が使えず、ゲストの「システム終了」の TRIM で戻ること、回収の余地は `diskutil apfs list` の使用量とホスト側のファイルの割り当て (`ls -ls`) の差で見積もれること
- 報告者の提案 (実測。根拠は上の4つ目と5つ目): 同じ skill に、原状を作り直すときの確かめの形を足す。許可の確かめは窓の大きさを変える AppleScript で行い (数えるだけの AppleScript では確かめにならない)、自動アップデートとおやすみモードを原状に含める
- dotfiles で確かめたこと (2026-11-26): worktree の配布の写し (追跡外、agentic-coding-tools の e1720e6) の macos-vm-verification の SKILL.md・macvm.py・references に、compact・TRIM・shut down・システム終了・SoftwareUpdate・おやすみの語は無い。止め方は、SKILL.md の手順5 (原状へ戻した後に VM を止める手順) が、起動中の VM を `prlctl stop "<vm>" --kill` で止めるとしている (素の stop は Apple の仮想化の macOS VM で rc 255になる。手順4で原状へ戻した後なので強制停止で失うものは無い、と理由も書いている)。ゲストの OS を終了させて止める経路は無い。TCC への言及は `references/macos-bootstrap.md` の18〜19行目の Full Disk Access だけで、アクセシビリティの許可の確かめ方は無い。doctor の「GUI セッション」の行は macvm.py の738行目と744行目にある
