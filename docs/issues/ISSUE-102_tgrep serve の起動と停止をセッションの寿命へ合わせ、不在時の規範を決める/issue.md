# feat: tgrep serve の起動と停止をセッションの寿命へ合わせ、不在時の規範を決める

## 背景

ISSUE-93 で検索の既定を `tgrep` にした。その実測は「このリポジトリで常駐サーバーが動いている」
状態で取ったもので、規範の一次実測を持つ `home/.claude/references/observation.md` の tgrep 節も
同じ前提で書かれている。

ところが常駐サーバーを起動・維持する仕組みはどこにも無い。2026-09-18 の dotfiles では
サーバーが動いておらず、既定の `tgrep` は古い索引を読んで、直前のセッションで書いた語へ 0 件を返した。
警告は出ず、ISSUE-93 が「外したときに劣化を申告しない」と書いた形を、規範に従った検索そのものが
踏んでいる。

**既定を `tgrep` にした規範は、常駐サーバーがあるときにしか成り立たない。**サーバーの起動と
停止をどこが持つかと、サーバーが無いときにどう引くかを決める。

ユーザーの意向は、SessionStart で起動し SessionEnd で停止する方向。

## 実測 (2026-09-18、tgrep 1.0.8)

### dotfiles ではサーバーが動いていない

プロセス一覧にも、`launchctl list` にも、`brew services list` にも `tgrep` は無い。
`tgrep status` は `Server: not running` と `Updated: 1d ago` を返した。

直前のセッションで書いた語「グロブとして働く」(ISSUE-52 の 2 行) を 3 経路で引いた。

| 経路 | `--stats` の末尾 | 結果 |
| --- | --- | --- |
| 既定 | `Query plan: ... (candidates: 0/298)` と `Search completed ...` | 0 件、rc 1 |
| `--no-index` | `Brute-force search completed ... (309 files)` | 2 件 |
| `git grep` | ― | 1 ファイル 2 件 |

stderr への警告は無い。索引が候補の母数にしたのは 298 files で、全走査の 309 files と
一致しない。索引が作られた後の変更を持っていない。

### 既定の検索には経路が 3 つある

observation.md の経路表は `(via server)` と `Brute-force` の 2 つしか持たない。サーバーが無く
索引があるときは、そのどちらでもなく**ディスク上の索引を直接読む**。`--stats` の末尾は
`Search completed` だけで、経路を名乗る語が付かない。

この経路は速く、エラーも出ず、最後に保存された後の変更を持たない。3 つのうちで最も気づきにくい。

### serve のライフサイクル

ignore の外に置いた使い捨てのディレクトリで測った (ignore の配下に置くと、後述のとおり対照ごと
0 files になる)。プローブの常駐は残していない。

| 観点 | 実測 |
| --- | --- |
| 常駐中に索引ディレクトリへできるもの | `serve.json` (pid と port) と `serve.lock` |
| 待ち受け | `127.0.0.1` の TCP (LISTEN) |
| 同じ場所で 2 本目を起動 | rc 2 で終了し、1 本目は生き残る。「another tgrep server is already running ... Stop the existing server before starting a new one.」 |
| 起動後に足したファイル | 2 秒以内に `(via server)` で引ける (ネイティブ監視、trace に `reindex: modified`) |
| 常駐メモリ | 1 ファイルの索引で約 13 MB |
| SIGINT で停止 | rc 0。`shutting down...` を出し、`serve.json` を消す。`serve.lock` は残る |
| SIGTERM で停止 | rc 143。`serve.json` が古い pid と port のまま残る。`tgrep status` は `not running` を正しく返す |
| SIGKILL で停止 | `tgrep status` は `not running`。同じ場所で起動し直せる |
| 停止後の索引ファイル | SIGINT でも SIGTERM でも、停止の直前に足したファイルが索引に無かった (`candidates: 0/1`) |

常駐中の変更は、変更の累積か定期的な確認を契機に索引ファイルへ保存される。契機と閾値は同梱の
README と `serve --help` の `--auto-save-mutations` が持つ。上の観測は起動から数秒・変更 1 件で
止めたもので、どちらの契機にも届いていない。言えるのは「停止の操作は未保存の変更を書かない」
までで、「常駐中の変更は失われる」ではない。

`tgrep serve --help` には、アイドル時の自動終了も、停止のサブコマンドも無い。初回の索引構築には
メモリと CPU の上限があり、既定値は `serve --help` が持つ (メモリは物理メモリに比例する)。

`serve.json` が持つのは pid と port だけで、トークンにあたるものは無い。プロトコルを読んで
いないので、認証が無いとまでは確かめていない。

### その他の面

- **ignore の配下はディレクトリで渡すと見ない。**`.cache` を渡すと `--no-index` でも 0 files に
  なる。ファイル自身を渡すか `--no-ignore` を付けると見る。対照の ignore の外の dot 配下
  (`home/.claude/references`) は 8 files を走査した
- **`-E` は `--encoding` である。**grep 流に `-E 'a|b'` と渡すと `unsupported encoding: a|b` で
  rc 2 になる。うるさく失敗するので、黙って置き換える `-r` (`--replace`) より害は小さい

## 設計の論点

### 並行するセッション

同じリポジトリで複数のセッションが並ぶと、先に終わったセッションの SessionEnd が、残っている
セッションの使っているサーバーを止めてしまう。止められた側は 3 つ目の経路へ黙って落ちる。

二重起動は `serve.lock` が防ぐので、起動側に排他は要らない (2 本目は rc 2 で終わる)。要るのは
停止側の判断で、参照カウント (セッション ID の集合をどこかに持つ) か、停止時に生存している
セッションを確かめる仕組みになる。

公式ドキュメントでは、`/clear` も SessionEnd (reason `clear`) を発火させ、SessionStart
(source `clear`) が続く。そのたびに停止と起動をやり直さない形にするかも決める。

SessionEnd の hook には、hook どうしで共有する実行時間の予算がある (値と延長の条件は公式の
hooks ページが持つ)。停止側の判断は、この予算に収まる形にする。

### 取り残し

クラッシュや強制終了で SessionEnd が発火するかは、公式ドキュメントに記述が無く、確かめていない。
発火しない前提で設計する。serve にはアイドル時の自動終了が無いので、回収する側を作らない限り
常駐が残り続ける。対象のリポジトリが増えるほど積み上がる。

回収の契機 (次の SessionStart で、生存するセッションの無いサーバーを止めるなど) と、
停止に使うシグナルを決める。SIGTERM は `serve.json` を古いまま残す。

### 起動のコスト

索引の無いリポジトリで起動すると、初回の索引構築が走る。SessionStart から起動するなら、
hook はサーバーの起動を待たずに返す形にする。ISSUE-83 が扱うのと同じく、セッション頭の
待ち時間を伸ばさないため。

`--max-memory` と `--max-cpu` の上限をどう置くかも決める。大きいリポジトリで既定のまま走らせると、
ホスト環境を守る規範 (user CLAUDE.md の「自分の作業でホスト環境を壊さない」) とぶつかりうる。

どのリポジトリで起動するかも決める。全リポジトリで起動するのか、索引が既にあるものだけか、
一覧を持つのか。

### サーバーが無いときの規範

サーバーが無いと、既定の検索は 3 つ目の経路で、最後に保存された後の変更を持たない答えを返す。
規範の候補は次の 2 つ。

- `--stats` の末尾に経路の語が無ければ、`--no-index` か `git grep` で引き直す
- サーバーの有無を先に `tgrep status` で確かめる

SessionStart でサーバーの不在を告げる形もありうる。その形を採るなら、ISSUE-83 (不在の確認が
プローブに加わる) と ISSUE-71 (SessionStart の告知が subagent に届かない) を先に片づける。
起動の方はこの制約を受けない。サーバーはディレクトリ単位なので、親のセッションが起動した
サーバーは、同じディレクトリで動く subagent の検索にも効く。

worktree で隔離した subagent は別のディレクトリで動くので、サーバーも索引も無い。この形での
挙動は測っていない。

### セキュリティ

待ち受けはループバックに限られ、LAN からは届かない。同じマシンでは、serve と無関係に起動した
別プロセス (実測では `tgrep status`) が `serve.json` の port へ問い合わせて応答を得た。
`serve.json` のモードは他ユーザーにも読める `-rw-r--r--` だった。個人の Mac で許容できるかを
判断する。ブラウザから届くかは、プロトコルを確かめていないので未確認。

### 採らない方向の案

launchd でリポジトリごとにサーバーを常駐させる案。対象が増えるたびに bootstrap をやり直すことになる
(ユーザーの意向)。
