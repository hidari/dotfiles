# ISSUE-102 spec: serve の寿命をセッションへ合わせ、不在を機構で塞ぐ

この文書は 2026-09-18 の設計時点のスナップショットである。決定と、その根拠になった実測を持つ。
起票時の実測と論点は同ディレクトリの `issue.md` が持ち、ここでは再掲しない。

## 追加実測 (2026-09-18、tgrep 1.0.8)

`issue.md` の実測に加えて、設計の分岐点を決めるために測った。

### serve が公開する TCP には認証が無い

| 面 | 実測 |
| --- | --- |
| 待ち受け | `127.0.0.1` の IPv4 のみ。IPv6 行は 0 件 (対照として同じ検査で他プロセスの IPv6 listener が 15 件見えている) |
| 認証 | 無い。`search` / `status` / `files` / `reload` の 4 メソッドが未認証で通る。それ以外は `-32601` |
| 返る内容 | `search` は一致行の `content` をそのまま返す。`pattern` に `.` を渡すと配下の全テキスト行が返り、`after_context` で非マッチ行も引ける |
| ブラウザ | HTTP のリクエスト行とヘッダを 1 行ずつ JSON として読み捨て、body 行の JSON-RPC を実行する。応答は HTTP ではないので読めないが、`reload` の副作用は起きる |
| `serve.json` | モード `-rw-r--r--`、中身は pid と port のみ。トークンにあたるものは無い |

到達面は同一ホストのプロセスに限られる。そこで動く任意のプロセスは既にホームディレクトリを読めるので、
索引経由で増える面は「gitignore されていないファイルの内容」に限られる。
逆に `--no-ignore` を付けて起動すると ignore 配下も索引に入り、この面から読めるようになる。

### 停止はシグナルだけで、SIGINT が唯一の graceful 経路

| シグナル | 実測 |
| --- | --- |
| SIGINT | rc 0。`shutting down...` を出し `serve.json` を消す。`serve.lock` は残る |
| SIGTERM | graceful handler を通らず、`serve.json` が古い pid と port のまま残る |
| SIGKILL | SIGTERM と同じ残り方 |

どの止め方でも同じ場所で起動し直せ、stale な `serve.json` は警告なく上書きされる。
クライアントと `tgrep status` は pid の生死で判定して fallback するので、stale の手動掃除は要らない。
JSON-RPC に停止メソッドは無く、サブコマンドにも無い。8 分の無通信では自発終了しない。

### 起動のコストは索引の有無で決まらない

このリポジトリ (310 files) で測った。

| 条件 | 待ち受けまで | 索引 |
| --- | --- | --- |
| 既存索引あり | 0.30 秒 | 待ち受け時点で `Indexing: complete`。起動時の reconcile が 2 日分の差分を拾い `Files` が 298 から 310 へ増えた |
| 索引ゼロ (`--index-path` で隔離) | 0.16 秒 | 310 files の構築が 0.1 秒、peak memory 36.9 MiB |

常駐メモリは RSS 20 MB。

このサイズでは初回構築が一瞬なので、README が書く「初回ビルド中は空の索引から答える」面は観測できなかった。
大きいリポジトリでは踏む。射程はここまでで、「構築中の 0 件は起きない」とは言えない。

### 索引構築中は経路の申告で見分けられない

構築中の serve は `(via server)` を申告しながら空の索引から答える。
`--stats` の経路申告は「serve 経由である」ことしか言わず、索引が揃っているかは語らない。
判定には `tgrep status` の `Indexing:` 行が要る。

ISSUE-93 が確立した「経路は `--stats` で判定する」は、serve が無いときの索引直読みは捕まえるが、
構築中の serve は捕まえない。

### 索引ディレクトリに置いた第三者のファイルは掃除されない

`.tgrep/` に平置きのファイルとサブディレクトリを置き、新規ファイルの反映・`reload`・SIGINT 停止を
通しても、どちらも残った。対照として同じ検体で `search` が新規ファイルを 1 件返すことを確かめており、
索引が実際に動いている状態での観測である。

射程は tgrep 1.0.8 のこの一巡まで。将来の版や他の契機 (periodic flush、Windows の `.retired` 掃除) は測っていない。

### Claude Code の hook 側

出荷バイナリ (2.1.276) の zod 定義と実測から確定させた。公式ドキュメントの要約はフィールド名を
取り違えていたので (`source` を `session_start_reason` と報告)、出典はバイナリ定義と実測ペイロードに取る。

| 面 | 実測 |
| --- | --- |
| SessionStart の入力 | `session_id` / `transcript_path` / `cwd` / `hook_event_name` / `source` の 5 キー |
| SessionStart の既定 timeout | 600 秒。同期でブロックするとセッション起動がそのまま止まる (78 秒ブロックで wall 79 秒) |
| SessionEnd の既定 timeout | 1.5 秒。兄弟 hook に長い `timeout` を書いても自分は延長されない |
| SessionEnd の延長 | その hook 自身に `timeout` を書く。env による全体延長は射程が広すぎるので採らない |
| detach した子 | hook 終了後も PPID 1 へ reparent して生き残る。プロセスグループの一括 kill は無い |
| SIGTERM / SIGHUP | SessionEnd が発火する |
| SIGKILL | SessionEnd は発火しない。hook が起こした子は孤児として残る |
| session_id | `--continue` で再利用される。参照カウントの鍵にすると二重計上する |

## 決定

### D1 対象は git リポジトリなら全部

`cwd` から root を解決し、git 管理下ならそこで serve を立てる。索引の有無を条件にしない。

索引の有無で分ける案は採らなかった。索引が無いリポジトリでは初回構築中の検索が空の索引から
答えうるが、このリポジトリのサイズでは 0.1 秒で、条件分岐を増やすほどの差にならない。
大きいリポジトリで構築中に当たる面は D5 の rc 1 経路が受ける。

### D2 停止の契機は SessionEnd と SessionStart の 2 つ

判定は 1 つ (このディレクトリを使っているセッションが他にいなければ止める)、契機が 2 つになる。

- SessionEnd: 自分を除いて数え、0 なら止める
- SessionStart: 全状態ファイルを走査し、生存が 0 のものを止める

SessionEnd だけに賭けない理由は、SIGKILL では発火しないため。孤児は次の SessionStart が回収する。

止め損ねる害 (常駐 20 MB と認証なしの TCP) と止めすぎる害 (使用中のセッションが索引直読みへ黙って
落ちる) は釣り合わない。判定は生存が確実に 0 のときだけ止める側へ倒す。

### D3 参照カウントは自前で持ち、鍵は PID

`${XDG_CACHE_HOME:-~/.cache}/claude/` 配下に、root ごとの状態ファイルを持つ。
`handoff-sentinel.py` の `_cache_root()` と同じ規則に揃える。規則を分けると
XDG_CACHE_HOME を設定したマシンで別の根へ落ちる。

Claude Code が書く `sessions/<pid>.json` は使わない。理由は 2 つで、内部実装なので契約が無いことと、
headless のセッションが登録されないため「他に誰もいない」と誤って判断して走っている headless の
足元を払うこと。

ファイル名は root のパスのハッシュにする。`handoff-sentinel.py` の `_sanitize()` は
`[^A-Za-z0-9_-]` を潰す charset ガードで、session_id (UUID) では衝突しないが、パスに適用すると
異なる root が同じ名前へ落ちる。charset を通っていても警告は出ないので、2 つのリポジトリが同じ
参照カウントを共有し、片方の SessionEnd がもう片方の serve を止めるまで気づけない。
これは user CLAUDE.md が「注入対策の charset 検証を名前空間の検証と兼用しない」として持つ形にあたる。

記録された PID はスナップショットなので、数えるときは必ず実体を確認する。

### D4 資源上限を明示し、ignore は既定のままにする

初回構築のメモリと CPU の上限を明示的に絞る。既定は物理 RAM と論理コアの 50% で、
ホスト環境を守る規範に対して緩い。値の canonical は実装が持つ。

`--no-ignore` は渡さない。これは機能ではなく安全側の決定で、渡すと ignore 配下が索引に入り、
認証の無い TCP から読める。

起動は待たずに返す。`tirith-check.py` が持つ detach の形 (新しいセッションを与え、
stdio を捨てる) をそのまま踏襲する。stdio を継承させると hook の JSON 出力が汚れる。

### D5 不在は規範ではなく機構で塞ぐ

`tgrep` をシェル関数で包み、常駐が無いときは索引を使わない経路へ落として stderr に 1 行告げる。

- サブコマンド (`serve` / `index` / `status` / `count-files` / `help`) は素通しする。ここに索引回避の
  フラグを足すと `serve` 自身が壊れる
- 検索のときだけ、状態ファイルではなく `.tgrep/serve.json` と pid の生死を見る。判定にプロセス起動を
  挟まない。`tgrep status` を毎回叩くと検索そのものと同じオーダーのコストが乗る
- 0 件 (rc 1) が返ったときだけ `tgrep status` を見て、索引構築中なら告げる。0 件は元々
  「真の不在」と「経路の失敗」を区別できない地点なので、追加のコストをここへ寄せる

常時層 (user CLAUDE.md) へは足さない。worktree で隔離した subagent も Bash 経由で `tgrep` を呼ぶので、
ラッパーは常時層と同じ相手へ届くと見込む。ただしその文脈では測っていないので、実装後に確かめ、
届かなければ置き場を決め直す。予算の余白は触らない。

ISSUE-93 が PreToolUse を却下した理由 (シェル文法の近似が終わらない) は、コマンド文字列を解析せず
自分の呼び出しだけを包むこの形には当たらない。ただし「部分的な網は止まらなかったことを安全と
読ませる」側は残るので、届かない経路を D6 の一次実測に明記する。

### D6 一次実測は references が持つ

`home/.claude/references/observation.md` の tgrep 節を書き直す。入れるのは常駐サーバーを前提に
測ったという断り、索引直読みの経路、構築中は経路の申告で見分けられないこと、ラッパーが届かない範囲。

同じ節へ `-r` が `--replace` であることと `-E` が `--encoding` であることを入れる。
前者は ISSUE-100 が canonical の置き場を未決にしていて、この節を候補に挙げている。
どちらも現状はどの規範層にも無い (`git grep` で確認済み)。

書き直すときは既存の実測も版を確かめて取り直す。上流 main の README は `--hidden` の扱いが
1.0.8 と違うと読める。

## テストと変異注入

判定ロジックは in-process で呼び、起動形だけ最後に 1 件だけ subprocess で pin する。
外部 CLI は偽バイナリを環境変数で差し込む。既存テストの形をそのまま踏襲する。

pin する機構は次の 7 つ。

1. 索引を ignore 無視で作るフラグを渡さないこと
2. 資源上限のフラグが渡ること
3. detach の 3 点 (新しいセッション、stdio を捨てる、待たない) が揃っていること
4. 停止シグナルが SIGINT であること
5. 生存するセッションが 1 つでもあれば止めないこと
6. 状態ファイル名が、charset ガードでは衝突する 2 つの root で別になること
7. ラッパーがサブコマンドを素通しすること

1 は変異で最も生存しやすい。渡さないことが既定の状態なので、起動コマンドを部分一致で検査すると
フラグを足しても赤くならない。argv 全体を集合として見て、含まれないことを明示的に検査する。
このリポジトリは同じ形を「変異注入の盲点は既定引数」として記録している。

変異は 3 種 (対象を壊す、hook 本体を壊す、配線を外す) を 1 件ずつ隔離して行い、
配線を外したときに config-guard の hook 配線検査が赤くなるところまで見る。
判定は exit code で行い、baseline を出力へ含める。

## 射程と未確認

- 索引構築中の 0 件は、このリポジトリのサイズでは観測できなかった。大きいリポジトリでの挙動は
  README の記述に依る
- worktree で隔離した subagent での挙動は測っていない。SessionStart が subagent の起動では発火しない
  ことは既知なので serve は立たないが、ラッパーがその文脈で実際に効くかは実装後に確かめる
- `search` が served root の外へ届くかは確定していない。パラメータ名を知らないまま投げた 0 件なので、
  未知のパラメータが無視された結果と区別できない
- serve.lock が flock なのか、二重起動の判定が lock と `serve.json` のどちらを見ているかは未確認
- `/clear` のときに SessionEnd と SessionStart が両方発火するかは、バイナリの列挙に双方 `clear` が
  あることまでで、発火させていない
- D5 の 3 つ目の機構 (0 件 rc 1 のとき `tgrep status` を見て構築中なら告げる) は実装していない
  (最終レビューでのユーザー判断)。0 件は日常の結果であり、そのたびに `tgrep status` を起動すると、
  D5 の 2 つ目が退けた「検索ごとのプロセス起動」のコストをそのまま持ち込むため。
  D1 の「構築中に当たる面は D5 の rc 1 経路が受ける」はこの機構に拠っていたので、D1 の根拠は
  次の 2 つに置き直す。構築の窓はこのリポジトリのサイズでは観測できないこと (上の「起動のコストは
  索引の有無で決まらない」) と、大きいリポジトリで踏んだときの見分け方 (`tgrep status` の
  `Indexing:` 行) を `observation.md` の tgrep 節が持つこと。構築中は機構ではなく規範で受けるので、
  D5 の「機構で塞ぐ」の射程は不在までで構築中には及ばない

## 上流への報告

認証の無い TCP に索引内容が載る面と、HTTP のヘッダを読み捨てて body 行を実行する面は、
このリポジトリの運用では受け入れるが、上流 (microsoft/tgrep) にとっては報告の価値がある。

報告はこの Issue に含めず、別 Issue として立てる。ISSUE-62 が同じ形を持つ。
実測は別の Issue が持ち、報告の工程だけを独立した Issue が持ち、報告時点の版の確認と
上流の反応の書き戻しをタスクに持つ。この spec が実測を持つので材料はそのまま渡せる。
