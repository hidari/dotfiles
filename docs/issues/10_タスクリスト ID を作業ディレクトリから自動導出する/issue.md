# feat: タスクリスト ID を作業ディレクトリから自動導出する

## 背景

Issue #9 で 2 アカウント間のタスクリスト共有を入れた。参照先は 1 つになったが、
どのリストを使うかは毎回 `CLAUDE_CODE_TASK_LIST_ID=<id>` を手で打って指定している。

```
CLAUDE_CODE_TASK_LIST_ID=dotfiles claude
```

手打ちである限り typo は避けられない。実際に運用中のリストを棚卸ししたところ、
同じプロジェクトを指すはずのリストが単数形と複数形に割れている例があった。
未知の ID は警告するが新規作成として通すため、typo は「履歴が分裂している」形でしか
後から気づけない。

さらに、ID を指定せずに起動したセッションは Claude Code が採番するセッション ID の
リストを使う。この形で作られたリストが 12 本あり、同じプロジェクトの進捗が
名前付きリストとセッション ID リストに分散していた。

作業ディレクトリから ID を導出すれば、この 2 つの分裂源が同時に消える。
打ち間違えようがなく、指定を忘れることもない。

## 設計

### ID の導出

新しいヘルパ `_claude_task_list_id()` を追加し、2 つのランチャから使う。

| 状況 | 導出される ID |
| --- | --- |
| git リポジトリ内 (サブディレクトリを含む) | リポジトリルートのディレクトリ名 |
| git リポジトリ外 | cwd のディレクトリ名 |
| 前置で明示指定 | 指定した値 (導出をスキップ) |

リポジトリルートを基準にするのは、サブディレクトリで作業してもリストが割れないため。
`git rev-parse --show-toplevel` で解決し、失敗したら cwd へフォールバックする。

zsh 専用の modifier (`${dir:t}`) は使わない。テストは bats が bash で関数を source して
実行するため、関数側を POSIX 互換に保つ必要がある。

未知の ID に対する警告は、導出・手打ちのどちらでも出す。

`cd /` のようにディレクトリ名が空になる場合は変数を設定せず、Claude Code 既定の
セッション ID リストに任せる。空文字を渡したときの挙動は未確認なので、未確認の前提に
賭けない。

### 既存リストの移行

棚卸しの結果は次のとおり。実際の ID とパスは個人の作業内容を含むため記録しない。
本 Issue の作業で使っているリスト自身は既に導出名と一致しているため、移行対象から外す。

| 分類 | 本数 | タスク数 |
| --- | --- | --- |
| 名前付き・中身あり | 3 | 156 |
| セッション ID・中身あり | 11 | 56 |
| 空 | 18 | 0 |

移行対象 212 件の状態は完了 178 件、未完了 34 件。

### 完了済みタスクの扱い (実測で判明した仕組み)

Claude Code はリスト内の全タスクが completed になった時点で、タスクファイルをまとめて
削除する。`.highwatermark` だけが残り採番は継続する。未完了が 1 件でも同居している間は
完了済みも保持される。実験で確認した。

| 状態 | 完了タスクのファイル |
| --- | --- |
| 未完了が同居している | 残る |
| 全件が completed になった | まとめて削除される |

つまりタスクリストは作業記憶として設計されており、使い切ったら消えるのが正常動作である。
棚卸しで「空」に分類した 18 本は放置や typo の跡ではなく、消化しきったリストだった。

あわせて `TaskList` は completed を返さず、全件完了後は `TaskGet` も取得できなくなる。
完了済みを移行しても読み手からは見えず、いずれ自動で消える。

この仕組みに逆らわない。完了済みを選別せず、リストごと移す。連れていった完了済みは
未完了を消化した時点で処理系が掃除する。結果として抽出も採番のやり直しも不要になり、
本物の統合が要る箱だけを扱えばよくなる。

移行前に全リストを `~/.claude/backups/` へ退避するので、失われるものはない。

### 移行先の決定

セッション ID リストの移行先は `~/.claude/projects/` から逆引きする。ただしディレクトリ名を
デコードしてはいけない。あの名前はパス区切りの `/` と名前中の `-` をどちらも `-` に潰す
非可逆エンコードで、名前にハイフンを含むディレクトリを誤って分割する。実際にこれで誤った
移行先を算出した。

セッションの jsonl に記録された `cwd` を読み、実行時と同じ導出ロジック
(`git rev-parse --show-toplevel` → basename、失敗したら cwd の basename) を適用する。
移行先が実行時の参照先と一致することを、同じ手順を使うことで担保する。

移行の規模は次のとおり。

| 種別 | 箱数 | 作業 |
| --- | --- | --- |
| 複数のリストが 1 つの導出名に集まる | 2 | 採番し直しと依存の張り替えを伴う統合 |
| 移行先が未作成または空 | 2 | ディレクトリのリネーム |
| 既に導出名と一致 | 2 | 何もしない |
| 記録された cwd が現存しない | 3 | 未完了 12 件を内容で仕分け |
| 検証用に作られた残骸 | 1 | 削除候補 |

移行スクリプトはリポジトリに入れず `<repo>/.cache/` に置いて実行し、終わったら捨てる。
1 回きりの操作であり、扱う値が個人の作業内容そのものだから。

### 掃除ツールは作らない

当初は空リストが溜まるため削除ツールを置く計画だった。上の仕組みが分かった時点で前提が
崩れたので採らない。空リストは使い切った健全な状態であり、残るのは `.highwatermark` と
`.lock` だけで実害がない。むしろ削除すると採番が 1 に戻り ID が再利用される。
