# マイルストーン表への所属漏れを config-guard で検査する

## 背景

ISSUE-46 が持つマイルストーン表から Issue が漏れる事象が繰り返し起きている。経路と日付は ISSUE-46 のタスクが持つ。いずれも起票そのものは規約どおりで、漏れたのは表への所属だけだった。

この漏れは沈黙する。表は所属だけを持つので、抜けはエラーではなく静かな欠落として出る。全件が入ることを数えて初めて分かる、と ISSUE-46 自身が書いている。

しかも既存のゲートを全部通る。ISSUE-74 を起票したコミット (49ac671) は config-guard scan・pre-commit・CI の 10 ジョブがすべて緑のまま main へ入り、表への追加は後続の別 PR (#198) で手当てすることになった。Issue 17 と Issue 18 が扱う不整合と同じく、ディレクトリの実体と表の記述はどちらもリポジトリ内に静的に存在するので機械検査できる。

`scripts/config-guard` の `related_refs.py` が部品の一部を持っている。`tracked_issue_markdown()` が追跡下の Issue ドキュメントを返し、`identifier_matches()` が 4 記法 (`ISSUE-N` / `Issue N` / `Issue #N` / `#N`) を吸収する。取り付けは `cli.scan()` へ 1 行で、`config-guard-scan` は `always_run: true` なので起票のコミットそのもので発火する。ただし `issue_numbers()` は closed を含む番号集合を返す (2026-09-04 実測: 追跡下 93 件のうち closed 配下 44 件がすべて含まれ、closed にしか存在しない番号が 29 件ある)。この検査が要るのは active 集合なので、絞り込みは新規に書くことになる。

漏れを止める経路は 2 つある。起票の手順へ「所属を決める」を入れる委譲と、dotfiles 側で検査して止める方法である。前者は手順の canonical が上流の `dev-workflow:in-repo-issue` skill にあるため上流への委譲になり、その裁定は ISSUE-46 のタスクが持つ。この Issue は後者だけを扱う。片方が他方を不要にする関係ではない。

## 着手前に確認すること

表の切り出しを列数や表の位置で絞ってはならない。1 つの絞り方が両方向へ同時に壊れる。どちらの方向へどの表が動くかは ISSUE-46 の「割り当ての検算」節が持つ。

そのうえで、**間違えても出力からは気づけない**。2026-09-04 に対照を取ったところ、対象の表 2 つを名指しした切り出し (16 行) と、h2 スコープでまとめて切った切り出し (32 行) が、未割り当ても内訳も重複計上も完全に同じ答えを返した。順序制約表にしか居ない識別子がその時点で 0 件だったためで、将来 Issue が 1 件でも表から落ちて順序制約表に残った時点から、静かに割り当て済みへ化ける。件数の一致を根拠にせず、検査が何行を見たかを対照と並べること。

## 決めること

識別子の解決規則。`identifier_matches()` の除外集合 `FOREIGN_REPOS` は `agentic-coding-tools` だけを持ち、`上流` を前置として認識しない。マイルストーン表の M4 行を実際に通すと `上流 ISSUE-15` と `上流 ISSUE-23` が自リポジトリの Issue 15 と Issue 23 として返る (2026-09-04 実測。既知の前置を持つ行は正しく空を返すので、除外の機構自体は生きている)。そのまま使うと上流の Issue が dotfiles 側の同番号として数えられる。除外集合へ足すか、検査側で前置を見るかを決める。

ISSUE-46 自身の扱い。表の外にあるのは ISSUE-46 だけで、検算は「この Issue 自身が 1」と散文で足している。検査側に自ファイルを除外する分岐を持たせると、除外集合は広がる方向にしか動かず、広がっても違反 0 件の緑にしかならない。
