# fix: apm ガードの到達が起動元シェルの鮮度に依存する

## 背景

2026-08-31 に apm ガードの shim が横取りしていない状態を踏んだ。原因は起動元のシェルが古いことで、そのシェルは shim を PATH へ足す行が入る 3 日前から生きていた。

セッション頭の告知はこれを検出できたが、手当ての文面が誤っており再起動 1 往復を空振りさせた。文面は PR で直したが、それは対症療法であって構造は残る。長寿命のシェルが居座る限り、`.zshrc` への PATH 変更は無音のまま効かない。

## 機構 (2026-08-31 実測)

Claude Code は session_start でシェルスナップショットを作り、Bash ツールは毎回それを source する。スナップショットの扱いは PATH とそれ以外で違う。

| 区画 | 出所 |
| --- | --- |
| 関数 / setopt / alias | `.zshrc` を非対話で毎回評価し直した結果 |
| 最終行の `export PATH` | Claude Code のプロセス PATH (起動元シェルからの継承) |

確かめ方は 2 つ。スナップショットには `.zshrc` が定義する関数 (`cppath` / `kill-port` / `port-proc` など) が入っている一方、`[[ -o interactive ]]` の内側で定義するエイリアス 7 個は 1 つも無く、alias は zsh 組み込み既定の 2 個だけである。もう 1 つは PATH の側で、`PNPM_HOME` は同日のコミットで `.zshrc` から消えているのに、その値に由来する `Library/pnpm` が現在の PATH に残っている。

つまり `.zshrc` は読まれているが、PATH だけは最終行で上書きされる。

## 決めること

`.zshenv` へ PATH 行を移す案は成立しない。`.zshenv` は毎回読まれるが、そこで prepend した PATH も同じ最終行に上書きされる。`settings.json` の `env` も同様で、加えて値に絶対パスが要るため gitleaks と config-guard の 2 層が committed な settings.json を拒む。

残る案は PATH に依存しない第 2 の横取り点を置くことである。関数はスナップショットを越えて生き残り、PATH 上の実体より優先される。置き場は `.zshenv` ではなく `.zshrc` でよい。上の機構のとおり `.zshrc` は毎セッション非対話で評価し直されるので、新規ファイルも新しい symlink も SYMLINK_PAIRS の追加も要らない。

ただし射程は shim より狭い。shim は exec の瞬間に立つのでフックのパーサが届かない形 (包み込み / 変数間接 / xargs) を拾うが、zsh 関数が拾えるのは同一シェル内の直接呼び出しと変数展開と eval までである。`bash -c` と `xargs` は覆えない。恒久策をプローブの測り直しだけに留める選択肢も残る。

`whence -w` は型を返しパスを返さないので、3 段判定を書くなら `whence -wa` を使う。

## 同じ機構の別の実例: mise の版上げ (2026-10-22)

他のリポジトリのセッションから受け箱経由で届いた報告 (報告者の実測)。`mise activate` で起動したセッションでは、起動時の PATH に版ごとの実体のディレクトリ (`installs/node/<旧版>/bin`) が shim より前に入る。mise の設定を書き換えて `mise install` しても、動いているセッションの `node` は旧版のまま走る。`mise current` は新しい版を返すので、それだけを見ると新しい版で検証したと誤認する。`which -a node` の先頭を見れば気づける。`mise exec -- <コマンド>` で包むと新しい版で走る。

dotfiles で確かめたこと: PR #275 で node の pin を 24.18.0 から 24.22.1 へ上げた直後、このセッションの Bash ツールでは `command -v node` が `installs/node/24.18.0/bin/node` を返し、`node --version` は v24.18.0 だった。`mise exec -- node --version` と、新しく起こしたログインシェルの `node --version` はどちらも v24.22.1 だった。PATH を最終行で上書きする上の機構と同じ形で、apm の shim に限らず、起動元シェルの PATH に版を焼き込むものは全部同じように古びる。

報告者の提案 (未検証): ツールチェインの版を上げる手順に「上げたあとの検証は `mise exec` で包むか新しいセッションで回す」と、実際に走った版を出す1行を入れる。dotfiles で版上げの手順を文面として持つのは、mise-update-notifier が週次の Issue に書く本文 (「反映する: `mise install`」) である。

同じ日の2回目の仕分けで、別のリポジトリからも同じ報告が届いた (報告者の実測)。セッションの途中で mise の版を切り替えても Bash ツールの `node --version` は古い版を返し、対話シェル (`zsh -ic`) では新しい版になった。報告元は手元のゲートを新しい版で回すために `mise exec --` を前置した。機構は上と同じで、上の dotfiles の確認がログインシェルで得た結果を、こちらは対話シェルで得ている。

2026-10-31の仕分けで、別のリポジトリから同じ型の報告が3件目として届いた。新しいのは手当てで、コマンドの頭で `eval "$(mise env -s zsh)"` を評価すると、Bash ツールのシェルの版が今の mise.toml に揃った (実測)。報告者の提案: subagent の brief の雛形に、この1行と実際に走る版の確認を入れる。
