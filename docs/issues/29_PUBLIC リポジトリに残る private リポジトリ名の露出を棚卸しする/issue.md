# refactor: PUBLIC リポジトリに残る private リポジトリ名の露出を棚卸しする

本 Issue でも Issue #21 および #25 と同じく、private リポジトリ名は伏字にする。
ファイルパスと件数は公開情報なのでそのまま書く。

## 背景

Issue #25 の Phase 4 でマージ前ゲートが検出した。#25 の新規記述は private リポジトリ名を
伏字にしているが、同じ PUBLIC リポジトリの現ツリーに実名が verbatim で残っており、
伏字が事実上無効化されている。

現ツリーの実測は 6 ファイル 31 行。うち 28 行が closed 配下の Issue ドキュメント、
残り 2 行が `home/.zshrc` と `scripts/tests/zshrc-claude.bats`、1 行が open な Issue の
ドキュメントである。件数は `git grep` で数えられるので、ここには内訳の性質だけ書く。

数えるときは公式 marketplace の名前が部分一致することに注意する。名前が前方一致で重なるため、
素の grep では公式側を private リポジトリ名として数えてしまう (実測で誤って倍近い件数を得た)。

#25 の spec が持つ露出の棚卸しは追加の設定ディレクトリ名しか数えておらず、private リポジトリ名の
現ツリー露出はその一覧から抜けている。

## 検査手段の候補

2026-08-11 の調査結果。予防に価値があるのは、露出が事後に取り消せないためである。リモートブランチを
削除して PR を閉じても commit と diff は公開のまま残り、GitHub には PR を削除する API が無い。

private リポジトリ名の denylist は PUBLIC リポジトリでは自己矛盾する。ルールを書くには守るべき
名前そのものを追跡下のファイルへ書くことになるためである。この矛盾はリポジトリ内で既に認識されていて、
`scripts/tests/gitleaks.bats` は fixture のリテラルを実行時に `printf` で合成して回避している。
したがって名前を列挙して弾く方向は採れない。

採れる候補は 2 つある。

- `docs/` 直下のサブディレクトリを allowlist で縛る。追跡下の `docs/` 直下は `issues` `known-issues`
  `superpowers` の 3 つのみで直下のファイルは 0 件なので、規約外のディレクトリを落としても偽陽性が
  出ない (実測)。直近の露出は規約に無いディレクトリへ着地したのでこれで捕捉できた。
  `.pre-commit-config.yaml` の `issue-scoped-artifacts` が同型の hook なので極性を反転するだけで
  書けるが、置き場は config-guard の方がよい。pre-commit と CI の双方で走るため `--no-verify` に
  backstop が効く
- リポジトリ参照を allowlist 反転で検査する。`<owner>/<repo>` のような汎用形にマッチさせ、名前が
  公開リポジトリの allowlist にあることを要求する。公開名は公開情報なので追跡下に置ける

採らない案も記録する。追跡外のファイルが新たに追跡下へ入るというイベントの検出だけをゲートにはしない。
`git diff --cached --diff-filter=A` で正確に検出でき、追跡済みファイルの `git mv` は `R` になるので
`mv` を特別扱いする必要もないが、main の 185 コミット中 73 件がファイル追加を含むため発火率が高すぎて
慣れで形骸化する。

検査の射程には非対称がある。pre-commit と CI が覆うのはこのリポジトリ 1 本だけで、
`home/.claude/CLAUDE.md` の prose ルールはマシン上の全リポジトリを覆う。静的検査を入れても prose 側の
ルールは消せない。
