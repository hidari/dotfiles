# GitHub Repository Rulesets 導入方針

対象: 個人アカウント（Pro）+ Organization（Team）の全リポジトリ
ラベル凡例: `確定` = 公式ドキュメントで確認済み / `推測` = 未検証の推論 / `未確認` = 要検証TODO

---

## 1. 目的

- `main` を常に動作する状態に保つ
- 直接プッシュを排除し、変更は必ず PR を経由させる
- CI の中身は各リポジトリの裁量に任せつつ、ゲートだけを共通化する
- おひとり様運用のため、レビュー承認ゲートは目的ではない（PR は「記録」として使う）

---

## 2. 前提条件

| 項目 | 内容 | ラベル |
|---|---|---|
| rulesets の利用条件 | パブリックリポは Free でも利用可。プライベートリポは Pro / Team / Enterprise が必要 | 確定 |
| Org レベル ruleset | 2025-06 以降、Team プランでも利用可能（それ以前は Enterprise 限定） | 確定 |
| 個人アカウント | アカウント全体に適用する ruleset は存在しない。リポジトリ単位で設定する必要がある | 確定 |
| ruleset の可搬性 | JSON でエクスポート／インポート可能。複数リポ・複数 Org への適用に使える | 確定 |
| プリセット | 公式のプリセット集 `github/ruleset-recipes` が存在する | 確定 |
| push rulesets | ファイル拡張子・パス長・パス・ファイルサイズによるブロック。Team プランのプライベート／internal リポで利用可 | 確定 |

## 3. 採用する共通ルール（ブランチ ruleset）

対象: デフォルトブランチ（`main`）

### 必須

- 直接プッシュの禁止 → PR 必須
- 必須ステータスチェック（後述の命名規約に依存）
- force push のブロック
- ブランチ削除の禁止
- linear history 必須

### 設定値の注意

- 必要な承認数は 0 に設定する
  - 理由: 自分の PR を自分で承認できないため、1 以上にすると詰む
  - `確定`: 承認数 0 は設定可能で、「PR を記録として残すが承認ゲートはかけない」運用になる
- bypass list は原則空にする
  - 詰んだ場合の逃げ道は「ruleset を一時的に Disabled にする」
  - `確定`: Dependabot は bypass 対象として指定可能（必要になった場合の保険）

### linear history 必須の意味

- 対象ブランチに到達するコミットが親を 1 つしか持たないことを強制する（= マージコミット禁止）
- squash merge / rebase merge は通る。merge commit は通らない
- 併せてリポジトリ設定の「Allow merge commits」を OFF にすること
  - そうしないとマージ直前まで気づかずに弾かれる
- `確定`: force push を禁止すると、bypass 権限がない限り管理者もデフォルトブランチのリネーム・変更ができなくなる

---

## 4. 最大の設計上の罠: 必須ステータスチェックの命名

必須ステータスチェックはチェック名を文字列で指定する。したがって:

- Org 一括の ruleset にすると、全リポジトリで同じジョブ名が存在する必要がある
- 指定した名前のチェックが一度も報告されない場合、その PR は永久にマージできない

### 対応方針

「CI の中身は各リポに任せる。ただし最終的な集約ジョブ 1 個の名前だけは共通とする」という契約にする。

- 集約ジョブ名の例: `ci-required`？
- 既存の「単一集約ジョブをマージゲートにする」CI 構成がそのまま適用できる
- この命名規約はSkillsかRules、あるいはスクリプトにして、新規リポジトリ作成時のチェック項目に含める

## 5. タグ用 ruleset

CalVer と SemVer が混在しているため、パターンマッチではなく「すべてのタグ」を対象にする。

| ルール | 設定 | 理由 |
|---|---|---|
| 削除の制限 (deletion) | ON | タグの消失を防ぐ |
| 更新の制限 (update) | ON | タグの付け替えを防ぐ |
| 作成の制限 (creation) | OFF | ON にすると新規タグが打てなくなる |

結果として「一度打ったタグは動かない・消えない、新しいタグは自由に打てる」状態になり、リリースの再現性が担保される。命名規則の強制は行わない。

`確定`: ruleset のターゲット指定には fnmatch 構文が使える（`*` はディレクトリ区切り `/` にはマッチしない）。将来スキームごとに分けたくなった場合はこちらを使う。

## 6. 見送る項目

### リポジトリのリネーム防止

不採用。基本おひとり様運用であり、リネームする可能性が現実にあるため。

### push rulesets（ファイル拡張子・パス・サイズ制限）

不採用。

- ディレクトリ構造が深くなったり説明的な命名になったりするため、パス長・パスパターンによるブロックは誤爆する
- ロゴデータ等でアプリネイティブなプロジェクトファイル（バイナリ・大容量）を意図的にコミットするケースがあるため、拡張子・サイズ制限も適さない
- 制限をかけるより、必要なファイルを素直に置ける状態を優先する

### 署名コミット必須

今回は見送り。「気が向いたら」リストへ。

- 守る対象は「コミットの作者が本人か」であり、単独運用では実質的な価値が薄い
- 効く場面は write 権限トークンの流出時（攻撃者が本人名義のコミットを作れる）だが、PR 必須 + CI 必須 + force push 禁止で当該経路はかなり潰れている
- `推測`: SSH 鍵での署名（`gpg.format=ssh`）が使えるため、GPG 鍵管理を避けられる。1Password の SSH エージェントに乗せられる可能性があるが、具体的な手順は未検証
- `確定`: GitHub の Web UI 経由の編集と API 経由のコミットは GitHub が署名する
- 注意点: Actions から git CLI で push するワークフロー（CHANGELOG やバージョンの自動コミット等）があると未署名のため弾かれる

導入する場合の順序:

1. ローカルで署名を有効化し、しばらく通常開発する
2. コミットが全て Verified になっていることを確認する
3. その後で ruleset に必須化を追加する

## 7. 運用方法

### 管理場所

パブリックな dotfiles リポジトリで管理可能。ruleset の JSON に秘密情報は含まれない。

注意点:

- プライベートリポジトリ名を JSON にベタ書きすると公開される。対象リポジトリ一覧は `gh repo list --json name` 等で実行時に取得し、JSON 側は「どのリポにも適用できる汎用定義」に留める
- 自身のガードレール構成が公開情報になる点は許容する（方針の宣言に近く、リスクは小さいと判断）

### 認証

- `gh auth login` 済みであれば `gh api` はそのトークンを使うため、通常は 1Password を挟む必要はない
- CI から実行する、または権限を明示的に絞りたい場合は fine-grained PAT を 1Password に格納し、`op run` で `GH_TOKEN` に注入する
- 個人アカウント用と Org 用でトークンのリソースオーナーが別になる点に注意

### 必要な権限

| 対象 | 必要権限 | ラベル |
|---|---|---|
| Org ruleset API | organization permissions の "Administration" (write) | 確定 |
| Repository ruleset API | repository permissions の "Administration" (write) | 未確認 |

### タスク化

`justfile` に `gh-rulesets-apply` 等のタスクを定義し、新規リポジトリ作成時に流すだけで済む状態にする。

## 9. 導入手順

1. 1 リポジトリで ruleset を Disabled で作成し、内容を確認する
2. Active に切り替えて実運用で問題がないか確認する
3. JSON をエクスポートし、dotfiles リポジトリに配置する
4. `just` タスク経由で Org 全体および個人リポジトリへ展開する
5. 各リポジトリの CI に集約ジョブ `ci-required` を用意する（未整備のリポジトリから順に）
