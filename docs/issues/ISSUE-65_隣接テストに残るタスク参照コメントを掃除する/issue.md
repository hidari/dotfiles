# chore(config-guard): コードに残るタスク参照コメントを掃除する

## 背景

ISSUE-59 のマージ前レビュー (boy-scout-sweep) が、今回触っていない隣接ファイルにタスク参照
コメントが 3 箇所残っていると報告した。着手の根拠にする前に数え直して 14 箇所 / 6 ファイルと
記録したが、**その 14 も過小評価だった。下の「射程と件数 (2026-09-13 に再検算)」節が現在値を
持つ。**

レビューが報告した 3 箇所はテスト 2 ファイルのみで、production source の 3 ファイル 9 箇所は
入っていなかった。レビューの射程が「触ったファイルの隣接」に限られていたためで、報告の欠陥
ではない。**棚卸しの表は見つけた分だけが載るので必ず過小評価に外れる**、という規範どおりの形。
14 という数もその外れ方をしていて、同じ規範を 2 回踏んでいる。

コードに書かれたタスク参照が問題なのは 2 つの理由による。1 つは PR の説明にあるべき情報が
コードへ入っていること。もう 1 つは参照先が動くことで、確認した範囲では `Issue #8` と
`Issue #36` はどちらも既に `docs/issues/closed/` 配下へ移っており、コメントが指す位置は
既に変わっている。

加えて `#<数字>` という記法自体が規約違反にあたる。この記法は GitHub の Issue / PR の
番号空間で、in-repo Issue は別の識別子を使う。同じ番号の GitHub オブジェクトと文脈でしか
区別できず、GitHub 側の autolink も発火する。

**この節はもともと「入口がコミットメッセージと一部の追跡ファイルに限られるため既存の
コメントは素通りしている」と書いていたが、実装と食い違っていた。** `issue-id.py` は
`--next` / `--check` / `--check-diff` / `--check-text` の 4 入口を持っていて、狭かったのは
入口ではなく取り付けの方だった。dotfiles のどこにも配線されておらず 1 度も走っていない。
訂正の経緯と取り付けは下の「検査の取り付け」節が持つ。

### 再検算の手順

記法ごとに追跡下の非 docs ファイルを走査し、ヒットを 4 区分へ分類する。件数だけを数えると
また外れる。`git ls-files` は `-z` で受けること (日本語パスがクォートされて黙って落ちる)。

分類が要るのは、この 4 区分が機械的に見分けられないため。テストデータと実際の参照は
どちらも同じ記法で書かれていて、違うのは「そのファイルが何を検証しているか」だけになる。

## 検査の取り付け (2026-09-13)

`issue-id.py --check-diff` を pre-commit へ配線した (`issue-ref-notation` hook)。

入口に `--check-diff` を選んだのは、`--check` が全走査で取り付け時点の違反を全部止めるため。
毎コミット赤になる hook は人が外すので、差分の追加行だけを見る形にした。全走査は手で回す
backstop として残る。

CI ミラーは張らない。検査器は apm の deploy 先に在り `home/.gitignore` が ignore するので、
fresh clone と CI には存在しない。捕捉対象がローカルでの編集時にしか発生しない点も
`issue-scoped-artifacts` hook と同じになる。不在の環境では python3 自身が exit 2 で落ちるため
取り付けは fail-closed で、検査が無音で消える形にはならない。

`python3` は `tool_provisioning` の免除集合へ入れた。pre-commit の entry から要求コマンドが
導出される仕組みなので、入れないと供給側の宣言が無いと報告される。実測では PATH 上の python3 は
brew 版だが、`issue-id.py` は標準ライブラリだけで動くので `/usr/bin/python3` でも足りる。
brew の python を宣言すると、実際に起動する実体と別物を供給側に書くことになる。

この検査が覆わないのは、差分の外に既に在る違反・CI・`--no-verify` でのコミット・pre-commit を
install していない環境。どれも全走査の手動実行が backstop になる。

検証は変異注入 3 種。検査対象を壊す (違反行を stage して exit 1 と行番号)、取り付けを外す
(hook の id を変えて配線テストが赤)、設計を崩す (入口を全走査へ変えて配線テストが赤)。

### 数え直しで分かったこと

置換前の active は 90 件だが、その内訳は識別子 66 件と**ディレクトリ名 24 件**だった。
ディレクトリ名の方は「ディレクトリ名が `ISSUE-<N>_<title>` 形式でない」という別の検査で、
識別子の記法とは無関係に最初から在る。識別子だけが 66 から 2 へ減っている。

**着手時に active 90 件と数えたのは、この 2 つを混ぜた数だった。** この Issue が繰り返してきた
「見つけた件数を対象の件数と読む」型の 4 回目で、今回は置換後の数え直しが捕まえた。

ディレクトリ名の 24 件はこの Issue の射程外。rename は番号もタイトル部も保存する操作になり、
`--next` の限界 (ブランチ間でタイトル部の改名を伴う移動を別の Issue と見て重複を報告し、
新規起票が止まる) に触れるため、別タスクへ切り出す。

## agentic-coding-tools への委譲 (2026-09-13)

配線して実データへ当てたことで、検出器が GitHub の番号空間を誤検出する形が 3 つ出た。
検査器の canonical はあちらなので、こちらでは直さず委譲する。

- 拡張子 `.lua` の色指定。`.css` / `.scss` は「色指定が数字記法と同じ形になり偽陽性になる」と
  して走査から除いてあるが、同じ理由が当てはまる `.lua` が免除に入っていない。実データでは
  nvim の palette と probe が該当した
- Markdown のリンク記法。`PR [#588](...)` は直前が `PR` ではなく `[` になるため許可されない。
  ISSUE-43 の spec が「リンクを落としてから識別子を読む必要がある」として既に記録している
- 括弧を挟む形。`後続の別 PR (#198)` は直前が `(` になるため同じく許可されない

3 つとも「識別子の直前に何が来るか」の判定が、前置の literal と識別子が隣接している前提に
依存している。解法の選択はあちらの領分なのでここでは決めない。

判断の材料として、免除を広げる方向の変更は「緑が健全を意味しない」側へ倒れる点を添える。
免除が広すぎると違反が静かに消えるので、緩める変更には緩めすぎる方向の変異が要る。
