# improve: セッション頭のプローブが逐次で走り待ち時間の上限が積み上がる

## 背景

`guard-health.py` の `collect()` は `guard_probes.PROBES` を先頭から順に呼ぶ。プローブが増える
たびに、外部プロセスの応答を待つ上限がそのぶん足し算で伸びる。

この層は SessionStart から呼ばれるので、伸びた時間はそのままセッション開始の待ちになる。健全な
環境では各プローブが数十ミリ秒で返るため通常は見えないが、上限が問題になるのは外部プロセスが
応答しなくなったときで、それはこの層が検出したい状態そのものにあたる。**沈黙を検出するための層が、
沈黙したときに最も長く待つ。**

## 実測 (2026-09-07)

タイムアウトを持つ subprocess の呼び出しが直列に 4 回ある。値は定数が canonical なのでここには
書かない。

| プローブ | 呼び出し | 上限を持つ定数 |
| --- | --- | --- |
| `probe_tirith` | `tirith check` | `guard_probes.TIRITH_PROBE_TIMEOUT` |
| `probe_task_list_id` | `git rev-parse --show-toplevel` (`hook_git.repo_root`) | `hook_git.RESOLVE_TIMEOUT` |
| `probe_task_list_id` | `git rev-parse --git-common-dir` (`_main_worktree_name`) | 同上 |
| `probe_herdr_pane` | `herdr pane list` | `guard_probes.HERDR_PROBE_TIMEOUT` |

`probe_apm` と `probe_private_ops` は subprocess を持たないので上限に寄与しない。

ISSUE-79 で `probe_task_list_id` と `probe_herdr_pane` を足す前は `probe_tirith` の 1 回だけ
だった。つまりこの Issue が扱う状態は ISSUE-79 が作ったものである。

`probe_task_list_id` が 2 回呼ぶのは、導出値との比較に加えて linked worktree の本体名も許容
するためで、後者は前者が食い違ったときにだけ走る。健全な場合は 1 回で返る。上限としては 2 回分を
見込む必要がある。

## 設計の論点

手当ての候補が 2 つあり、どちらも挙動を変える。

### 並列化

`collect()` をスレッドで回す。上限は最も遅いプローブ 1 つぶんになる。

懸念は、プローブが順序に依存していないことを確かめる必要がある点。現状はどれも独立に見えるが、
それは実装を読んでの判断で、機構としては保証されていない。並列化を入れるなら「登録簿へ足す
プローブは他と独立であること」が新しい制約として増える。その制約を検査する層は無い。

### 合計上限

`collect()` 全体に締め切りを持たせ、超えたら残りを「検査できなかった」として報告する。上限は
プローブの数によらず一定になる。

懸念は、打ち切られたプローブが「沈黙」と報告される点。この層は「健全」と「検査できなかった」を
区別する設計 (`_pane_unverified` がその形) なので、打ち切りは第 3 の状態として扱う必要がある。

### どちらも採らない案

上限そのものを下げる。ただし各定数は「応答しない」を判定するための値で、通常経路の待ち時間では
ない。下げると遅い環境で偽の沈黙が出る。
