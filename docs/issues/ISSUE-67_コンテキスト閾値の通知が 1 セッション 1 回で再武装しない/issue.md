# fix(hooks): コンテキスト閾値の通知が 1 セッション 1 回で再武装しない

## 背景

`home/.claude/hooks/handoff-sentinel.py` の PostToolUse 経路は、推定コンテキストがしきい値を
超えたときに引き継ぎの書き出しを促す。この通知はセッションごとに 1 度しか鳴らず、以後は
超過幅がどれだけ広がっても鳴らない。

別リポジトリのセッション (agentic-coding-tools) からの報告で発覚した。そちらの実測では、
しきい値を超えて通知を受けた時点から 1 時間半・11 万 tokens 作業を続け、使用率が 50% 台から
61% へ伸びたが二度目の通知は無かった。推定値はフック自身の `_context_tokens` を当該
トランスクリプトへ当てて出したもので、判定と同じ経路の数字である。

## 機序 (このリポジトリ側で読んで確認した)

`handle_posttool` は超過を検出したあと `_notify_once(_session_state_file(session_id, "notified"))`
を通る。`_notify_once` は state ファイルの排他生成 (`open(..., "x")`) で、既存なら False を返す。
つまり **1 セッション 1 回のラッチ**であり、鳴った時点で役目を終える。

第 2 の網は無い。

- `handle_stop` も `_notify_once` を使うが、契機が「ツール呼び出しの破損が規定回数」で state も
  別ファイル (`.blocked`)。コンテキスト閾値とは無関係
- `handle_record` は provenance ファイルを消すだけで、ラッチには触らない。引き継ぎを書き出しても
  再武装しない

しきい値の既定は `DEFAULT_CONTEXT_WINDOW_TOKENS` と `DEFAULT_CONTEXT_THRESHOLD_PCT` が持ち、
どちらも環境変数で上書きできる。段は 1 つしかない。

## 併せて見つけたもの: state ファイルの後始末が無い

`.notified` と `.blocked` は作られたきり消えない。`unlink` はコード中に 1 箇所しかなく、
それは provenance の消費に使われている。実測でこのマシンの state ディレクトリには
**292 個**のファイルが溜まっていた。

実害は小さいが 2 つある。無制限に増えること。そして中身を目で見て調べようとしたときに、
どのセッションのものか分からない大量のファイルに埋もれること。実際に上流のセッションは
別 session id の `.notified` を見て一瞬「横取り」を疑っており、state ディレクトリが user
スコープで全セッション共有であることを確かめて解消している。

## 決めること

段が 1 つで、しかも state ファイルが「通知を受けて対処した」と「通知を受けて放置した」を
区別しない。この 2 つは別の問題で、片方だけ直すこともできる。

案は 3 つある。どれを採るかは決めていない。

- **段を増やす。**第 2・第 3 のしきい値を足し、state を段ごとに分ける。単純だが、段の値を
  いくつにするかという新しい判断が要る
- **前回通知時からの増分で再武装する。**state に通知時のトークン数を書き、そこから一定量
  増えたら再び鳴らす。「書き出したのに作業を続ける」場合を自然に覆う。`handle_record` を
  契機にする案もあるが、書き出しただけで作業を続ける場合に何度も鳴るので、増分で条件を
  作る方が素直

**案ごとに外部への影響が違う。**agentic-coding-tools が `skills/meta/session-handoff` を配って
おり、その手順が `handoff-sentinel.py record` を呼ぶ。`record` の CLI 契約 (引数・終了コード・
副作用) を変える案を採ると、あちらの配布物も追随が要る。増分での再武装を `record` の内側で
実装するなら契約は変わらないので影響しない。契約を変えるかどうかで切り分けること。

閾値の段を増やす案は影響しない。あちらの skill が「しきい値などの検知条件は hook が canonical。
ここには書かない」と明記していて、値を持っていないためである。発動経路も種類として書かれて
いるので、新しい段の通知も同じ経路の 1 つとして扱われる。
- **現状維持で「1 回で足りる」と決める。**その場合、なぜ 1 回で足りるのかをフックの
  docstring へ書く。書かないと、次に同じ疑いを持った人が同じ調査を最初からやり直す

判断の材料として、この機構が守ろうとしている失敗が何かを先に確かめること。通知が 1 回でも
実際に引き継ぎが書かれてセッションが切り替わるなら、段を増やしても鳴る先が居ない。
