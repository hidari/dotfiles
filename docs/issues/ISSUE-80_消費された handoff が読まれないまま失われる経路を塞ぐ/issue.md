# fix(hooks): 消費された handoff が読まれないまま失われる経路を塞ぐ

## 背景

2026-09-06 に、引き継ぎ書が 1 本、誰にも読まれないまま消えた。

`home/.claude/hooks/handoff-sentinel.py` の `handle_session` は、provenance の照合を
通った `.cache/handoff.md` を `handoff-consumed-<時刻>.md` へリネームし、provenance を
削除したうえで内容を `additionalContext` として返す。この一連が「消費」である。

事故のときは、消費したセッションが 57 秒で死んだ。注入された内容は誰にも読まれず、
provenance は既に消えているので次のセッションは何も注入しなかった。

内容そのものは `handoff-consumed-<時刻>.md` として残るので失われない。失われるのは
「次のセッションが自動で読む」という経路のほうである。

## 何が観測されていないか

フックは消費までしか観測していない。読み手が実際に読んだかどうかは誰も見ていない。

`handle_record` は provenance を書くだけ、`handle_session` は消費して返すだけで、
どちらも「注入された内容がモデルの文脈に入って、そのセッションが実際に作業を始めた」
ことを確かめる経路を持たない。

## 決めること

### 読まれたことをどう定義するか

厳密な定義は取れない。近似の候補が 2 つある。

- そのセッションが最初の PostToolUse を迎えたら読まれたとみなす。フックは既に
  PostToolUse を受けているので新しい配線が要らない。57 秒で死んだセッションは
  ツールを 1 度も使っていない可能性が高く、事故の形は捕まえられる
- そのセッションが何らかの応答を返したら読まれたとみなす。より正確だが、
  フックからは観測できない

### 検出したときに何をするか

- 次のセッションの頭で「前回消費された引き継ぎが読まれていない可能性がある」と
  告げるだけにする。復帰の判断はユーザーへ渡す
- consumed ファイルから自動で復帰させる。ただし provenance を消した後なので、
  復帰させる内容の信頼をどう担保するかを決める必要がある (この面は ISSUE-58 が扱う
  prompt injection の議論と地続きになる)

## 実装で決めたこと

記録は `<session_id>.unread` に置き、どの repo のものかは中身の `repo_id` で持つ。

消す側 (`_clear_unread`) はツール呼び出しごとに走るので、そこから repo_id を導けない。
導出には git の起動が要る。記録を repo 単位にすると、消す側は state ディレクトリを舐めて
`session_id` で照合するしかなくなる。その走査の量を決めるのは掃除機構を持たない
`.notified` で、増えることと無関係なこの経路が伸び続けることになる。

session 単位にすると消す側はファイル名を直接引けて O(1) になり、走査は 1 セッション 1 回の
`_pending_unread` へ移る。そちらは既に git を起動している経路なので追加コストは実質ない。
「他セッションの記録を消さない」不変条件も、中身の照合ではなくファイル名が担保する形になる。

告知の記録を消すのは、注入まで含めて出力を組み立て切ってからにする。先に消すと、注入側の
例外をフックの包括 except が握った瞬間に告知だけが誰にも届かないまま失われ、本 Issue が
塞ごうとしている事故を関数の内側で再現する。

`session_id` を持たない payload では記録しない。消す側はその id からファイル名を作るので、
記録しても誰にも消せない。空の id が作る名前は先頭がドットになり、集める側の glob からも
外れるため、誰にも見えない記録が残ることになる。

## 「復帰させない」の前提

「復帰させないので不要」という判断は、消費 (リネーム + provenance 削除) を SessionStart の
一撃で確定させる現在の形を前提にしている。

注入だけを先に行い、確定は最初の PostToolUse まで遅らせる二相の消費にすると、provenance が
確定まで残るので「消した後の内容を何を根拠に信用するか」という問い自体が発生しない。つまり
prompt injection の議論を避けられたのは設計の帰結であって、制約ではない。

本 Issue は告知までを射程とするが、二相の消費を検討するときはこの前提から読み直すこと。
