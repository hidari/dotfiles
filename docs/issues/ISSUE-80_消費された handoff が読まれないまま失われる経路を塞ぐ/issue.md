# fix(hooks): 消費された handoff が読まれないまま失われる経路を塞ぐ

## 背景

2026-09-06 に、引き継ぎ書が 1 本、誰にも読まれないまま消えた。

`home/.claude/hooks/handoff-sentinel.py` の `handle_session` は、provenance の照合を
通った `.cache/handoff.md` を `handoff-consumed-<時刻>.md` へリネームし、provenance を
削除したうえで内容を `additionalContext` として返す。この一連が「消費」である。

事故のときは、消費したセッションが 57 秒で死んだ。注入された内容は誰にも読まれず、
provenance は既に消えているので次のセッションは何も注入しなかった。

内容そのものは `handoff-consumed-<時刻>.md` として残るので失われない。失われるのは
「次のセッションが自動で読む」という経路のほうである。

## 何が観測されていないか

フックは消費までしか観測していない。読み手が実際に読んだかどうかは誰も見ていない。

`handle_record` は provenance を書くだけ、`handle_session` は消費して返すだけで、
どちらも「注入された内容がモデルの文脈に入って、そのセッションが実際に作業を始めた」
ことを確かめる経路を持たない。

## 決めること

### 読まれたことをどう定義するか

厳密な定義は取れない。近似の候補が 2 つある。

- そのセッションが最初の PostToolUse を迎えたら読まれたとみなす。フックは既に
  PostToolUse を受けているので新しい配線が要らない。57 秒で死んだセッションは
  ツールを 1 度も使っていない可能性が高く、事故の形は捕まえられる
- そのセッションが何らかの応答を返したら読まれたとみなす。より正確だが、
  フックからは観測できない

### 検出したときに何をするか

- 次のセッションの頭で「前回消費された引き継ぎが読まれていない可能性がある」と
  告げるだけにする。復帰の判断はユーザーへ渡す
- consumed ファイルから自動で復帰させる。ただし provenance を消した後なので、
  復帰させる内容の信頼をどう担保するかを決める必要がある (この面は ISSUE-58 が扱う
  prompt injection の議論と地続きになる)

## 実装で決めたこと

記録は `<repo_id>.unread` に置く。次のセッションは前のセッションの id を知らないので、
session 単位にすると自分宛でない記録を見つけられない。

消す側 (`_clear_unread`) はその repo_id を導けない。導出には git の起動が要り、消す側は
ツール呼び出しごとに走るためである。代わりに state ディレクトリを舐めて `session_id` で
照合する。他セッションの記録を消さないことはこの照合だけが担保しており、テストの
「session_id が違う PostToolUse では読まれた扱いにしない」がそこを pin する。

実 state ディレクトリ (324 件) での走査は 1 回あたり 296 マイクロ秒だった。git の起動より
2 桁速い。単一プロセスでの計測なので絶対値は割り引いて読むこと。
