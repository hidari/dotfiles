# refactor: config-guard の Markdown フェンス走査を 1 実装へ寄せる

## 背景

config-guard に Markdown のコードフェンスを追跡する実装が 2 つある。

- `markdown_links.extract_link_targets` (`FENCE_PATTERN`)
- `instruction_refs.prose_lines` (`_FENCE`)

正規表現は完全に同一 (`^\s*(` + バッククォート 3 つ以上 + `)`) で、フェンス内を除外して
本文だけを読むというループの目的も同じ。片方だけを直すと、もう片方は黙って古い規約の
まま残る。CLAUDE.md の「同じ制約を 2 箇所に書かず canonical を 1 つ決める」に反する。

`~~~` によるフェンスをどちらも扱わないことも、インデントを許す点も、閉じないフェンスが
以降を skip する点も、2 箇所で独立に決まっている。どれか 1 つを変えたい日が来たときに、
変更が 1 箇所で済むという保証が無い。

### 3 つ目が来ることが分かっている

Issue #30 (Markdown 内のシェルスニペットを構文検査する) は、フェンス内を **抽出する**
検査を作る。今の 2 つはフェンス内を **捨てる** ので向きは逆だが、フェンスの開始と終了を
決める規約は同じものを使う必要がある。3 つ目が別実装で入ると、規約が 3 箇所へ散る。

### 単純な共通化では足りない可能性

`markdown_links` の docstring は「構造的な取りこぼしのクラスを踏んだときは、regex の
逐次強化ではなく extract_link_targets の中身を CommonMark トークナイザへ差し替える。
抽出はこの関数 1 つに隔離してある」と宣言している。共通化はこの約束を壊さない形にする
必要がある。regex の共有だけを行うと、ループの重複は残ったまま「canonical へ寄せた」と
読める状態になるので、そこで止めないこと。

- [ ] 移行後も既存 2 検査の結果が全 Markdown で不変であることを、追跡下の全ファイルに
      対する対照で確かめる (実装の等価性は目視では分からない)
- [ ] 変異注入で pin する。共通化した機構を壊したとき、両方の検査が赤くなること
