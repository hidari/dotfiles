# agent: マージ前ゲートに観点ごとの dispatch プロンプトのテンプレートを持たせる

## 背景

非公開の利用側リポジトリから委譲された (2026-09-17)。ISSUE-99 と同じ委譲元で、マージ前の横断レビューを 3 巡回した実測から出てきた。

ユーザーの裁定は次のとおり。

- テンプレートは `dev-workflow:pre-merge-quality-gate` の中に置く
- 観点は束ねず、いまの観点別の分け方を保つ。観点の数は起動条件 (E2E の影響確認と PUBLIC 漏洩スイープ) で変わるので、skill に数を literal で書かない

### 今の gate (v0.7.0 と v0.8.0 で SKILL.md は同一)

- 観点ごとの prompt は Phase 1 の番号付きリストへ直書きされていて、共通のブロックは無い。書き方も観点ごとに違う
  - simplify と E2E の影響確認は、skill へ渡す args だけを書く
  - code-reviewer は 1 行の要素の列挙
  - Boy Scout と PUBLIC 漏洩スイープは逐語の長文
- 事実上の共通要素は、観点ごとに別の文言で重複している。確信度のしきい値、0 件の明示、`<file>:<line> → ...` の出力形の 3 つ
- 集約出力は観点ごとの `completed / skipped (reason)` の 1 行で、担当外の発見や 0 件の根拠を受ける欄が無い
- 出力フォーマット節は、Boy Scout の漏れを「プロンプト改善対象として記録する」と書くが、記録先が無い

### 実測 (利用側リポジトリ)

- コントローラは dispatch prompt を毎回 3〜4k トークン手書きしており、自身のコンテキストを圧迫していた
- 2 巡目で最も重い欠陥を出したのは Boy Scout の観点だった。与えた 4 つのカテゴリのどれにも当たらないものを、担当外として別枠で報告してきた。担当を狭めすぎると、範囲外の最も重い欠陥を取りこぼす
- 3 巡目は全ブリーフに担当外の枠を置いた。枠から 3 件が出て、2 件が反証を生き残った。最も多くの観点 (5 つ) が独立に指した指摘のうち 2 件は、枠から出ていた
- 観点どうしは正反対を返す (simplification と altitude、reuse と efficiency)。束ねる案は衝突しやすい組を分ける限り成立しうるが、束ねないと決めた

### テンプレートの共通要素

利用側で再利用できると分かった要素。

1. コントローラの理解を鵜呑みにせず実測で確かめ、食い違ったら実測を正とする
2. 作業ツリーを変更せず、実験は隔離したコピーで行う
3. さらに subagent を起動しない
4. 0 件なら、何を何件読んだ結果かを添えて明示する
5. 環境の制約 (認証、隔離など) を伝えるときは、回避の禁止まで併記する
6. 担当外の発見を返す枠
7. リポジトリ固有の誤検出源 (日付の表記揺れ、注入待ちのプレースホルダ、正当な WHY コメントなど) を差し込む口

今の gate の prompt 群に、1〜3、5、7 は無い。6 は Boy Scout だけが一部を持つ (隣接ファイルの候補と、PR の範囲を大きく超えるリファクタを、別 Issue の提案として返す)。4 は、件数まで求めるのが PUBLIC 漏洩スイープだけで、Boy Scout は 0 件の明示だけ、code-reviewer には規定そのものが無い。

### 反証の試行結果 (2026-09-28の委譲)

同じ委譲元から、反証の試行結果が新しい委譲として届いた。数値は委譲元のマージ前ゲートで元データから検算済みと添えられている。こちらでは、件数のある基準・3回目・4回目について件数と費用の割り算が合うことを確かめた (1・2回目は件数が届いていない)。

ユーザーの裁定 (2026-09-28、委譲元での裁定)。

- マージ前ゲートでは、出た指摘を深刻度によらず全件反証する
- 反証は観点ごとの指摘を束ねて1 agent に当てる。束の中でも指摘ごとに独立の判定 (holds / partially_holds / refuted) を返させる。指摘の ID はコントローラが採番し、schema の enum で固定する
- 反証の結果は裁定の材料で、指摘を落とすかはコントローラが決める
- 集約するのは gate 側だけ。タスク単位の反証 (SDD の fix loop の前に置く反証と、scoped re-review を外すこと) は利用側で試行を続けるので、今回は依頼されていない
- 反証の対象を important 以上に絞る案は退けた

実測。トークンは workflow の記録にある workflowProgress の tokens で揃えてある (完了通知の subagent_tokens と1トークン単位で一致する物差し)。値はレビュー / 反証 / 反証1件あたりの順。

- 基準 (試行前、指摘1件に1 agent): 881,683 / 2,377,437 / 約79.2k。下の「決めること」に書いた回で、30件と全体の73%に割り算が合う
- 1回目 (指摘1件に1 agent): 1,124,204 / 4,232,648 / 約94.1k
- 2回目 (途中で1件1 agent から束へ切り替え): 1,712,516 / 1,595,928 / 約82.1k (1件1 agent)、約19.9k (束)
- 3回目 (束、29件): 637,848 / 746,346 / 約25.7k
- 4回目 (束、17件): 462,146 / 525,528 / 約30.9k

実測から読めること。

- 全件を束ねた3・4回目の反証1件あたりは、基準の約1/3と約2/5だった。agent ごとの固定費を按分した効果で、反証そのものが安くなったわけではない。3回目の束の件数 (1〜12) と費用から最小二乗で引くと、固定費は1 agent あたり約113k、限界費用は1件あたり約6.3k だった (3回目だけから引いた値)
- refuted で落ちた指摘は1〜4回目で6件、1件、0件、1件だった
- 落ちた数は反証の効き目をほとんど数えていなかった。束ねた3・4回目では、反証が提案どおりの修正の害を示し、それを根拠に処分 (直し方を変えた、見送った、人へ回した) が変わった指摘が、指摘の ID で数えて29件中12〜14件と17件中8件あった。どれも important 未満 (boyscout / nice-to-have / minor) で、important 以上に絞っていたら全部失われていた。4回目はほかに、refuted になった important 1件を人の選択へ回した
- 同じ欠陥を複数の観点が出したときに反証が割れる現象 (基準の回では、これを理由にコントローラが反証を退けた) は、3・4回目では起きなかった

委譲元が改めた指標。

- 反証が処分を変えた指摘の数。指摘の ID 単位で深刻度別に数え、落とした・直し方を変えた・見送った・人へ回したものを含める
- 反証が提案どおりの修正の害を示した数。判定に害の有無を「なし / 提案の形に害 / 条件付き」の列挙と本文で返させ、「提案の形に害」と「条件付き」は分けて数える。自由文だけだと、読み方で件数が10〜15のように揺れた
- important 以上に絞る案を検討し直す条件は、important 未満の指摘から処分を変えた指摘が1件も出ない回が2回続くこと

未測定と注意。

- 束ねた形の判定の質 (1 agent の中で指摘ごとの判定が独立か) は測っていない。全件を束ねた回は3・4回目の2回だけで、2回目は途中から束にした部分だけ
- 反証役のモデルの版が回によって違う (基準と1回目、2回目、3・4回目で opus の版が3種)
- agent の最終応答の usage は完了通知と一致せず、agent によっては約2倍ずれる (fable に限らず opus でも起きた)。回をまたいで比べるときは workflowProgress で揃える
- 3回目から引いた固定費 (1 agent あたり約113k) は、1件1 agent の回の1件あたり (約79.2k〜94.1k) より大きい。束の agent と1件1 agent の agent は固定費が同じではないことになり、固定費を按分した効果という説明だけでは数字がかみ合わない。理由は測っていない (こちらで割り算から気づいた点で、委譲元の記述には無い)

## 決めること

- テンプレートの形と置き場。SKILL.md の本文か、同梱のファイルか。共通部と観点固有部をどう分けるか。観点を 1 つ足す単位がテンプレート 1 枚になる (上流 ISSUE-61 の未決に関わる)。gate が関連に挙げる superpowers の requesting-code-review は、同梱ファイルとプレースホルダの一覧の形で dispatch テンプレートを持ち、2 と 3 に当たる節も含む。出発点にできる
- CLAUDE.md との関係。このリポジトリのグローバル CLAUDE.md は、要素ごとに向きが違う。
  - 1、3、4 は subagent 自身への規範で、subagent にも注入される。テンプレートへ写すと同じ規範が 2 箇所にできるので、CLAUDE.md を持たない配布先のために写すのか、参照にとどめるのかを決める。写すなら、写しの drift を見る手段も決める
  - 2 と 5 は、委譲する側に brief へ書くことを求める規範である。テンプレートはその義務を満たす手段にあたり、写しにはならない
  - 6 と 7 は CLAUDE.md に無く、テンプレートに書かないと届かない
  - 反証の指摘 ID をコントローラが採番して schema に含めることと、迷ったときの既定の判定を反証役へ指示しないことは、グローバル CLAUDE.md の委譲のカテゴリが委譲する側へ求める規範にあたる。2と5と同じ向きで、反証のテンプレートはその義務を満たす手段になり、写しにはならない
- 受け側。担当外の発見と 0 件の根拠を受ける欄が要る。欄の形は上流が持つ。skip の根拠を受ける形を決めるタスクは上流 ISSUE-59 にあり、出力フォーマット節の欠陥を扱う上流 ISSUE-33 の追記と衝突しないことを条件にしている (どちらも未了)。この Issue は要件と実測を材料として両方へ渡す。出力フォーマット節の「プロンプト改善対象として記録する」の記録先も同じ節の話なので、同じく渡す
- skill 経由の観点への届け方。simplify と E2E の影響確認は、gate 側で prompt を持たない。共通要素を args に載せるか、届かないと明記するか
- 起動数の写しの置き場を、上流 ISSUE-47 と同時に決める
- 反証の工程を含めるか。決まった (2026-09-28)。含める。裁定と実測は「反証の試行結果」節にある。基準にした 3 巡目では、反証 (指摘 1 件に 1 agent) がワークフロー全体の費用の 73% を占めた。反証は 30 件中 10 件を落とし、そのうち 4 件は別の観点が出した同じ指摘が生き残っていたので、コントローラが反証を退けて直した
