# agent: マージ前ゲートに観点ごとの dispatch プロンプトのテンプレートを持たせる

## 背景

非公開の利用側リポジトリから委譲された (2026-09-17)。ISSUE-99 と同じ委譲元で、マージ前の横断
レビューを 3 巡回した実測から出てきた。

ユーザーの裁定は次のとおり。

- テンプレートは `dev-workflow:pre-merge-quality-gate` の中に置く
- 観点は束ねず、いまの観点別の分け方を保つ。観点の数は起動条件 (E2E の影響確認と PUBLIC 漏洩
  スイープ) で変わるので、skill に数を literal で書かない

### 今の gate (v0.7.0 と v0.8.0 で SKILL.md は同一)

- 観点ごとの prompt は Phase 1 の番号付きリストへ直書きされていて、共通のブロックは無い。書き方も
  観点ごとに違う
  - simplify と E2E の影響確認は、skill へ渡す args だけを書く
  - code-reviewer は 1 行の要素の列挙
  - Boy Scout と PUBLIC 漏洩スイープは逐語の長文
- 事実上の共通要素は、観点ごとに別の文言で重複している。確信度のしきい値、0 件の明示、
  `<file>:<line> → ...` の出力形の 3 つ
- 集約出力は観点ごとの `completed / skipped (reason)` の 1 行で、担当外の発見や 0 件の根拠を
  受ける欄が無い
- 出力フォーマット節は、Boy Scout の漏れを「プロンプト改善対象として記録する」と書くが、記録先が無い

### 実測 (利用側リポジトリ)

- コントローラは dispatch prompt を毎回 3〜4k トークン手書きしており、自身のコンテキストを圧迫していた
- 2 巡目で最も重い欠陥を出したのは Boy Scout の観点だった。与えた 4 つのカテゴリのどれにも
  当たらないものを、担当外として別枠で報告してきた。担当を狭めすぎると、範囲外の最も重い欠陥を
  取りこぼす
- 3 巡目は全ブリーフに担当外の枠を置いた。枠から 3 件が出て、2 件が反証を生き残った。最も多くの
  観点 (5 つ) が独立に指した指摘のうち 2 件は、枠から出ていた
- 観点どうしは正反対を返す (simplification と altitude、reuse と efficiency)。束ねる案は衝突しやすい
  組を分ける限り成立しうるが、束ねないと決めた

### テンプレートの共通要素

利用側で再利用できると分かった要素。

1. コントローラの理解を鵜呑みにせず実測で確かめ、食い違ったら実測を正とする
2. 作業ツリーを変更せず、実験は隔離したコピーで行う
3. さらに subagent を起動しない
4. 0 件なら、何を何件読んだ結果かを添えて明示する
5. 環境の制約 (認証、隔離など) を伝えるときは、回避の禁止まで併記する
6. tgrep に grep 流の `-r` を渡さない。tgrep の `-r` は `--replace` で、一致部分が黙って置き換わる
   (再帰は既定の動作なので、フラグ自体が要らない)
7. 担当外の発見を返す枠
8. リポジトリ固有の誤検出源 (日付の表記揺れ、注入待ちのプレースホルダ、正当な WHY コメントなど)
   を差し込む口

今の gate の prompt 群に、1〜3 と 5〜8 は無い。4 は、件数まで求めるのが PUBLIC 漏洩スイープだけで、
Boy Scout は 0 件の明示だけ、code-reviewer には規定そのものが無い。

## 決めること

- **テンプレートの形と置き場。**SKILL.md の本文か、同梱のファイルか。共通部と観点固有部をどう
  分けるか。観点を 1 つ足す単位がテンプレート 1 枚になる (上流 ISSUE-61 の未決に関わる)
- **受け側。**集約出力に、担当外の発見と 0 件の根拠を受ける欄を足すか。上流 ISSUE-33 と
  上流 ISSUE-59 が同じ面を扱っている
- **skill 経由の観点への届け方。**simplify と E2E の影響確認は、gate 側で prompt を持たない。
  共通要素を args に載せるか、届かないと明記するか
- **環境に依存する要素。**6 (tgrep) は配布先に tgrep が無い環境では意味を持たない。配布物に
  どう書くか
- 起動数の写しの置き場がテンプレート化で動くので、上流 ISSUE-47 と同時に決める
- **反証の工程を含めるか。**利用側で試行中で、結果を待ってから決める。基準にした 3 巡目では、
  反証 (指摘 1 件に 1 体) がワークフロー全体の費用の 73% を占めた。反証は 30 件中 10 件を落とし、
  そのうち 4 件は別の観点が出した同じ指摘が生き残っていたので、コントローラが反証を退けて直した。
  反証が正しく落としたのは 6 件
