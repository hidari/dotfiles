# chore: 保留にしたタスクリスト統合 3 本を適用する

## 背景

Issue #10 でタスクリストを導出名へ寄せる移行を行ったが、統合 3 本を保留にした。移行先となる 2 つのリストを別の Claude Code セッションが同時に書き換えていたためである。

統合は「移行先の採番上限を読む → その値をオフセットにファイルを書く → 上限を更新する」という read-modify-write なので、読んでから書くまでの間に移行先へタスクが増えると採番が壊れる。

移行スクリプトは `.cache/migrate-task-lists.sh` にある (リポジトリ管理外)。`ONLY` 環境変数で 1 本ずつ処理できるよう直してあり、`.highwatermark` が実在する最大 ID より小さいことがある問題への対処も入れてある。この対処が無いと移行先の既存タスクを上書きする。

## タスク

- [ ] 移行先 2 本を担当するセッションが動いていないことを確認する
- [ ] バックアップを取り直す (前回のものは移行前の状態なので古い)
- [ ] dry-run で残りの統合対象を確認する
- [ ] `ONLY` で 1 本ずつ適用し、各回で移行先の既存ファイルがハッシュ単位で変わっていないことを確認する
- [ ] 未完了タスクの subject 集合が保たれたことを確認する
- [ ] Issue #10 の未チェック項目を閉じる

## 着手条件の絞り込み (2026-07-29 実測)

「他にセッションが動いていないこと」は条件として広すぎた。統合 3 本の移行先は 2 本のリストに集中しており、**その 2 本を担当するセッションだけが停止していればよい**。無関係なセッションは動いていて構わない。着手前に実行中プロセスの作業ディレクトリを実測し、移行先と重なるものが無いことを確認する。

```bash
ps -eo pid,command | grep -E '[c]laude'
lsof -a -p <pid> -d cwd -Fn | grep '^n'
```

## 採番の実測結果

移行先 2 本とも `.highwatermark` が実在する最大 ID より小さかった (乖離は 9 と 34)。Issue #10 で記録した「セッション中の採番が書き戻されない」現象は解消しておらず、移行スクリプトの補正はこれからも必要である。

隔離した使い捨てリストで採番の挙動を実測した。`.highwatermark` を据え置いたまま外部プロセスが高い ID のファイルを 1 つ置くと、同一セッションの次の採番はそのファイルより上に飛んだ。**採番は `.highwatermark` だけでなくディレクトリ上のファイルも見ている**と読める。これが正しければ ID 衝突そのもののリスクは当初の想定より低い。

ただし確度は中程度に留める。実験は headless (`-p`) で行っており、対話セッションが同じ経路を通る保証を取れていない。

## 未解決の危険

**全タスク完了時の一括削除が、外部から追加された未完了タスクを巻き込むか**が分かっていない。これが「巻き込む」なら、移行先のセッションが自分のタスクを全部完了させた瞬間に移行したタスクが消える。ID 衝突とは独立した経路なので、採番の実測結果では打ち消せない。

実測を試みたが結論は出なかった。注入なしの対照でも一括削除が発火せず、測定器そのものが動いていないことが分かったためである。対照を取らずに「注入したタスクが残った」だけを見ていたら、安全と誤結論していた。

決着させるなら対話セッションで再実験する必要がある。それまでは移行先のセッションを止めてから適用するのが確実で、実験のコストを払う理由も薄い。
