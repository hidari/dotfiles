# chore: herdr-core の配下でローカルネットワークの許可が外れる件を確かめ検査を決める

## 背景

ISSUE-66 の「受け箱から届いた別の原因の候補 (2026-10-22)」節に、ad-hoc 署名のターミナルのホストを brew で上げると「ローカルネットワークの許可も同じ仕組みで外れる」という報告がある。その続報が2026-11-02に受け箱から届いた。ISSUE-66 の主題 (偽バイナリの初回の起動の遅れでテストが不安定になる) とは別の、ホストの許可でコンテナへ届かなくなる問題なので、この Issue へ分けた (2026-11-02、ユーザー決定)。2026-11-04の仕分けで、同じ配下で起きたフルディスクアクセスの許可の報告も足した。

### 報告者の申告

他のリポジトリのセッションの報告で、根拠は報告者の申告をそのまま書く。

- 端末多重化ツールが Homebrew 版から `~/.local/bin` の素の実行ファイルに替わると、配下で起動した Apple 署名でないバイナリ (backend、uv の Python、Playwright の Chromium) が OrbStack のコンテナへ `errno 65 (No route to host)` で届かなくなった。接続を試みてもシステム設定のローカルネットワークの一覧に行が増えず、許可して直す道が無かった (実測)
- 責任元のホストは `TERM_PROGRAM` では分からない (ghostty と出たが、実際の親は多重化ツールだった)。親は `p=$$; while [ "$p" -gt 1 ]; do ps -o pid=,ppid=,comm= -p $p; p=$(ps -o ppid= -p $p | tr -d ' '); done` でたどって確かめる (実測)
- `.command` ファイルを `open -a Terminal` で開いて backend と E2E を起動すると、Terminal.app の許可で通った (実測)。ISSUE-66 の同じ節にある初回の起動の遅れの報告と同じ回避の経路にあたる
- 報告者の提案: 多重化ツールを `~/.local/bin` の素の実行ファイルで配る構成では、配下のプロセスがローカルネットワークの許可を得る道が無い可能性がある。.app の形で配るか、Apple 署名でないバイナリからローカルのコンテナへ TCP で届くかを確かめるプローブをセットアップの検査に足すことを検討してほしい (実測1回。.app にすれば直るかは推測)

仕分けたセッションの解釈: 報告は多重化ツールの名前を書いていないが、「Homebrew 版から `~/.local/bin` の素の実行ファイルへ」は ISSUE-139 の herdr ターミナル版から herdr-app への移行と形が一致する (推定)。

### dotfiles で確かめたこと (2026-11-02)

- 仕分けたセッション自身の親を上のループでたどると `~/.local/bin/herdr-core` だった。`codesign -dv` では herdr-core が ad-hoc (linker-signed、TeamIdentifier なし) で、`/Applications/Herdr.app` は TeamIdentifier を持つ署名だった。シェルの親は署名付きの .app ではなく ad-hoc の herdr-core である。このため、.app の形で配られていても、そのままでは報告者の提案の手当てにならないと読める (推定。許可がどのプロセスの署名で決まるかは確かめていない)
- herdr-core を置くのは dotfiles ではない。追跡下に配置の記述は無く、型定義 (`gpui-kit.d.ts`) が名前を持つだけだった。配り方は dotfiles の側では選べず、選べるのは検査か案内になる。ファイルの更新時刻は2026-11-01で、アプリが自分で更新していると見える (推定。そうなら版ごとに許可が外れる形が繰り返しうる)
- errno 65 そのものは再現を試していない

### 報告者の申告 (2026-11-04の仕分け): フルディスクアクセス

2026-11-02に届いた別のまとめから、同じ形の配下で起きた別の許可 (TCC のフルディスクアクセス) の報告を足した。

- ターミナル多重化ツールの常駐バイナリの配下で動く Claude Code から、macOS の `~/Downloads` 配下のスクショを Read すると EPERM (TCC、ダイアログ無し) になった。Claude Code の親をたどった先の常駐バイナリをフルディスクアクセスに足すと、そのバイナリを再起動しなくても同じセッションから読めた。「ファイルとフォルダ」の一覧にはダイアログが一度出たアプリしか出ないので、そちらでは足せない (実測)
- 許可の責任元はアプリ名や `TERM_PROGRAM` ではなく、`ps -o pid=,ppid=,comm=` で親をたどって確かめる (実測)。上の申告の2つ目と同じ
- 報告者の提案: ターミナル多重化ツールを更新したときに見直す許可の一覧 (ローカルネットワーク・デベロッパツール) に、フルディスクアクセスを足す (実測)

仕分けたセッションの解釈: ローカルネットワークの側は一覧に行が増えず許可して直す道が無かったのに対し、フルディスクアクセスは手で足せて再起動なしで効いた。同じ配下の問題でも、許可の種類で直し方が分かれる (推定)。報告は多重化ツールの名前を書いていない。

### dotfiles で確かめたこと (2026-11-04)

- 仕分けたセッションの親を上のループでたどると、今回も `~/.local/bin/herdr-core` だった
- `~/Downloads` の EPERM そのものは再現を試していない

## タスク

- [ ] herdr-core の配下から、Apple 署名でないバイナリで手元のコンテナへ TCP で届くかを確かめる。対照として、同じバイナリを `open -a Terminal` の `.command` の配下からも当てる
