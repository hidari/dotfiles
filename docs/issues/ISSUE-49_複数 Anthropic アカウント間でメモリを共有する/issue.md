# feat: 複数 Anthropic アカウント間でメモリを共有する

## 背景

Claude Code のプロジェクトメモリは `<config-dir>/projects/<slug>/memory/` にあり、設定
ディレクトリごとに完全へ独立する。アカウントを 2 つ使い分けているため、同じプロジェクトでも
アカウントを替えると記憶が引き継がれない。

`references` と `skills` は dotfiles の実体を指す symlink で共有できているが、メモリ側には
その仕掛けが無い。共有できている側があることは、メモリでも同じ手が効くことの根拠にならない。
読み書きの経路が違う可能性がある。

**欠落は警告として出ない。**「メモリが数件しかない正常なセッション」として返るので、記憶を
失ったまま作業が進み、失ったこと自体に気づけない。

アカウントは将来さらに増える可能性がある。2 つ決め打ちの仕組みにはしない。

## 実測 (2026-08-26)

日付付きのスナップショットとして扱うこと。

### 両アカウントの状態

| 項目 | `~/.claude` | もう一方 |
| --- | --- | --- |
| projects 数 | 41 | 14 |
| dotfiles プロジェクトの memory 件数 | 36 | 39 |
| memory の最終更新 | 2026-08-23 03:16 | 2026-08-25 02:59 |

27 プロジェクトは `~/.claude` 側にしかメモリが無い。それらを別アカウントで開くと記憶ゼロから
始まる。

### 素朴な共有が 2 通りとも壊れる

2026-08-24 に 3 プロジェクト分を手で移行した際、元を消さずにコピーし、あわせてファイル名を
kebab 化した。結果として同じ内容が別名で両側に残っている。

| 側 | 命名 | 例 |
| --- | --- | --- |
| `~/.claude` | アンダースコア区切り | `feedback_agent_count_limit.md` |
| もう一方 | ハイフン区切り | `feedback-agent-count-limit.md` |

dotfiles プロジェクトで両側に同名で存在するのは `MEMORY.md` の 1 件だけで、しかも内容が違う
(16302B と 17776B)。

この形が素朴な解を両方とも壊す。

- ディレクトリごと symlink を張ると、片側の `MEMORY.md` が失われる
- ファイル単位で symlink を張ると、命名が違うので同じ知識が二重に登録される

移行後も両側が独立に育っている。片側は 2026-08-23 で止まり、もう一方だけが更新されている。

### symlink はディレクトリ単位で効く

`/private/tmp` に probe リポジトリを作り、128bit のノンスを索引へ植えて完全一致で判定した。
前半だけの一致は判定に使っていない。

| 命題 | 構成 | 結果 |
| --- | --- | --- |
| 索引が注入されるか | `memory/` を symlink | 注入される |
| 書き込みが symlink を壊すか | `memory/` を symlink | 壊れない |
| symlink 越しに新規作成できるか | slug ディレクトリを symlink | `memory/` が実体側へ生える |

書き込みの前後でディレクトリの inode は変わらず、`MEMORY.md` の inode だけが変わった。索引は
置換で更新されるが、置換は symlink の内側で起きるのでディレクトリを指すリンクは無傷になる。
同じ理由でファイル単位の symlink と hard link は壊れる。

slug ディレクトリを symlink にした構成では、その下に `memory/` が実ディレクトリとして生え、
セッションログも実体側に落ちた。`projects/` を丸ごと共有する形なら、新規プロジェクトも実体側へ
集まる。

### メモリの読み書きで分かった付随事項

- 索引と実体は分離している。毎セッション自動で載るのは `MEMORY.md` だけで、個別のファイルは
  description を見て必要なときに読まれる。ノンスを個別ファイルに置くと注入を測れない
- メモリのキーは git リポジトリのルートへ丸められる。セッションログのキーは作業ディレクトリを
  そのまま変換する。同じセッションで 2 つのキーが食い違う
- permission は二層で、層ごとに symlink の扱いが違う。ファイル読み書きの許可はリンクを解決する
  前のパスで判定され、シェルのサンドボックスは解決した後の実体パスで判定する
- headless 実行では許可するツールの明示が要る。編集を自動承認するモードと作業ディレクトリの
  追加だけでは、メモリへの読み書きが拒否される

## 実装 (2026-08-27)

実体を中立な第三の場所 `~/.claude-shared/projects/` へ置き、両設定ディレクトリの `projects`
そのものを symlink にした。ユーザーの裁定で、セッションログの共有は許容し、実体は片側ではなく
中立な場所に置く形を採った。

### 統合の判断

両側にあるファイルは新しい側を採った。根拠は片側固有行 32 件の全数確認で、独自情報は 0 件だった。

- 15 件は `name` / `modified` / `originSessionId` の差だけ
- 12 件は新しい側で更新された行の旧版
- 2 件は新しい側で訂正済みの誤情報。和集合を採っていたら反証済みの記述が復活していた
- 1 件は行の位置が変わっただけでリンクは保持されている
- 1 件は `[[...md]]` から `.md` を落とした表記修正

`MEMORY.md` はセクション構造を保ったまま、リンク先ファイル名をキーに和集合を取った。
本文が「単純に片方を採ると片側の行が落ちる」と書いていた前提は、実測では成立しなかった。
その後に片側だけが育った結果、包含関係へ変わっていた。

### 実測で確認したこと

| 命題 | 結果 |
| --- | --- |
| 片側で書いた記憶がもう片側から読めるか | ノンス完全一致 / 対照 0 件 / inode 同一 |
| 逆向きも成立するか | 成立 |

`memory/` 単位ではなく `projects/` 単位で張るのが要点で、前者では新規プロジェクトが漏れる。
実際に `memory/` 単位で張った段階では漏れ、`projects/` 単位に変えたら塞がった。

### 数え方で踏んだ罠

- 本文の「27 プロジェクトは片側にしか存在しない」は projects 数の引き算で、実際に片側にしか
  メモリが無いのは 14 件だった。着手前に数え直すこと
- `find` は既定で symlink に降りないので、既に symlink 共有されていた 1 プロジェクト 156 件が
  見えず、総数が 890 と 1046 でずれた。`-L` の有無で結果が変わる
- 片側だけを kebab 正規化して突き合わせると、両側ともアンダースコア命名のプロジェクトが
  全件 missing に化ける。対照は検証対象と同じ規約で作ること

## 確認 (2026-08-27、アカウント切り替え後)

### Claude Code が実際に共有実体を読むか

ファイルシステム上の共有とは別命題なので、切り替え後のセッションで確かめた。

| 命題 | 結果 |
| --- | --- |
| セッションが別の設定ディレクトリで動いているか | `session-env/<id>` が片側にのみ生成。もう片側の `shell-snapshots` は 6 週間前が最新 |
| 6 週間休眠していた側に、もう片側が当日書いたメモリが載るか | 載る (索引 39 行が共有実体と先頭・末尾まで一致) |
| 統合で落ちたファイル (再現) | 0 件。見かけ上の 35 件は snake_case → kebab の改名で 35/35 とも対応先あり |

### 移行中にログが分岐していた

退避にしか存在しないレコードが 167 件あり、すべて移行を実行していた 3 分間に集中していた。

`mv` でディレクトリを移すと、稼働中セッションが開いている fd は移動先の inode を指したまま
書き続ける。新パス側には同じ時間帯の穴が空く (共有側は同窓 0 行)。「移動したそばから
ファイルが再作成される」より深く、書き込み先そのものが分岐していた。

この事実は `setup_shared_symlinks` が既存の `projects` を絶対に動かさない根拠になっている。

## 検討の経緯 (すべて決定済み)

### 共有の実現手段

symlink はディレクトリ単位で効く。取り得る形は `projects/` を丸ごと symlink する案で、新規
プロジェクトも実体側へ集まるので取りこぼしが出ない。

採らない形が 3 つある。

- ファイル単位の symlink と hard link。索引が置換で更新されるので壊れる。hard link は切れても
  両側が実ファイルのまま残るので、壊れたことが外から見えない
- `memory/` 単位の symlink。新規プロジェクトの `memory/` は実ディレクトリとして生えるので、
  リンクを張り直すまで共有網から漏れる。slug の導出規則を複製する必要も出る
- 双方向の同期スクリプト。設定ディレクトリが増えるたびに組み合わせが増える

symlink が効いたので、同期スクリプトと単一 canonical からの配布は比較の対象から外れた。

### セッションログの扱い

`projects/` を丸ごと共有すると、メモリだけでなくセッションログも共有される。共有して困らないか、
メモリだけに絞る形が要るかを決める。

### 命名の統一

canonical はファイル名の stem を kebab 化したもので、frontmatter の `name` も同じ値へ揃える、
という規約が移行時に確定している。`~/.claude` 側は移行前の命名のまま残っている。

`[[...]]` 記法は `name` を指すので、命名がずれている側では参照が解決しない。

### `MEMORY.md` の扱い

同名で内容が違う唯一のファイル。索引なので、共有するなら統合が要る。単純に片方を採ると
もう片方にしかない行が落ちる。

### 対象範囲

dotfiles プロジェクトだけを共有するのか、全プロジェクトを対象にするのか。`~/.claude` 側に
しかない 27 プロジェクトをどう扱うかもここで決まる。

### アカウントが増えたときの拡張

設定ディレクトリの一覧をどこが持つかを決める。追跡下に置くと設定ディレクトリ名が公開される
ので、置き場は既存の外部化と揃える必要がある。
