# refactor: 観測カテゴリの主語を観測へ引き上げ未被覆の軸を塞ぐ

## 背景

`home/.claude/CLAUDE.md` の観測カテゴリ (「観測した結果がその主張の証拠になっているか確かめ、
観測自体を加工や連結で壊さない」) は、規範の主語が 3 つに縛られている。「報告」「0 件・空・緑」
「Bash」で、それぞれ独立した箇条書きの頂点になっている。

過去の引き継ぎ書から観測の失敗事例 24 件を集め、既存カテゴリとは独立に分類したところ、
どの主語にも入らない軸が 5 つ出た。分類軸は事例そのものから立てたもので、カテゴリの側から
渡していない。

塞ぐには主語を「観測」へ引き上げる再構成が要る。個々の軸を箇条書きとして足すと、既に
最大を占めているカテゴリがさらに膨らみ、しかも主語の非対称は残る。

このカテゴリは常時ロード層で最大を占める。2026-08-25 時点で 5212 バイト、ファイル全体の
19.6 パーセント。上限そのものは config-guard の `instruction_budget` が canonical を持つ。

## 未被覆の軸

### 軸A 対象の同一性 — 見ているものが主張の対象と別物

カテゴリに「観測しているものが主張の対象と同じか」を問う項が 1 つも無い。実害が最も大きい。

- 残留していたホストプロセスが返した HTTP 200 を、コンテナが復帰した証拠として読んだ
- 作業ディレクトリを移さずラベル文字列だけ付けて、同じ対象を 2 回測った
- 識別子を正しく渡しても別の対象が返る API が 2 つあった (job の識別子を渡すと最新試行の
  ログが返る形)
- 名前が同一で中身が別物の成果物 (検証環境と本番のインストーラがファイル名まで一致)

### 軸C 観測が対象を汚す、装飾が値に混ざる

「合成した対照・プローブは検証対象と同じ構造上の位置に置く」の項は「機構が別経路で成立する」
話で、向きが逆 (プローブが対象に混ざる形) を扱っていない。

- grep が検査コード自身をヒットさせ「パターンは存在する」というもっともらしい誤答を返した
- 計測結果を計測対象の内部へ書き込む自己参照計測。書いた瞬間に数値が古くなる
- 観測の最中に対象を編集してベースラインを壊した。委譲のカテゴリには「実験は隔離コピーで」
  という規範があるが、自分で観測するときの規範が無い
- 出力に混ざる不可視・付随文字 (ANSI エスケープ、行番号とタブを内容のインデントと取り違え)

### 軸E 逆方向の誤読 — 健全を異常と、成功を失敗と読む

「0 件・空・緑を健全の根拠にする前に」の項も「失敗が成功に見える結果として返る」の項も、
向きが一方向しかない。

- 正常時も空である出力を「サービス停止」と読んだ
- 失敗を返した操作が実際には成功していた
- fail-fast で打ち切られた先を「通った」と読んだ
- 非決定的な flake の 1 標本ずつの緑赤を「自分の変更が原因」と読んだ (同一コミットでの
  3 回反復で確定した)

### 軸F 介入が当たったことを確かめていない

変異注入の規範は `home/.claude/rules/testing-practices.md` が持つが、これは `paths` 付きの
scoped rule なので、Dockerfile や workflow YAML やワンライナーを触っている最中には発火しない。
一方で委譲のカテゴリは常時ロード層から implementer へ変異注入を指示している。**指示だけが
常時ロードにあり、確認手段が発火しない状態**になっている。

- 変異注入が実際には適用されておらず、「変異が当たっていない」と「pin が死んでいる」が
  同じ緑で返った
- 停止・実行・置換が黙って空振りした (サブシェルが起動したプロセスの kill に失敗しても
  テストは緑)

### 軸J 同型欠陥が兄弟として残る

同じ形の欠陥が複数箇所にあり、1 つ目を直したときに 2 つ目に気づけない形が 3 リポジトリで
独立に発生した。ボーイスカウトルールは「触った場所」までしか及ばず、「直したあと同型を探す」
という手続きを持たない。

## 部分的にしか覆われていない軸

塞ぐ対象に含めるかは再構成の設計で決める。

- 軸B 観測範囲。API の既定パラメータが範囲を静かに絞り、しかも件数の内部整合が保たれる形は、
  「その検査が実際に何を何件見たか」を正しく適用しても素通りする
- 軸D 中継層。ハーネスのバックグラウンド完了通知そのものが嘘だった事例が 2 リポジトリで
  独立に再現した
- 軸G 出典を開かずに書く。「由来を問わない」の抽象則は覆うが、同じ行の列挙に「自分の記憶」
  「参照先の文書」「並行セッションの前提」が無い
- 軸H 母集団の不一致。「対照側も同じだけ壊れる」の項は規約の一致を求めるが、母集団の定義の
  一致は求めていない

## カテゴリ冒頭の宣言が実態より広い

これは軸とは別の、独立して直せる欠陥。

カテゴリ冒頭は「手当ての詳細と一次実測は `~/.claude/references/observation.md` が持つ」と
宣言しているが、少なくとも 2 箇所で偽になっている。参照先を実測した結果は次のとおり
(2026-08-25)。

| カテゴリ側の記述 | 参照先の状態 |
| --- | --- |
| 未読ファイルを追跡下へ入れるときは「先に全文を読み」 | 「全文」の出現 0 件。事例は在るが手当てが無い |
| 未確認の前提は「並列 fan-out に渡す前に自分の再現で確定させる」 | fan-out と並列の出現 0 件 |

canonical カテゴリの検算 2 (指名した参照先が本当にその情報を持つか) と 3 (書いた宣言の範囲が
実態より広くないか) に現状で抵触している。手当てを参照先へ足すか、宣言の射程を狭めるかは
再構成と同じ判断になるので、この Issue で扱う。

## メタな観察

集めた事例のうち 5 件は、該当する規範を引用あるいは記載済みの状態で同じ失敗を踏んでいる。
どの引き継ぎ書も原因の診断が一致していて、**列挙をチェックリストとして照合し、抽象則の適用を
そこで止めること**にある。

同じ形は資料を作る作業中にも 2 回出た。片方は行番号を「飾り」として付けたまま別の数字を
混入させた例で、カテゴリの見出しが名指しで禁じている「加工」そのものだった。もう片方は
委譲先が渡された glob の誤りを検出して報告した例で、そのまま使えば 3 リポジトリすべてで
それらしい 0 件が返るところだった。後者は「手順書は canonical を名乗るぶん疑われにくく、
誤りは妥当に見える 0 件で返る」の実例であり、規範が実際に機能した側の記録でもある。

## 採らない案

蒸し返し防止のために理由ごと残す。いずれも反証済み。

### 個々の軸を箇条書きとして足す

主語の非対称が残ったまま、常時ロード層で最大のカテゴリがさらに膨らむ。軸が 5 つあるので
足す量も小さくない。

### 「網羅ではない」型の枷を足す

同型の枷が既に 3 箇所ある。それでも上のとおり事例は積み上がった。4 個目を足す根拠が無く、
一律に強化すると既存の枷まで背景化させる。

### 具体列挙を参照先へ全面移設する

収支が合わない。参照先が同等以上を持つ範囲を全部移しても常時ロード層から減るのは概算で
3 キロバイト程度だが、参照先は全体で 16817 バイトあり (2026-08-25 実測)、開かれれば全体を
読むことになる。損益分岐は数ロードに 1 回で、得になるのは参照が読まれないときだけ。
得の大きさと予防の喪失が同じ量の裏表になっている (減る側の値は概算)。

加えて、参照先には常時ロード層のどこからも指されない孤児の節が既に 1 つある
(`### venv の絶対パスと console script`。カテゴリ本体と rules のいずれからも当該語の
出現が 0 件であることを確認した)。「参照先へ置けば保全される」という想定に反例がある。

### 分業を規約化して跨いだ行を一律処理する

「カテゴリは判定基準、参照先は手当て」という線引き自体が反証された。参照先との逐語被覆率を
測ると、Bash 節の畳み込み対象だった行より重複が高い行が 8 本ある。また shell-out の項は
Bash の項と同型の親子構造を持っており、片方だけを消す構造的根拠が無い。線は行と行の間ではなく
1 文の中を走っている。
