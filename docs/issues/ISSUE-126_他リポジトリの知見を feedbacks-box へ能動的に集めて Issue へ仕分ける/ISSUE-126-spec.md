# ISSUE-126 spec: 他リポジトリの知見を feedbacks-box へ能動的に集めて Issue へ仕分ける

2026-10-20 のブレインストーミングと、その後の設計レビューで決めたことのスナップショット。今の挙動はコードとテストが持つ。

## 意図

他リポジトリの作業で得た知見のうち、リポジトリを越えて効くものを dotfiles へ確実に届け、最終的に CLAUDE.md / rules / skill / plugin のような決定論的に効く形へ寄せる。

対象として想定している知見は次のようなもの。

- 言語・ビルド・特定の仕組みでの性能チューニングの手法 (効いたもの、効かなかったもの)
- 新しく使った skill や plugin の使用感 (どの場面で効き、どこで外れたか)

なぜ今か。ユーザーは Claude の Memory に干渉しない方針だが、Memory はセッションごとに溜まって整理されず、増えすぎて Claude 自身が混乱しているように見えることがある。検証できる知見は Memory ではなく、規範や skill へ集約して残したい。

今の経路は届かない。受け箱 `docs/.feedbacks-box/` と、箱の中身を dotfiles の SessionStart で告げる `home/.claude/hooks/feedbacks-box.py` は PR 253 で入ったが、送る側は非公開の運用指示の一文だけに頼っている。2026-10-20 に transcript を数えたところ、その指示が読み込まれたセッションは多いのに、箱へ書き込んだのは数セッションだった。送るきっかけになる瞬間が無いことが原因だと見ている (推測)。

## 全体の流れ

```mermaid
flowchart LR
    W["他リポジトリのセッション"] -->|"コミットのあとの Stop で案内"| S["送信 skill が自リポの .cache のまとめを更新"]
    S -->|"SessionEnd で hook がコピー (取りこぼしは次の SessionStart)"| B["dotfiles/docs/.feedbacks-box/"]
    B -->|"SessionStart で告知"| D["dotfiles のセッション"]
    D -->|"main から切った worktree で起票し PR をマージ"| I["main の in-repo Issue (新規か既存へ追記)"]
    I -->|"通常の作業として後日"| R["CLAUDE.md / rules / skill / plugin"]
```

## ゴール

- 他リポジトリのセッションが、作業の区切りで、リポジトリを越えて効く知見をセッションのまとめとして残し、セッションの終わりに箱へ届く。Claude が思い出すことに頼らない
- 箱に届いたものは、dotfiles のセッションが自動で in-repo Issue へ仕分け、main まで入れる
- ユーザーが「dotfiles に送っといて」と頼んだときも同じ書式で残せる

## 非ゴール

- 箱から規範・skill・plugin への昇格と、既存との重複の整理は自動で行わない。仕分けでできた Issue を、ユーザーがふつうの作業として着手する (ユーザーの判断: 毎回実装まで進むと、他の作業の邪魔になる)
- 刈り込みの工程と、公開範囲の一般化の手順そのものは親の ISSUE-97 に残す。この Issue では仕分けの時点で最低限の公開範囲の配慮だけを持つ (後述)
- Memory への反映は経路に含めない
- コミットの無い調査だけのセッションは、当面は自動では拾わない。ユーザーの依頼だけが経路になる (ユーザーの判断。運用して取りこぼしが気になったら別の合図を足す)

## アンチゴール (技術的には動いても失敗とみなすもの)

- 箱が Memory と同じくらいノイズだらけになる。知見の無いセッションが空のまとめを置く、1 セッションから何通も届く、仕分け済みの知見がもう一度届く、など
- 案内が本来の作業の邪魔になるほど頻繁に出る。または hook の故障と見分けがつかない形で出る
- 非公開リポジトリの名前や案件の中身が、PUBLIC な dotfiles の追跡下 (Issue・コミット・PR) へ書き写される
- 送られてきた主張が、裏付けを取らないまま規範として扱われる (ISSUE-88 で 3 件が反証された前例)
- 仕分けが、ユーザーの作業中のブランチや live 設定 (dotfiles の working tree) を書き換える

## 決まったこと

### 送る側: まとめは自リポジトリの中に書き、届けるのは hook

- Claude がまとめを書くのは、作業中のリポジトリの `.cache/` 配下のセッションごとのファイル。cwd の中なので書き込みの許可を広げない (ユーザーの判断。箱へ直接書く案は、cwd の外への Write の許可を settings.json に足す必要があり採らなかった)
- まとめは作業中に何度でも丸ごと書き直してよい。箱へ届くのはセッションの終わりの 1 回だけなので、受け取る側と競合しない
- 箱へ届けるのは hook。SessionEnd でまとめを箱へコピーする。SessionEnd が来なかったもの (クラッシュ等) は、そのリポジトリの次の SessionStart で届ける。届けたまとめは送る側から消すか、届けた印を残して二重に届けない
- 箱の場所は hook が自分の実体の位置 (dotfiles の作業ツリー) から導く。skill にも settings.json にも絶対パスを書かない

### 送る側: 送信 skill

- まとめの書式と、まとめを更新する手順を持つ skill を新しく作る。置き場は agentic-coding-tools で、apm で配る (既存の skill の置き場の規約)
- まとめはセッション単位の要約で、知見を貼り付けた断片ではない。そのセッションで何を試し、何が効き、何が効かなかったかを読める形にする
- 各知見に、どこまで確かめたか (実測した / ドキュメントを読んだだけ / 推測) を添える。仕分けとその後の昇格で、裏付けの要否を決める材料にする
- 知見が無ければ何も書かない。まとめのファイルが無いセッションは何も届かない
- skill はまとめの置き場 (作業中のリポジトリの `.cache/` 配下のどのファイルか) を、hook の案内の文面か、自分で導ける規則から得る。ユーザーの「送っといて」でも同じ場所へ書くので、依頼の経路も箱のパスを知らなくてよい
- skill が配られていない環境 (新しいマシン、pin を上げる前、apm install の失敗) で hook が存在しない skill を名指ししない。hook は skill の有無を確かめ、無ければ案内しない

### 送る側: 案内 (Stop hook)

- user スコープで全リポジトリに配線する Stop hook が、まとめの更新を案内する
- 出力は `hookSpecificOutput.additionalContext` の形にし、`decision: block` は使わない。block は 2.1.304 で毎回「Stop hook error」の通知になり、hook の故障と見分けがつかない (レビューでバイナリと公式ドキュメントから確認。実装時に現行版で再確認する)
- 区切りの合図はコミット。前回の案内のあとで、そのセッションで新しいコミットができていたときだけ案内する。最初の案内はセッション最初のコミットのあと (ユーザーと決めた)
- 1 セッションあたりの案内の回数に上限を置く
- subagent では案内しない。workflow の子のように別プロセスで動く自動のセッションでも案内しない。子が `agent_id` を持つかは未実測なので、見分け方は実装時に実測で決める
- 受け箱を持つリポジトリ自身 (今は dotfiles) では案内しない
- 同じ Stop に配線された handoff-sentinel の `stop` と共存させる。`stop_hook_active` のときに判定を飛ばす場合も、コミットの有無の状態を消費しない (相手の継続の中で飛ばした案内を次の Stop で拾い直せるように)。複数の hook の出力の合成は公式ドキュメントに書かれていないので、共存の挙動をテストか実測で pin する
- hook の故障で作業を止めない (既存の hooks と同じ fail-safe)

### 受け取る側: 仕分け

- dotfiles のセッションは、箱にまとめがあると SessionStart で告げられ (既存)、ユーザーの依頼の区切りで自動で仕分けを始める。受け取る側には案内の hook を足さない (Claude の判断。PR 253 以降、届いた分は処理されている)
- 仕分けの出口は main の in-repo Issue。Issue が別の worktree やブランチにあると気付けないので、main までマージする (ユーザーの判断)
- 仕分けはユーザーの作業中のブランチと dotfiles の working tree (live 設定の実体) を触らない。main から切った別の worktree で、Issue の追加と追記だけをコミットし、PR を作ってマージする。main は ruleset で PR が必須 (2026-10-20 に `rules/branches/main` で `pull_request` を確認)
- まとめの中の知見ごとに、既存の Issue へ追記するか新規に起票するかを決める。重複の検索と起票の手順は in-repo-issue skill に従う
- 追跡下へ書き写すときは、非公開リポジトリの名前と案件の中身を落とし、知見を一般化した文面にする。どこまで確かめたかの印は Issue へ持ち越す。コミットと PR の本文は commit-and-pr-message skill の検査を通す
- マージを終えたまとめを箱から消す。反映を終えるまで消さない
- 並行する dotfiles のセッション同士が同じまとめを二重に仕分けないよう、仕分けに取りかかったことが他のセッションから分かる形を持つ (形は実装者が決める)
- feedbacks-box.py の告知の文面を、この手順 (出口は main の Issue だけ、Memory へは入れない、別 worktree で行う) に合わせて変える。手順の canonical は告知の文面のまま

### 非公開の運用指示

- PRIVATE_CLAUDE.md にある箱の説明とファイル名の規約は、この設計に合わせて書き換える (他リポジトリの Claude は箱へ直接書かず、送信 skill の規則に従う)。ファイルは dotfiles の外 (private-ops) にあるので、書き換えはユーザーの確認を取って行う

## 制約

- dotfiles は PUBLIC。箱は ignore 済みで中身は公開されないが、仕分けで生まれる Issue・コミット・PR は公開される
- 常時ロード層 (CLAUDE.md) の予算に余裕は無い (canonical は config-guard の `instruction_budget`)。手順は skill と hook の文面に持たせ、常時層には足さない
- hook の配線は `home/.claude/settings.json` に置く。hook 本体は配線と同じコミットで入れる (config-guard の hook_wiring が mode 755 のファイルを母集団にするため)
- SessionEnd の hook は短い持ち時間しか持たない (メモリの記録では 1.5 秒の共有予算)。コピー以外の重い処理を置かない
- テストは既存の hooks のテスト群 (claude-hooks の pytest) に足す。案内の判定 (コミットの有無、回数の上限、subagent と自動のセッション、受け箱を持つリポジトリ、skill の有無、fail-safe) と、届ける処理 (SessionEnd、次の SessionStart での取りこぼしの回収、二重に届けない) は分岐ごとに pin する
- hook はセッションの外から来たデータ (リポジトリ名、ファイル名) を文面へ載せるとき、feedbacks-box.py と同じく引用して偽の行を差し込めないようにする
- dotfiles の CLAUDE.md は PR のマージ前に `/simplify` と code-reviewer のレビューを求めている。仕分けの PR も例外にしない (Claude の判断。緩めるならユーザーが決める)

## 実装者に任せること

- セッション中のコミットの検出方法。レビューで次の崩れ方が挙がっているので、どれを受け入れるかを plan で明記する: transcript は Stop の時点で最後のメッセージを含む保証が無く、subagent の transcript は別ファイル。HEAD の比較はブランチ切り替え・pull・rebase・amend でも動き、別の worktree でのコミットを取りこぼす。reflog の種別を見れば切り替えと amend は弁別できる
- 案内の回数の上限の値
- まとめのファイル名 (送信元のリポジトリ名、日付、セッションを識別する短い値を含める) と、箱へ届けたあとの扱い (消すか印を残すか)
- 送信 skill の名前と、まとめのテンプレートの見出し
- 案内の hook と届ける hook を新しいファイルにするか、既存の hook に足すか
- 並行する仕分けの排他の形
