# docs(skills): session-handoff の発動経路の説明を実装へ揃える

## 背景

PR #200 で `home/.claude/hooks/handoff-sentinel.py` にレートリミット逼迫の通知を足し、
引き継ぎを促す経路が 4 つになった。既存の 3 つはコンテキスト超過、ツール呼び出し破損、
ユーザーからの手動依頼である。

`session-handoff` skill の description は「発動経路は3つ」と書いており、本文の
「5. 発動経路に応じて締める」も 3 経路ぶんの案内しか持たない。実装が先に進んで説明が
取り残された状態にある。

## 直せない理由

この skill の canonical は agentic-coding-tools 側にある。dotfiles が追跡している skill
ファイルは 0 件で、`home/.claude/skills/` は apm の展開先として ignore されている
(`home/.gitignore` の `.claude/skills/`)。したがってこのリポジトリでは直せない。

## 影響の見積り

低い。フックが出す `additionalContext` は自己完結しており、skill 名を直接名指ししたうえで
緊急時の行動 (他の作業を中断してメモリまで書く) も文面に含む。skill の 5 番目の手順を
読まなくても正しく動く。

ただし description は skill を起動するかどうかの判断に使われるので、経路の数え方が実態と
ずれたままだと、レートリミット由来の通知を受けたエージェントが「この skill の担当ではない」
と読む余地が残る。

## 決めること

### 上流へ渡す形

dotfiles から agentic-coding-tools への修正は委譲で行う運用になっている。Issue の起票と
エージェント間メッセージングのどちらを使うか、また向こうで直すのを待つか、こちらから
変更を提案するかを決める。

### 同種の drift を見る層を持つか

今回の乖離は「dotfiles 側の実装が変わり、上流の説明が古びる」という形で、どちらのリポジトリ
の検査にも引っかからない。フックのしきい値や経路の数を上流が再掲しない規約は既にあり
(`handoff-sentinel.py` の docstring が「他ファイルはこれらの値を再掲しない」と宣言し、
上流の SKILL.md も「しきい値などの検知条件は hook が canonical」と委譲している)、経路の
数だけがその規約の外に落ちている。数を書かない形へ寄せれば drift 自体が消える。

- [ ] 経路の数を上流が持たない形にできるか決める。できるなら検査は要らない
