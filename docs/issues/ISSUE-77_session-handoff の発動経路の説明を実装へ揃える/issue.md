# docs(skills): session-handoff の発動経路の説明を実装へ揃える

## 背景

PR #200 で `home/.claude/hooks/handoff-sentinel.py` にレートリミット逼迫の通知を足し、
引き継ぎを促す経路が 4 つになった。既存の 3 つはコンテキスト超過、ツール呼び出し破損、
ユーザーからの手動依頼である。

`session-handoff` skill の description は「発動経路は3つ」と書いており、本文の
「5. 発動経路に応じて締める」も 3 経路ぶんの案内しか持たない。実装が先に進んで説明が
取り残された状態にある。

## 直せない理由

この skill の canonical は agentic-coding-tools 側にある。dotfiles が追跡している skill
ファイルは 0 件で、`home/.claude/skills/` は apm の展開先として `home/.gitignore` が除外して
いる。したがってこのリポジトリでは直せない。

上流を直すだけでも手元には届かない。`home/apm.yml` が session-handoff を版で pin しているので、
pin を上げて `apm install` を通すまで展開物は古いままになる。

## 影響の見積り

低い。フックが出す `additionalContext` は自己完結しており、skill 名を直接名指ししたうえで
緊急時の行動 (他の作業を中断してメモリまで書く) も文面に含む。skill の 5 番目の手順を
読まなくても正しく動く。

ただし description は skill を起動するかどうかの判断に使われるので、経路の数え方が実態と
ずれたままだと、レートリミット由来の通知を受けたエージェントが「この skill の担当ではない」
と読む余地が残る。

## 決めること

### 上流へ渡す形

dotfiles から agentic-coding-tools への修正は委譲で行う運用になっている。Issue の起票と
エージェント間メッセージングのどちらを使うか、また向こうで直すのを待つか、こちらから
変更を提案するかを決める。

### 同種の drift を見る層を持つか

今回の乖離は「dotfiles 側の実装が変わり、上流の説明が古びる」という形で、どちらのリポジトリ
の検査にも引っかからない。

既に似た委譲はある。`handoff-sentinel.py` の定数群が「他ファイルはこれらの値を再掲しない」と
書き、上流の SKILL.md も「しきい値などの検知条件は hook が canonical」と委譲している。ただし
どちらも射程は値と検知条件で、経路の数は最初から外にある。数を書かない形へ寄せれば、少なくとも
経路の数の drift は消える。経路そのものの列挙と、経路ごとの締め方は hook の挙動の再掲なので、
そちらは残る。

### 締め方を経路ごとに書く構造をどうするか

レートリミット由来の通知は 1 種類ではない。予告の段と緊急の段があり、求める行動が違う。予告は
区切りの良いところで引き継ぎを書かせ、緊急は他の作業を中断して引き継ぎとメモリまで書かせる。
skill の手順 5 は経路ごとに締め方を書き分ける構造なので、3 を 4 に増やすだけでは 2 段が 1 つに
潰れる。段を経路として数えるか、締め方の側で分岐させるかを決める必要がある。
