# agent: 新しく書く日本語の文面から AI 臭さを減らす

## 背景

Hidari は、エージェントが書く日本語の文面から AI が書いた文章らしさ (AI 臭さ) を減らしたいと考えている (2026-09-26)。きっかけは ISSUE-106 の F08 で、以前 markdown-practices にあった「強調したい場合を除いて、数字の前後に空白を入れないこと」の扱いを決める場面だった。

- 数字の前後の空白は、ISSUE-106 の反映前の指示ファイル群 (両 CLAUDE.md と `home/.claude/` 配下の Markdown 14本) で空白ありが148箇所、空白なしが14箇所だった。`docs/issues` 配下の Markdown 127本でも5703対684で、規則は守られていなかった (インラインコードとコードブロックは数えていない。2026-09-26実測)。ISSUE-106 のブランチでこの規則を rule から外した
- Hidari の判断は「過去の文面は直さない。これから書くものは、強調する意図のとき以外は数字の前後に空白を入れない」。memory (feedback-no-space-around-digits-in-new-text) に記録し、以後のセッションは散文として守る
- 散文の規則はエージェントに守られなかった実績がある。markdown-practices は `*.md` を Read したときにしか載らないので、会話・コミット本文・PR 本文には届かない。検査で強制するなら、過去の文面を対象から外すために追加行だけを見る形が要る

Hidari は、k16shikano の gist にある `japanese-tech-writing` skill (https://gist.github.com/k16shikano/fd287c3133457c4fd8f5601d34aa817d、Unlicense、SKILL.md 1本でスクリプトなし) を使えば AI 臭さ全体が減るかもしれないとも考えている。この skill は段落と論証の構成、LLM っぽい空句 (「重要なのは〜」「正面から扱う」など) と翻訳調の比喩 (「運ぶ」「効く」「開かれた問い」など) の禁止、冗長の排除を定める。数字の前後の空白には触れていない (「空白」「スペース」「半角」「数字」で0件。2026-09-26時点の版)。

同じ markdown-practices の「テキスト上の見た目のために文の途中で改行を行わないこと」も散文の規則のままで、同じファイルの「静的検査可能なルールはプロンプトではなく、その環境の linter か ast-grep で記述する」と食い違っている。ISSUE-106 のブランチで触った references は結合したが、追跡下の Markdown 161本のうち122本 (うち closed の Issue が47本) に文中の改行が4430箇所残っている。数えたのは、前の行が「。！？」で終わらない地の文の継続行と、リスト項目の継続行である (2026-09-26実測)。

## 決めること

- japanese-tech-writing skill を入れるか。入れるなら経路 (apm で gist を直接参照できるか、agentic-coding-tools へ取り込んで配るか) と、上流の更新をどう追うか (gist は2026-09-25にも更新されている)。書籍の原稿向けの規範も含むので、指示ファイル・Issue・コミット本文に当てたときに合わない項目が無いかも見る
- 空白をなくす範囲を数字の前後に限るか、英単語や識別子の前後 (「PR の」「live 設定」など) まで広げるか。インラインコードの前後をどう扱うか
- 数字の前後の空白を検査で強制するか。強制するなら、追加行だけを見る仕組み (pre-commit の hook が staged の差分を読む形など) と、強調の意図で空白を置く場合の逃げ道をどう作るか。検査が届かない面 (会話・PR 本文) は skill か常時層の散文で扱うか
- 文中の改行を検査で強制するか。強制するなら、残りの4430箇所を先に結合するか、追加行だけを見るか。closed の Issue はスナップショットなので対象から外すか
