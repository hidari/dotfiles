# Markdown 相対リンク検査の設計

## 背景と目的

Issue を `docs/issues/closed/` へ移すたびに、その Issue を指す相対リンクと、その Issue から出ているリンクの両方が切れる。`../10_...` と `../closed/10_...` の書き分けが両端の open / closed 状態に依存するためで、close する側とは別のファイルへ波及編集が要る。

これは仮説ではなく実績がある。`closed/9_.../issue.md` のリンクは導入コミットの時点で `../closed/7_...`（= `docs/issues/closed/closed/7_...`）と壊れており、main 上で壊れたまま残っていた。PR #77 のレビューで検出して直したが、検出したのは人間とレビューエージェントの目視である。

pre-commit には ruff / mypy / pytest / gitleaks / ast-grep / shellcheck が揃っているのに、Markdown の相対リンクを見るものが 1 つも無い。CLAUDE.md MUST GLOBAL の「静的検査可能なルールはプロンプトではなく、その環境の linter か ast-grep で記述する」に真正面から該当する。

本設計は追跡下の Markdown の相対リンクが実在するかを機械検査し、pre-commit と CI で止める。

## 確定した設計判断

- ゴールは検出のみとする。リンク形を open / closed 非依存にする構造変更（Issue のタスク 5）は行わない。`dev-workflow:in-repo-issue` スキルは別リポジトリにあり、仕様変更を同期させるコストが検出の価値に見合わない。検査が入れば close 時の作業は「切れたリンクを探す」から「指摘された箇所を直す」に変わり、見落としが構造的に消える。
- 検査範囲は追跡下の全 `.md`。`docs/` に絞らない。除外リストを持たない分だけ実装が単純で、将来 README や skills に相対リンクが増えても自動で守られる。現時点で壊れたリンクは 0 件なので導入コストもゼロ。
- 実装は既存の `scripts/config-guard` へチェックを 1 つ足す形にする。独立プロジェクトの新設は CI ジョブ 1 つと pre-commit hook 5 つを増やし、外部 linter の導入は依存を増やす。調査用に書いたプロトタイプは実リポジトリ全体を正しく判定して 60 行（コメント込み）だったので、どちらの周辺コストも検査本体の規模に見合わない。config-guard は既に `tool_refs`（stale なツール名参照の検出）を持っており、リンク検査は「stale なファイル参照の検出」として同族である。
- アンカーの実在は検査しない。見出しから anchor slug を生成する規則は処理系ごとに違い、自前実装は必ず drift する。パス部分だけを見る。
- リンク先は実在のみを判定し、「追跡下のファイルか」までは見ない。現在追跡外を指すリンクは 0 件で、必要になってから足せる。

## アーキテクチャ

`scripts/config-guard/src/config_guard/markdown_links.py` を新設し、`check_markdown_links(repo_root: str) -> list[Finding]` を公開する。`cli.py` の `scan()` から既存 5 チェックと同じ形で呼ぶ。

検査対象の列挙は既存の `run_git` ヘルパーで `git ls-files -z '*.md'` を実行して取る。`Path.rglob` を使わない理由は 2 つある。`.venv` や `apm_modules` を自前で除外する必要がなくなること、そして既存モジュール `apm_gitignore.py` が同じく git 経由で判定しており、パターンを揃えられることである。

`run_git` はロケーション系 `GIT_*` を除いた環境で git を起動する。pre-commit 経由の実行で hook 側の repo を読んでしまう事故を防ぐためのもので、本チェックもこの恩恵をそのまま受ける。

git の exit code が 0 以外なら例外を送出する。`apm_gitignore.py` の `_is_ignored` と同じ方針で、git のエラーを「リンクが無い」と取り違えて findings を量産することを防ぐ。

## 判定ロジック

リンクの抽出は正規表現 `\]\(([^)]+)\)` の 1 本。画像記法は同じ形なので自然にカバーされる。

ただし抽出の前にコード領域を除く。設計ドキュメントはリンク記法そのものを例示することがあり、それを実リンクと読むと存在しないパスを指摘し続ける。実際この機能の spec と plan 自身が 13 件の誤検出を生んだ（plan のコードフェンス内 12 件、spec のインラインコード内 1 件）。一般的な Markdown リンクチェッカーもコードブロックを検査対象から外す。

除外は 2 段構えとする。

1. 行頭（インデントを許す）のバッククォート 3 つ以上でフェンスの内外をトグルし、フェンス内の行は抽出しない
2. フェンス外の行からはインラインコード（バッククォートのペア）を取り除いてから抽出する

`~~~` によるフェンスは扱わない。リポジトリに 0 件で、扱わないことによる副作用も「フェンス内が検査される」だけであり、実害が出た時点で足せる。インデントは `^\s*` で許す。`home/.claude/skills/windows-vm-verification/SKILL.md` に 3 スペースインデントのフェンスが実在するため、行頭固定では取りこぼす。

抽出した各ターゲットを次の順で判定する。

1. `https:` / `http:` / `mailto:` / `ftp:` で始まる（大文字小文字を無視）→ 検査しない。ネットワークを叩かない。
2. `#` で始まる → 検査しない。同一ファイル内アンカー。
3. それ以外 → `#` があればその前だけを取り、`urllib.parse.unquote` でデコードし、リンク元ファイルの親ディレクトリからの相対で解決して実在を確認する。

デコードの順序が重要である。アンカーを切り落としてからデコードする。逆順にすると、`%23` でエスケープされた `#` がデコードで裸の `#` になり、パスの一部が誤ってアンカーとして切り落とされる。

検出時は `Finding(source, detail, message)` を返す。`source` はリンク元の repo 相対パス、`detail` はリンク文字列そのもの、`message` は解決先を含む理由文とする。既存の `Finding` の並びに従う。

## 配線

`.pre-commit-config.yaml` の `config-guard-scan` hook の `files` パターンに `.*\.md$` を足す。CI は既存の config-guard ジョブが `uv run config-guard ../..` を回すので変更不要。

リンク検査は「変更されたファイルだけ見る」では機能しない。リンク先を消したとき、壊れるのはリンク元であり、そのファイルは変更されていないためである。既存の `config-guard-scan` hook は `pass_filenames: false` で常にリポジトリ全体を走査するため、この性質にそのまま合致する。`files` は「いつ発火するか」だけを決めている。

ただし `files` の判定に使われる staged ファイル一覧に、削除されたファイルが含まれるかは未確認である。含まれない場合、「リンク先の `.md` を削除しただけのコミット」では hook が発火しない。Issue の close はディレクトリの rename なので新しいパスが `.md` にマッチして発火するはずだが、これも推測である。実装時に次の 2 ケースを実測して確定させる。

1. `.md` を `git rm` して commit したとき hook が発火するか
2. `.md` を含むディレクトリを `git mv` して commit したとき hook が発火するか

いずれの場合も CI 側は常にリポジトリ全体を走査するので backstop になる。実測の結果 pre-commit が発火しないケースが残るなら、それは「CI で捕捉する」と割り切って spec に記録する。`always_run: true` への変更は、`.md` に無関係なコミットでも毎回 config-guard 全体が走ることになるため採らない。

## テスト仕様

`scripts/config-guard/tests/test_markdown_links.py` に置く。`tmp_path` に最小のリポジトリを組んで実行する。git 呼び出しを含むため、テスト内で `git init` して `git add` する。

仕様として表現するもの。

1. 生きた相対リンクを検出しない
2. 壊れた相対リンクを検出する
3. `%20` を含むリンクをデコードして解決する（デコードしなければ生きたリンクを壊れていると誤判定する）
4. 外部 URL（`https:` / `mailto:`）を検査しない
5. `#anchor` だけのリンクを検査しない
6. `file.md#section` はパス部分だけを検査する。パスが生きていれば検出せず、壊れていれば検出する
7. リンクを含まない `.md` で何も検出しない
8. 検出時の `Finding` がリンク元ファイルとリンク文字列を含む
9. 追跡外の `.md` を検査しない（`git add` していないファイルは対象外）

各テストは変異注入で赤くなることを確認する。デコードを外す、外部 URL の skip を外す、アンカーの切り落としを外すなど、1 箇所ずつ隔離して行う。
