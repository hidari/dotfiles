# CLAUDE.md — Claude Code 開発ガイドライン

このファイルは、Claude Code に対して、すべてのプロジェクトに適用されるグローバルガイダンスを提供します。

本文書の[MUST], [SHOULD], [MAY]は、RFC 2119に準拠します。[MUST GLOBAL]は本文書独自の拡張です：

- [MUST GLOBAL]：MUSTの上位概念。プロジェクトごとのCLAUDE.mdより優先される
- [MUST]：絶対的要求事項。例外なく従う必要がある
- [SHOULD]：強い推奨事項。特別な理由がない限り従う
- [MAY]：任意事項。状況に応じて採用を判断

## [MUST GLOBAL] 語彙と前提

規範はカテゴリーごとにまとめてある。見出しが示す強度がそのカテゴリーの既定で、既定と異なる強度の項目だけが行頭にラベルを持つ。
この節には文書自身の語彙と、どのカテゴリーにも属さない前提を置く。

### 語彙
- プロダクトコードに対するテストコードは以下の分類とする
  - ユニットテスト：外部依存なしの高速テスト。ローカルマシンとGithub Actions上のCIで実行される
  - 統合テスト：複数のモジュールの連携を確認するテスト。ローカルマシンとGithub Actions上のCIで実行される
  - 契約テスト：library-contract アダプタ層が外部サービスと交わす契約を、Fake/実物の両面で検証する
  - E2Eテスト：ユーザーの操作シナリオをベースにエンドツーエンド（E2E）で検証する。テスティングフレームワークは対象プロダクトの性質に合わせるが、実行・メンテナンスコストが非常に高いため、クリティカルパス以外は必要最小限のテストとして実装する
- ボーイスカウトルール: 触った場所を、触る前より良い状態にして離れること
  - 対象は今回の変更で触ったファイルと、その中で見つけた既存 (Pre Existent) の問題
  - スコープ外でも直す。レビューで見つけた問題を「今回の担当ではない」という理由で残さない
  - ただし影響範囲が大きい変更や重要な設計判断を要する問題は別タスクへ切り出す。境界は「今回の PR のレビュー範囲に収まるか」に置く
  - 隣接ファイルは表記揺れを判断するための参照であって、それ自体を直す対象にはしない
  - この定義が canonical で、プロジェクトごとの CLAUDE.md は再定義せずここを参照する

### 前提
- [MUST GLOBAL] どんなときでもユーザーデータを守るセキュリティを第一に考え、決して手を抜かない
- 私の開発スタイルは先に大きな問題を潰しながら主目的をまず通すこと
  - 途中で切り出したり、設計段階で分けた課題に取り掛かるのは主目的を達成したあとにすること
  - 特に作業途中で発見した問題の調査中に別の問題を発見した場合に作業が入れ子になることは避ける
  - 影響範囲が限定的であることが予想される場合はボーイスカウトルールに則って対応することは可
- 個人情報（実メールアドレスや実名、マシンローカルのホームディレクトリに含まれるユーザー名などを含む）はコミット、コミットメッセージ/コードに載せないこと
- 非常に重要なこととして、ユーザー（Hidari）は個人開発者のため、プロダクトに投下できるリソースに限りがあるため以下の点を重視する
  - 手動テストによる動作確認を最小限にすることをなにより重要視する
  - CIコストがかなり負担となるため可能な限りローカル環境のVM、Linuxコンテナ、Mac上で検証を行い、CIでの検証はmainマージとリリース時にのみ抑える方針とする
- [MUST] DRY原則、KISS原則と "Single Responsibility" を適用したテスタブルで拡張性のある設計を行うこと
  - 単体テスト、統合テストを必ず記述し、UIを持つプロダクトはE2Eテストまで用意して機能の動作を保証する
- [MUST] 外部ライブラリやパッケージなどの依存関係は極力少なく維持すること
- [MUST] あらゆる作業は抽象と具象の視点、局所的と大局的の視点を適度に往復しながら常に全体最適を目指すこと
- [MUST GLOBAL] プロダクトコードとテストコードが ファーストクラスドキュメント（= the single source of truth） となるように書き、テストコードはリグレッションテストであるとともに 仕様としてのテスト の考え方を徹底する
- 外部ライブラリは library-contract パターンで切り離し層をつくること
  - 切り離す理由は次のとおり
    - 外部ライブラリのバージョンアップ時の挙動確認テスト（契約テスト）を行いやすくする
    - 外部ライブラリを差し替え可能にすることでメンテナンスされなくなった場合の移行を簡単にする
    - サプライチェーン攻撃の影響範囲をアダプター層に限定し、コアドメインロジックを保護する
    - テスト時にFake/Mock実装へ差し替えて高速なユニットテストを可能にする
    - コアドメインロジックを外部ライブラリのAPI破壊的変更から隔離する
- 各テストのカバレッジは可能な限り高く保つが、行カバレッジよりも分岐カバレッジを優先する
- [MUST] コードやテスト、ドキュメントは書かずに済むことが drift を根本的に防ぎ、保守性と拡張性を高めることに繋がるため、その方法を常に模索すること
  - 現状のClaudeの作るコードなどはそうはなっておらず、不必要に複雑なコード、テスト、ドキュメントが書かれがちで drift しやすい
  - 特にコメントとテストコードは drift しやすいし気づきづらいので注意が必要
  - 書かないことでそもそも drift する面を減らすこと
  - 特にSDDを行う際には直接的な実装コード片をできる限り減らし、Mermaidによる図示やデシジョンテーブルなどの各種テスト技法を用いること
- [MUST] 設計ドキュメントはその時々の状況や文脈を包含するスナップショットとして無理に継続更新を行わないこと
  - 設計ドキュメントを最新に保ち続けるのではなく意図をプロダクトコードやテストコード、それらのWhy(not)コメントに乗せそれらを更新する
  - それらに収まらない事項に関しては VCS のコミットメッセージも活用してよい
  - プロダクト全体のデザインや運用ドキュメントは実際に使用するものであり、現状のコードと drift すると実害が出るため、例外として更新する

## [MUST] 観測した結果がその主張の証拠になっているか確かめ、観測自体を加工や連結で壊さない

- [MUST GLOBAL] 未読のファイルを追跡下へ入れるとき（`mv` による移動も含む）は先に全文を読み、gitleaksなどの緑を安全の根拠にしない
  - 検出集合の canonical は `.gitleaks.toml` で、そこに無いカテゴリ（プロジェクト名・ボリューム名）は素通りする
  - 実際に未読の docs を移動して PUBLIC へ push し、branch を消しても closed PR の diff は公開のまま残った
- ユーザーの「実機で全部 OK」報告や症状の伝聞など、他者由来の報告・前提を検証済みの網羅的事実として扱わないこと
  - 健全と結論する前に壊れやすい配置（端・境界・空・最大・最初/最後）を列挙して報告がそれを踏んだか確かめ、単独で並べるだけでなく掛け合わせも見て、未確認の前提は subagent の並列 fan-out に渡す前に自分の再現で確定させる
  - 報告は真実でも網羅ではない[実機 OK は壊れるグリッド端カードを未踏なだけだった]などの場合がある
  - live-smoke ルールと同じ「狭い signal ≠ 広い主張」族で some-path pass ≠ all-path healthy
- 監査結果や棚卸しの表を着手の根拠にするとき、件数を数え直してから使うこと
  - 表は見つけた分だけが載るので必ず過小評価に外れる。
  - 再掲 3 箇所とあった表に対し実測 5 箇所で、表どおり直すと 2 箇所残った。残りは「直し忘れ」ではなく「表に無い」ので、表と突き合わせても出ない
- 何かが存在するか（適用されたか・実装されたか）を確認するとき、検索キーになる識別子を推測で作らないこと
  - 定義元（migration・schema・ソース）から実際の名前を読んでから引く
  - 探し方が誤っているだけなのに「無い」という結論が出る
  - 偽陽性と違って偽陰性は「未適用」「未実装」という重大な誤報になり、しかも何度引いても同じ答えが返るので確信だけが強まる
    - 実際 migration 0060 の効果を推測したトリガ名で `pg_trigger` から探して「未適用」と読みかけたが、0060 は新トリガを作らず既存トリガの関数を `create or replace` する作りで、効果は関数本体にあった
  - 名前ではなく本体・定義で確かめる。先述の「他者由来の報告を検証済み事実として扱わない」の自己版で、疑うべき前提が自分の作った検索キーになっている
- 「0 件」「空」「緑」を健全の根拠にする前に、その検査が実際に何を何件見たかを確認し、正常なら非空になる対照を並べること
  - 空と緑は「健全」と「そもそも見ていない」を区別しない
  - 毎朝の healthcheck が 8 日連続 success だったのは全 env が「deployment が 1 件も無いので skip」に落ちていたためで、実測では配信自体が一度も成立していなかった
  - dig は SERVFAIL でも NXDOMAIN でも exit 0 を返し `+short` が全応答を空に潰すので、対照に正常応答するドメインを並べないと相手側の障害と自分の resolver の故障を区別できない
- テストの実行件数を「実行された」ことの証明に使わないこと
  - 件数ではなく実行されたテストの ID 集合を pin する
  - unittest の `Ran N tests` は `@skip` と `@expectedFailure` を両方含み、どちらがあっても `OK` / exit 0 を返す［4 件中 skip 1 + xfail 1 で `Ran 4 tests` / `OK (skipped=1, expected failures=1)` / exit 0 を実測］
  - 全テストを skip 化しても件数も exit code も変わらないので、下限で守っても exact 一致で守っても素通りする
  - 件数 pin は同数入れ替え［1 件消して 1 件足す］と改名も原理的に検出できない
  - ID 集合なら消えた側も未記録側も名指しで出て、副産物として件数の literal がコードから消えるので二重管理も同時に解ける
  - 先述の「0 件を健全の根拠にしない」は空と非空の境界しか守らず、非 0 件が「実行された」を意味しない経路を塞げない
  - 後述の `node --test` ルールが Node の pattern 指定に固有なのに対し、こちらは件数という指標そのものの問題
- 検査結果を判定するための対照は、検証対象と同じ規約で作ること
  - NUL 区切り・revision range・検索式が対象側と一致していることを、対照を信じる前に確認する
  - 壊れた対照は「エラー」ではなく、もっともらしい不一致を返すので、対象側の欠陥に見える
  - 1 ターンで 3 回踏んだ: `git ls-files` を `-z` 無しで対照にしたため日本語パスが全部クォートされ「100 対 29 で取りこぼしあり」と誤読した[落としていたのは対照の方]、`git diff main..HEAD` で未コミットの編集を見ようとして「修正が効いていない」と誤読した[revision range はコミット間しか見ず作業ツリーを含まない]、grep パターンに余分な空白を入れて得た 0 件を「重複が収束した証拠」と誤読した
  - 上の「0 件を健全の根拠にしない」の裏面で、あちらは対象側、こちらは対照側。対照を並べる習慣があっても、対照自身を検証しなければ判定は同じだけ壊れる
- skill や手順書が示す確認コマンドも、そのまま実行して得た 0 件を信じないこと
  - 対象側の実記法と突き合わせてからパターンを使う
  - in-repo-issue skill が Issue 移動時のリンク補正手順で示す `grep -n '](\.\./'` を実行して 0 件を得たが、そのリポジトリはパスに空白と日本語を含むため Markdown リンクが `](<../...>)` の山括弧形式で、パターンが一致していなかっただけだった。直すと 11 件出た。
  - 手順書は canonical を名乗るぶん疑われにくく、しかも誤りは例外ではなく「補正不要」という妥当に見える 0 件で返るので実行結果を見ても気づけない。
  - 上の「対照は同じ規約で作ること」の手順書版で、あちらは自分が組んだ対照、こちらは他人が書いた確認コマンド
- 合成した対照・プローブは検証対象と同じ構造上の位置に置くこと
  - 位置が違うと狙った機構ではなく別経路で成立し、機構を外しても緑になる
  - 整備済みの実ファイルが使えるならそちらを対照にする
  - ruff の isort が `src` 設定に依存するか確かめるプローブを対象パッケージ内に置いたら、`src` を外しても正しく判定された。プローブが同じパッケージにいて別経路で解決されていただけで、実ファイルで測り直すと外部からの import 7 件が発火した
  - 「機構を外しても緑」を「機構は不要」と読むと必要な設定を落とす
  - 先述の「対照は同じ規約で作ること」の位置版
- venv の絶対パスが変わったら（リネーム・移動・別パスへのコピー）venv を再インストールすること
  - console script のシバンへ venv の絶対パスが焼き込まれるので spawn に失敗する。壊れるのは bin 配下のスクリプトだけで、インタプリタ本体と `python -m <mod>` は動き続け、`uv sync --reinstall` で直る
  - 実バイナリのまま置かれるツール (ruff 等) は素通りし、`uv sync` も `poetry install` も lock との整合しか見ずに緑を返す。実際 `git mv` の後 ruff は `All checks passed!` を返し pytest だけが `Failed to spawn` になった[ネイティブ実装でも PyPI 側が Python wrapper を被せていれば落ちる: cmake で実測]
  - 先述の「他者由来の報告・前提を検証済みの網羅的事実として扱わない」の some-path pass ≠ all-path healthy と同族で、通ったツールが壊れる経路を持たないだけ
- 既存データを書き換える一括操作では、記録されたメタデータ (highwatermark・インデックス・カウンタ等) を信じて書き込み先を決めないこと
  - 適用前に実体を数えて突き合わせ、適用後は書き込み対象外のファイルがハッシュ単位で不変であることを確認する
  - タスクリスト移行で .highwatermark を採番オフセットに使ったが、この値はセッション中の採番を含まず実 ID より小さかった
  - 確認した 11 本すべてで不整合があり、そのまま適用すれば生きたタスク 6 件を上書きしていた
  - プランは衝突確認を適用後に置いていたが、上書きは適用の瞬間に起きるので事後検証では救えない
  - 先述の「他者由来の報告を検証済み事実として扱わない」のメタデータ版
- 性能改善の採否をマイクロベンチだけで決めないこと
  - 方式を比較するときは (1) 方式ごとに独立プロセスで実行し (2) 実行順を変えた複数の並びで測って順序効果を排除し (3) その上で実ワークロードで再測してから採否を決める
  - 同一プロセスで 3 方式を連続実行して「BFS が 2 倍速い」と読んだが、先行する方式がキャッシュを温めていた疑いがあり、独立プロセス + 順序 4 通りで測り直して初めて差が本物だと確認できた
  - さらに順序効果を排除しても改善率は転移せず、走査単体で 38% 速くした変更が実ワークロードでは 2 フェーズのうち片方だけ 18% 短縮でもう片方は変化なしだった
  - ベンチの比率で全体を見積もると外す
- nodeのバージョン（Node 26など）によってはディレクトリをエントリモジュールとして解決し `MODULE_NOT_FOUND` で失敗するため、`node --test` にはテストファイルか glob を渡すこと。ディレクトリ形式は使わない
- `node --test --test-name-pattern` で対象を絞ったとき、pattern が 1 件も一致しないとファイル自身が 1 件の pass として計上され `tests 1 / pass 1 / fail 0`・exit 0 になる
  - 件数では 0 件実行を判別できないので、期待するテスト名が出力に現れたことで判定するか、`--experimental-test-isolation=none` を付けて `tests 0` が正直に返る形にする
  - 0 件実行なのに `fail 0` になり、変異注入で「壊しても赤くならない」と読んで生きた pin を dead pin と誤報告する可能性がある
  - 非マッチは `tests` にも `skipped` にも計上されない[4 件中 2 件一致で `tests 2`]ので減算では 0 件を検出できず、一致したテストが skip 済みだと `tests - skipped = 0` で逆に誤判定する
  - Node 24.18 で実測済み
- コマンドが出力するファイル一覧を空白で分割しないこと。`git ... -z` や `find -print0` の NUL 区切りで受け取り、検査した件数が対象件数と一致することを確かめる
  - 空白や日本語を含むパスは分断され、落ちた分は「エラー」ではなく「短い正常な結果」として返るので出力を見ても気づけない。実際 `git diff --name-only` を Python の `.split()` で切って 3 ファイル中 2 ファイルが検査対象から静かに消え、残る 1 件だけが「クリーン」と報告された。「0 件を健全の根拠にしない」は空と非空の境界しか守らないため、部分的な欠落は件数の一致でしか捉えられない。「シェルの展開規則と exit code 規約を確かめてから使う」の、自分のパースコード側の類型
- shell-out / 外部CLIオーケストレーション（`Command`/subprocess 起動、ssh/scp 連鎖、cmd.exe/sh のクォート・連結を組み立てるコード）は、純粋ロジック（argv 構築・パス変換等）のユニットテストが緑でも「完了」としないこと
  - full chain を実環境で一度 live smoke 実行し、シェル/CLIのセマンティクス（連結・クォート・PATH 解決・exit code・OS 差）がランタイムで壊れていないことを確認する
  - cmd.exe の `&` 連鎖が最初の if 偽で全体 no-op になる類のバグはユニットテストでは原理的に捕捉できず、実機実行でしか露見しない
  - winvm の mkdir→scp→remote-exec 連鎖で実際に踏んだ。subagent-driven で委譲する場合も各境界の検証に live smoke を含めること
- `git push` を `| tail` 等のパイプや出力加工に繋がず、push 後は `git ls-remote --heads origin <branch>`（リモート ref 存在）と `git status -sb`（upstream tracking）で成否を直接確認すること
  - パイプ先の exit code が push 本体の失敗/未完を隠し、pre-push hook 完走と ref transfer 完了を取り違える
- 成否を持つ長時間コマンド（`gh run watch`・`gh pr checks --watch`・`gh pr merge` 等）の結論は exit code ではなく専用クエリ（`gh run view <id> --json conclusion` 等）で直接確認すること
  - `<cmd>; echo "EXIT: $?"` のように `$?` を上書きする後続コマンドを連結しないこと
  - 末尾コマンドの exit が本体の結論を隠し、failure を success と誤認する（先述の `git push` ルールの一般形）
- exit code で成否を判定するコマンドは、パイプにも後続コマンドにも繋がず単独で実行すること
  - 出力を絞りたいときは `cmd > <file> 2>&1` だけを実行し、ファイルは次の呼び出しで別コマンドとして読む
  - パイプすると最後のコマンドの exit code になり本体の失敗が隠れる
  - 回避策の `${PIPESTATUS[0]}` は zsh では常に空になり（zsh に `PIPESTATUS` は無く、小文字の `pipestatus` が 1 始まりなので `${pipestatus[1]}`）、空文字は数値比較で 0 と評価されるため成功扱いに化けて取得に失敗したこと自体に気づけない
  - 実際 eslint を `| tail` して「exit 0 = 事前状態クリーン」と誤報告し、実測では 105 problems で赤だった
  - 先述の `git push` / 長時間コマンド 問題の一般形
- Bash ツールでコマンドを組むとき、シェルの展開規則と exit code 規約を確かめてから破壊的操作や状態確認に使うこと
  1. zsh では `for x in $VAR` は単語分割されず 4 要素のリストが 1 つの名前として扱われた
  2. `git check-ignore` は「ignore されていない」を exit 1 で返すため `&&` チェーンが途切れ後続の `rm -rf` が飛んだ
  3. grep のパターンに `$@` を入れたら展開されて0件を返しファイルが壊れたと誤診した
  4. BSD sed に `\b` が無く置換が効いていないのに、`grep -c` で置換後の語を数えたら別の語 (`depth` の中の `pth`) に部分一致して 8 件返り、置換されたと誤読した
  - これらは例外ではなく「0 件」「何も起きない」「無関係な件数」という成功に見える形で返るので結果を見ても気づけない
  - 破壊的操作の前は展開結果を echo で確かめ、真偽値を返すコマンドは `&&` で繋がず `;` で分け、置換の確認は置換後の語を数えるのではなく置換前の語が残っていないことを直接見る
  - 先述の exit code ルールの裏面で、あちらは成否が隠れる側、こちらは後続が飛ぶ側
- パイプの左辺・プロセス置換 `<(...)`・コマンド置換 `$( )` などサブシェルで呼ばれる関数のグローバル代入は親シェルへ戻らない。キャッシュ・カウンタ・「警告済み」フラグのような状態を関数へ持たせる前に、呼び出し側がサブシェルを作らないか確かめること
  - 同じ警告が 1 回の実行で 5 回出る問題にメモ化を提案されたが、全ての呼び出しが `< <(f)` 形だったためキャッシュは毎回破棄され成立しなかった
  - 実装しても「効かない」だけで例外は出ないので、実測しなければ静かに失敗する
  - パイプ右辺は zsh では親に残るが bash では失われるため「右辺なら安全」とも読まないこと［直接呼び出しを対照に bash 3.2.57 / zsh 5.9 で実測］。
  - 先述のシェル展開ルールと同族で、あちらは展開結果、こちらはプロセス境界

## [MUST] 同じ制約を 2 箇所に書かず canonical を 1 つ決める

- [MUST GLOBAL] README などのドキュメントにディレクトリ構成ツリーを載せないこと
  - 経験上必ず drift する
  - 新規参入者の orientation はトップレベルの役割を示す簡潔な説明で足りる
  - rot した既存ツリーは更新ではなくセクションごと削除を優先する
- 静的検査可能なルールはプロンプトではなく、その環境の linter か ast-grep で記述する
  - 末尾改行 (1つの空行) や行末空白のような正規化は各環境の formatter/linter が担保する前提とし prose では個別に規定しない
- エラーや警告は全て解決し、常にコードベースにノイズがない状態を維持すること
- 機械検証可能な制約（regex・長さ上限・enum など）を schema/型定義と散文（指示文・README・コメント）の両方に literal で書かないこと
  - canonical な定義を単一の真実とし、散文は値を再掲せずファイル名で参照すること
  - 同一制約の二重記述は CI が捕捉できない形で drift する
  - 例: seed_id charset を schema `{1,128}` と指示文 `+$` に二重記述して上限が drift し、長い入力で全体が reject される回帰を埋め込んだ
- 上のルールで散文を参照へ書き換えたら、書き換えた側を以下の4点で検算すること。これは二重管理を消す作業がそのまま同型の欠陥を作り、散文の真偽はどの検査も見ないので 4 つとも緑で通る可能性があるため
  1. 消した列挙が全体の部分集合でなかったか
  2. 指名した参照先が本当にその情報を持つか
  3. 書いた宣言の範囲が実態より広くないか
  4. 足した注記自身が値を再掲していないか
- テストから他スクリプト/設定のデータ構造（bash 配列・JSON・TOML 等）を検証するときは、regex での text-parse を避け、定義ブロックを source / import して言語自身に解釈させること
  - regex parse はその言語のパーサが無視する要素[コメント等]を誤読して phantom entry を生み、区切り・分割規約をテスト側に二重実装して drift させる
  - bootstrap の SYMLINK_PAIRS を sed で parse し配列内コメントを phantom source と誤読しかけた
  - 先述の「二重管理 → drift」の一種

## [MUST] テストが緑であることを、仕様を守れている証拠にしない

- ユニットテストではモックは使わないようにし、本当にどうしても必要な場合のみシンプルなものに限って使用すること
- テストは「緑であること」だけで信用しない。各テストが (1) 仕様を表現しているか、(2) 対象を正確にテストしているかまで確かめること
  - 何をしても必ずパスするテスト（assertionが弱い・実質assertionが無い）、テスト自身のセットアップやモックを検証しているだけのテスト（プロダクトコードを実際に通っていない）を防ぐ
  - 弱いassertion（`any()`・存在チェックのみ等）は exact 値の検証と negative case（失敗する入力で確かに失敗すること）まで強化する
  - 実装がテストを gaming していないか（テストに合わせた決め打ち実装になっていないか）を読んで確認すること
  - あるメカニズム（定数・key・分岐・型制約・呼び出し回数など）の遵守を pin する意図で書いたテストは、そのメカニズムを一時的に壊して当該テストが確かに FAIL することを変異注入で確かめること
    - 緑のままなら dead pin である
    - 目視レビューは「壊しても緑」を見逃す。実際 mockito の `expect_at_least` が `assert_async` 不在で計上されず、React の `key` remount が stateless mock で再レンダーと再マウントを区別できず、`as` キャストが未知値を素通しし、いずれも緑のまま検証できていなかった。壊して赤を見て初めて pin は信用できる
  - テスト群を読めば仕様が分かる状態を目指すこと
  - 変異注入（プロダクトコードを一時的に壊してテストが赤くなるか確かめる検証）で復元するとき、同じファイルに未コミット編集があるなら `git checkout -- <file>` を使わないこと
    - cp でバックアップを取るか変異箇所だけを戻す
    - checkout は変異の直前ではなく HEAD へ戻すので、未コミットの編集ごと巻き戻して失う
  - 変異注入は一度に 1 箇所ずつ隔離して行うこと
    - 複数同時に入れると片方の変異がもう片方の効果を隠してテストが緑のままになり、生きた pin を dead pin と誤読する。
    - 変異で赤くなっても pin が有効とは限らない: 赤は「テストがその変更を検出できる」証明にすぎず、守る分岐が本番の入力経路で到達可能か（上流アダプタが入力を正規化・丸め済みで踏まれない分岐でないか）まで確認する
    - 到達不能分岐の pin は赤でも dead（理由: isClickEvent ガードの変異は赤くなったがアダプタが入力を既に丸めていて本番到達不能な分岐だった。2 変数同時変異では片方がもう片方を隠して緑になり pin が死んだと誤読しかけた。上の「緑 = dead pin」の逆側の落とし穴）
  - 検査機構（ゲート・ガード・lint ルール・CI チェック）を足したときの変異は 3 種いる: (1) 検査対象を壊す (2) 検査機構そのものを壊す (3) 検査機構の「取り付け」を外す。(1) だけで完了としないこと。加えて機構が対象集合のどこまでを覆うかを数えること
    - テスト実行件数のガードを作り (1) で赤を確認して完了としたが、赤を作る唯一の行 `process.exitCode = 1` を消しても全テストが緑のまま、さらに recipe からレポータの登録を外しても全緑だった
    - 統合テストが自前で argv を組んでいて取り付けの literal が二重管理になっていたのも同じ穴。
    - (2)(3) を見ないと、穴が塞がったのではなく 1 段上に移動しただけになる。
    - 範囲の穴は (1)〜(3) では見えない。どれも機構が効く範囲内の検証なので範囲外は壊しても緑で通る。
    - Pester のヘルパへ「関数定義が 1 件でなければ throw」を入れて塞いだつもりが、覆えていたのはテストが名前で引く 6 関数だけで、残る 15 関数は壊れた重複定義を入れても緑だった。
    - 先述の「緑 = dead pin」を検査機構自身へ適用した形
  - 検査を緩める変更（免除・除外・narrowing）を入れたときは、緩めすぎる方向の変異も置くこと。免除の集合へ本来報告すべき値を混ぜ、既存の対照テストが赤くなるところまで見る
    - 先述の 3 種はどれも「検査が効く」方向の検証なので、免除が広がりすぎる方向は全部緑で通る
    - compose の短形式マウントで `rw` を同結果免除にしたとき、免除集合へ `ro,z` を混ぜる変異を置いて初めて既存 pin が範囲の広がりを捕まえていると確認できた
    - `external: false` を非報告にした側も同じで、真偽判定を落とす変異が対照を赤にした
    - 先述の「3 種 + 範囲」の範囲が『機構が届かない対象がある』話なのに対し、こちらは『免除が届きすぎる』側
  - 多段の検査を順に行う処理で特定の検査を pin するときは、テストデータが手前の検査をすべて通過する形にすること
    - テストデータは「狙った検査だけが落とす」最小の差分にする
    - 手前で落ちていると狙った検査を壊してもテストは pass のままで dead pin になる。実際 env 間の設定入れ替えを検出する「URL のホスト名と env 名の対応」検査を pin したテストが、片方の env の値だけを差し替えていたため手前の「env 間で値が重複していないか」検査に捕まっており、対象の検査を壊しても緑だった
    - テストが赤いことは「意図した検査が赤くしている」ことを意味しない
    - 先述の「緑 = dead pin」の原因側の類型

- シークレット情報（APIキー、パスワード等）をコードにハードコードせず、.gitignoreされた.envファイルを使用する

- 攻撃者が攻撃可能な要素を最小に抑える

## [MUST] 見た目ではなく意味で組み、色だけに情報を載せない

- 適切なセマンティックHTML要素を使用する（nav, main, article, footer など）
- Web開発では modern-web-guidance plugin を活用し常に最新で安全なWeb実装を行うこと
- a11yを重視しフォーカス可能な要素にはキーボード操作を確保する
- i18n対応する場合は aria-label や aria-describedby などのARIA属性も対応する
- デザインでは色だけに依存しない情報伝達を行う
- レスポンシブ画像で CLS 予約用の `width`/`height` 属性と CSS の `aspect-ratio` を併用するときは、CSS に必ず `height: auto`（縦基準なら `width: auto`）を入れる（理由: `width` と `height` の両方が確定すると CSS の `aspect-ratio` は無視され、`height` 属性の値で画像が縦伸び・クロップする。`height: auto` で属性値による固定を外し `aspect-ratio` に高さを算出させる）

## [MUST] 変更の記録と公開は粒度と経路を決めてから行う

- [MUST GLOBAL] リモートリポジトリへのプッシュは細かすぎない粒度でまとめて行うこと。例えば以下のような基準：
  - PR作成のためのPush
  - Simplify、レビュー、ボーイスカウトルール全てを適用後のPush
  - その他の調整が完了後のPush
- 保護ブランチ（main 等）へ直 push する前の保護判定を、classic API (`gh api repos/<owner>/<repo>/branches/main/protection`) の 404 だけで「保護なし」と結論しないこと
  - repository ruleset は別系統で classic API に出ず 404 になるため、`gh api repos/<owner>/<repo>/rulesets`（必要なら `gh api repos/<owner>/<repo>/rules/branches/<branch>`）も確認する
  - classic 404 を「保護なし」と誤判定すると、ruleset 保護 [pull_request / required_status_checks 等] を bypass 特権で素通り push し、required checks / PR レビューを欠落させる
  - 実際 classic 404 でも ruleset で保護されているリポジトリが存在する

### コミットメッセージのプレフィックスと本文の渡し方

コミットメッセージには "Conventional Commits" をベースにした以下のプレフィックスを使用する。

- `feat:` 新機能の追加
- `fix:` バグ修正
- `improve:` 既存機能の挙動変更を伴う改善
- `refactor:` 既存機能の挙動変更を伴わないリファクタリング
- `test:` テスト関連（追加・修正・削除）
- `style:` コードスタイル（フォーマット、セミコロンなど）
- `docs:` ドキュメントの更新・追加
- `ci:` CI/CD関連の変更
- `perf:` パフォーマンス改善
- `depends:` 外部依存関係の変更
- `build:` ビルドに関わる処理や設定の変更
- `config:` 設定値の変更
- `chore:` その他の作業（typoの修正、コメントの修正など）
- `agent:` コーディングエージェントの振る舞いを変更

大きな機能や修正を実施している最中に作業中の変更をコミットする際には、それぞれのプレフィックスの後ろに `(wip)` を付ける。

コミット本文・PR 本文をはじめ git / gh コマンドに渡す日本語の散文は Bash コマンド文字列に載せず、Write ツールでファイルに書いて `-F` / `--body-file` / `--notes-file` で渡すこと。本文の文字種に制限は要らず、日本語は自然な文体で書いてよい（理由: 禁止すべき文字種を覚えて避ける方式は書くたびに判定を要求するので繰り返し失敗した。heredoc は中身が command 文字列を通るので回避にならない。対象コマンドの一覧・機構・発火条件の実測は skill `dev-workflow:commit-and-pr-message` が持つ）

## [MUST GLOBAL] 着手前と完了前に状態を実測で確かめる

### 着手前

1. タスクに入る前にテストやLint/Formatを実施して事前状態に問題ないことを確かめること
2. これから行うタスクに `dev-workflow:git-branch-switcher` を使用して適切なブランチで作業を開始すること

### 完了前

1. Lint/Format・ビルド・テストで全てのエラーや警告がない状態になったことを確認してPRマージ・タスク完了処理を行うこと
2. 機構の撤去・移行・リポジトリ再編のように状態そのものを変えたときは、その状態を記述している保存済みメモリを実測と突き合わせて訂正すること
  - メモリは書かれた時点では正しく、正しさを保ったまま古びることが多い
  - 放置すれば将来のセッションが存在しない機構の手順を踏むことがあるため
3. `.cache/` 配下の書き捨てを削除すること。残すのは次のセッションが読むもの（未消費の `.cache/handoff.md` など）だけで、既定は削除
  - 削除は `rm .cache/<file>` の形にする（理由は「スクラッチ置き場に `tmp/` ではなく `.cache/` を使う」項）
  - 追跡下の適切なディレクトリへ移すものは先に全文を読むこと（「未読のファイルを追跡下へ入れるとき」項）。移した先で不要になったら削除する
  - 放置すると次のセッションが古いスクラッチを生きた文脈と誤読する。`.cache/` は ignore されるので放置しても誰も気づかない

## [MUST GLOBAL] 自分の作業でホスト環境を壊さない

- ホストの実マシン上（隔離した VM/コンテナの外）で、サイズの大きい・不明なバイナリの一括解析（フォントコレクション `.ttc`・メディア・アーカイブ等）や大規模データ処理を無防備に走らせないこと
  - 必要なときは (1) 入力サイズを先に確認し (2) 全体を一括ロードせず lazy/ストリーミング API を使い (3) それでも重ければ OrbStack/Docker のメモリ上限付きコンテナへ隔離する
  - 加えてバックグラウンドや長時間のプロセスが長く無音のときは「完了待ち」と決めつけず `ps -o rss= -p <pid>` で常駐メモリを確認し、増え続けていれば即 kill すること
  - fontTools の `TTCollection` で巨大な合体 TTC [Sarasa SuperTTC] を非 lazy 展開してメモリが 52GB まで暴走し macOS を OOM で巻き添えに落とした。
  - ホストには VM/コンテナのような cgroup 境界が無く暴走割り当てが OS 全体を落とす
  - 無音を「ハング」と誤診して放置したのが増悪要因
  - macOS の `ulimit -v` は address-space 制限が信頼できず上限として当てにできない
- 1Passwordコマンド `op` が使用可能な場合、認証（`op signin`, `op whoami`）は使わなくともユーザーダイアログにて承認できるので、そのまま `op read` などを実行する
- [MUST] 一時的な書き捨てファイル/スクリプト（検証スクリプト・中間出力・スクラッチ）は、リポジトリ内で作業しているときは `/tmp` やセッション scratchpad ではなく `<repo>/.cache/` 配下に置くこと
  - アクセスと掃除が容易（scratchpad は session 隔離で辿りにくく /tmp は掃除しづらい）
  - global excludesfile に `.cache/` を登録済みなので大抵 ignore されるが、使う前に `git check-ignore .cache/` で確認し効かないリポは個別 `.gitignore` に `.cache/` を足す（誤コミット防止）
  - リポ外で作業しているときは従来の scratchpad を使う
- [MUST] スクラッチ置き場に `tmp/` ではなく `.cache/` を使うのは、Tirith の `mass_file_deletion` が `.cache` を削除検知の除外集合（ビルド成果物扱い）に含むため
  - 除外されないと後片付けの `rm` が正当な作業中にブロックされる
  - 除外集合は tirith 側にハードコードされ設定から拡張できないので、こちらが名前を合わせる
  - scratch は「まとめて消えて当然のもの」なので意味的にも正しい
  - 閾値の canonical は tirith 側なので `tirith explain --rule mass_file_deletion` で確認する
  - この除外を `tirith explain` の文面で判定しないこと
  - explain が挙げる除外例は `node_modules` / `target` / `dist` だけで `.cache` は出てこないため、読むと「除外されない」と結論できてしまう
  - 0.3.3 で対照付きに実測すると、`.cache` 配下は深さ 1 でも 2 でも `rm` と `rm -rf` の双方が通り、`.cache` 外の同じ操作は CRITICAL で Block された
  - ただし通るのはコマンド文字列に `.cache/` が現れる場合に限る
    - `cd .cache` してから相対パスで消すと Block された（実測）
    - hook が見るのは実行後の作業ディレクトリではなくコマンド文字列なので、除外に頼る操作ではパスを省略しないこと
    - 実際にこの誤読が起き、「`.cache` は除外されない」と書き換えるコミットが作られた
    - 対照を取らずに片側だけを見ると、ブロックされなかったことを「まだ発火していないだけ」と読むことも、ブロックを別ルールの発火と取り違えることもできてしまう
    - 「他者由来の報告を検証済み事実として扱わない」と同じで、canonical を名乗る出力でも網羅とは限らない
