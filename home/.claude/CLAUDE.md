# CLAUDE.md — Claude Code 開発ガイドライン

このファイルは、Claude Code に対して、すべてのプロジェクトに適用されるグローバルガイダンスを提供します。

各カテゴリには判定に要る規範だけを置く。手当ての詳細と一次実測は、カテゴリ冒頭で名指しする `~/.claude/references/` のファイルが持つ。

本文書の[MUST], [SHOULD], [MAY]は、RFC 2119に準拠します。[MUST GLOBAL]は本文書独自の拡張です：

- [MUST GLOBAL]：MUSTの上位概念。プロジェクトごとのCLAUDE.mdより優先される
- [MUST]：絶対的要求事項。例外なく従う必要がある
- [SHOULD]：強い推奨事項。特別な理由がない限り従う
- [MAY]：任意事項。状況に応じて採用を判断

## [MUST GLOBAL] 語彙と前提

規範はカテゴリーごとにまとめてある。見出しが示す強度がそのカテゴリーの既定で、既定と異なる強度の項目だけが行頭にラベルを持つ。
この節には文書自身の語彙と、どのカテゴリーにも属さない前提を置く。方針を決めた理由は `~/.claude/references/premises.md` が持つ。

### 語彙
- プロダクトコードに対するテストコードは以下の分類とする。ユニットと統合はローカルマシンと Github Actions 上の CI の両方で実行する
  - ユニットテスト：外部依存なしの高速テスト
  - 統合テスト：複数のモジュールの連携を確認するテスト
  - 契約テスト：library-contract アダプタ層が外部サービスと交わす契約を、Fake/実物の両面で検証する
  - E2Eテスト：ユーザーの操作シナリオをベースにエンドツーエンド（E2E）で検証する。テスティングフレームワークは対象プロダクトの性質に合わせる。実行・メンテナンスコストが非常に高いため、クリティカルパス以外は必要最小限にする
- ボーイスカウトルール: 触った場所を、触る前より良い状態にして離れること。この定義が canonical で、プロジェクトごとの CLAUDE.md は再定義せずここを参照する
  - 対象は今回の変更で触ったファイルと、その中で見つけた既存 (Pre Existent) の問題。スコープ外でも直し、レビューで見つけた問題を「今回の担当ではない」という理由で残さない
  - ただし影響範囲が大きい変更や重要な設計判断を要する問題は別タスクへ切り出す。境界は「今回の PR のレビュー範囲に収まるか」に置く
  - 隣接ファイルは表記揺れを判断するための参照であって、それ自体を直す対象にはしない

### 前提
- [MUST GLOBAL] どんなときでもユーザーデータを守るセキュリティを第一に考え、決して手を抜かない
- ユーザー（Hidari）の開発スタイルは先に大きな問題を潰しながら主目的をまず通すこと
  - 途中で切り出した課題や設計段階で分けた課題に取り掛かるのは主目的を達成したあと。調査中に別の問題を見つけて作業が入れ子になることを避ける
  - 影響範囲が限定的であることが予想される場合はボーイスカウトルールに則って対応することは可
- ユーザー（Hidari）が扱うプロジェクトにはPrivateリポジトリとPublicリポジトリが混在しているためリポジトリの公開範囲は常に確認すること
- 個人情報（実メールアドレスや実名、マシンローカルのホームディレクトリに含まれるユーザー名などを含む）はコミット、コミットメッセージ/コードに載せないこと
- ユーザー（Hidari）は個人開発者でプロダクトに投下できるリソースに限りがあるため、手動テストによる動作確認を最小限にすることをなにより重要視する
  - CIコストがかなり負担となるため可能な限りローカル環境のVM、Linuxコンテナ、Mac上で検証を行い、CIでの検証はmainマージとリリース時にのみ抑える
- [MUST] DRY原則、KISS原則と "Single Responsibility" を適用したテスタブルで拡張性のある設計を行い単体テスト、統合テストを必ず記述し、UIを持つプロダクトはE2Eテストまで用意して機能の動作を検証可能にすること
- [MUST] 外部ライブラリやパッケージなどの依存関係は極力少なく維持すること
- 外部ライブラリは library-contract パターンで切り離し層をつくること
- [MUST] あらゆる作業は抽象と具象の視点、局所的と大局的の視点を適度に往復しながら常に全体最適を目指すこと
- [MUST GLOBAL] プロダクトコードとテストコードが ファーストクラスドキュメント（= the single source of truth） となるように書き、テストコードはリグレッションテストであるとともに 仕様としてのテスト の考え方を徹底すること
- 各テストのカバレッジは可能な限り高く保つが、行カバレッジよりも分岐カバレッジを優先すること
- [MUST] コードやテスト、ドキュメントは書かずに済むことが drift を根本的に防ぎ、保守性と拡張性を高めることに繋がるため、その方法を常に模索すること
  - 特にコメントとテストコードは drift しやすく気づきづらい。書かないことでそもそも drift する面を減らす
  - 特にSDDを行う際には直接的な実装コード片をできる限り減らし、Mermaidによる図示やデシジョンテーブルなどの各種テスト技法を用いること

## [MUST] 観測した結果がその主張の証拠になっているか確かめ、観測自体を加工や連結で壊さない

手当ての詳細と一次実測は `~/.claude/references/observation.md` が持つ。

- [MUST GLOBAL] 未読のファイルを追跡下へ入れるとき（`mv` による移動も含む）は先に全文を読み、gitleaksなどの緑を安全の根拠にしない
- 報告・前提を検証済みの網羅的事実として扱わないこと
  - 由来を問わない。ユーザーの報告や症状の伝聞、監査レポート、記録されたメタデータ、自分の測定、自分が作った検索キー、いずれも同じ。列挙は網羅ではない。判定は出所の種類ではなく「その前提を自分で再現したか」で行う
  - 健全と結論する前に壊れやすい配置（端・境界・空・最大・最初/最後）を列挙して報告がそれを踏んだか確かめ、単独で並べるだけでなく掛け合わせも見て、未確認の前提は subagent の並列 fan-out に渡す前に自分の再現で確定させる
  - 監査結果や棚卸しの表は見つけた分だけが載るので必ず過小評価に外れる。着手の根拠にするときは件数を数え直す
  - 記録されたメタデータ（highwatermark・インデックス・カウンタ等）を信じて書き込み先を決めない。既存データを書き換える一括操作では、適用前に実体を数えて突き合わせ、適用後は書き込み対象外のファイルがハッシュ単位で不変であることを確認する
  - 自分の測定も同じ。マイクロベンチだけで採否を決めず、独立プロセスでの実行・実行順の入れ替え・実ワークロードでの再測を通してから決める
  - 検索キーになる識別子を推測で作らず、定義元（migration・schema・ソース）から実際の名前を読んでから引く。偽陰性は「未適用」「未実装」という重大な誤報になり、しかも何度引いても同じ答えが返るので確信だけが強まる
- 「0 件」「空」「緑」を健全の根拠にする前に、その検査が実際に何を何件見たかを確認し、正常なら非空になる対照を並べること
  - 空と緑は「健全」と「そもそも見ていない」を区別しない。結果の形は「0 件」「空」「緑」に限らない。判定は形が一致するかではなく、その検査が実際に何を何件見たかで行う
  - 対照側も同じだけ壊れる。対照は検証対象と同じ規約で作り、NUL 区切り・revision range・検索式が対象側と一致していることを対照を信じる前に確認する。壊れた対照は「エラー」ではなく、もっともらしい不一致を返すので対象側の欠陥に見える
  - 時刻の対照はタイムゾーンで壊れる。コマンドが返す絶対時刻をコンテキストの「今日」と突き合わせず、相対時刻か `date -u` の UTC 同士で比べる
  - 他人が書いた確認コマンドも同じ。skill や手順書が示すパターンをそのまま実行して得た 0 件を信じず、対象側の実記法と突き合わせてから使う。手順書は canonical を名乗るぶん疑われにくく、誤りは「補正不要」という妥当に見える 0 件で返る
  - 合成した対照・プローブは検証対象と同じ構造上の位置に置く。位置が違うと狙った機構ではなく別経路で成立し、機構を外しても緑になる。「機構を外しても緑」を「機構は不要」と読むと必要な設定を落とす
  - 非 0 件も証明にならない。テストの実行件数を「実行された」ことの証明に使わず、件数ではなく実行されたテストの ID 集合を pin する
- Bash ツールでコマンドを組むとき、成否と状態が沈黙して失われる経路を先に潰すこと
  - 破られ方に共通するのは、失敗が「エラー」ではなく「成功に見える結果」として返ること。列挙は網羅ではない。判定は形が一致するかではなく、その検査が失敗を検出できる経路を持っているかで行う
  - これまで塞いだ経路は成否が隠れる・後続が飛ぶ・プロセス境界を越えない・パースが静かに欠ける。手当ては参照先が持つので組む前に開く。この一覧は踏んだ記録で、チェックリストではない
- shell-out / 外部CLIオーケストレーション（`Command`/subprocess 起動、ssh/scp 連鎖、cmd.exe/sh のクォート・連結を組み立てるコード）は、純粋ロジックのユニットテストが緑でも「完了」としないこと
  - full chain を実環境で一度 live smoke 実行し、シェル/CLIのセマンティクスがランタイムで壊れていないことを確認する。subagent-driven で委譲する場合も各境界の検証に含める
- `node --test` にはテストファイルか glob を渡すこと。ディレクトリ形式はバージョンによって解決に失敗する

## [MUST] 同じ制約を 2 箇所に書かず canonical を 1 つ決める

手当ての詳細と一次実測は `~/.claude/references/canonical.md` が持つ。

- [MUST GLOBAL] README などのドキュメントにディレクトリ構成ツリーを載せないこと。経験上必ず drift する
  - rot した既存ツリーは更新ではなくセクションごと削除を優先する
- エラーや警告は全て解決し、常にコードベースにノイズがない状態を維持すること
- 機械検証可能な制約（regex・長さ上限・enum など）を schema/型定義と散文（指示文・README・コメント）の両方に literal で書かないこと
  - canonical な定義を単一の真実とし、散文は値を再掲せずファイル名で参照すること。同一制約の二重記述は CI が捕捉できない形で drift する
- 上のルールで散文を参照へ書き換えたら、書き換えた側を以下の4点で検算すること。これは二重管理を消す作業がそのまま同型の欠陥を作り、散文の真偽はどの検査も見ないので 4 つとも緑で通る可能性があるため
  1. 消した列挙が全体の部分集合でなかったか
  2. 指名した参照先が本当にその情報を持つか
  3. 書いた宣言の範囲が実態より広くないか
  4. 足した注記自身が値を再掲していないか
  - 検算器は対象に合わせて作り直す。識別子の照合で「情報が落ちていないか」は見えるが、射程の広がりや強度ラベルの降格は見えない

## [MUST] テストを書き始める前に順序と方式を決める

- 最初に仕様を表現するテストコードを作成し、それを満たすプロダクトコードを書くこと（TDD的アプローチ）
- さらに必要な場合は後からテストコードを追加すること
- プロダクトコードを変更する際は、変更後の動作をテストコードで表現してからプロダクトコードを書くこと
- JS エコシステムでは `npm` / `npx` ではなく `pnpm` を既定で使うこと（セキュリティ面で劣ると判断している）
  - settings.json の `permissions.deny` にも該当コマンドを入れてあるが (canonical はそちら)、deny が止めるのは実行しようとした瞬間なので、その手前でこのルールを読んで選ぶこと
  - E2E テストは公式 Playwright Test Agents（`pnpm exec playwright init-agents --loop=claude` で生成される Planner / Generator / Healer）を使用して作成する
  - playwright を devDependency に持たないプロジェクトでは `pnpm dlx` で代替する

## [SHOULD] 委譲先の報告を自分の実測の代わりにせず派生は 1 段に留める

手当ての詳細と一次実測は `~/.claude/references/delegation.md` が持つ。

- [MUST GLOBAL] 計画、実装どちらを行うにも反復的な計画、実装を行うアプローチで進めること
  - 特にSubagent-Drivenで作業を行う際、指揮役が対象タスクを以下のいずれかと判断した場合、可能な場合はSubagentに Fable モデルを使用すること
    - 難しい設計や厳密性が求められるドキュメント、プランのレビューを行う場合
    - 実装タスクのサイズが L, XL 以上で複雑である
    - 大規模な調査・監査や、設計・移行計画の起案である
    - セキュリティ、権限関連、暗号化関連のコードなどクリティカルである
  - 走らせる Fable Subagent は可能な限り適用対象と適用範囲を絞ること。現在のトークン価格では 5 つ並行でも相当な負担になり、10 も 20 も同時に使えばまたたく間にリミットへ達する
- 複雑な問題の検証にはSubAgentsを積極的に使用する。Agent / Task tool と Workflow の使用はこの記述をもって恒久的に許可済みとし、都度の確認は要らない
  - ただし派生は 1 段まで。subagent として起動された側はさらに subagent を spawn しないこと
- 実装プランを実行する際は `superpowers:subagent-driven-development`（Subagent-Driven）を既定とする。タスクごとに新鮮なSubAgentをdispatchし、各境界でfmt+test緑をコントローラ側が検証し、報告とgit statusを突合してからコミットする
  - 長時間ゲート（E2E・フルビルド・`gh run watch` 等 秒〜分オーダーで待つコマンド）は最初からコントローラが回し、implementer には実装と変異注入（pin したメカニズムを壊して赤くなることの確認）までを任せる。行動を prompt で禁じるより分業の設計で構造的に防ぐ方が確実
  - 複数エージェントの構造化出力どうしを突合するときは、相関キーにモデルが再生成する自由文字列（title・見出し等）を使わず、こちらが採番した ID を schema に含めて返させること。突合の失敗は例外ではなく「全件未検証」という静かな結果で返る
  - 反証を subagent へ委ねるとき、迷ったときの既定値（「確信が持てないなら refuted=true」等）を指示しないこと。迷った反証者が全員同じ側へ寄るので、一致が独立確認の証拠にならない
  - brief に「機序は特定済みだから裏取りだけでいい」と書いて implementer の探索を抑制しないこと。implementer が実測で brief に反論してきたら、まず疑うべきは brief の方
  - subagent に環境の制約（認証が引き継げない・特定の API が使えない・隔離下で参照できない等）を伝えるときは、回避を試みることの禁止を併記すること。制約の説明はエージェントにとって「解くべき問題」に見えるので、「そこには行くな」まで書いて初めて制約になる
  - レビューや検証を並列 subagent へ委譲するとき、実験はリポジトリ本体ではなく隔離コピーで行わせること。本体を変異させられると、その間の親側の観測が壊れる
  - 複数の設計案を並列生成させるとき、少なくとも 1 つには「前提そのものを疑え」という出発点を与えること。同じ問題設定を渡すと案は同じ前提へ収束し、judge も相対比較しかできないので全案が同じ穴を持ったまま勝者が決まる
- 常時ロードされる指示のコストは session_start だけでなく subagent の起動ごとに払う。観測フックのログには現れないので、量の見積もりにログを使わないこと

## [MUST GLOBAL] 攻撃者が使える面を最小に保ち防御を 1 層に頼らない

手当ての詳細と一次実測は `~/.claude/references/security.md` が持つ。

- プロダクトコードは多層防御を敷き、基本的なセキュリティ対策を徹底する
- ユーザー入力は必ずバリデーション・サニタイズする
- 外部入力から識別子を動的に作るとき（シェル関数名・オブジェクトのキー・属性名・テーブル名など）、注入対策の charset 検証を名前空間の検証と兼用しないこと
  - 「危険な文字を通さないか」と「作ってよい名前か」は別レイヤー。charset を通っていても警告は出ないので、実際に使うまで気づけない
  - 専用の接頭辞へ閉じても塞がるのは外部名との衝突だけなので、接頭辞の内側に静的定義や派生名が同居するなら、それらと衝突しないこと（派生に使う接尾辞の予約など）まで検査する
- SQLインジェクション対策としてパラメータ化クエリを使用する
- XSS対策としてユーザー入力をエスケープする
- 認証・認可のチェックを適切に行う
- シークレット情報（APIキー、パスワード等）をコードにハードコードせず、.gitignoreされた.envファイルを使用する
- HTTPSを使用し、セキュリティヘッダーを適切に設定する
- 攻撃者が攻撃可能な要素を最小に抑える

## [MUST] 変更の記録と公開は粒度と経路を決めてから行う

手当ての詳細と一次実測は `~/.claude/references/git-workflow.md` が持つ。

- [MUST GLOBAL] リモートリポジトリへのプッシュは細かすぎない粒度でまとめて行うこと。例えば以下のような基準：
  - PR作成のためのPush
  - Simplify、レビュー、ボーイスカウトルール全てを適用後のPush
  - その他の調整が完了後のPush
- 保護ブランチ（main 等）へ直 push する前の保護判定を、classic API (`gh api repos/<owner>/<repo>/branches/main/protection`) の 404 だけで「保護なし」と結論しないこと
  - repository ruleset は別系統で classic API に出ず 404 になるため ruleset 側も確認する。使う endpoint の選び方は参照先が持つ
  - classic 404 を「保護なし」と誤判定すると、ruleset 保護を bypass 特権で素通り push し、required checks / PR レビューを欠落させる

### コミットメッセージのプレフィックスと本文の渡し方

コミットメッセージには "Conventional Commits" をベースにしたプレフィックスを使用する。一覧と作業中コミットに付ける標記の規約は `~/.claude/references/git-workflow.md` が持つ。

コミット本文・PR 本文をはじめ git / gh コマンドに渡す日本語の散文は Bash コマンド文字列に載せず、Write ツールでファイルに書いて `-F` / `--body-file` / `--notes-file` で渡すこと。本文の文字種に制限は要らず、日本語は自然な文体で書いてよい。機構と発火条件の canonical は skill `dev-workflow:commit-and-pr-message`

## [MUST GLOBAL] 着手前と完了前に状態を実測で確かめる

### 着手前

1. タスクに入る前にテストやLint/Formatを実施して事前状態に問題ないことを確かめること
2. これから行うタスクに `dev-workflow:git-branch-switcher` を使用して適切なブランチで作業を開始すること

### 完了前

1. Lint/Format・ビルド・テストで全てのエラーや警告がない状態になったことを確認してPRマージ・タスク完了処理を行うこと
2. 機構の撤去・移行・リポジトリ再編のように状態そのものを変えたときは、その状態を記述している保存済みメモリを実測と突き合わせて訂正すること
  - メモリは書かれた時点では正しく、正しさを保ったまま古びる。放置すれば将来のセッションが存在しない機構の手順を踏む
3. `.cache/` 配下（リポ外で作業していたときは scratchpad）の書き捨てを削除すること。残すのは次のセッションが読むもの（未消費の `.cache/handoff.md` など）だけで、既定は削除
  - 削除は `rm .cache/<file>` の形にする（理由は「スクラッチ置き場に `tmp/` ではなく `.cache/` を使う」項）
  - 追跡下の適切なディレクトリへ移すものは先に全文を読むこと（「未読のファイルを追跡下へ入れるとき」項）。移した先で不要になったら削除する
  - 放置すると次のセッションが古いスクラッチを生きた文脈と誤読する。`.cache/` は ignore されるので放置しても誰も気づかない

## [MUST GLOBAL] 自分の作業でホスト環境を壊さない

手当ての詳細と一次実測は `~/.claude/references/host-environment.md` が持つ。

- ホストの実マシン上（隔離した VM/コンテナの外）で、サイズの大きい・不明なバイナリの一括解析（フォントコレクション `.ttc`・メディア・アーカイブ等）や大規模データ処理を無防備に走らせないこと
  - 必要なときは (1) 入力サイズを先に確認し (2) 全体を一括ロードせず lazy/ストリーミング API を使い (3) それでも重ければメモリ上限付きコンテナへ隔離する
  - バックグラウンドや長時間のプロセスが長く無音のときは「完了待ち」と決めつけず `ps -o rss= -p <pid>` で常駐メモリを確認し、増え続けていれば即 kill すること。ホストには cgroup 境界が無いので暴走割り当てが OS 全体を落とす
- 1Passwordコマンド `op` が使用可能な場合、認証（`op signin`, `op whoami`）は使わなくともユーザーダイアログにて承認できるので、そのまま `op read` などを実行する
- [MUST GLOBAL] 一時的な書き捨てファイル/スクリプト（検証スクリプト・中間出力・スクラッチ）は、リポジトリ内で作業しているときは `/tmp` やセッション scratchpad ではなく `<repo>/.cache/` 配下に置くこと
  - 使う前に `git check-ignore .cache/` で確認し、効かないリポは個別 `.gitignore` に `.cache/` を足す（誤コミット防止）
  - リポ外で作業しているときは従来の scratchpad を使う
- [MUST GLOBAL] スクラッチ置き場に `tmp/` ではなく `.cache/` を使うのは、Tirith の `mass_file_deletion` が `.cache` を削除検知の除外集合に含むため。除外されないと後片付けの `rm` が正当な作業中にブロックされる
  - ただし除外が効くのはコマンド文字列に `.cache/` が現れる場合に限る。`cd .cache` してから相対パスで消すと Block される。
  - hook が見るのは作業ディレクトリではなくコマンド文字列なので、除外に頼る操作ではパスを省略しないこと
  - 閾値と除外集合の canonical は tirith 側だが、`tirith explain` の文面で除外の有無を判定しないこと。除外例に `.cache` は挙がっていないため読むと逆の結論が出る
