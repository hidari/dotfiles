# [MUST] ビルドの遅さも設定の効果も、観測しやすい量を証拠にしない

手当ての詳細と一次実測は `~/.claude/references/rust-build.md` が持つ。

- 遅さの出所がビルドの中にあることを確かめるまで Cargo へ手を入れないこと
  - ホスト OS の常駐プロセス（ファイル索引・署名検証・ウイルス対策）が真因のとき、その負荷はビルド側のどの計測にも現れず、profile もクレート分割も効かない
  - タスクランナーを自リポジトリのクレートにしていると、最初にそれを呼んだ工程の中へランナー自身の cold build が紛れる。alias に `--quiet` が付いていればログにも出ない。工程の名前ではなく、開始から最初の出力までの時刻差で分解する
  - `target/` に溜まったファイル数は profile と feature 構成をまたぐ累積であって、1回のビルドのコストではない。日常的な `cargo clean` は次のビルドを必ずフルにするだけの純損
- profile のキーの射程を、書いた場所ではなく rustc の実引数で確かめること
  - 素の `[profile.<name>]` は per-package の上書きが無い限り依存グラフ全体へ降りる。配布物を最適化したつもりで、依存全部のコンパイル時間を払う形になりやすい
  - 上書きは `package.<名前>` → `package."*"`（workspace member 以外のすべて）→ `build-override` → `[profile.<name>]` の順に探され、最初に一致したものが勝つ。`package."*"` を置くと、`build-override` が追加で効くのは自 workspace の build script と proc macro だけになる
  - 既定値の再掲は何も変えないのに「検討済み」に見え続ける
  - 依存グラフ全体へ降りる profile の行を変えると全ユニットの fingerprint が変わり、直後に1回だけフルビルドが入る。回帰と読まず、その回では測らない
- デバッグ情報などを落としたら、落とした軸と対称な退避先 profile を置くこと
  - `inherits` は継承元の per-package 設定と override テーブルをまとめて引き継ぐ。退避先で軸を1つ戻し忘れるとその範囲だけデバッガで中へ入れず、コンパイルもテストも緑のままなので実引数を見るまで気づけない
  - 到達する入口と成果物の回収経路を同時に決める。profile ごとに target ツリーが別に積み上がるうえ、日常の入口から通らない設定は緑のまま腐る
- feature による除外が成立するのは1回の build invocation の中だけだと理解すること
  - feature はビルドごとに和集合を取るので、同じ feature を立てる member が1つでも居れば `--workspace` のゲートは和集合を払う。ゲートが緑でも、単一パッケージの配布ビルドから除外されている証拠にはならない
  - 排他な feature を同時に立てる `--all-features` は `cfg(not(...))` 側を1つも通らないので、出荷構成のゲートの代用にならない
- 設定が効いたかを、そのキーが動かすはずの量で判定すること。rustc へ渡ったフラグの有無は「設定が届いたか」の確認であって効果の証拠ではない
  - cargo の既定と rustc の既定は一致しないので、フラグが付いたことは出力が変わった証拠にならず、既定と同じに見えることも no-op の証拠にならない。両方向に誤る
  - 動かすはずの量はキーごとに違う。`debug` / `strip` なら生成物のバイト数とファイル数、`codegen-units` / `lto` ならコンパイル時間と成果物サイズの両方を実ワークロードで測る
  - 切り離したプローブクレートで測るときは、本体と上書きのテーブル（`package."*"` など）の有無を先に突き合わせる
- 時間を比べる前に、両条件で実行された単位の集合が一致していることを確かめること
  - profile・feature・ターゲット指定はコンパイル対象とテスト対象を静かに減らし、減っても緑のまま速くなる。`--lib --bins` のような絞り込みは統合テストと doctest を丸ごと落とす
  - 共有依存を持つ連続した cargo 呼び出しでは、先頭が cold のコンパイルを全部背負う。工程ごとの時間はその構成の増分ではないので、増分を知りたい構成は最後へ置く
  - ホスト実機での前後比較は user CPU と生成物のサイズで判定し、並行負荷を拾う wall は参考値に留める
- コンパイルキャッシュの採否を incremental compilation との取引で決めること。incremental でコンパイルされる crate は sccache がキャッシュしないので、常に cold な CI と反復編集が主なローカルとでは採否の向きが逆になる
