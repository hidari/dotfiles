# [MUST] テストが緑であることを、仕様を守れている証拠にしない

手当ての詳細と一次実測は `~/.claude/references/testing.md` が持つ。
regex での text-parse の項だけは `~/.claude/references/canonical.md` が持つ。

- ユニットテストではモックは使わないようにし、本当にどうしても必要な場合のみシンプルなものに限って使用すること
- テストは「緑であること」だけで信用しない。各テストが (1) 仕様を表現しているか、(2) 対象を正確にテストしているかまで確かめること
  - 何をしても必ずパスするテスト（assertionが弱い・実質assertionが無い）、テスト自身のセットアップやモックを検証しているだけのテスト（プロダクトコードを実際に通っていない）を防ぐ
  - 弱いassertion（`any()`・存在チェックのみ等）は exact 値の検証と negative case（失敗する入力で確かに失敗すること）まで強化する
  - 実装がテストを gaming していないか（テストに合わせた決め打ち実装になっていないか）を読んで確認すること
  - テスト群を読めば仕様が分かる状態を目指すこと
  - あるメカニズム（定数・key・分岐・型制約・呼び出し回数など）の遵守を pin する意図で書いたテストは、そのメカニズムを一時的に壊して当該テストが確かに FAIL することを変異注入で確かめること。緑のままなら dead pin であり、目視レビューでは「壊しても緑」を見逃す
    - 変異は一度に 1 箇所ずつ隔離して入れる。複数同時だと片方がもう片方の効果を隠して緑のままになる
    - 赤くなっても pin が有効とは限らない。守る分岐が本番の入力経路で到達可能かまで確認する。到達不能分岐の pin は赤でも dead
    - テストが赤いことは「意図した検査が赤くしている」ことを意味しない
    - 復元に `git checkout -- <file>` を使わない。checkout は変異の直前ではなく HEAD へ戻すので、未コミットの編集ごと失う
    - 検査の発火条件がファイルの追跡状態に依存することがある。新規ファイルは追跡下へ入れてから変異させる
  - 検査機構（ゲート・ガード・lint ルール・CI チェック）を足したときの変異は 3 種いる。(1) 検査対象を壊す (2) 検査機構そのものを壊す (3) 検査機構の「取り付け」を外す。(1) だけで完了としないこと
    - 加えて機構が対象集合のどこまでを覆うかを数える。範囲の穴は (1)〜(3) では見えない。どれも機構が効く範囲内の検証なので範囲外は壊しても緑で通る
  - 検査を緩める変更（免除・除外・narrowing）を入れたときは、緩めすぎる方向の変異も置くこと。免除の集合へ本来報告すべき値を混ぜ、既存の対照テストが赤くなるところまで見る
  - 多段の検査を順に行う処理で特定の検査を pin するときは、テストデータが手前の検査をすべて通過する形にすること。手前で落ちていると狙った検査を壊しても pass のままで dead pin になる
- テストから他スクリプト/設定のデータ構造（bash 配列・JSON・TOML 等）を検証するときは、regex での text-parse を避け、定義ブロックを source / import して言語自身に解釈させること
  - regex parse はその言語のパーサが無視する要素[コメント等]を誤読して phantom entry を生み、区切り・分割規約をテスト側に二重実装して drift させる
