# [MUST] コンパイルが通ったことを、実行時と CI の健全性の証拠にしない

- プロダクションコードで `panic!` / `.unwrap()` / `.expect()` を使わず、`thiserror` 等で構造化したエラー型を `Result` で伝播させること
  - テストコードやフィクスチャの `.unwrap()` は許容してよいが、プロダクションコードの公開関数へ染み出させない
  - clippy の `missing_panics_doc` をクレート単位で allow するときは、テスト側の都合であることを理由コメントに残し、プロダクション側では警告を維持する
- TLS や crypto のバックエンドを差し替えられる crate は `default-features = false` にして pure-Rust のバックエンド（rustls 系）を明示選択すること
  - 既定のままだと C 依存を引き込み、ローカルと CI で環境が非対称になる
  - バックエンドがトレイト化された crate は、未選択でもコンパイルが通り実行時にだけ panic する。feature を明示し、可能なら起動時にバックエンドが登録済みであることを検証する
- 外部サービスの生成型（OpenAPI generator が出す strict な enum / struct）をコアの制御フローで直接 match / 消費しないこと
  - 未知バリアント・未知フィールドの受け皿（`#[serde(other)]`、タグなし `Value` の catch-all）を持たせ、サーバ側のスキーマ進化で deserialize を hard-fail させない
- `tests/` 直下へ `.rs` を足すと、その数だけテストバイナリが生成され、共有ヘルパの再コンパイルと再リンクが線形に増える。エントリポイントは 1 本へ集約し、個々のテストは配下ディレクトリへ置いて `mod` で束ねること
  - 線形に増えるのはディスクと user CPU で、コア数ぶん並列にリンクされるので wall には出にくい。wall が変わらないことを「増えていない」証拠にしない
  - 集約後の健全性は「ファイル数」ではなく、実行されたテストの ID 集合で確認する。壊れたスタブはファイル数の検査を素通りし、件数は同数の入れ替えを検出しない

# [MUST] ビルドのコストに手を入れる前に律速を測り、入れた後は効いていることを別の量で確かめる

手当ての詳細と一次実測は `~/.claude/references/rust-build.md` が持つ。

- キャッシュを足す前にビルドの律速を実測すること。キャッシュは同じ作業を繰り返さないための手当てで、1回あたりの作業量は減らさない
  - 律速がコンパイル側かリンク側かは環境で入れ替わる。削減の見積もりを立てる前に測る
- ビルドを速くする配線（コンパイラキャッシュ・CI のキャッシュ）は、外れてもエラーではなく緑のまま効かない形で返る。wall ではなく、配線の生死を示す指標で判定すること
  - 指標の観測手段が対象のビルドと同じプロセス・同じ RUN にあることまで確かめる。別の RUN で統計を取ると、新しく起動したサーバの空の統計を読むことになる
  - 「保存するものが無い」と「一度も呼ばれていない」が同じ 0 になる指標で判定しない。cold と warm を通じて一定になる、要求の側の件数で見る
  - 指標は配線と同じ変更で pin する。後から足すと、効いていなかった期間が観測できない
- ビルド設定の canonical は workspace root の `Cargo.toml` に置き、workflow や Dockerfile の `CARGO_PROFILE_*` 環境変数で上書きしないこと
  - `[profile.<name>.package.<name>]` には環境変数の形が無い。環境変数で上書きする経路を混ぜると、ビルド経路ごとに設定が食い違う
- ビルドの並列度に上限を置くこと。`CARGO_BUILD_JOBS`（`build.jobs`）に固定値を書くとコア数に関係なくその数で走るので、`min(nproc, 上限)` を自前で算出する
  - 上げすぎたときの症状はコンパイルエラーではなく、ビルド基盤側の不可解なエラーになる
- 計装・`CARGO_TARGET_DIR`・rustflags を変えるツール（カバレッジ計測など）は fingerprint が別物になる。キャッシュキーが一致して `Cache hit` と出ても再コンパイルするので、warm かどうかをログの hit 表示で判定しないこと
