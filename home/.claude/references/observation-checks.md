# 検査と探針を組むときの観測の一次実測

`~/.claude/references/observation.md` の「0 件・空・緑を健全と読む」節と「live smoke」節の続き。容量の都合で分けた。dead pin と変異注入の定義は `~/.claude/rules/testing-practices.md` が持つ。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。

## 比較の結果が報告と合わないときは比較器を疑う

比較の結果が実装者の報告や期待の件数と合わないときに開く。壊れた対照の型は `~/.claude/references/observation.md` の「対照側も同じだけ壊れる」節が持つ。

使い捨ての検証ツールの誤りは、検証対象の欠陥と同じ形で出る。決着はツールの出力どうしでは付かず、一次の実体へ降りる。

2つのコミットの間で、Rust の定数の配列のキー集合を shell の正規表現で取り出して比べた。1行の `("名前", 数)` だけを拾う正規表現だったので、rustfmt が折り返した行を取りこぼして偽の差分 (入れ替わり) が出た。ブロックの中の文字列リテラルを全部拾う形に替えると、実装者の報告の件数と一致した (実測)。この実測からのまとめは「比較の結果が実装者の報告の件数と合わないときは、先に比較器を疑う」。

## 経路を踏んだことを数える witness

経路を踏んだことや検査が見た件数を数える witness を置くときに開く。非0件を証明にしない判定は `~/.claude/references/observation.md` の「非 0 件も証明にならない」節が持つ。

- witness (この経路を踏んだことを示す非0の数) は、数える条件を機構の発火条件まで絞らないと dead pin になる。機構を消す変異でも、偽の増分で非0のまま緑だった。手当ては、witness ごとに機構を消して0へ落ちることを確かめること
- 検査が見た件数を、検査に渡す配列とは別の変数で数えていたら、渡し忘れの変異でも件数だけが合って緑になった。件数は実際に検査へ渡す配列から数える

## 実行されたことの証拠を取る

外部依存の不在で早期 return するテストを持つスイートの結果を読むときと、実行されたテストの ID 集合を取りたいときに開く。

- 統合テストが外部依存の不在を `println!` で知らせて早期 return する構成では、そのテストも passed に数えられるので、スキップの印 (`⏭` など) が0件でも「実行された」の証拠にならない。libtest の `--show-output` を渡し、成功したテストの stdout ブロックの数が全件数と一致すること (陽性の対照) を確かめてから印の0件を読むと、証拠になった (実測)。スキップを passed に数えない仕組みの無いプロジェクトでは、テストランナーへ `--show-output` などの引数を渡す口を make のターゲットに用意しておく
- 早期 return したテストも passed のまま ID の集合に入るので、件数ではなく ID の集合を照合しても見分けられない
- 対象の ID の集合は、依存の有無を判定する関数を直接呼ぶテストだけでなく、その関数を包む補助関数の呼び出し元まで辿って作る。補助関数の名前はテスト名ではないので、直接の呼び出しだけを数えると0件の穴に見える (実測)
- Playwright の reporter に json を常設して .cache/ へ出すと、実行されたテストの ID の集合をいつでも取れる。PLAYWRIGHT_JSON_OUTPUT_NAME は json の reporter が有効なときしか効かない (実測。報告日は未記録、Playwright の版は未記録)

## 期待値を canonical の設定から作る

配信後の応答ヘッダのように、付け忘れを smoke で確かめるときに開く。

smoke で応答ヘッダの付け忘れを見るとき、期待する値を写さず「付けない経路に無く、付ける経路に在るもの」として実物から導くと、canonical を1つに保てる。

配信後の応答ヘッダの検査を、期待するヘッダの名前と値を配信の canonical の設定 (routes の headers) から作り、「期待 N 本のうち一致 M 本」を出す形で、配信の前と後に同じスクリプトで測って差分を取った。この形は手書きの grep の取りこぼしを件数で露出させた。最初に手で書いた `^(strict-transport):` のような名前の途中で切れたパターンは、3本しか当たらない結果を「健全」に見せかけていた (実測)。

## 版で割れる探針は両向きに当てる

deploy の後に新旧の版を見分ける探針を当てるときに開く。

- 「戻った」を判定する探針は、新しい版で ok を返すことと、古い版の期待を当てたら FAIL することの両方を先に見てから使う。片方向だけだと、どちらの版でも同じ結果を返す探針を見逃す (実測)
- deploy の後に外から当てる書き捨ての探針に「期待する版」(新版と旧版) の切り替えを持たせ、deploy の前と後で両向きを当てた (実測)。deploy の前に手元の新版へ両向きで当てたときに、dead な行が2つ見つかった。1つは、表示の文言を決め打ちしたせいで対照の行が赤くなり、反対向きの行が別の理由で緑になった形。もう1つは「状態 X では出ない」の行で、旧版がその前のメッセージで接続を切るため、状態 X に入らないまま空虚に緑になった形。文言はページから読み、状態に入ったことを同じ行で示すように直したら、旧版と新版で割れる行だけがちょうど逆向きに割れた (実測)
- 手当て: 版で割れる行は、新版と旧版の両向きを deploy の前に当て、割れない行が両向きで緑、割れる行がちょうど逆に割れることを見る。否定の主張の行は、前提の状態に入ったことを同じ行で示す

## 道具が PATH に無い状態は空の一時ディレクトリで作る

hook の command 文字列や fallback をテストから `sh -c` で起こし、道具が PATH に無い状態を作るときに開く。プローブの置き場所の型は `~/.claude/references/observation.md` の「プローブの構造上の位置」節が持つ。

hook の設定を読んでその command 文字列をテストから `sh -c` で起こすと、「hook を外す」「fallback を壊す」変異がテストで赤になり、人が新しいセッションを開く確認を1回に減らせた。PATH は `/usr/bin:/bin` ではなく空の一時ディレクトリにする。CI の `/usr/bin` に task runner があると実物を起こす (実測)。

## 処理系の版は宣言だけでは拒まれない

リポジトリで処理系の版を pin しているときと、タスクランナーのレシピが処理系を起動するときに開く。

- 言語の処理系の版をリポジトリ直下の版ファイル1つに pin していても、手元の PATH で別の版が先に解決されると、タスクランナーのレシピはその版のまま最後まで緑で通った。処理系を起動するレシピの依存に「PATH の処理系の版が版ファイルと一致しなければ止める」ガードを置いた (実測)
- 版の pin には「どの版を使うか宣言する層」と「違う版を拒む層」の2つがあり、版ファイルと setup 系の action と mise は前者しか持たない。後者はレシピの依存に置く安いガードで足りた。just は1回の起動の中で依存の重複を除くので、多数のレシピに付けてもガードは1回しか走らない (実測。just --dry-run で数えた)
- ガードを「どの解決器が版を決めるか」の推論で作ると、推論の前提の外で穴が開いた。PATH の処理系だけを照合すると、バージョンマネージャの環境変数による上書きで、shim 越しのパッケージマネージャの中だけが別の版で走るのを通した。次にバージョンマネージャの解決を照合すると、本体が PATH に無く shim だけがある構成で照合ごと飛ばされた。起動の経路ごとに、実際に起動される処理系をその経路で直に測る形 (パッケージマネージャの `exec node --version`) にすると、どちらの構成でも止まった。1回あたり約0.2秒だった (実測)
- 手当て: 処理系の版を pin しているリポジトリでは、宣言だけで済ませず、違う版を拒むガードと、その取り付けをタスクランナーの解釈から導く検査を対で置く。ガードの照合の対象は、版を決める仕組みではなく、起動の経路ごとに実際に起動される処理系にする

## 時間で打ち切る子が sudo で孫を起こす

子プロセスを時間で打ち切る仕組みを書き、その子が sudo で孫を起こすときに開く。full chain の live smoke の理由は `~/.claude/references/observation.md` の「live smoke」節が持つ。

長時間の外部プロセスを回すタスクランナーには、既定でプロセスグループ単位の時間の上限と、グループ kill のあとに join する順序を共通部品として持たせる (実測)。

この既定には穴がある。子が中で `sudo -- sh -c "cmd1 && cmd2"` を起こす場合 (Playwright の `install-deps` がそう)、非 root からプロセスグループへ送った SIGTERM は root の sh と孫に EPERM で届かず、sudo は直接の子 (sh) にしか中継しない。孫が親を失ったまま残り、apt なら dpkg のロックを握る。単体テストを孫の sleep で代用すると緑のまま通るので、非 root + sudo の full chain で live smoke する。宛先は打ち切る直前に ps の pid/ppid で採った子孫の木にし、`sudo kill` でも送ると、sudo-rs と sudo 1.9 (use_pty) の両方で残党が出なかった (実測)。

## 失敗の経路を偽コマンドで通す

ユニットテストの無い shell-out の殻で、失敗の経路を確かめるときに開く。

ユニットテストを持たない shell-out の殻 (秘密の値を URL に入れて外部コマンドへ渡し、失敗の文言を出す) で、失敗の文言から秘密を伏せる処理を、失敗するだけの偽コマンドを PATH の先頭に置いて実物の秘密の取得から通しで動かして確かめた (実測)。

伏せる処理ありの本物と、伏せる処理を外した対照の2回を並べると、「秘密の形の文字列0件」が見ていないから0件ではないと示せた。対照ではちょうど1件出て、プレースホルダーは0件になった。出力は件数と秘密の形を伏せた行だけにし、対照のログは確かめたらすぐ消した (実測)。

秘密の形 (32桁の16進など) を grep で数えるときは、同じ形をした秘密ではない値 (公開の識別子) を先に除外しないと誤検出になる (実測)。
