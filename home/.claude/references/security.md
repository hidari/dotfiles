# セキュリティの一次実測

`~/.claude/CLAUDE.md` の「攻撃者が使える面を最小に保ち防御を 1 層に頼らない」カテゴリが持つ規範の、手当ての詳細と一次実測。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。

## charset 検証を名前空間の検証と兼用した事故

設定ファイルの行を `^\.[A-Za-z0-9._-]+$` で検証して eval へ流していた。

- `.git` は関数 `git` を生やして外部コマンドを shadow した
- `.claude-dev` は静的定義のランチャを潰した

どちらも charset を通っていて、警告も出なかった。

接頭辞を固定し、派生に使う接尾辞を予約することで塞いだ。

逆向きの兼用もある。Make の `$(filter prefix_%,$(VAR))` で名前空間を検査すると、filter は値を空白で語に切って語ごとに照合するので、空白を含む値 (`prefix_a other`) が通る。名前空間の検査とは別に、文字種の検査を置く (実測)。

## 多層防御の層の入力の出所

下の層の判定に渡す値を組むとき、レビューで「層がある」ことを確かめただけでは足りない。テナントの一致を判定する下の層へ渡す2つのラベルを同じ値から組んでいたので、判定は恒真になり層として効いていなかった。層があるかを見たレビューは見逃し、ラベルの出所を問うて初めて見つかった (実測)。判定に入る値がそれぞれどこから来るかを、層ごとに辿る。

## 検査・置換と切り詰めの順序

入力の検査や秘密の置換を、正規化や長さの切り詰めと別の層に置くと、順序で検査が外れる。

- 長さの検査より前に全文へ走る正規化 (置換) を足すと、それまで有界だった入力に無界の処理が入る。この回帰はセキュリティの観点のレビューが拾った (実測)。正規化を検査より前に置く変更のレビューでは、正規表現の後戻りの計算量を確かめる
- 外部コマンドの失敗の理由を下の層で長さの上限で切り、秘密の値を上の層 (呼び出し元) で置き換える構成では、秘密が切れ目をまたぐと前半だけが置き換わらずに残るはずである。置き換えは切る前、つまり切る層と同じかそれより下で行う (推測。コードを読んで順序を確かめただけで、またがる入力での再現はしていない。切れ目に秘密がまたがる入力を作れば安く確かめられる)

## 秘密のヘッダと redirect

fetch や HTTP クライアントの包みで、認証ヘッダや秘密の独自ヘッダ (認証プロキシの service token など) を全要求へ足すときに踏む。

fetch の仕様は、別オリジンへの redirect で Authorization 以外のヘッダを落とさない。全要求へ足す包みは、302を辿った先へ秘密を運ぶ。包みは接続先と同じオリジンにだけ足し、redirect は `manual` にする (実測)。

テストは別ポートのもう1台のサーバへ302を返させ、そちらに届いた件数0を、接続先が受け取った件数を対照にして pin する。オリジン判定の「scheme が同じか」の腕は、テストのサーバが全部平文だと消しても緑で通る。接続先を https として名乗り、同じ host とポートへ平文で要求を出して、腕を外す変異で赤になることを確かめる (実測、変異で赤を確認)。

同じ形はほかの経路にもある。

- Python の urllib の既定の opener は redirect を追い、Request に付けた Authorization ヘッダも redirect 先へ送りうる。Basic 認証を付ける採取の道具は、redirect を追わない opener にする (ドキュメントのみ、実測なし)
- ブラウザ自動化で保護下のフロントを開くとき、bypass のヘッダを context 全体の `extraHTTPHeaders` に付けると、別ドメインの API への要求にも秘密のヘッダが付く。route で配信先のホストへの要求にだけ付ける (仕組みからの判断で、漏れそのものは観測していない)

## 秘密の値を会話に出さずに扱う

`op read` などで秘密を読み、ヘッダ・環境変数・照合・失効の確認に使うスクリプトを組むとき、また秘密を表示する画面を撮るときに踏む。会話・ログ・subagent・transcript へ値が入っても警告は出ない。

### 値を渡す

書き捨てのシェルスクリプトの中で、`op read` の結果を直接ヘッダや子プロセスの環境変数へ流し、値を出力に載せない (実測)。次の形は、値がプロセスの引数にも画面にもファイルにも出なかった (いずれも実測)。

- API トークンは `curl --config -` へ標準入力から `header = "Authorization: Bearer ..."` の行で渡す
- DuckDB には鍵を環境変数で渡して SQL の中で `getenv` で読み、SQL 自体は標準入力から渡す
- GitHub の Environment の secret は `op read -n "<op の参照>" | gh secret set <NAME> --env <環境>` で入れる。`-n` は末尾の改行を付けない。成否はパイプの両側を見る (zsh の `pipestatus` の扱いは `~/.claude/references/observation.md` の「成否が隠れる」項)

### 値を出さずに確かめる

値の代わりに形と件数だけを出す (いずれも実測)。

- 用途の判別は、接頭辞・長さ・文字種 (32桁の hex か など) と、提供元の verify API の HTTP ステータスだけで足りた
- 実物の API 応答は、値ではなくキーと型だけを出す書き捨てのスクリプトを `.cache/` に置いて形を調べる
- 秘密の値どうしの一致は、両方を変数に読んで等値比較の結果だけを出すか、ハッシュの先頭だけを比べる
- 漏れた範囲は、元の transcript から値をメモリの上でだけ取り出し、ディレクトリ配下の全ファイルを bytes で照合して件数とパスだけを出す。環境変数の広がりも、値を含むファイルの数で数える
- ログに値が残っていないことを件数で言うときは、値ごとに合成の1行を対照に置き、「0件」と「見ていない」を区別する (判定の規範は CLAUDE.md の「0 件」「空」「緑」の項)

### 値が空だと全行に一致する

値を変数に読んで `grep -cF "$VAR"` で出現を数えるとき、参照の解決に失敗して値が空だと、空のパターンが全行に一致して件数がログの総行数になる。`grep -v` 系や「0件なら健全」の判定では偽の緑になりうる。数える前に変数の長さ (非空であること) を検査し、件数と並べて出す。長さのガードで実際に止められた (実測)。

### 失効と入れ替えを HTTP のステータスで確かめる

401という数字だけでは、「失効したトークンを拒んだ」と「トークンが届いていない」を区別できない。`op read | sed | curl --config -` のようにパイプで渡すと、左の `op read` が失敗しても右の curl はトークン無しで走り、後者の401が返る (実測)。

- 本文で見分ける。アプリが返す固定の本文は、資格情報を照合して弾いた場合とヘッダが無い場合で文言が違うので、全部401でも「照合まで届いて弾かれた」と「別の理由の401」を区別できた。401のときだけ固定の本文を出す probe にする (実測)
- 対照を置く。ヘッダ無しの組を対照にすれば、正の対照 (200) が取れない入れ替え前でも測定が成立する。削除するトークンは、消す前に同じ probe を一度回して「生きていて広い権限を持つ」ことを記録しておくと、削除後の401を削除の証拠として読める。権限を絞った新しいトークンが403、削除した古いトークンが401と並べると、「トークン自体の拒否」と「権限の外の拒否」を区別できた (いずれも実測)

### 画面とスクリーンショット

画面に文字で出た秘密は、スクリーンショット1枚で transcript に入る。

- 設定の画面のスクリーンショットに、画面に並んでいた Webhook の URL (知っていれば投稿できる秘密) の一部が入った。秘密の値を表示する画面では撮らず、名前で要素を探して押し、読むのは URL とメールアドレスを置換した文字だけにする (実測)
- 漏れた Webhook は、末尾を削るなどの編集では無効にならない。削除して作り直す (実測)
- 利用者に DevTools のスクリーンショットを頼むと、リクエストヘッダの `Authorization: Basic` の値まで写り込むことがある。頼むときは General の欄だけを指定する (実測)

## 見えない文字と書式文字

外から来た値を端末へ出すとき、またソースや入力の中の見えない文字を拒否する集合を作るときに踏む。

制御文字だけを置き換えても、Unicode の書式文字 (bidi の上書き、ゼロ幅、BOM) が残ると、行の並びを入れ替えられたり、別の値が同じ見た目になったりする。Unicode プロパティの Cc と Cf を1本の正規表現で当てると両方を覆えた。テストで改行を剥いでから検査すると、改行の漏れを見逃す (実測)。

拒否する集合は文字の列挙ではなく Unicode の性質で作る。列挙はレビューのたびに穴 (タグ文字、異体字セレクタ、クメール文字の母音記号など) が見つかった (実測)。

- ソースの検査は Default_Ignorable_Code_Point (JS の正規表現なら u フラグで `\p{...}`) に、その集合に入らない U+2028・U+2029・U+FFF9〜FFFB を足す形が漏れにくかった。入れる前に、追跡下のテキストで一致が0件であることを確かめた (実測)
- 性質に寄せたあとで外の書式制御を1件だけ名指しで足したら、同じ理由が当てはまる Cf の文字が29個残っていた。名指しの例外を1件でも足したら、その理由が当てはまる一般カテゴリ全体を数え、基準を一般カテゴリと性質の和 (Cc・Zl・Zp・Cf・DI) から通すものだけを引く形にする (実測)
- 書記素の結合子 U+034F を文字クラスに直接入れると、Biome の noMisleadingCharacterClass が止める (実測)
