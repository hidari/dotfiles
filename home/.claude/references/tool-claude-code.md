# Claude Code の harness の一次実測

`~/.claude/references/tools.md` が名指しする、Claude Code の harness (auto mode の分類器、/goal、Workflow、ツールの入力、MCP の読み込み) の事実と手当て。

規範の遵守そのものには要らない。下の各節の場面に入るとき、harness の挙動が想定と食い違ったとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。どの節も版に依存するので、節に添えた版と報告日を見てから使う。記録の無いものは「版は未記録」「報告日は未記録」と書く。

subagent と Workflow へ委ねるときの判定は `~/.claude/references/delegation.md` が、ブラウザの MCP の挙動は `~/.claude/references/testing-e2e-tools.md` が持つ。ここには書き直さない。

## 背景のプロセスを起動して止める

dev サーバなどの背景のプロセスを Bash で起動・停止・kill するとき、GUI のスパイクを起動するときに踏む。報告日は未記録、Claude Code の版は未記録。

- 通った形: 背景のプロセスの起動、子プロセス、kill を1つの Bash コマンドに詰めず、サーバは run_in_background で起動し、curl の `--retry-connrefused` で待ち、TaskStop で止め、書き換えは Edit で行う形に分けると通った (実測。分類器の拒否の理由は推測)
- 1つに詰めて拒否された形は次の5つで、そのうち3件は auto mode の分類器によるものと記録されている
  - dev サーバの起動と foreground の sleep と pkill の1行
  - プレビューサーバの起動と kill
  - MCP サーバの子の webServer (vite) の kill
  - dev サーバの再起動とソースの書き換えを1本の Python にまとめた変異の実行
  - user スコープの deny の `Bash(pkill:*)` が、複合コマンドの一部に当たって全体を拒否した
- プロセス名での kill: 変異ごとに開発サーバを起動し直すスクリプトのプロセス名の pkill と、`pkill -f` が auto mode に拒否された。開発サーバをバックグラウンドのタスクとして起動して TaskStop で止めると、プロセス名で kill せずに済み、子プロセスも残らなかった (どれも実測。停止の後に該当プロセスが0件であることを数えた)。他の作業の同名プロセスを巻き込みうる操作は止められると見てよい、という見立てが添えられていた
- GUI のプロセス: 自分が起動した GUI のプロセスでも、kill / pkill がよそのプロセスへの干渉として止められた。GUI のスパイクは最初から `--quit-after` と Cmd+Q (GPUI はメニューを作らないと Cmd+Q が効かない) と「最後の窓を閉じたら終わる」を付けておく (実測)
- auto mode ではプロセスを外から止められないため (実測)、Rust の GUI のスパイクの雛形にこれらを最初から入れておく (提案)

止めるものを自分が起動したものに絞る判定は `~/.claude/references/host-environment.md` の「起動したものを使い終わったら落とす」節が、MCP が残す webServer の止め方は `~/.claude/references/testing-e2e-tools.md` の「MCP が webServer を残してポートを握る」項が持つ。

## auto mode の分類器が止める操作

auto mode でリリース・本番のデプロイ・シークレットの書き込み・force push・CLI の拡張の導入・Claude Code の設定の編集を打つとき、それらを含む手順や skill を書くときに踏む。報告日は未記録、Claude Code の版は未記録。

- 止まったら: 回避を探さず、`! <コマンド>` の形でユーザーに打ってもらうと1往復で進む (実測)
- 本番のデプロイ (Production Deploy): ユーザーが「最後まで」と指示していても、タグを push してデプロイする release の recipe が Production Deploy として拒否され、会話の中の指示は本番デプロイの許可として扱われなかった (実測)。本番の deploy の workflow_dispatch を auto mode の Bash から打ったときも止まった (実測)
- シークレットの書き込み (Secret-Store Writes): 本番のシークレットの差し替え (1Password の参照から GitHub の environment のシークレットへ置く recipe) を auto mode の Bash から打つと止まった (実測)
- 許可した recipe: リリースの手順を just の recipe に閉じ込め、その recipe の名前だけを permissions.allow に完全一致で載せると、auto mode が生の tag push と gh api の設定変更を拒否する中でも、許可した recipe は通った (実測)
- force push (Git Destructive): 並行する PR を先に squash マージしたあとで、push 済みの別の PR のブランチを main へ rebase すると force push が要る。分類器は `git push --force-with-lease` も Git Destructive として止めるので、ユーザーに `!` で打ってもらうことになった。push 済みの PR を後から main へ寄せる見込みがあるなら、rebase の前に経路 (ユーザーの force push か、別の方法か) を決めておく (実測)
- 拡張の導入: `gh extension install` は分類器に止められた。ユーザーに `!` で打ってもらう前提で手順を組む (実測)
- 設定の編集 (Self-Modification): 自分の settings.local.json の MCP の項目を Edit で直そうとすると Self-Modification として止められ、ユーザーに手で直してもらう必要があった (実測)。プロジェクトの .claude/settings.json の permissions を Bash (python や jq) で書き換えると、絞る方向でも分類器が自己改変として止め、Edit ツールで出し直すとユーザーの承認を経て通った (実測)。前者は Edit でも止まった settings.local.json、後者は Bash で止まり Edit の承認で通った settings.json である
- 検査の変異のために settings を書き換えたいときは、レシピの本文を取り出して写しに向けて走らせると、本物を触らずに済む (実測)
- 自律を想定するなら、release の recipe を許可する permission rule をリポジトリ単位で持つか、シークレットの差し替えや本番の deploy を含む release 系の skill に「auto mode では分類器が止めるので、その時点でユーザーに `!` での実行を案内して止まる」と最初から書いておく (提案)。permission rule で通す側は、防御を1層にしない観点との兼ね合いを見て決める

squash で先に入った PR の上のブランチを載せ替える前にツリーのハッシュを比べる形は `~/.claude/references/git-workflow.md` の「squash マージ後の取り込み確認」節にある。

## /goal に渡す DoD

/goal に渡す DoD や「止まってよい条件」を書くとき、無人の実行に渡す spec を点検するときに開く。報告日は未記録、Claude Code の版は未記録。

/goal の Stop hook (評価器) は DoD の各項目を transcript の証拠で判定するので、取りこぼしに強い。そのかわり文面を字句どおりに照合し、満たせなくなった条件があると閉じるまで同じ判定を繰り返す (実測)。DoD には閉じられる条件だけを書く。

### 後から取り返せない手順の条件

- マージ前のゲートを「増分を自分で読み直す」で済ませ、「CI が success なら Merge OK」という条件付きの結論のままマージしたところ、後から満たせない条件を Stop hook が評価し続け、ユーザーが /goal clear するまで止まらなかった (実測)
- 後から取り返せない手順の条件には、確かめ方を具体的に書く。例: マージのコマンドの直前に、CI の結果を見た後の無条件の Merge OK を出す (提案)
- DoD の「X を最終報告へ写してから Y を消す」を、最終報告でまとめて写すつもりで先に後片付けをして逆順にした。最終報告は会話の最後に出すので、構造的に必ず消す方が先になる。判定役は順序で読むため取り返せず、ユーザーの /goal clear が要った (実測)
- 「写してから消す」の形の項目は、消す前に写しを中間の成果物として書き出す (提案)

### 文面どおりには満たせなくなる条件

- 両立しない項目: DoD に「作業ツリーはクリーン」と「記録の追記のコミットは人の指示を待つ」を同時に入れると両立しない。Stop hook は文面をそのまま照合するので、免除の文があっても止め続け、AskUserQuestion で人の判断を受けて抜けた (実測)。人の判断で変わる状態を1項目に寄せ、他の項目がそれを前提にしないようにする
- 実装の細部: レビューで export を外すなど DoD の実装の細部を良い方向へ変え、ユーザーがそれを承認しても、hook は満たされないまま止め続け、ユーザーの /goal clear でしか抜けられなかった (実測)
- DoD は実装の細部 (「X を export する」) ではなく満たすべき性質 (「重複定義が0」「外から使える」) で書き、「ユーザーが明示的に決めた逸脱は、その決定に従ったと報告すれば満たしたものとする」の1行を入れる (提案)。上の両立しない項目の例では免除の文があっても止め続けたので、この1行が効くかは確かめが要る
- ゆれる観測: DoD に「公開ページの前後一致」と書くと、仕組み上ゆれるページ (起動時刻を種にした並び、リクエストごとに変わる値) で文言どおりには満たせなくなる (実測)
- 観測がゆれる検査は、何をどこまで一致させるか (除外する箇所) まで条件の文に書く。会話の中でユーザーが基準を変えても評価器は文言で判定する (提案)
- 空でも真になる条件: 無人の実行 (/goal など) に渡す spec は、通常の builder check に加えて「聞けずに走る人」の観点で点検する。DoD には「止まる条件に当たって報告した」を正しい終わり方として含め、「子が全部 closed」のような空でも真になる条件は ID の集合で書く (提案。根拠として、計画に足りない点を2体の agent に挙げさせた点検の実測が添えられている)

### ユーザーの操作を待つ条件

- マージがユーザーの `!` の操作のリポジトリでは、goal の実行中にマージを待てない。handoff からの再開を、マージ準備 (マージの dry-run) を終点にした1本目と、マージ後の2本目に分けた (実測)
- DoD の「止まってよい条件」を待ちの原因の種類 (承認のタイムアウト) で書いたため、分類器の拒否でユーザーの操作を待つ間、Stop hook が二十数回止め続けた (実測)
- 条件は原因ではなく「回避せずにユーザーの操作を待っている状態」で書き、本番を触る goal では必ず入れる (提案)
- 止まってよい条件に「auto mode の分類器が必要な操作を止めた」を入れたまま、判定が返らない一時エラーで止まると、評価器は条件に当たらないとして戻した。評価器は「拒否された」と「判定が返らない」を別物として読む (実測)
- DoD に「分類器が拒否した (deny の判定)」と書き、判定が返らない一時エラーは時間を置いて再試行し、続けて10回返らずにターンが止まったときだけ止まってよい、と分けて書く (提案。10回という回数を含めて実測と申告)
- 評価器は DoD の停止条件も文言で判定する。AskUserQuestion の「後でやる」という答えは「手作業を後日に回すと言った」と認められなかった。条件と同じ言葉の選択肢で聞き直すと通った (実測)

## Workflow と subagent の戻り値を JSON で読む

Workflow の結果ファイルや subagent の戻り値を JSON として parse するとき、subagent に JSON の結果を返させる指示を書くときに踏む。報告日は未記録、Claude Code の版は未記録。

- Workflow の結果の通知が指す出力ファイルを JSON として読むと Extra data で失敗した。各 agent の戻り値は journal.jsonl を読むほうが確実だった。journal の label は null で、どの観点の結果かは戻り値の中身で見分けた (実測)
- Workflow で subagent の返り値を受けると、内容が instruction-shaped と判定されたときに harness が1行目に注意書きを足すことがあり、JSON をそのまま parse すると失敗する。1行目の注意書きを外した本文を、agent 自身に書かせた scratch のファイルと deep-equal で突き合わせてから使った (実測)
- subagent に JSON の結果を返させるとき、scratch にも同じ JSON を書かせ、sandbox の中で JSON.parse が通るのを確かめてから返させると、壊れた結果の返却が止まった。1体目は JS の断片が混じった JSON を返し、指示を足した2体目からは全件が parse でき、scratch の中身とも一致した (実測)

複数の agent の構造化出力を突き合わせるキーの決め方は `~/.claude/references/delegation.md` の「構造化出力どうしの突合キー」節が持つ。

## ツールが `\u` のエスケープを解いて書く

Edit・Write・Bash のツールで、バックスラッシュと u と4桁の16進で書くエスケープを含むソースを書くとき、そのエスケープが残っているかを grep で確かめるときに踏む。報告日は未記録、Claude Code の版は未記録。

- 機序: Edit ツールは new_string の中の `\uXXXX` を JSON のエスケープとして解き、生の文字をファイルに書く (実測)。Write でも、Edit の置き換え後の文字列でも、元のソースにあった ASCII のエスケープ (U+200B の例) が、見えない文字そのものに化けて書き込まれた (実測)。Bash の heredoc (引用符付きでも) に書いたエスケープも、ファイルに入る前に見えない文字そのものに化けた (実測)
- 気づきにくさ: U+3040 のような未割り当ての文字は見えないので、差分を目で見ても気づけない。`od -c` と、エスケープの文字列での grep が0件になることで気づいた (実測)。実行時の値は同じなのでビルドもテストも緑のままで、ゲートのレビューが差分の削除行と od のバイト列で見つけた例もある (実測)
- 書き捨てのファイルへ Edit ツールで、U+3040 から U+30FF までの範囲をこのエスケープで書いた文字クラスを書くと、`od -c` では `343 201 200` (U+3040 の生のバイト) と U+30FF の生の文字が入っていて、`u3040` での grep は0件だった (2026-10-23に確かめた)
- grep で確かめるときの罠: Bash ツールのコマンド文字列も、同じくエスケープを解いてからシェルへ渡す。バックスラッシュと u で始まるエスケープをパターンに書いた grep は生の文字を探すことになり、正しくエスケープが残っているファイルに0件を返し、生の文字が入ったファイルには1件を返した。「書いた後にエスケープの文字列で grep して残っていることを確かめる」形は、Bash ツールから打つと正反対の答えになる。バックスラッシュを含まない `u3040` のようなパターンと、Python で code point を数える形では正しく数えられた (2026-10-23に確かめた)
- 書くときの手当て: `\u` を書かない形 (正規表現なら Unicode プロパティ) にするか、Python の read と replace で書く (実測)。スクリプトの中でバックスラッシュを `chr(92)` で組み立てて書き、書いたあとでファイルを走査して確かめる形もある (実測)
- 直すときの手当て: 修正案の文面を写さず (写すとまた見えない文字が入る)、スクリプトでバイトを指定して置き換える。テストでは `String.fromCodePoint(0x200b)` のように ASCII だけで書くと化けない (実測)
- ソースに見えない文字 (U+200B などのゼロ幅の文字) がそのまま入っていないことを、リポジトリの衛生の検査 (lint か ast-grep) で止める。エスケープが化けても緑のまま通るため (提案)

## プロジェクトの MCP サーバが一覧に出ない

プロジェクトの `.mcp.json` のサーバが `/mcp` や ToolSearch に出てこないとき、`.mcp.json` や settings.local.json のテンプレートを配るときに開く。報告日は未記録、Claude Code の版は未記録。

- セッションの途中で作ったとき: セッションの途中で作った .mcp.json のサーバは /mcp に出てこなかった (実測)。プロジェクトの MCP サーバは起動時にしか読まれない様子で、Playwright Test Agents を使うにはセッションの再起動が要る (推測)。MCP の要らない配線を先に WIP コミットしてから再起動すると、待ちが無駄にならない
- 無効化のリストに入っているとき: プロジェクトの `.mcp.json` にある MCP サーバが ToolSearch にも `/mcp` の一覧にも出なかった原因は、リポジトリの `.claude/settings.local.json` の `disabledMcpjsonServers` に名前が入っていたことだった。設定の各スコープ (user の settings.json、`~/.claude.json` のプロジェクトの項目、リポジトリの `.claude/settings*.json`) を順に grep して見つけ、`~/.claude.json` の側の同名のリストは空だった。項目を消して `/mcp` から reconnect したら、ツールが出てきた (実測)
- 設定ファイルの `disabledMcpjsonServers` に入ったサーバは `/mcp` の一覧に出ないので、そこから有効にできなかった。`~/.claude.json` の側の無効化とは扱いが違う (実測)
- リポジトリへ配る settings.local.json のテンプレートに `disabledMcpjsonServers` が入っていないかを確かめ、入れるなら「`/mcp` に出なくなる」ことを手順書に添える (提案。推測)

Test Agents を取り付けた後の再起動は `~/.claude/references/testing-e2e-tools.md` の「取り付けたあとの生成物」項にもある。
