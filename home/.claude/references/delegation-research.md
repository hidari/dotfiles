# 調査と点検の委譲の一次実測

`~/.claude/references/delegation.md` の続き。調査や点検を subagent や Workflow に委ねて、その結果を文書や計画へ写すときの観測を持つ。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。

## 調査の verified の札

外部の文書の事実を subagent や Workflow に調べさせて設計文書へ写すとき、レビュアーや批評役の所見と修正案を採るときに開く。委譲先の報告を検証済みの事実として扱わない判定そのものは `~/.claude/CLAUDE.md` の観測のカテゴリが持つ。

- 症状: subagent の Web 調査が「確認済み」とした記述が出典のページに無い言い回しで、別のレビューの agent が出典を開き直して否定した。検索の要約から持ち込んだベンダーの changelog や制限の表も、ページを開いて文言を確かめると主張の一部はページに無かった (どちらも実測)
- 手当て: 調査の verified の札は、出典を開き直すまで信じない (実測)。外部の文書の事実を設計文書へ入れる前にページを開いて文言を確かめる手順を、subagent への指示の定型に入れる
- Workflow による並列の調査で、出典の URL と原文の引用と確信度 (verified-primary / secondary / inferred) を schema で必須にすると、推測と一次情報の区別が結果に残り、どの行を自分で確かめ直すべきかが決めやすかった (実測)
- 調査レポートを最新化するとき、時間で変わる主張を調査役に書き出させ、一次情報で確かめた差分のリストを返させて、別の検証役が1件ずつ独立に判定するワークフローにした。検証役は確認できなかった出典を見つけ、誇張も削った (実測)
- docs の同じ事実 (無料枠の保持日数) がページによって3日と7日で食い違っていたので、出典はページと読んだ日付まで書く (実測)
- 前のセッションの subagent の抽出 (未検証の調査報告) を、計画に書く前に領域ごとの検証の席で1つずつコードに当て直すと、訂正が5席で合わせて約20件、計画の前提を変える未決の点が約40件出た。検証の席に「報告の主張を再現し、違えば訂正を返す」と「設計の判断とコードが噛み合わない点を open_questions に返す」を分けて書かせると、計画の文面に入れないと Interfaces が書けない決定が網羅的に浮いた (どちらも実測)
- レビュアーの所見の根拠が手元の生の資料と食い違っていたが、結論の一部は正しかったので、結論だけを採って根拠は採らなかった。所見の前提は一次資料で確かめる (実測)
- リリース前の消費側の批評役が書いた修正案 (「git add すれば戻る」) が誤っていた。批評役の指摘は正しくても、修正案は実装とテストに照らしてから採る (実測)

## 設計書を点検させる観点

設計書や spec を書き終えて、計画や無人の実行に渡す前に開く。

- 設計書を書いたあと、別の subagent に「計画を立てるのに足りない点」だけを挙げさせると、設計書の中の2つの値の組み合わせが、外部 API に課金したあとで捨てる経路を作ることを見つけた。返った数字は自分で数え直して再現してから採った (実測)
- 無人で走らせる前の spec の点検を、性格の違う2体の subagent に任せた。1体は「計画を立てる人」、もう1体は「人に聞けないまま最後まで走る人 (止まる所、完了を自分で判定できない所、隠れた前提を挙げる)」 (実測)。指摘の重なりは半分ほどで、残りはそれぞれにしか出なかった。「聞けずに走る人」の側は、許可設定の書き換えに人の承認が要ること、検証データがもう無いこと、性能の要件の合否の式が無いことなど、無人の実行が止まる所を具体的に挙げた (実測)
