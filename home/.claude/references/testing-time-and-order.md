# 時間と並行と実行順に依存するテストの一次実測

`~/.claude/rules/testing-practices.md` の「テストが緑であることを、仕様を守れている証拠にしない」カテゴリのうち、時間切れ・タイムゾーン・並行・テストどうしの実行順に依存するテストが、手元の条件では黙って緑になる形の、手当ての詳細と一次実測。入口は `~/.claude/references/testing.md`。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。

## 時間切れのテストの代役 CLI

時間切れを確かめるテストの代役 CLI を `sleep` だけのシェルスクリプトにすると、子を殺しても孫の sleep が出力のパイプを持ち続けて打ち切りが遅れる (`exec sleep` にする)。本体の側は子をプロセスグループの頭にし、上限でグループごと kill してから読み手を join する (推測)。テストは孫がパイプを握る形 (`sh -c 'sleep 600 & sleep 600'`) にして外側の期限を付けないと「子だけ kill」の実装でも緑になる (実測。変異で赤を確かめた)。グループごと止まるかは、実際に走らせて `ps -o pid,pgid,ppid` で孫の pgid が子と同じか (孫が setsid していないか) を確かめてから設計に乗せる。子が sudo で孫を起こすとグループへの kill が届かず、孫の sleep の代役では緑のまま通る穴は `~/.claude/references/observation-checks.md` の「時間で打ち切る子が sudo で孫を起こす」節にある。

## タイムゾーンに依存する日付処理

タイムゾーンで挙動が変わる日付処理の pin は、テスト内で `vi.stubEnv('TZ', ...)` により UTC 以外を当て、「ローカル日付と UTC 日付がずれている」ことを確かめる前提テストを並べると、UTC で動く CI でもローカル時刻へ戻す変異を赤にできた。stubEnv を外す変異で前提テストが赤になることも確かめた (実測。報告日は未記録、vitest の版は未記録)。

手元が日本時間のホストでは「端末のタイムゾーンで割り当てる」変異が見えない。テストを TZ を切り替える仕組みで包み、さらに夏時間の切り替えの日を入力に入れないと、setDate(+1) と +24時間が3つのゾーンのすべてで一致して見分けられない。ずれるゾーンを当てても、入力の日が差の出ない日なら区別できない (実測。node で計算して確かめた)。

TZ を切り替える道具が持つゾーンの一覧はただの配列なので、describe.each でゾーンを回しても、本体を切り替えの関数で包まなければ手元のゾーンのまま3回回るだけになる。計画のレビューで見つかった。表の名前だけが変わって条件が変わらない形で、上の前提テストを並べていれば捕まる (実測。コードを読んで確かめた)。

## 行の確保と二重送信の防止

「条件つき UPDATE で行を確保する」関数を「select で状態を読んでから id だけで update する」形に壊す変異は、単一セッションの決定表を全部緑のまま通し、2セッションで同じ行を取り合う並行テストだけが赤になった。確保・二重送信の防止を pin するなら、並行テスト (A がロックを持って待ち、B がロック待ちに入る形) を必ず置く。決定表の全列挙だけでは競合は守られない (実測)。

## テストどうしの漏れと実行順

負荷の高いときだけ落ちるテストが、前のテストの非同期処理の漏れ (完了を待たずに終わり、次のテストの beforeEach の後にモックを呼ぶ) だと読めたとき、プロダクトの処理に「1回目は短く、2回目は長く」の非対称な遅延を一時的に入れると決定的に再現できた。一律の遅延では再現しない。toHaveBeenCalledWith は「どれか1回が合えば通る」ので、漏れと本物が同じ poll の間にそろうと通ってしまうため。受け取った値が直前のテストの期待値と一致していたことが、漏れだと読む手がかりになった (実測)。

E2E が spec どうしで状態を共有していないことは、db-reset を挟まずに全件を2回続けて流して確かめた。1回目の緑は spec の実行順に助けられていただけだった (実測)。
