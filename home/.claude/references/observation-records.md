# 記録と文書へ書くときの観測の一次実測

`~/.claude/references/observation.md` の「報告を網羅と読む」節の続き。測った値や一次資料の値を文書へ写すとき、複数のファイルへまとめて書き換えや削除を当てるときの観測を持つ。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。

## 測定の結果を文書へ書く

測定の結果や数値を、文書・Issue・PR の本文へ書くときに開く。

- 症状: 測定の結果を文書へ書くとき、ログに無い時刻を推定で書いたり、区間を取り違えたりした (実測)。自分で書いた表には、中央値の取り方、外れ値の原因の取り違え、最大値の1秒のずれの誤りが3件あり、書いた本人の見直しでは見えなかった (実測)
- 手当て: 書いた数値を、結論ではなく一次のログだけを渡した独立の役に導き直させる。生のログだけを渡した独立のレビュアーは14件の数字のうち6件を「導けない、言い過ぎ」と返し、subagent にログから導き直させると上の表の3件が見つかった (どちらも実測)。Issue に配信と smoke の記録を書く前に、主張ごとに ID を振り、証拠の置き場ごとの検証役と取りこぼしを探す critic を立てて一次ログと突き合わせると、引き継ぎ書とメモリから写した値の食い違いが6件 (別の run の件数、同じ言葉が別の検査を指す、読み取り専用と書いた SQL に書き込みが混ざる) 出た (実測)。証拠のログを消す前に、この突き合わせを済ませる
- 記録から上限しか言えないものは上限で書く (実測)
- 測った数字の範囲を、前のセッションの数字とこのセッションの数字を混ぜて書くと、critic に「一次資料と合わない」と指摘された。範囲を書くときは出所 (どの回の測定か) を一緒に書く (実測)
- 1回だけの測定で「keepalive で接続が保たれる」と書きかけ、2回目の測定で keepalive のある接続も不規則な時刻に切られることが出た。過去の生存の記録も、観測の窓の中でたまたま起きなかっただけと読める。長時間の接続についての主張は、窓の長さと回数を添えて書く (実測)
- PR の本文に数値を写すとき、測り方 (どの版か、単独か通しか) を落とすと、数値は正しいまま主張の範囲が広がる。本文を書いたあとで一次の記録と照らして見つけた (実測)

## 一次資料も版と日付で古びる

ツールの既定値や外部サービスの上限を、文書から引用するときに開く。版を上げて主張を確かめ直す手当ては `~/.claude/references/observation.md` の「検索キーの偽陰性」項が持つ。

- ツールの最新のドキュメントの既定値 (例: pnpm の minimumReleaseAgeStrict は値を明示すると true) が、リポジトリが固定した旧い版には存在しないことがあった。版付きのドキュメント (例: pnpm.io/10.x/settings) を引くか、固定した版で実測する (実測)。設定値の既定や挙動を引用するときは、どの版のドキュメントの記述かを添える
- 設計書に書き写した Cloudflare Workers の上限が古くなっていた。一次資料から写した外部サービスの上限 (容量・メモリ・時間) には取得した日付と URL を添え、設計を左右する場面では原文を読み直してから使う
- docs の同じ事実 (無料枠の保持日数) がページによって3日と7日で食い違っていたので、出典はページと読んだ日付まで書く (実測)

## まとめて書き換える

複数のファイルへ sed やスクリプトでまとめて置換や差分を当てるときに開く。

- 複数のファイルへの書き捨ての置換や差分の適用は、置換ごとに元の文字列 (原文の抜粋) が本文にちょうど1件あることを確かめ、全部が当たってから書き込み、当たらなかったものを報告させると、半端な書き換えが残らなかった (実測)
- 調査役に、追記を指定した抜粋の行の後ろへ挿入させると、空行なしで直前の段落にくっつき、Markdown の上では同じ段落になった。挿入の後に空行で分ける後処理が要った (実測)
- 同じ文が別の箇所 (字下げまで同じ) にもある設定ファイルで sed のパターン置換を使ったら、直すべきでない側まで書き換えた。反証役が「そちらは残す」と明記していても、置換の範囲には効かない。行番号を指定するか、1箇所ずつ Edit する (実測)
- 空白と括弧を含むパスの Markdown リンクを sed でまとめて山括弧の形に直したところ、タイトルに括弧がある1行だけ照合が外れた。直したあとにリンク先が実在するかを全件数え直して見つけた (実測)。同じ作業で、awk の index で列を揃えようとして空白の数を1回目は数え間違え、直したあとに列を数え直して気づいた (実測)
- 要件定義資料の63項目と実装の突き合わせを、節ごとの監査役10体と各レーンの反証役10体の Workflow で回し、結果の JSON からスナップショットの文書をスクリプトで生成した (実測)。結果の文書を手で書かず構造化した結果から生成し、コントローラの訂正を「旧の文字列・新の文字列・現れる回数」の一覧で当てて回数を assert すると、訂正の取りこぼしと当たりすぎが止まる。ID の集合が定義元から機械的に抜いた集合と一致することも生成の時に assert した。指摘が来ても生成し直すだけで全体に効いた (実測)

## 書き換えの対象外が変わっていないことを確かめる

一括の書き換えや削除を当てる前後と、formatter の `--write` を作業ツリー全体へかけるときに開く。判定そのものは `~/.claude/CLAUDE.md` の観測のカテゴリの「記録されたメタデータ」の項 (一括操作の前後) が持つ。

- 一括置換の前後で、置換の対象外の追跡ファイル全部のハッシュを突き合わせ、境界の取り違えによる偽陽性の破壊 (長い数字列や UUID の一部) が0件であることを件数付きで示した (実測)
- ホスティングの管理画面で見つけにくい環境変数を REST の書き捨てスクリプトで消すとき、既定は dry-run、対象の本数が期待と一致しなければ1本も消さない、消した後に引き直して対象外の行の id の集合が不変であることを確かめる形にした (実測)
- `biome check --write .` は git の ignore だけを除くので、未追跡のまま置いている文書も整形の対象に入る。整形の対象が広がる更新の前に、触ってはいけない未追跡のファイルのハッシュを取って前後で比べる (実測。報告日は未記録、Biome の版は未記録)
