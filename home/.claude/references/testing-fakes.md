# Fake と stub と fixture の作り方の一次実測

`~/.claude/rules/testing-practices.md` の「テストが緑であることを、仕様を守れている証拠にしない」カテゴリと、`~/.claude/CLAUDE.md` の語彙が定める契約テストについて、Fake・stub・fixture の作り方が pin を殺す形の、手当ての詳細と一次実測。入口は `~/.claude/references/testing.md`。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。

## Fake が本物の条件を写していない

fake が本物の通知や出力の条件を写していないと、その条件に依存する機構の pin が dead になる。

- fake の ResizeObserver を「最初の通知は新しく observe した要素にだけ届ける」形にすると、本物の性質 (箱の大きさが変わらないと通知しない) に合い、「中身が変わったら観測をつなぎ直す」実装の変異を赤で捕まえられた。全 observer へ届ける素朴な fake では、つなぎ直しを外す変異が緑で残る (実測)
- CLI を PATH の先頭の stub で差し替えるテストで、stub が `--json` で頼まれていない項目まで返していると、「FIELDS から status と conclusion を消す」変異が全部緑のまま通った。本物の gh は頼まれた項目しか返さない。stub が頼まれた項目へ削って返すようにすると、同じ変異が14件のアサーションで赤になった (実測)。本物の CLI が出力を絞る引数 (`--json` の項目、`--limit` など) を stub にも解釈させ、argv の pin と並べる (提案)

## 記録の時機と引かれた回数

E2E の Fake で「重ねて呼ばれていない」を pin するとき、記録を await の後で積むと遅れて届いて2回目を見逃しうる。呼ばれた回数を関数の先頭 (await より前) で同期に数えると、ガードを外す変異で確実に赤になった (実測)。

「上限を超えたら読みを止める」の pin は、結果だけでなく代役のストリームが引かれた回数まで見る。結果だけだと、読み切ってから捨てる実装が緑で通る (実測)。

## 2つの出力を一緒に動かす Fake

テストの Fake が2つの出力 (判断の値と、その副作用のカウンタ) を同じ条件で一緒に動かしていると、実装が読む先を片方からもう片方へ移しても、旧実装へ戻す変異が緑のままになる。Fake に2つを食い違わせる口を足し、2方向の例で赤を確かめて塞いだ (実測)。読む値を移す変更では、移す前と後の値を Fake が別々に置けることを確かめて2方向の例を置く (提案)。

## 外部 API の契約テストの fixture

外部 API の契約テストの fixture は、実 API の応答から鍵の集合を写して作る (値は伏せる)。mockito の手書きの最小の JSON が片方の綴りしか持っておらず、DTO の受け皿の食い違いを契約テストは緑のまま通した (実測)。fixture を書き換えた前提 (応答の形) は実サービスの観測テストで裏取りし、厳しくした判定が実サービスで確信のある答えを返すことを応答の形の証拠にする (提案。実サービスでの裏取りは推測で、報告の時点では実行中)。

実物の API の応答の形を、値を出さずに調べる手当ては `~/.claude/references/secrets.md` の「値を出さずに確かめる」節にある。その形で実物を読むと spec の想定と実物の形が食い違い、実物を読んだ段階でモデルを作り直した (実測)。外部 API を正規化して検査するコードの計画では、パーサを書く前のタスクに「実物の応答の形 (キーと型だけ) を読む」手順を入れ、spec の想定する形を実測で確かめてからパーサの形を決める (提案)。
