## zsh の `=` で始まる語

zsh で `=` から始まる語 (区切りの `echo ====` など) を引数に書くときに踏む。Bash ツールのシェルが zsh のときも同じ形で踏む。

- 機序: zsh は `=` から始まる語を `=cmd` のコマンドパス展開 (EQUALS オプション) として解釈し、`echo ======` は `===== not found` でコマンドごと失敗する (実測)
- 症状: 区切りの echo が複合コマンドごと exit 1になり、`&&` でも `;` でも後ろのコマンドが走らず、後続の出力が黙って消える (実測)
- 再現: `zsh -c 'echo ====x; echo after'` は `echo after` も走らず rc 1になる。bash では両方が出て、zsh でも `"====x"` と引用すれば通る (2026-10-23に zsh 5.9 で再現)。Bash ツールで `sed ...; echo =====; sed ...` を打ったときも `(eval):1: ===== not found` が出て後ろの sed の出力が出なかった (2026-11-15)
- 手当て: 区切りは `-----` や `---` にするか、`echo '==='` のように引用符で囲む (実測)

## zsh のクォートしないグロブ

zsh でクォートしないグロブ (`grep -r --include=*.ts`、grep の対象のファイル引数、git のコマンドのパスの引数) を書くときに踏む。

- 機序: 一致0件のグロブは nomatch の展開エラー (`no matches found`) になり、そのグロブを含む単純コマンドは起動されない。`;` や `&&` でつないだ後続もその場では走らない (実測)
- 症状: ループの中では件数の変数が空のまま「0件」と出て、検査が何も見ていないのに「無い」と読める。出力が空でも0件ではない。パイプの中では展開に失敗した段だけが落ちて後段は走るので、git のコマンドを wc へパイプすると wc が0を返し rc も0になり、「影響する変更0件」と読める何も見ていない0件になる。同じ範囲のファイル一覧を対照に並べて気づいた (実測)
- 再現: `zsh -f -c 'git log --oneline -- nonexist_*.zz | wc -l; echo "rc=$?"'` は `no matches found` を出したうえで wc が0を出し、rc は0だった (2026-11-13に zsh 5.9 で再現)
- 手当て: グロブは `--include='*.ts'` のようにクォートするか、`git grep` のパススペックを使う。存在しないはずの文字列を対照に混ぜて0になることと、実在の文字列が1以上になることを並べて確かめる (実測)

## zsh の小文字の `path`

zsh のスクリプトやループで `path` などの小文字の変数名を使うときに踏む。

- zsh で小文字の `path` を変数名に使うと PATH と結びついて上書きされ、以降のコマンドが見つからなくなった。`for path in ...` のループ変数でも踏んだ。小文字の特殊変数 (`path` など) をループ変数に使わない (実測)
- `zsh -c 'for path in /a /b; do :; done; ls'` は `command not found: ls` の rc 127で、ループの後の PATH は `/b` だった (2026-11-02に確かめた)

## bash の `set -e` は引数の中のコマンド置換を見ない

bash の `set -e` のスクリプトで、引数の中にコマンド置換を書くときに踏む。

bash の `set -e` は、`cd "$(git rev-parse --git-common-dir)"` のように引数の中のコマンド置換の失敗を見ない。`cd ""` が成功して処理が続き、パスがリポジトリの外を指した。コマンド置換は単独の代入の行で受ける (委譲先の reviewer がリポジトリの外で再現)。

## macOS の bash は3.2

macOS で bash のスクリプトを書くとき、とくに配列を作ってその配列を引数にコマンドを呼ぶときに踏む。報告日は未記録、bash 3.2 (macOS の標準)。

- macOS の標準の bash は3.2なので、`${var^^}` や連想配列など bash 4以降の構文は使えず、bad substitution になる。`#!/usr/bin/env bash` でも PATH 次第で3.2になる (実測)
- macOS の /bin/bash 3.2には `mapfile` が無い。`mapfile -t P < <(...)` が失敗して配列が空になり、続く `pnpm update "${P[@]}"` が引数なしの全依存の更新に化けて package.json まで書き換えた (実測)
- 空配列の展開を `set -u` が止めるかは版による。macOS の /bin/bash 3.2.57では `set -u; P=(); printf '<%s>' "${P[@]}"` が `P[@]: unbound variable` で止まる (実測、2026-11-23)。bash 4.4以降では止まらない (推測。既知の挙動)。上の事故で止まらなかった理由は未確認で、`set -u` が無かったか、より新しい bash で走ったかのどちらかが考えられる
- 手当て: 配列は while read で作り、空なら止めるガードを置く (実測)
- 配列が空のときに引数なしで走ると意味が変わるコマンド (pnpm update など) の前には、要素数のガードを置く (提案)

## `&&` の連結の中の `A || B`

`&&` で連結するシェル片 (Makefile の変数に入れた片など) の中に `A || B` を書くときに踏む。

- `&&` と `||` は同順位で左結合なので、前段の失敗 (例: シークレット取得コマンドの失敗) で `||` の側が走り、後続まで進む。分岐は `{ …; }` で囲むか、`set -eu` の別スクリプトに出す (実測、`false && test -z "$X" || { echo RAN; } && echo CONTINUED` で両方出る。`bash -c` と `zsh -c` のどちらでも RAN と CONTINUED が出て rc 0だった。2026-11-13に確かめた)
- `A && B || C` の形は shellcheck の SC2015 がシェルスクリプトでは既に指摘する。残る隙間は shellcheck が解析しない Makefile のレシピの行

## background の待ちのループ

background に待ちのループを置くとき、ポーリングのループの終了条件を書くときに踏む。

- 自分に当たる照合: `until ! pgrep -f "<コマンド>"; do sleep N; done` の形の待ちのループを background に置くと、終わらないまま残った。`pgrep -f` はコマンド行の全文を照合するので、その文字列を含むループ自身の zsh に当たり、条件が永遠に偽になる。待つ対象はプロセス名ではなく、pid (`kill -0 <pid>`) か、終わったときに書かれるファイルで見る (実測)
- 満たされなくなる条件: 待ちのシェルを「HEAD の subject が一致するまで」で書くと、ブランチを切り替えた後に満たされず孤児として残り、10本ほど溜まった。条件はレポートの出現や子プロセスの終了にし、ブランチを切り替える前に自分の待ちを止める (実測)
- 否定形の終了条件: `gh pr checks` を30秒ごとに呼ぶループの終了条件を「未完了の語を含まない」にすると、API の connection reset のエラー文が条件を満たし、途中で完了として抜けた。「完了の印がある」の肯定形にして欄の値で判定すると、一過性のエラーを越えられた (実測)

成否を持つ長時間コマンドの結論を専用のクエリで読む形は `~/.claude/references/observation.md` の「成否が隠れる」項が持つ。

## `kill(pid, 0)` は zombie に成功を返す

子プロセスの終了を `kill(pid, 0)` で待つとき、プロセスグループをまとめて止めて消えるのを待つときに踏む。

`kill(pid, 0)` は zombie に成功を返す。自分の直接の子を `wait` / `poll` で回収せずに「全員が消えたか」を待つと猶予を必ず使い切る。macOS は回収待ちの zombie だけのグループへの `killpg` に EPERM を返すこともある (実測)。

## `make -n` は `$(MAKE)` を含む行を実行する

`make -n` で副作用の無い確認 (dry-run) をしようとするとき、`make -n` の出力で配線を pin するときに踏む。報告日は未記録、踏んだ側の make の版は未記録 (下の再現は GNU Make 3.81)。

- `make -n` で dry-run したターゲットが、レシピ内の待機ループを実際に走らせて120秒の timeout まで止まった。レシピ全体が `$(MAKE)` を含む1行のシェルだと、`-n` でも待機ループまで実走する (実測)
- 走る範囲: `$(MAKE)` を含むレシピの行はその行がまるごと実行され、同じ行の書き込みが実際にファイルを作った。行頭に `+` を付けた行も実行された。`$(MAKE)` で呼ばれた側には `-n` が引き継がれ、呼ばれた側のレシピは表示されるだけで実行されなかった (実測、GNU Make 3.81、2026-11-01)。待機ループが走ったのは、ループが `$(MAKE)` と同じ行にあったからと読める (未確認。元のレシピは見ていない)
- 手当て: `make -n` を当てるのは再帰の無い葉のターゲットだけにする (実測)
- 配線をテストで pin するなら、検査の呼び出しを image を作る小さな target の別の行に置き、`make -n MAKE='echo make'` で読む (実測)

## perl のワンライナーの日本語のパターン

perl のワンライナーで日本語を含むパターンを照合・置換するときに踏む。

- `perl -CSD` だけだと、コマンドに書いた日本語がバイト列のままで (`use utf8` が無いため)、日本語のパターンが無音で0件になり、`-i` の置換は何も変えずに rc 0を返す。ASCII だけのパターンや `\p{Han}` の部分だけは効くので置換が一部だけ黙って当たり、空振りに気づきにくい。`-CSD -Mutf8` で正しく効いた。バイト列のまま照合して直したときは、その過程で行頭のコメント記号の後の空白が落ちた (実測)
- 手当て: 日本語を含む置換は Edit か、`use utf8` を付けた perl か python で行い、適用後に grep で件数を数える (実測)
- `-CSD -Mutf8` を既定の形にする (提案)

置換が入ったことを diff で確かめる形は `~/.claude/references/testing-mutation-harness.md` の「変異が入ったことを確かめてから結果を読む」節にある。

## perl の `s` の区切りと同じ文字

perl の `s` で、区切りと同じ文字を含むパターンや置換の文字列を書くとき、コードを差し込む置換を書くときに踏む。

- 置換の側: `s|||` で区切りに `|` を使い、置換の文字列にクロージャの `||` を含めると、置換がファイルの先頭に入り、`or die` も発火しなかった。コードを差し込む置換は、区切りにコードに出ない文字を使うか Edit ツールで行う (実測)
- パターンの側: `perl -pi -e 's|...|...|'` の区切りに `|` を使い、パターン側にも `\|` を含めたら区切りが崩れ、ファイル中の `_` が全部置換文字列に化けた。置換は Python の `str.replace` で件数を assert してから当てる形が安全 (実測)
- 区切りと同じ文字を `\|` とエスケープすると、その文字はリテラルの `|` ではなく正規表現の選言として働く。`s|b\|c|X|` は「b か c」に当たり、`a_b|c` は `a_X|c` に、`foo_bar` は `foo_Xar` になって、狙っていない行まで置換された (2026-11-01に確かめた)。「`_` が全部化けた」形は、元のパターンを見ていないので再現していない
