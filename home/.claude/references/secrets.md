# 秘密の扱いの一次実測

`~/.claude/CLAUDE.md` の「攻撃者が使える面を最小に保ち防御を 1 層に頼らない」カテゴリの、秘密の値と秘密のヘッダの扱いの手当てと一次実測。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。

## 秘密のヘッダと redirect

fetch や HTTP クライアントの包みで、認証ヘッダや秘密の独自ヘッダ (認証プロキシの service token など) を全要求へ足すときに踏む。

fetch の仕様は、別オリジンへの redirect で Authorization 以外のヘッダを落とさない。全要求へ足す包みは、302を辿った先へ秘密を運ぶ。包みは接続先と同じオリジンにだけ足し、redirect は `manual` にする (実測)。

テストは別ポートのもう1台のサーバへ302を返させ、そちらに届いた件数0を、接続先が受け取った件数を対照にして pin する。オリジン判定の「scheme が同じか」の腕は、テストのサーバが全部平文だと消しても緑で通る。接続先を https として名乗り、同じ host とポートへ平文で要求を出して、腕を外す変異で赤になることを確かめる (実測、変異で赤を確認)。

同じ形はほかの経路にもある。

- Python の urllib の既定の opener は redirect を追い、Request に付けた Authorization ヘッダも redirect 先へ送りうる。Basic 認証を付ける採取の道具は、redirect を追わない opener にする (ドキュメントのみ)
- ブラウザ自動化で保護下のフロントを開くとき、bypass のヘッダを context 全体の `extraHTTPHeaders` に付けると、別ドメインの API への要求にも秘密のヘッダが付く。route で配信先のホストへの要求にだけ付ける (route で付けたのは実測と申告。全体に付けたときの漏れは仕組みからの推測で、観測していない)

## 秘密の値を会話に出さずに扱う

`op read` などで秘密を読み、ヘッダ・環境変数・照合・失効の確認に使うスクリプトを組むとき、また秘密を表示する画面を撮るときに踏む。会話・ログ・subagent・transcript へ値が入っても警告は出ない。

### 値を渡す

書き捨てのシェルスクリプトの中で、`op read` の結果を直接ヘッダや子プロセスの環境変数へ流し、値を出力に載せない (実測)。値が出なかった範囲は形ごとに違う (いずれも実測)。

- API トークンは `curl --config -` へ標準入力から `header = "Authorization: Bearer ..."` の行で渡す。引数にも画面にも出なかった
- DuckDB には鍵を環境変数で渡して SQL の中で `getenv` で読み、SQL 自体は標準入力から渡す。鍵はプロセスの引数にも SQL のファイルにも出なかった
- GitHub の Environment の secret は `op read -n "<op の参照>" | gh secret set <NAME> --env <環境>` で入れる。値は画面にもログにも出なかった。`-n` は末尾の改行を付けない。成否はパイプの両側を見る (zsh の `pipestatus` の扱いは `~/.claude/references/observation.md` の「成否が隠れる」項)

### 値を出さずに確かめる

値の代わりに形と件数だけを出す (いずれも実測)。

- 用途の判別は、長さと形 (32桁の hex か など) と、提供元の verify API の HTTP ステータスだけで足りた
- 実物の API 応答は、値ではなくキーと型だけを出す書き捨てのスクリプトを `.cache/` に置いて形を調べる
- 秘密の値どうしの一致は、両方を変数に読んで等値比較の結果だけを出すか、ハッシュの先頭だけを比べる
- 漏れた範囲は、元の transcript から値をメモリの上でだけ取り出し、ディレクトリ配下の全ファイルを bytes で照合して件数とパスだけを出す。環境変数の広がりも、値を含むファイルの数で数える
- ログに値が残っていないことを件数で言うときは、値ごとに合成の1行を対照に置き、「0件」と「見ていない」を区別する (判定の規範は CLAUDE.md の「0 件」「空」「緑」の項)

### 値が空だと全行に一致する

値を変数に読んで件数を数えるときの空のパターンの罠は、`~/.claude/references/observation.md` の「後続が飛ぶ」項にある。数える前に変数が空でないことを確かめる。

### 失効と入れ替えを HTTP のステータスで確かめる

401という数字だけでは、「失効したトークンを拒んだ」と「トークンが届いていない」を区別できない。`op read | sed | curl --config -` のようにパイプで渡すと、左の `op read` が失敗しても右の curl はトークン無しで走り、後者の401が返る (実測。機構は `~/.claude/references/observation.md` の「成否が隠れる」項)。

- 本文で見分ける。アプリが返す固定の本文は、資格情報を照合して弾いた場合とヘッダが無い場合で文言が違うので、全部401でも「照合まで届いて弾かれた」と「別の理由の401」を区別できた。401のときだけ固定の本文を出す probe にする (実測)
- 対照を置く。ヘッダ無しの組を対照にすれば、正の対照 (200) が取れない入れ替え前でも測定が成立する (実測)
- 削除するトークンは、消す前に同じ probe で「生きていて広い権限を持つ」ことを記録しておくと、削除後の401を削除の証拠として読める。権限を絞った新しいトークンの403と並べると、「トークン自体の拒否」と「権限の外の拒否」を区別できた (いずれも実測)

### 画面とスクリーンショット

画面に文字で出た秘密は、スクリーンショット1枚で transcript に入る。

- 設定の画面のスクリーンショットに、画面に並んでいた Webhook の URL (知っていれば投稿できる秘密) の一部が入った。秘密の値を表示する画面では撮らず、名前で要素を探して押し、読むのは URL とメールアドレスを置換した文字だけにする (実測)
- 漏れた Webhook は、末尾を削るなどの編集では無効にならない。削除して作り直す (実測)
- ユーザーに DevTools のスクリーンショットを頼むと、リクエストヘッダの `Authorization: Basic` の値まで写り込むことがある。頼むときは General の欄だけを指定する (実測)
