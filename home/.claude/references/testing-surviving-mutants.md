# 緑で残った変異の一次実測

`~/.claude/rules/testing-practices.md` の「テストが緑であることを、仕様を守れている証拠にしない」カテゴリが持つ変異注入の規範のうち、変異が緑で残ったときに、pin が弱いと決める前に疑うものについての、手当ての詳細と一次実測。入口は `~/.claude/references/testing.md` で、変異注入と dead pin の定義は rules が持つ。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。

到達不能な分岐が見逃しとして現れる形は `~/.claude/references/testing.md` の「赤くなっても pin が有効とは限らない」、ブラウザが先に止めていた形は同じファイルの「緑の原因が守る対象とは別の層にある」にある。

## 変異が等価か、fixture の値で区別できない

変異が緑のとき、pin の弱さより先に (a) 変異が等価でないか (b) fixture の値がそろっていて区別できないかを疑う。(a) は空の表から insert して0行だった例、(b) は持ち越す列の値が全行同じで「最古」と「最新」の取り違えを区別できなかった例 (実測)。

そろっていたのが fixture と既定値だった形もある。エラーの文言を「定数のファイル名」から「呼び手が渡したパスの名前」へ揃える直しに、文言を定数名へ戻す変異を当てた。テストの入力のファイル名を既定値の定数と同じにしていたため、文言が定数の名前でもパスの名前でも期待値と一致し、どちらの実装でも緑になっていた。本数とカバレッジは正常に見えるので、レビューでは見えない形の dead pin だった。入力のファイル名を既定値と違う名前 (例: 既定が foo.toml なら mine.toml) にすると、文言を定数へ戻す変異5件がすべて狙ったテストで赤になった。既定値と同じ入力は、既定値へ戻る変異を構造的に検出できない (いずれも実測)。既定値と呼び手の値のどちらを使うかを見分けたいテストでは、入力に既定値と同じ値を使わない (提案)。

区別できない値の形はほかにもある (いずれも実測)。

- 秘密を伏せる置換: エラー文の中の秘密を文字列置換で伏せるとき、テストの架空の値が周りの固定文字列の部分文字列 (例: `acc` と `/accounts/`) だと、置換がパスまで壊して偽の赤や偽の緑を生む。架空の値は周りの文字列と衝突しない形にする
- 並べ替えの決め手: 「並べ替えの最後の決め手を外す」変異は、DuckDB の並列の集計だと同じ件数の行の順が実行ごとに揺れるので、1回の実行では確率的にしか赤くならない。見本に、その列だけが違う行を足すと決定的に赤くなった

入力の日付が差の出ない日だと区別できない形は `~/.claude/references/testing-time-and-order.md` の「タイムゾーンに依存する日付処理」にある。

## 機構の有無で出力が変わる入力を置く

パストラバーサルの検査で、外に実在しないファイルを指すテストは、ガードを丸ごと消しても「ファイルが無い」で同じ結果になり緑のまま残る。外に実在するファイルと、接頭辞だけが同じ兄弟ディレクトリを置いて初めて赤になった (実測)。

ソースの grep 系の検査でコメントを落とすとき、文字列の中身まで落とすと補間 `\(...)` の中のコードを隠す側へ壊れた。中身は残してコメントだけを落とすと、字句の状態を誤っても数えすぎる側に倒れる。ただしその設計では、テストの入力に「誤るとコードの位置でコメントが始まる」仕掛け (文字列の中の `/*` など) を入れないと、走査を壊しても緑のままになり、5件中4件の変異がそれで素通りした (実測)。壊れる向きを安全側へ倒す設計と、その機構を通る入力を fixture に置くことが対になっている。

fixture の深さが pin の射程を決める。実コードの構造の深さを fixture が持たないと、その深さに依存する機構が守られない。

## 同じ役目の処理が複数ある

多層防御の片方の層を外す変異が緑でも dead pin とは限らない。もう片方の層を外した条件を作り、そこで「変異あり=赤 / なし=緑」の対照を並べると、各層が単独で効くかを見分けられた。DB の行レベルセキュリティなら素通りするロールで backend を動かし、FOUC 防止のインラインスクリプトなら後から同じ値を当て直すモジュールスクリプトを route で空の200にして reload した (実測)。

同じ役目の処理を2か所に置くと (前のタイマーを消す処理、同じ役目のガード)、片方を外す変異がもう片方に覆われて緑のままになり、どちらの pin も効かない。1つに絞ると変異がそれぞれ赤になった (実測)。両方残すなら、片方ずつ外したときに赤くなるテストを別々に置く (提案)。2か所を残したまま、片方だけが効く入力を選ぶ形もある。失敗の文言から秘密を伏せる処理に、切る前に伏せる内側の処理と、全体の文言を伏せる外側の処理があると、内側を外す変異が外側に隠れて緑になる。内側の処理だけが救える入力 (秘密が切れ目をまたぐ長さ) を使うと避けられた (実測)。切る層と伏せる層の順序は `~/.claude/references/security.md` の「検査・置換と切り詰めの順序」にある。

解釈器と reducer に同じ前提の判定が二重にあると、本番は解釈器の側で止まり、有界 BFS は本番が通らない reducer 側の判定を証明することになる。判定の入力を1つにまとめて reducer の1つの guard に寄せると、模型と本番の経路が一致した (実測)。

## どのテストの射程にも入らない行

「届かなかったときの既定値」を `|| code=000` のように置く行は、正常系のテストも静的な配線のテストも通らず、既定値を成功の値へすり替える変異が緑のまま通った。行の形で pin して初めて赤になった (実測)。
