# 観測と検証の一次実測

`~/.claude/CLAUDE.md` の「観測した結果がその主張の証拠になっているか確かめ、観測自体を加工や連結で壊さない」カテゴリが持つ規範の、手当ての詳細と一次実測。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。規範の文面はここに再掲しない。

ただし「Bash コマンドの沈黙経路」節は例外で、コマンドを組む前に開く。
手当ての canonical がここにしか無いため、遵守の時点で要る。

## 報告を網羅と読む

### 未読ファイルを追跡下へ入れる

未読の docs を移動して PUBLIC へ push した。branch を消しても closed PR の diff は公開のまま残った。
gitleaks の検出集合の canonical は `.gitleaks.toml` で、そこに無いカテゴリ (プロジェクト名・ボリューム名) は素通りする。

### 壊れやすい配置

ユーザーの「実機で全部 OK」報告が真実でありながら網羅ではなかった例がある。
壊れるグリッド端のカードを未踏だっただけだった。

### venv の絶対パスと console script

venv の絶対パスが変わったら (リネーム・移動・別パスへのコピー) 再インストールする。
console script のシバンへ venv の絶対パスが焼き込まれるので spawn に失敗する。

壊れるのは bin 配下のスクリプトだけで、インタプリタ本体と `python -m <mod>` は動き続け、`uv sync --reinstall` で直る。

実バイナリのまま置かれるツール (ruff 等) は素通りし、`uv sync` も `poetry install` も lock との整合しか見ずに緑を返す。実際 `git mv` の後 ruff は `All checks passed!` を返し pytest だけが `Failed to spawn` になった。
ネイティブ実装でも PyPI 側が Python wrapper を被せていれば落ちる (cmake で実測)。

これは live-smoke ルールと同じ「狭い signal ≠ 広い主張」の形で、some-path pass は all-path healthy を意味しない。

### 監査表の過小評価

再掲 3 箇所とあった表に対し実測 5 箇所で、表どおり直すと 2 箇所残った。
残りは「直し忘れ」ではなく「表に無い」ので、表と突き合わせても出ない。

### 記録されたメタデータ

タスクリスト移行で `.highwatermark` を採番オフセットに使ったが、この値はセッション中の採番を含まず実 ID より小さかった。
確認した 11 本すべてで不整合があり、そのまま適用すれば生きたタスク 6 件を上書きしていた。

プランは衝突確認を適用後に置いていたが、上書きは適用の瞬間に起きるので事後検証では救えない。

### 自分の測定と順序効果

実行順の入れ替えは1回で済ませず、並びを複数取って順序効果を消す。

同一プロセスで 3 方式を連続実行して「BFS が 2 倍速い」と読んだが、先行する方式がキャッシュを温めていた疑いがあり、独立プロセス + 順序 4 通りで測り直して初めて差が本物だと確認できた。

さらに順序効果を排除しても改善率は転移せず、走査単体で 38% 速くした変更が実ワークロードでは 2 フェーズのうち片方だけ 18% 短縮でもう片方は変化なしだった。
ベンチの比率で全体を見積もると外す。

### 検索キーの偽陰性

探し方が誤っているだけなのに「無い」という結論が出る。

実際 migration 0060 の効果を推測したトリガ名で `pg_trigger` から探して「未適用」と読みかけたが、0060 は新トリガを作らず既存トリガの関数を `create or replace` する作りで、効果は関数本体にあった。
名前ではなく本体・定義で確かめる。

## 0 件・空・緑を健全と読む

### 何を何件見たか

毎朝の healthcheck が 8 日連続 success だったのは全 env が「deployment が 1 件も無いので skip」に落ちていたためで、実測では配信自体が一度も成立していなかった。

dig は SERVFAIL でも NXDOMAIN でも exit 0 を返し `+short` が全応答を空に潰すので、対照に正常応答するドメインを並べないと相手側の障害と自分の resolver の故障を区別できない。

### 対照側も同じだけ壊れる

対象側との一致を確かめる規約の例は、NUL 区切り・revision range・検索式。壊れた対照が返すもっともらしい不一致や一致は、対象側の欠陥にも検査の通過にも見える。

1 ターンで 3 回踏んだ。

- `git ls-files` を `-z` 無しで対照にしたため日本語パスが全部クォートされ「100 対 29 で取りこぼしあり」と誤読した。落としていたのは対照の方
- `git diff main..HEAD` で未コミットの編集を見ようとして「修正が効いていない」と誤読した。revision range はコミット間しか見ず作業ツリーを含まない
- grep パターンに余分な空白を入れて得た 0 件を「重複が収束した証拠」と誤読した

一致側へ倒れる形も踏んだ (2026-09-18)。4 つのリポジトリの公開範囲を 1 つのループで調べて 4 件とも `PUBLIC` を得たが、実際は 4 件とも PRIVATE だった。BSD sed が `+?` を解釈せず置換が失敗し、空文字を受け取った `gh repo view` が 4 回とも cwd のリポジトリを答えていた。4 件が揃っていること自体がもっともらしく見える。`sed: RE error` は stderr に出ていたので、`2>/dev/null` を付けていれば同じ値 4 件だけが残り、気づく手がかりが消えていた。

手当ては、リポジトリを解決させたい対象の中でコマンドを走らせて、そのコマンド自身に解決させること。シェルの正規表現で識別子を組み立てない。対照として remote URL も並べると、解決先が cwd へ落ちたときに URL と名前が食い違うので見分けられる。

### 時刻の対照はタイムゾーンで壊れる

相対時刻は `gh <sub> --json createdAt --template '{{timeago .createdAt}}'` で取れる。
`--template` は `--json` と併用しないと使えない。

`gh` の JSON は常に UTC で返るのにコンテキストの日付はローカル時刻 (JST) 由来なので、素朴に比べると最大 1 日ずれる。
2026-08-13 に `createdAt` を「今日」と突き合わせて「24 時間 stuck」と誤読し、開始 6 分後の健全な CI 2 本をキャンセルした。

`TZ` 環境変数の設定では防げない。
2026-08-24 の再実測では、`TZ` 無指定・`Asia/Tokyo`・`America/New_York` の 3 通りとも `createdAt` と `timefmt "2006-01-02T15:04:05Z07:00"` が同じ `Z` 表記を返し、`timeago` も変わらなかった。
同じ時点でコンテキストの「今日」は 2026-08-24、`date -u` は 2026-08-23 で実際に 1 日ずれていた。

壊れているのは観測値そのものではなく観測値と対照の突き合わせ方で、上の「対照側も同じだけ壊れる」と同じ型。

### 他人が書いた確認コマンド

in-repo-issue skill が Issue 移動時のリンク補正手順で示す `grep -n '](\.\./'` を実行して 0 件を得たが、そのリポジトリはパスに空白と日本語を含むため Markdown リンクが `](<../...>)` の山括弧形式で、パターンが一致していなかっただけだった。直すと 11 件出た。

### プローブの構造上の位置

整備済みの実ファイルが使えるならそちらを対照にする。

ruff の isort が `src` 設定に依存するか確かめるプローブを対象パッケージ内に置いたら、`src` を外しても正しく判定された。プローブが同じパッケージにいて別経路で解決されていただけで、実ファイルで測り直すと外部からの import 7 件が発火した。

### 非 0 件も証明にならない

- unittest の `Ran N tests` は `@skip` と `@expectedFailure` を両方含み、どちらがあっても `OK` / exit 0 を返す。4 件中 skip 1 + xfail 1 で `Ran 4 tests` / `OK (skipped=1, expected failures=1)` / exit 0 を実測。全テストを skip 化しても件数も exit code も変わらないので、下限で守っても exact 一致で守っても素通りする
- 件数 pin は同数入れ替え (1 件消して 1 件足す) と改名も原理的に検出できない。ID 集合なら消えた側も未記録側も名指しで出て、副産物として件数の literal がコードから消えるので二重管理も同時に解ける
- `node --test --test-name-pattern` で対象を絞ったとき、pattern が 1 件も一致しないとファイル自身が 1 件の pass として計上され `tests 1 / pass 1 / fail 0`・exit 0 になる。期待するテスト名が出力に現れたことで判定するか、`--experimental-test-isolation=none` を付けて `tests 0` が正直に返る形にする
- 0 件実行なのに `fail 0` になるため、変異注入で「壊しても赤くならない」と読んで生きた pin を dead pin と誤報告する可能性がある (両語の定義は `~/.claude/rules/testing-practices.md`、手当ては `~/.claude/references/testing.md`)。非マッチは `tests` にも `skipped` にも計上されない (4 件中 2 件一致で `tests 2`) ので減算では 0 件を検出できず、一致したテストが skip 済みだと `tests - skipped = 0` で逆に誤判定する (Node 24.18 で実測)

## Bash コマンドの沈黙経路

これまで踏んだ「成功に見える結果」の形には「0 件」「何も起きない」「無関係な件数」「短い正常な結果」がある。

### 成否が隠れる

exit code で判定するコマンドはパイプにも後続コマンドにも繋がず単独で実行する。
繋ぐと最後のコマンドの exit code になり、本体の failure を success と誤認する。

- 出力を絞りたいときは `cmd > <file> 2>&1` だけを実行し、ファイルは次の呼び出しで別コマンドとして読む
- `git push` は繋がずに実行し、push 後は `git ls-remote --heads origin <branch>` (リモート ref 存在) と `git status -sb` (upstream tracking) で直接確認する。パイプ先の exit code が push 本体の失敗/未完を隠し、pre-push hook 完走と ref transfer 完了を取り違える
- 成否を持つ長時間コマンド (`gh run watch`・`gh pr checks --watch`・`gh pr merge` 等) の結論は専用クエリ (`gh run view <id> --json conclusion` 等) で確認する。`<cmd>; echo "EXIT: $?"` のように `$?` を上書きする後続コマンドを連結しない
- 回避策の `${PIPESTATUS[0]}` は zsh では常に空になる。zsh に `PIPESTATUS` は無く、小文字の `pipestatus` が 1 始まりなので `${pipestatus[1]}`。空文字は数値比較で 0 と評価されるため成功扱いに化けて、取得に失敗したこと自体に気づけない

実際 eslint を `| tail` して「exit 0 = 事前状態クリーン」と誤報告し、実測では 105 problems で赤だった。

### 後続が飛ぶ

真偽値を返すコマンドは `&&` で繋がず `;` で分け、破壊的操作の前は展開結果を echo で確かめる。

- `git check-ignore` は「ignore されていない」を exit 1 で返すため `&&` チェーンが途切れ後続の `rm -rf` が飛んだ
- zsh では `for x in $VAR` は単語分割されず 4 要素のリストが 1 つの名前として扱われた。同じ `for` でもコマンド置換 `for x in $(cmd)` は分割されるので向きが反対になる。分割された側の手当ては「パースが静かに欠ける」項
- grep のパターンに `$@` を入れたら展開されて 0 件を返しファイルが壊れたと誤診した
- BSD sed に `\b` が無く置換が効いていないのに、`grep -c` で置換後の語を数えたら別の語 (`depth` の中の `pth`) に部分一致して 8 件返り、置換されたと誤読した。置換の確認は置換後の語を数えるのではなく置換前の語が残っていないことを直接見る
- `$c:home/...` のような変数展開は zsh が `:h` を history modifier (dirname 相当) として解釈し、パスが静かに化ける。`${c}:home/...` と書く

### プロセス境界を越えない

サブシェル (パイプ左辺・プロセス置換 `<(...)`・コマンド置換 `$( )`) で呼ばれる関数のグローバル代入は親シェルへ戻らない。
キャッシュ・カウンタ・「警告済み」フラグのような状態を関数へ持たせる前に、呼び出し側がサブシェルを作らないか確かめる。

同じ警告が 1 回の実行で 5 回出る問題にメモ化を提案されたが、全ての呼び出しが `< <(f)` 形だったためキャッシュは毎回破棄され成立しなかった。
実装しても「効かない」だけで例外は出ないので、実測しなければ静かに失敗する。

パイプ右辺は zsh では親に残るが bash では失われるため「右辺なら安全」とも読まない (直接呼び出しを対照に bash 3.2.57 / zsh 5.9 で実測)。

### パースが静かに欠ける

コマンドが出力するファイル一覧を空白で分割せず、`git ... -z` や `find -print0` の NUL 区切りで受け取り、検査した件数が対象件数と一致することを確かめる。

空白や日本語を含むパスは分断され、落ちた分は「エラー」ではなく「短い正常な結果」として返る。
実際 `git diff --name-only` を Python の `.split()` で切って 3 ファイル中 2 ファイルが検査対象から静かに消え、残る 1 件だけが「クリーン」と報告された。

「0 件を健全の根拠にしない」は空と非空の境界しか守らないため、部分的な欠落は件数の一致でしか捉えられない。

## live smoke

ランタイムで壊れるシェル / CLI のセマンティクスの例は、連結・クォート・PATH 解決・exit code・OS 差。

cmd.exe の `&` 連鎖が最初の if 偽で全体 no-op になる類のバグはユニットテストでは原理的に捕捉できず、実機実行でしか露見しない。

winvm の mkdir → scp → remote-exec 連鎖で実際に踏んだ。

## node --test にディレクトリを渡さない

node のバージョン (Node 26 など) によってはディレクトリをエントリモジュールとして解決し `MODULE_NOT_FOUND` で失敗する。
