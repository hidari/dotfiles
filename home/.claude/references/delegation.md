# 委譲と subagent 運用の一次実測

`~/.claude/CLAUDE.md` の「委譲先の報告を自分の実測の代わりにせず派生は 1 段に留める」カテゴリが持つ規範の、手当ての詳細と一次実測。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。

調査や点検を委ねるとき (外部の文書の事実を調べさせて設計文書へ写す、所見や修正案を採る、設計書・spec・実装計画を計画や着手や無人の実行へ渡す前に点検させる) は `~/.claude/references/delegation-research.md` を開く。

## Agent tool と Workflow の許可

Claude Code 2.1.229では「Do not call the AgentTool unless the user requested it」「Do not use workflows or deep-research unless the user requested it」の2行がバイナリに定数として埋まり、settings.json でも起動引数でも消せなかった (2026-08-13実測)。2.1.280と2.1.282のバイナリでは2行とも文字列どおりには見つからず、代わりに「Do not use the ${mt} tool, workflows, or deep-research unless the user, a CLAUDE.md file, or a skill asks for it」の1行があり、許可の出どころとして CLAUDE.md が名指しされている (2026-09-24と2026-09-26に実測。`${mt}` へは `"Agent"` を代入する箇所があるがスコープは未確認で、この行がどの条件で注入されるかも確かめていない)。

消せない側ではなく、条件を満たす側を CLAUDE.md で明示する。Workflow ツールの説明 (2.1.282) が挙げる opt-in の経路に CLAUDE.md は無い。settings の `ultracode` が有効な間は、「セッションで ultracode が有効」の経路で opt-in される。CLAUDE.md の許可だけで Workflow の条件を満たすかは確かめていない。

## 派生を 1 段に留める

深さに上限が無いと、どの結論が誰の実測に基づくかを親が辿れなくなり、トークンも指数的に増える。

Agent tool の fork と Workflow の nesting は仕組み側で 1 段に制限されているが、通常の subagent 起動には制限が無いので規約で塞ぐ。

## implementer への長時間コマンド委譲

prompt で名指しして禁じたが 5 回連続で再発した。
implementer は長時間コマンドに対して Monitor / watch を仕掛け、そのままターンを終える挙動を取る。

prompt による禁止では止まらず、分業の設計で構造的に防ぐ側へ切り替えて解決した。
コントローラがゲートを回せば赤も直接読める。

## 構造化出力どうしの突合キー

レビューの findings と反証の verdicts を title の完全一致で突合した。
反証側が指示に無い「指摘 N: 」を前置したため、17 件全部が「未検証」に落ちた。

突合の失敗は例外ではなく「全件未検証」という静かな結果で返ったので、出力を読むまで壊れていることに気づけなかった。
生成側は装飾を足すので文字列一致は必ず壊れる。

## 反証者への既定値の指示

「確信が持てないなら refuted=true」を既定値として指示した結果、妥当な指摘 4 件が 2 名一致で refuted に落ちた。全件を読み直して初めて拾えた。

一致していたのは独立に確認したからではなく、迷った反証者が全員同じ側へ寄っただけだった。

反証の判定が全件同じで返ったときも、ふるいが効いたとは読まない。レビューの指摘をそれぞれ反証させる検証役を並べたら、27件中27件が「本物」と返り、ふるいとして働かなかった。全件が同じ判定になったら検証段が識別していないと見なし、深刻度はコントローラが自分で付け直す (実測)。一方で、23件すべてが反証を経ても成り立ち、前の実装者の誤りを早く見つけられたという評価もある。

監査役と反証役の2票が揃っても、同じ古い一次資料 (起票時のままの Issue 本文の冒頭) を読んでいれば独立の確認にならない。2体とも、末尾の追記で覆った状態を見落とした。Issue や文書の本文を一次資料として確かめさせるときは、反証役への指示に「Issue の本文は末尾の追記まで読む」を入れる (実測)。

## brief の断定

brief の断定が implementer の実測で訂正される事例が連続した。
根因ファイルも breakpoint も brief の記述と違っており、brief をそのまま信じる従順な implementer なら無関係な箇所で詰まっていた。

brief は仮説であって確定事実ではなく、コードに触れているのは implementer の実測。
「報告・前提を検証済みの網羅的事実として扱わない」の Subagent-Driven 版。

## subagent への制約伝達

隔離した `CLAUDE_CONFIG_DIR` では Keychain 認証を引き継げないと brief に書いたところ、subagent が `security find-generic-password` で認証情報を読み出そうとし、続けて `~/.claude.json` の複製も試みた。

auto mode classifier がブロックして実害は無かったが、防御が 1 層しか働いていない状態だった。

制約の説明はエージェントにとって「解くべき問題」に見える。「そこには行くな」まで書いて初めて制約になる。

## 並列 subagent の実験場所

並列の subagent に実験や変異をさせるときと、Workflow や並列の subagent が走っている間にコントローラが作業ツリーへファイルを置いたりコミットしたりするときに開く。

マージ前ゲートの 6 並列で、subagent が提案の妥当性を確かめるために本体のファイルを変異させた。
一瞬の `exit 2` を退行と誤診しかけた。

テストが赤いのに `git status` が clean という矛盾で気づいたが、矛盾が出なければ誤った結論のまま進んでいた。

隔離コピーで pnpm を使わせるときの brief の要件は `~/.claude/references/host-environment.md` の「書き捨ての置き場 `.cache/` はツールからは本体の一部」節が持つ。

読むだけの役が走っている間に作業ツリーを書き換えるとき (変異注入 (定義は `~/.claude/rules/testing-practices.md`)、ファイルの追加、コミット) も踏む。読むだけのレビューの subagent を変異注入と並行で走らせると、レビュー役が変異の入ったファイルを読んだ (実測)。このときは指摘に混ざらなかったが、混ざれば存在しない欠陥を報告する。手当ては、変異の注入と復元が終わってから出すか、`git show <sha>:<path>` でコミットの中身を読ませること。本体を書き換える実装役と並行する読み取りだけのレーンは、HEAD へ detached で進めた別の worktree を読ませると、作業中の変更と混ざらなかった (実測)。

Workflow の実行中に作業ツリーへ新しいファイルを置いたときも同じ型を踏んだ。監査役がそれを読んで「未追跡」「未コミット」と結果に書き込み、後でコミットすると結果だけが古くなった。fan-out の間は作業ツリーを変えないか、変えたことを後で結果と突き合わせる (実測)。

## 設計案の並列生成

テスト件数ガードの設計で、4 案中 3 案が揃って「件数の exact 一致」へ収束した。

「既存の A/B/C 案に縛られず制約だけから設計をやり直せ」と出発点を変えた 1 案だけが、件数という指標そのものを捨てて同数入れ替えと skip 化の検出に到達した。
収束は合意ではなく問題設定の反映である。
judge も案どうしの相対比較しかできないので、全案が同じ穴を持ったまま勝者が決まる。

前提を疑う役が他の観点の出さない穴を出した例は、設計案の生成のほかに、着手前の調査と計画のレビューにもある。

- 調査に前提を疑う役を1体入れて初めて、「Node 製の CLI」と思っていたものの実行環境の層 (別のランタイム) が出てきた (実測)
- 実装計画を、観点を分けた6体の並列レビュー (spec の網羅、Task 間の整合、セキュリティ、テストが機構を通るか、行番号のずれ、前提を疑う) で Workflow に回し、指摘の id は呼び手が接頭辞を決めて採番させた。同じ欠陥 (既存の不変トリガに一括 UPDATE が当たって migration が落ちる) を6観点中5観点が独立に見つけ、観点をまたいで同じ指摘が出たものは事実の面の裏取りをほぼ省けた。前提を疑う観点を1体入れると、他の観点が出さない配信の手順の穴が出た (どれも実測)。計画のレビューを並列に委ねるときは観点の1つに前提を疑う役を入れ、DB の配信経路の性質 (未適用の migration を一括で流すか) を、疑う前提として名指しする
- 前提を疑う席を置いたレビューで、spike の結論 (「環境変数が効かないので build に手を入れるしか無い」) の飛躍が見つかった。席の推した原因 (環境変数が届いていなかった) は外れたが、測り直しで別の経路が見つかり、計画の1タスクが丸ごと消えた。反証の席の価値は「推した原因が当たること」ではなく「測り直す理由を作ること」にある (実測)

## 常時層のコストは dispatch ごとに払う

subagent はツールを一切使わずに `~/.claude/CLAUDE.md` の本文と由来パスを引用できる。

この経路は `~/.cache/claude/instructions-loaded.jsonl` に記録が出ない (subagent を 1 本起動してもログ行数が変わらなかった)。
「ロードされているのにログが 0 件」の実例なので、削減効果の検証にログは使えない。

## 道具を絞った subagent の閉じ込め

道具を絞った subagent の定義で、監査やレビューを読むだけの役に閉じ込めて回すときに開く。

- 道具を Read / Glob / Grep だけに絞った subagent の定義をプロジェクトの `.claude/agents/` に置き、セキュリティレビューを領域ごとの finder と検証役で回した。subagent には読むだけをさせ、ネットワークとコマンドの実行は親だけが行い、実物での確認が要るものは「読み取りだけの具体的なリクエスト」を schema の欄で返させて親が実行した (実測)
- 閉じ込めは自己申告だけでは確かめられない。本番と同じ経路 (Workflow の agentType) でプローブを1体動かし、見えている道具の一覧とモデルを返させてから、記録の model 欄と呼ばれた道具の名前を数えて突き合わせる形が効いた (実測)

## 同じ作業木で implementer を並列に動かす

同じ作業木で複数の implementer を並行させるとき、または並行中に pre-commit 付きでコミットするときに開く。

- 持ち物で分ける: brief にファイルの持ち物の一覧を書き、テストは自分の持ち物のファイルを1つずつ回させ (全体のゲートは禁止)、変異は origin を外した clone に自分のファイルを写して当てさせると、衝突せずに終わった (実測)。worktree が lint を壊すリポジトリで隔離を使わず、この規律に「変異は cp と cmp で戻させて git checkout を禁じる」「index を触る変異は、変異の前と同じ git status に戻ることで判定させる」「全体のゲートはコントローラが1回だけ回す」を足して5組で回すと、5組とも狙ったテストだけが赤くなり、最後の全体のゲートは緑だった (実測)
- 並列の修正役へ渡す前に、許すキーの集合や正規表現などの値をコントローラが決めて brief に書くと、解釈が割れなかった (実測)
- Workflow で、触るファイルが分かれる2つの変更 (コアのロジックと、CSS と e2e) を同じツリーで並べて実装させ、各ラインに独立したレビューを付けた (実測。うまくいったかは未記録)
- worktree が lint を壊す機序: Workflow の isolation: worktree はリポジトリの中の `.claude/worktrees/` に作るので、走っている間にルートで `biome lint .` を打つと、worktree の biome.json を入れ子のルート設定として見つけて止まる。node_modules の symlink を置いた worktree は変更ありと見なされて自動では消えず、`worktree-wf_*` のブランチも残る (実測。報告日は未記録、Claude Code と Biome の版は未記録)
- pre-commit の stash の機序: pre-commit は、コミットの間 staged でない変更を stash して戻す。並行して作業ツリーを編集している subagent がいる間にコミットすると、編集中の変更が一時的に消える。並行のタスクが終わるまでコミットを待って避けた (報告者の札は「ドキュメントのみ」で、根拠は pre-commit の出力の "Stashing unstaged files"。pre-commit の版は未記録)。worktree で隔離する手もある
- pre-commit の stash の手当て: implementer にはコミットさせず、触るディレクトリを分けてコントローラが `git add <dir>` ごとにコミットすると、stash の巻き込みが起きず、報告のファイル数と git status の行数で検算できた (実測)

## 出力を変えない変更の境界で全出力を比べる

出力を変えないはずのリファクタや依存の版上げを、Subagent-Driven で進めるときに開く。境界の fmt+test の緑は、出力が同じであることを見ていない。

- 道具やスクリプトを書き換えたあと、書き換える前の全出力を残して流し直し、全ファイルを cmp かハッシュで突き合わせると、挙動を変えていないことを1回で示せた。評価の道具の書き換えと、生成スクリプトの宣言データ駆動への書き換えの2件で使った。テストの無い経路 (COMMIT の失敗時の補償) を含むリファクタでは、関数の本体を前後のコミットから切り出してバイトで比べた。ゲートの緑はこの経路を見ていない (いずれも実測)
- リファクタの PR で、変更前に同じコミットを2回ビルドして出力の全ファイルの sha256 が一致することを対照にし、各タスクの境界で出力の差分を取って「出力を変えないこと」を示した (実測)。変わらないはずのリファクタでは差分0件をそのまま証拠にでき、変わるはずの変更では差分が予想どおりのファイルだけかを確かめられた。2回のビルドの一致を先に取っておくと、ハッシュの差が非決定性によるものではないと言える (実測)
- 依存の版上げでも同じ対照を取り、2回のビルドの sha256 の一覧の揺れが0件だったので、版上げの前後で dist の sha256 が一致したことを「出力が変わらないのでリリース不要」の根拠にできた (実測)。ビルドのログの `vite vX.Y.Z building` の行で、比べた2回が本当に別の版で走ったことも確かめた。一致は「新しい版で動いていない」ときも同じ形になるため (実測)
- フォーマッタの更新で設定ファイルの引用符が変わったとき、変更前後を YAML のパーサで読んでデータが同じかを比べ、別のファイル同士では DIFFERENT になる対照も取ると、意味が変わっていないことを機械的に確かめられた (実測)

## 上位モデルの subagent が利用上限で落ちたとき

上位のモデルを指定した subagent や Workflow の役が、利用上限 (429) で落ちたときに開く。

最上位のモデルの subagent が利用上限 (429) で落ちたとき、作業ツリーと scratch に何も書かれていないことを確かめてから、同じ brief のまま次のモデルへ出し直した。反証役に Fable を指定し、上限で落ちたら既定のモデルで同じ prompt を回し直す2段の Workflow にした例もある (どちらも実測。報告日は未記録、Claude Code の版は未記録)。出し直した分は、コントローラの検証とレビューを厚くする (提案で、実測ではない)。
