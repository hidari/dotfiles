# 変異の当て方と赤の読み方の一次実測

`~/.claude/rules/testing-practices.md` の「テストが緑であることを、仕様を守れている証拠にしない」カテゴリが持つ変異注入の規範のうち、変異を当てる手順と、赤や緑がどの検査から来たかの読み方についての、手当ての詳細と一次実測。入口は `~/.claude/references/testing.md` で、変異注入と dead pin の定義は rules が持つ。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。

## 変異が入ったことを確かめてから結果を読む

変異が実際に入ったかを diff で確かめてから結果を読む。perl の置換パターンが対象の行と合わず、変異が入らないまま緑で残った (実測)。

入っても効かない形もある。YAML の top-level にキーを足す変異を perl で注入したら、対象ファイルにもともと同じキーがあり、YAML の重複キーは後勝ちなので注入が意味を失い、テストが緑のままだった。変異の失敗をテストの穴と読み違えかけた。キーを足す変異は、既存のキーの中へ足す形と、キーが無いファイルへ足す形の両方で入れる (実測)。YAML や JSON にキーを足す変異は重複キーで黙って無効になりうるので、既存のキーの有無を確かめてから入れる (提案)。

## 実行役の型

変異の実行役に「退避、置き換え、テスト、cp で復元、ハッシュ照合、失敗したテスト名と assert の文言の抽出」をまとめると、狙った検査で止まったかまで1回で読めた (実測)。置換の前後の文字列と期待の赤を列挙し、1件ずつ当てて終了コードと赤くなったテスト名を集め、最後に元のバイト列との一致を assert するスクリプトにまとめると、初回の実装で生き残りを1件見つけ、書き直し後の31件も一度で確かめられた (実測)。復元の側は `~/.claude/references/testing.md` の「復元に checkout を使わない」にある。

置換の当て先がちょうど1件であることを確かめ、1件でなければ注入せずに止める。この作りで次のものを捕まえた (いずれも実測)。

- 置換元の文字列が複数か所に一致して、2か所に同時に入って原因が分からなくなる事故
- 当て先が2件に当たって止まり、包む側と包まれる側に同じ検査の行を置いた設計で当て先の文字列が重なっていたこと
- テストの中の同じリテラルへの誤爆

### 当て先が0件になる

変異を当てる探針がレシピの見出しの行まで含めた literal を当て先に持っていると、見出しに依存を1つ足しただけで当て先が0回になる。並列レビュー4観点とコードレビューは誰もこれに気づかず、探針を実際に回すゲート (当て先が一意でなければ止まる作り) だけが赤で捕まえた。当て先は本文の一意な行だけにすると、見出しの変更と切り離せる (実測)。

変異の一覧がソースの行の文字列を錨にしている仕組みでは、錨の行に検査を足すと錨が外れて、変異のハーネスが黙って効かなくなる。錨が一度だけ一致することを確かめるハーネス自身のテストがあると、それが赤になって気づける (実測)。

## 無変異の対照を同じ経路で先に回す

変異の前に、変異を当てる経路と同じ経路で無変異の陽性対照を回す。実装役に回させなかった層 (シミュレータのテスト) まで回したら、型の変更に追随していない契約テストの赤が見つかり、対照なしではその赤を「変異が捕まった」に数えるところだった (実測)。委譲先が回せない層も含めることを変異注入の手順に明示する (提案)。

起動の形そのものが壊れていると、どの変異でも同じ赤が出る。Python の検査スクリプトとそのテストを書き捨ての場所へ写し、写したディレクトリで `python3 -I -m unittest test_x.py` を回すと、`-I` が cwd を import の経路から外すので、テストのモジュール自体を読み込めずに `unittest.loader._FailedTest` で赤になる。どの変異でも同じ赤が出るので「全部の変異を捕まえた」に見える。テストのファイルを `python3 test_x.py` で直に起動する形にすると、狙ったテストだけが落ちた。変異の結果を赤の件数ではなく落ちたテストの名前と文言まで出して読んだので、全部の変異が同じ1件で落ちていたことに気づけた。変異なしの写しで同じ起動の形を回して緑を見る対照を先に置くと、起動の形そのものが壊れているかを先に分けられる (いずれも実測)。手順に「変異なしの写しで同じ起動の形が緑になる対照を先に回す」と「落ちたテストの名前を並べて、全部の変異が同じ1件で落ちていないかを見る」を足す (提案)。緑のテストを1本だけ持つ `test_x.py` で、`python3 -I -m unittest test_x.py` は `FAILED (errors=1)`、直に起動する `python3 -I test_x.py` は `OK` になった (2026-11-15に再現した)。

## 赤の帰属は落ちたテストの名前で読む

判定を件数ではなく ID の集合で持つ理由は `~/.claude/references/observation.md` の「非 0 件も証明にならない」にある。変異の判定でも、rc だけでなく、狙った FAIL の行が出たかで読む。rc が非0でもテストが走っていない形を次のとおり踏んだ (いずれも実測)。

- bash で `$var` の直後に全角の読点を書くと、そのバイトが変数名の続きとして読まれ、`set -u` で unbound variable になってハーネスごと落ちた。rc は非0だが FAIL の行は出ない。`${var}` で閉じる
- cargo test の `--` の後ろに libtest が知らない `--no-fail-fast` を渡したら、テストが1本も走らないまま `rc=1` になり、「変異で赤になった」と読みかけた (`--no-fail-fast` は cargo の側のオプション)。狙ったテストの ID が FAILED の行に出たかで判定する
- 落ちたテストの名前を vitest の JSON レポーターの assertionResults から failed の fullName として出し、戻したあとは毎回 `git diff --quiet` を見るスクリプトで、狙った検査が赤くしたことを確かめられた。最初の版は JSON の読み込みのパスの誤りで名前が出ず、rc だけでは帰属できなかった

名前を集める側が空を返す形もある。zsh の関数の中で `$(...)` の出力を grep して変異の結果を集めたところ、一部の変異で何も出ず、赤か緑か読めなかった。1本ずつ出力の末尾まで見直すと、どれも狙った赤だった。出力の無い行を「緑」と読まない (実測)。

## 観測の仕組みを変えたら変異をやり直す

簡素化の提案でテストの観測の仕組みを変えたら (Mutex のカウンタを Cell にする等)、変異注入をやり直す。変えたまま信じると pin が黙って死ぬ (実測)。

## 計測で経路を確かめる pin

経路を通ったことの確認には、計測の仕組みを外す変異を少なくとも2形当てる。E2E で「古い応答が届いた」をテストランナー側の時刻で近似した確認は、変異「遅延0」では赤だったが「待つ相手を外す」変異では緑のままで、dead pin だった。判定を時刻ではなく応答の本文 (作った行の識別子が無いこと) へ置き換えると、計測を外す変異で赤になった (実測)。

## 計画に書いた変異は着手前に回す

着手前の検査で、隔離した場所で実際に Playwright を動かすレンズが、計画に書いた変異注入3つが赤にならないことを見つけた。writing-plans の self-review と builder check を通した後の計画でも、33件の指摘が全件成り立った (実測)。計画の self-review に「変異注入の手順を書いたら、それが本当に赤になるかを着手前に実測する」を足す。机上で書いた変異は赤にならないことが多く、実装役に「赤くするためにテストを曲げる」誘因を作る (提案と見立て。実測ではない)。
