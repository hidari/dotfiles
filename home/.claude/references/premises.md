# 前提の背景

`~/.claude/CLAUDE.md` の「語彙と前提」カテゴリが持つ規範の、そう決めた理由。

規範の遵守そのものには要らない。方針を疑うとき、別の選択肢と比べるときに読む。

## library-contract パターンで切り離す理由

外部ライブラリを直接使わずアダプタ層で包むのは次の 5 点による。

- 外部ライブラリのバージョンアップ時の挙動確認テスト (契約テスト) を行いやすくする
- 外部ライブラリを差し替え可能にすることで、メンテナンスされなくなった場合の移行を簡単にする
- サプライチェーン攻撃の影響範囲をアダプター層に限定し、コアドメインロジックを保護する
- テスト時に Fake / Mock 実装へ差し替えて高速なユニットテストを可能にする
- コアドメインロジックを外部ライブラリの API 破壊的変更から隔離する

## 書かずに済ませることを模索する理由

2026-08時点で Claude が作るコードは不必要に複雑なコード・テスト・ドキュメントを書きがちで、そのぶん drift しやすかった。Fable 5.1 の移行文書 (claude-api skill の `shared/model-migration.md`、Claude Code 2.1.282同梱) も、頼まれた以上に周辺のコードを直す・余分なテストを書く・書き捨ての確認を恒久的なテストとしてコミットする傾向を挙げている。

コメントが黙って偽になる典型は、ライブラリや toolchain の振る舞いを根拠にしたコメントである。「clippy の `unused_async` は trait の実装を対象から外すので、await の無い async fn の trait 実装は落ちない」と書いたコメントが、Rust 1.98 で `unused_async_trait_impl` が足されて偽になった (実測)。このようなコメントを書くなら確かめた版を添え、依存や toolchain を上げたら主張を確かめ直す。版つきのコメントは、旧版の tarball を registry から `.cache/` へ落として該当関数の本文を新しい版と diff すると、短く確定できた (変わったのがバンドラの変数名の付け替えだけ、のように)。主張が複数あるなら、主張ごとに1体の subagent で新しい版の同梱ソースと突き合わせられる (いずれも実測)。

## テストコードをファーストクラスドキュメントとして書く理由

プロダクトコードとテストコードが the single source of truth になっていれば、別途ドキュメントを保つ必要がなくなり drift の面が減る。
