# テストと変異注入の一次実測

`~/.claude/rules/testing-practices.md` の「テストが緑であることを、仕様を守れている証拠にしない」カテゴリが持つ規範の、手当ての詳細と一次実測。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。規範の文面はここに再掲しない。

## 変異注入で pin を確かめる

### 目視レビューは「壊しても緑」を見逃す

緑のまま検証できていなかった例。

- mockito の `expect_at_least` が `assert_async` 不在で計上されていなかった
- React の `key` remount を stateless mock で検証していて、再レンダーと再マウントを区別できていなかった
- `as` キャストが未知値を素通ししていた

### 復元に checkout を使わない

cp でバックアップを取るか、変異箇所だけを戻す。

### 一度に 1 箇所ずつ隔離する

isClickEvent ガードの検証で、2変数を同時に変異させたところ片方がもう片方を隠して緑になり、生きた pin が死んだと誤読しかけた。

### 赤くなっても pin が有効とは限らない

赤は「テストがその変更を検出できる」証明にすぎない。
本番で到達不能になる典型は、上流のアダプタが入力を正規化・丸め済みで踏まれない分岐である。

isClickEvent ガードの変異は赤くなったが、アダプタが入力を既に丸めていて本番到達不能な分岐だった。上の「変異注入で pin を確かめる」の逆側の落とし穴。

## 検査機構を足したときの 3 種の変異と範囲

検査機構そのものと取り付けを壊す変異を見ないと、穴が塞がったのではなく 1 段上に移動しただけになる。

テスト実行件数のガードを作り、検査対象を壊す変異で赤を確認して完了としたが、赤を作る唯一の行 `process.exitCode = 1` を消しても全テストが緑のまま、さらに recipe からレポータの登録を外しても全緑だった。
統合テストが自前で argv を組んでいて取り付けの literal が二重管理になっていたのも同じ穴。

### 範囲の穴は 3 種の変異では見えない

Pester のヘルパへ「関数定義が 1 件でなければ throw」を入れて塞いだつもりが、覆えていたのはテストが名前で引く 6 関数だけで、残る 15 関数は壊れた重複定義を入れても緑だった。

これは「変異注入で pin を確かめる」を検査機構自身へ適用した形。

## 検査を緩める変更には緩めすぎる方向の変異を置く

3 種の変異はどれも「検査が効く」方向の検証なので、免除が広がりすぎる方向は全部緑で通る。

compose の短形式マウントで `rw` を同結果免除にしたとき、免除集合へ `ro,z` を混ぜる変異を置いて初めて、既存 pin が範囲の広がりを捕まえていると確認できた。
`external: false` を非報告にした側も同じで、真偽判定を落とす変異が対照を赤にした。

範囲の穴が「機構が届かない対象がある」話なのに対し、こちらは「免除が届きすぎる」側。

## 多段の検査ではテストデータが手前を通過する形にする

テストデータは「狙った検査だけが落とす」最小の差分にする。

env 間の設定入れ替えを検出する「URL のホスト名と env 名の対応」検査を pin したテストが、片方の env の値だけを差し替えていたため手前の「env 間で値が重複していないか」検査に捕まっており、対象の検査を壊しても緑だった。

これは「変異注入で pin を確かめる」の原因側の類型。

## 発火条件が tracked に依存する検査

`bootstrap.bats` の reverse-drift テストは `git ls-files` を使うので tracked ファイルしか見ない。
新規ファイルを untracked のまま変異注入すると dead pin に見える。
git add してから変異させると、意図したテストだけが赤くなり未カバーのパスを名指しする。

pre-commit の `files` も同じ性質を持つ。新規 hook は untracked のあいだ Skipped で走らない。
