# テストと変異注入の一次実測

`~/.claude/rules/testing-practices.md` の「テストが緑であることを、仕様を守れている証拠にしない」カテゴリと、`~/.claude/CLAUDE.md` の「テストを書き始める前に順序と方式を決める」カテゴリが持つ規範の、手当ての詳細と一次実測。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。

この文書は変異注入と検査機構の基本を持つ。場面ごとの詳細は次のファイルに分けた。

- 変異を当てるスクリプトを書くとき、変異の赤や緑がどの検査から来たかを読むとき: `~/.claude/references/testing-mutation-harness.md`
- 変異が緑で残り、pin が弱いのかを決める前: `~/.claude/references/testing-surviving-mutants.md`
- Fake・stub・契約テストの fixture を書くとき: `~/.claude/references/testing-fakes.md`
- 生成物を検査するとき、生成物を読み戻す検査を書くとき: `~/.claude/references/testing-generated.md`
- 期待値・オラクル・否定の assertion・テストのヘルパを書くとき: `~/.claude/references/testing-oracles.md`
- 時間切れ・タイムゾーン・並行・テストの実行順に依存するテストを書くとき、負荷の高いときだけ落ちるテストを追うとき: `~/.claude/references/testing-time-and-order.md`
- E2E を書くとき、E2E の緑を疑うとき: `~/.claude/references/testing-e2e.md`

例外が 1 つある。「E2E の生成」節の手順は、E2E を作る瞬間に引く手順で、規範ではなく手順であることを理由に常時層から外した。

## E2E の生成

- 公式 Playwright Test Agents を `pnpm exec playwright init-agents --loop=claude` で生成し、planner / generator / healer で作成する
- playwright を devDependency に持たないプロジェクトでは `pnpm dlx` で代替する
- Test Agents で生成したあとの扱いは `~/.claude/references/testing-e2e.md` の「Playwright Test Agents で生成するとき」節が持つ

## 変異注入で pin を確かめる

### 目視レビューは「壊しても緑」を見逃す

緑のまま検証できていなかった例。

- mockito の `expect_at_least` が `assert_async` 不在で計上されていなかった
- React の `key` remount を stateless mock で検証していて、再レンダーと再マウントを区別できていなかった
- `as` キャストが未知値を素通ししていた

### 復元に checkout を使わない

cp でバックアップを取るか、変異箇所だけを戻す。

変異の直前に取ったコピーで戻し、全変異のあとに対象ファイルのハッシュを前後で比べると、未コミットの編集を失わず、復元できたことを1行で示せた (実測)。`git stash` も使わずに済み、並行の作業を巻き込まない (実測)。

作業ツリーをその場で書き換えて try/finally で戻すハーネスは、プロセスごと止まると finally に届かず変異が残る。変異を当てる subagent が利用上限で途中で止まって1件残った例と、ハーネスを止めて残った例があった。引き取る前に変異前のハッシュと照合し、変異の表の元と変異後の文字列の出現数を数えて残りを特定し、HEAD の中身で書き戻して mtime を進める (実測)。探針を一時的にソースへ書き込んで後で戻す形のゲートも同じで、途中でタスクごと止めると探針がツリーに残った。2回止めて2回とも別のファイルに残り、次のゲートは整形の検査で落ちた。止めたら編集の前に status を見て、差分が探針だけであることを確かめてから取り除き、ハッシュを HEAD と照合する。予防として、長いゲートは途中で止めず、指摘は返ってからまとめて当てる (実測)。

### 一度に 1 箇所ずつ隔離する

isClickEvent ガードの検証で、2変数を同時に変異させたところ片方がもう片方を隠して緑になり、生きた pin が死んだと誤読しかけた。

### 赤くなっても pin が有効とは限らない

赤は「テストがその変更を検出できる」証明にすぎない。

isClickEvent ガードの変異は赤くなったが、アダプタが入力を既に丸めていて本番到達不能な分岐だった。上の「変異注入で pin を確かめる」の逆側の落とし穴。

緑の側にも同じ形がある。変異の見逃しは pin が弱いとは限らず、到達不能な分岐は見逃しとして現れ、正解は pin の強化ではなく分岐の撤去になる。仕様から操作を取り除いたあとに、残ったガードの変異を名前で回すと、取り除いた操作だけがそのガードの項を通っていたため変異が生き残り、網の穴が見つかった。目視のレビューは「どのガードにも負のテストがある」と判断していた (実測)。

### 緑の原因が守る対象とは別の層にある

キーボードが起こした click の配送の途中で同じボタンの `click()` を呼ぶと、HTML の click in progress flag で何もせずに戻るので、ガードを外した変異でも緑のままだった。2回目を止めていたのはブラウザで、ガードではなかった。`dispatchEvent(new MouseEvent("click"))` で送ると、ガードを外した変異が赤になった (実測)。

緑で残るほかの形は `~/.claude/references/testing-surviving-mutants.md` にある。

### 赤がテストより手前の段で出る

警告をエラーにするビルドで、変異が引数や変数を未使用にすると、テストより先にコンパイラの未使用警告で赤くなる。変数を使い続ける形 (固定値ではなく `n % 2`、述語を評価して結果を捨てる) で入れ直し、赤の原因がテストの失敗であることをログで確かめる (実測)。

止める段がタスクランナーの設定の parse にあたる形もある。必須の引数を持つ just のレシピを、引数なしで別のレシピの依存に足す変異は、justfile 自体が parse できなくなり、狙った検査ではなく setUpClass で赤になった。依存の形で引数を渡す (`(recipe "00")`) と、狙った検査で赤になった (実測)。どちらも、変異がビルドや設定の段で止まり、テストが1本も走らないまま赤に見える。

## 検査機構を足したときの 3 種の変異と範囲

検査機構そのものと取り付けを壊す変異を見ないと、穴が塞がったのではなく 1 段上に移動しただけになる。

テスト実行件数のガードを作り、検査対象を壊す変異で赤を確認して完了としたが、赤を作る唯一の行 `process.exitCode = 1` を消しても全テストが緑のまま、さらに recipe からレポータの登録を外しても全緑だった。
統合テストが自前で argv を組んでいて取り付けの literal が二重管理になっていたのも同じ穴。

### 取り付けを確かめる規約と入口

検査器の取り付けを接頭辞の規約 (`verify_*.py` のような名前) で確かめる仕組みがあるなら、新しい検査器を規約の名前にすれば手書きの取り付けの pin が要らない。ただし規約が見るのは呼び出しがあるかどうかだけで、本数・`|| true`・順序は見ないので、そこは行の完全一致で pin した (実測)。多目的なスクリプトのサブコマンドとして検査を足すと規約の射程から漏れ、justfile から呼び出しを消しても何も赤くならなかった。規約の接頭辞を持つ薄い入口を足すと射程に入り、呼び出しを外す変異が名指しで赤になった (実測)。

取り付けには、検査を走らせる CI の job が発火する条件も入る。版の固定のような整合性の検査を足したとき、その検査を走らせる CI の job が入力のファイルだけを変えた PR で発火するかを path-filter で確かめると、入力 (ツールの版のファイル、compose、package.json) が job のキーの外にあり、pytest に置くと一度も走らないまま gate が緑になる形だった。path-gate の無い静的検査の job に登録して塞いだ (実測)。

自クレートへの dev-dependency で有効にする test-support の feature が `--workspace` の起動で揃う穴を塞ぐために、クレート単位の clippy の段をローカルの全部入りのゲートへ足したが、CI は clippy だけの入口を回していて全部入りのゲートを回さないので、merge-gate を守っていなかった。しかも段は1クレートしか覆わず、同じ依存を持つ別のクレートの bin が範囲の外に残った (実測)。ゲートを足すときは、どの入口 (ローカル / CI) から呼ばれるかと、覆うクレートの集合を数える。

### 範囲の穴は 3 種の変異では見えない

Pester のヘルパへ「関数定義が 1 件でなければ throw」を入れて塞いだつもりが、覆えていたのはテストが名前で引く 6 関数だけで、残る 15 関数は壊れた重複定義を入れても緑だった。

これは「変異注入で pin を確かめる」を検査機構自身へ適用した形。

検査の射程を広げたときは、広げた分だけが赤くなる変異を計算で作る。コントラストの検査で比べる背景を1つから2つに広げたとき、「元の背景の上では基準を満たし、新しい背景の上では満たさない色」を変異に使うと、ほかの検査に隠されずに新しい背景の検査だけが赤くなった (実測)。射程を広げたら、広げた側の各ファイルに存在しない番号を書く変異を当て、そのファイルの該当行で赤になることを確かめる (実測)。

検査の対象を参照や一覧で決め、見つからないものを黙って飛ばすと、足し忘れが検査されないまま緑になる。見つからない CSS 変数を飛ばすコントラストのテストは新しいトークンを書き忘れたテーマを検査せず、見つからなければ落とす形に直して初めてトークンを消す変異が赤くなった。UI テストの判定を通過した名前の一覧で行う形も、一覧に足し忘れたテストが消えても緑で通るので、テストを足したら判定の経路に載ったかまで見る (実測)。

名前で照合する静的な走査器を広げたとき、直した箇所を元の形に戻す変異で射程の穴を探させると見つかった。走査器は分割代入した束縛 (`const { error } = ...`) は見るが、分割代入しないプロパティの連鎖 (`res.error?.message`) と、受け取った値をそのまま console へ渡す自前の helper (`reject(..., { detail })` や `deps.log`) を見ていなかった。どちらも元の形に戻してもテストは全部緑だった (実測)。名前で照合する静的な検査を書くときは、同じ値を分割代入しない形で読むと見えるかと、値を受け取って出口へ渡す自前の helper があるかを確かめ、直した箇所を元の形へ戻す変異を1本は置く。どちらも検出0件の緑で返る (提案)。

## 検査を緩める変更には緩めすぎる方向の変異を置く

3 種の変異はどれも「検査が効く」方向の検証なので、免除が広がりすぎる方向は全部緑で通る。

compose の短形式マウントで `rw` を同結果免除にしたとき、免除集合へ `ro,z` を混ぜる変異を置いて初めて、既存 pin が範囲の広がりを捕まえていると確認できた。
`external: false` を非報告にした側も同じで、真偽判定を落とす変異が対照を赤にした。

範囲の穴が「機構が届かない対象がある」話なのに対し、こちらは「免除が届きすぎる」側。

### 形の崩れた項目を読み飛ばす例外

外部の公開一覧 (例: Node の `dist/index.json`) を「1項目でも形が崩れたら一覧ごと拒否」で読む検査に、上流が新しい形の項目 (未リリースのメジャーのプレリリース) を足して毎日落ちた。例外を足すときは「その形なら飛ばす」で広く切らず、判定の対象の外にあることが言えるもの (対象のメジャーより新しいメジャー) だけに絞ると、対象の中に新しい形が来たときは今までどおり落ちる。広く切ると、接尾辞の付いた本物の該当を落として「該当なし」の緑になる。境界の比較 (`<=` と `<`) と比較の有無にそれぞれ変異を入れて pin を確かめた (実測)。

同じ一覧には2026-10-29からプレリリース (`v27.0.0-alpha.0.0.0`) が1件混ざっている。版を X.Y.Z に限って読み、読めなければ一覧全体を err にする作りの検査は、この1件で止まり、セキュリティリリースを知らせなくなる。semver のプレリリースの形と確かに読めるものだけを読み飛ばし、それ以外は err のままにすると、fail-closed を保ったまま直る (実測)。

この2つの手当ては向きが食い違う。後者はプレリリースの形で切る側なので、前者が挙げた「接尾辞の付いた本物の該当を落とす」穴をそれだけでは塞がない。読み飛ばすプレリリースでも判定に効く印 (security の印など) が立っていればエラーにする形なら、その穴を塞げる (推測)。

### 免除の行が当たり続けているか

描画を測る E2E の判定に「免除の一覧の各行が1件以上に当たる」assert を置くと、しきい値を緩める変異 (44から18へ) まで赤にできた。免除した要素が寸法で合格して免除に当たらなくなるため (実測)。免除の一覧が死んだ行を持たないことを assert すると、免除の外側の判定 (しきい値) を壊す変異も観測できる。

検査の docstring に理由つきで書いた免除 (「載っていないことは見ない。外の仕事も起票するため」) は、運用の実態が変わると理由ごと古くなる。免除の範囲に入った漏れは検査が緑のまま通るので、免除の理由が今も成り立つかは、実データを全件数えて確かめるまで分からなかった (実測)。

## 多段の検査ではテストデータが手前を通過する形にする

テストデータは「狙った検査だけが落とす」最小の差分にする。

env 間の設定入れ替えを検出する「URL のホスト名と env 名の対応」検査を pin したテストが、片方の env の値だけを差し替えていたため手前の「env 間で値が重複していないか」検査に捕まっており、対象の検査を壊しても緑だった。

これは「変異注入で pin を確かめる」の原因側の類型。

## 発火条件が tracked に依存する検査

`bootstrap.bats` の reverse-drift テストは `git ls-files` を使うので tracked ファイルしか見ない。
新規ファイルを untracked のまま変異注入すると dead pin に見える。
git add してから変異させると、意図したテストだけが赤くなり未カバーのパスを名指しする。

pre-commit の `files` も同じ性質を持つ。新規 hook は untracked のあいだ Skipped で走らない。

pre-commit は hook を走らせる前に unstaged の変更を退避するので、hook が呼ぶ検査スクリプトや設定に入れた変異は、stage しないと変異前のファイルで検査されて緑になる。壊したファイルを stage してから `pre-commit run` で回す。設定ファイル自体が unstaged だと実行を拒否する (実測)。
