# 期待値とオラクルとテストのヘルパの一次実測

`~/.claude/rules/testing-practices.md` の「テストが緑であることを、仕様を守れている証拠にしない」カテゴリのうち、期待値・オラクル・否定の assertion・テストのヘルパが、比べる相手と同じ値を持ったり空の入力を通したりして黙って緑になる形の、手当ての詳細と一次実測。入口は `~/.claude/references/testing.md` で、変異注入と dead pin の定義は `~/.claude/rules/testing-practices.md` が持つ。

規範の遵守そのものには要らない。手当ての具体が要るとき、規範を疑うとき、似た失敗を踏んで「これは既知か」を確かめるときに読む。

## 期待値をプロダクトと共有しない

pin と本体が同じ値を見ると守れない。呼び出し口が定数の base を使うことの pin は、import した定数と比べると定数の値を変える変異で緑のままで、リテラル (`''`) と比べると全部赤になった。テストの列挙を本体と共有すると「本体の配列から1つ抜く」変異が緑になるので、並列レビューの片方が共有を勧めても列挙は独立に残し、変異で赤を確かめた (実測)。

## 否定の assertion

「値を出さない」を assertNotIn だけで見るテストは、検出が壊れて空のリストを返しても緑になる。否定の主張は、同じ実行で検出が非空であることと組にしないと dead pin になる (実測)。「検出の結果に秘密の値が出ないこと」を見るテストを assertNotIn から exact な期待値 (場所と種類だけの1行) に変えると、「検出が空を返す」変異をそのテストも捕まえるようになった (赤の本数が3から4へ増えた。実測)。

シェルのテストハーネスで否定の assert が非0の終了をすべて PASS と数えると、パイプのヘルパーが grep のエラー (終了コード2) や SIGPIPE (141) で偽に倒れたときに検査が緑で素通りし、秘密を argv に出さない pin がこの形だと黙って外れる (実測。定義を読み使用箇所を数えた段階で、修正は未着手)。否定の assert を終了コード1だけに絞る規約を足す (提案)。

## 成功を undefined で返すヘルパ

テストのヘルパが成功のときに `undefined` を返し、`expect(errorCode(raw)).toBe(ErrorCodes.NEW_CODE)` と比べていた。まだ定義していない定数も `undefined` なので「どちらも無い」で一致して緑になり、TDD の赤が出なかった (6件中1件しか赤くならなかった)。成功を番兵の文字列で返すと6件とも赤になった (実測)。

## 番兵の値は比べる相手の値の域の外に置く

確率で落ちる property-based test の反例を読むと、テストのオラクルが「存在しない人」を表す番兵の ID を、生成器が実際に作れる ID の集合からも選べる形になっていた。生成器の手でその ID が本物の行を持つと、行の無い人として送った要求が本物の人として解決され、期待と判定がずれる。番兵を生成器の値の域の外へ出し、「番兵がどの候補の集合にも出発点の世界にも無い」ことを決定的な単体テストで縛ると、再発を止められる。変異注入で番兵の値を元に戻し、テストが赤になるかを確かめた (実測)。property-based test のオラクルに番兵の値 (存在しない ID・空の名前など) を置くときは、生成器の値の域の外にあることを assert で縛る (提案)。

## 双条件の性質は両方の向きを別々に確かめる

計画の文書に書いた性質 (「A の後に B が消えた ⇔ 関数が B を返す」のような双条件) は、実装してみると片方の向きが偽のことがあった。生成器の偏りで性質テストが偶然に緑になっていて、反例を手で組んで初めて分かった。双条件の性質は、両方の向きを別々の反例で確かめる (実測)。

## 全列挙の件数はオラクルの側で決まる値で置く

全列挙の件数の pin を、プロダクトの出力ではなくオラクルの側だけで決まる値で exact に置くと、入力の領域を縮める変異 (回転を消すなど) も赤にできた。プロダクトの出力件数だけの pin はこの変異を緑で通す (実測)。

拒否集合のテストを UCD の範囲表の全符号位置で回し、弾いた件数・通した件数・表の行数を exact で pin した。範囲の端を縮める・広げる・丸ごと外す、の変異がどれも狙ったテストで赤になった。代表値だけのテストでは端の縮みが素通りする (実測)。

## 名前で拒む denylist

置いてはいけないものを名前で拒む denylist は、新しい経路が足されたときに黙って穴になる。設定ファイルの鍵の検査を鍵の集合の exact な許可リストへ置き換えると、名前を知らない鍵を足す変異が拒否リストでは緑、許可リストでは赤だった。ast-grep で証人型ごとに破り方を並べた denylist を型の数だけ写すと1本だけに腕が入って揃わなくなり、許す形を1つに決める allowlist を証人の名前の一覧に当てる1本に寄せた (utils は引数を取れないので、構築の場所のルールは型ごとに残る) (実測)。正当な鍵を足すたびにテストを直す手間は、判断の関門として働く (評価。実測ではない)。

## 列挙の失敗を握りつぶす後片付けの helper

テストの掃除の helper が一覧の失敗を `let Ok(..) else { return; }` で捨てていたため、deserialize の失敗で掃除が何か月も何も消しておらず、誰も気づかなかった。列挙が失敗すると0件の掃除と区別できない (実測)。
